Chapter 10 Parallel Make

Modern machines have 8, 16, 64 cores. A Makefile that uses one of them is a crime. This chapter covers -j, the GNU jobserver protocol (how recursive Make coordinates without exploding your machine), race conditions, and the handful of gotchas that ruin parallel builds.

The basics: -j N

$ make -j 4         # up to 4 jobs in parallel
$ make -j           # unlimited jobs (all of them right now)
$ make -j $(nproc)  # one job per core

-j with no number means "no limit". That's usually a bad idea: a bare make -j on a Makefile with 10,000 targets will spawn 10,000 shells and hang your machine. Always pass a number.

A reasonable default: nproc on Linux, sysctl -n hw.ncpu on macOS, or just -j 8 and call it a day.

How parallel Make schedules

When you run make -j N, Make builds the dependency graph as usual, then walks it, scheduling up to N recipes at once. A recipe can start as soon as all its prerequisites are built. Two recipes with no mutual dependency can run in parallel.

Given this graph:

       hello
      /  |  \
 main.o greet.o util.o
    |     |      |
 main.c greet.c util.c

Running make -j 4:

  1. Make walks to hello, sees it needs three .os.
  2. The three .o compilations are independent — all three start at once.
  3. Once all three are done, the link step runs.

Total wall-clock time: (time to compile the slowest .c) + (time to link). Sequential time: sum of all three compiles + link. Potential 3× speedup.

Interleaved output

Make doesn't buffer recipe output by default — multiple recipes printing simultaneously interleave on your terminal. For a quick build this is usually fine. For debugging, it's a nightmare.

GNU Make 4.0+ has --output-sync:

$ make -j 8 --output-sync=target
$ make -j 8 -O=line
ModeBehaviour
none (default)Output interleaves freely.
linePrint each line atomically. Lines from different recipes may still interleave but individual lines stay whole.
targetBuffer all output from a recipe until it finishes, then flush as a block. Usually what you want.
recurseLike target, but also buffers sub-make output as a unit.

The shorthand -O (capital O, not zero) is equivalent to --output-sync=target.

The jobserver — how recursive Make doesn't fork-bomb you

Here's a puzzle. You type make -j 8. Your Makefile includes a recursive call $(MAKE) -C subdir. The sub-make also wants to run 8 jobs in parallel. If each of your 8 top-level jobs spawns a sub-make that runs 8 of its own, you'd get 64 simultaneous processes, not 8.

The GNU jobserver protocol solves this elegantly. It works like a token pool:

  1. The top-level Make creates a pipe and writes N-1 tokens (bytes) to it.
  2. Before running a recipe, Make tries to read a token from the pipe. If none available, it waits.
  3. When the recipe finishes, Make writes the token back.
  4. Sub-makes are told about the pipe via the MAKEFLAGS environment variable. They participate in the same pool.

Net effect: across the entire process tree, at most N recipes run simultaneously — whether they're in the top Make, a sub-make, or a sub-sub-make.

Why N-1 tokens?

The top-level Make holds one implicit "slot" for itself — it counts as one of the N. So it writes N-1 additional tokens. A sub-make inherits the pool and can read tokens for its own recipes without counting itself as an extra consumer.

Why $(MAKE) needs the + prefix (or full name)

For the jobserver to work, a recursive Make invocation must not go through sh -c's usual dance. Specifically, Make recognises recipe lines that explicitly mention $(MAKE) (or ${MAKE}) and treats them as recursive, passing the jobserver fd through.

If you try to obscure the recursive call — e.g. by running it in a subshell — Make can't tell, and the sub-make is left without a jobserver. The standard form:

.PHONY: build-sub
build-sub:
	$(MAKE) -C subdir

When you need to force "run this even under -n" (e.g. for a custom dry-run compat), use the + prefix:

build-sub:
	+$(MAKE) -C subdir

Race conditions

Parallel Make is correct only if your dependency graph correctly captures every real prerequisite. A missing edge means two recipes that actually depend on each other might run simultaneously.

Race 1 — implicit directory creation

build/a.o: src/a.c
	mkdir -p build
	$(CC) $(CFLAGS) -c $< -o $@

build/b.o: src/b.c
	mkdir -p build
	$(CC) $(CFLAGS) -c $< -o $@

Two parallel jobs both run mkdir -p build. With mkdir -p this is usually safe, but some filesystems or race conditions can produce errors. Fix: make the directory an order-only prerequisite (Chapter 7).

Race 2 — shared intermediate

output.a output.b: input
	process input        # produces both output.a and output.b

Two parallel jobs both run process input. They overwrite each other's outputs. Fix: grouped target (&:) — Chapter 7.

Race 3 — non-atomic writes

A recipe that writes directly to its target without intermediate staging can produce garbage if interrupted: 

report.csv: process.py data.csv
	python $< data.csv > $@

If Python crashes mid-stream, you have a partial CSV. Fix: write to a temp file, rename atomically on success: 

.DELETE_ON_ERROR:
report.csv: process.py data.csv
	python $< data.csv > $@.tmp
	mv $@.tmp $@

Combined with .DELETE_ON_ERROR:, a failed build leaves no stale output.

Race 4 — cross-recipe state

Two recipes that both modify a shared file (a log, a database, anything) without explicit ordering. Fix: add a dependency, or use .NOTPARALLEL to force these specific recipes to run sequentially.

Load-based throttling

$ make -j 16 -l 4

-l N: don't spawn new jobs if the system's 1-minute load average is above N. Useful when you're building on a shared machine, or on a laptop you want to keep responsive.

When parallel doesn't work

Some recipes can't parallelise. For them:

.NOTPARALLEL:                       # whole Makefile is serial
.NOTPARALLEL: test                  # only "test" is serial (GNU Make 4.4+)

Or force sub-make sequential while keeping the top parallel:

test:
	$(MAKE) -j 1 run-tests

This spawns a sub-make with -j 1, overriding the inherited jobserver. The sub-make runs sequentially; the top Make can still parallelise other targets concurrently.

Measuring speedup

$ make clean && time make
...
real    0m9.832s
user    0m9.411s
sys     0m0.406s

$ make clean && time make -j 8
...
real    0m1.742s
user    0m10.221s
sys     0m0.612s

user time stays roughly the same — the total CPU work is the same. real (wall) time drops by up to -j× depending on how parallelisable your graph is.

The ratio user/real tells you your actual parallelism. If -j 8 gives you user/real = 6.0, you're getting 6× of your theoretical 8×. Missing 2× might be: serial link step, Make's own overhead, a bottleneck file all targets depend on.

Hands-on: measure your project

Hands-on · wall-clock vs cpu time

With any of the C Makefiles from earlier chapters, run:

$ make clean
$ time make
$ make clean
$ time make -j 2
$ make clean
$ time make -j 8
$ make clean
$ time make -j 8 --output-sync=target

Note how much faster -j 8 is, and how clean the output becomes with --output-sync. This is cheap speedup — maybe the single highest-ROI habit you'll pick up in this tutorial.

Stick MAKEFLAGS += -j 8 --output-sync=target in your ~/.makerc or equivalent, or alias make:

alias make='make -j 8 --output-sync=target'

Exercises

EX 10.1 easy Observe interleaving

Write a Makefile with three targets, each of which prints "start N", sleeps 1s, prints "end N". Run sequentially (make -j 1) and in parallel (make -j 3). What differs?

Show solution 
.PHONY: all a b c
all: a b c

a: ; @echo start a; sleep 1; echo end a
b: ; @echo start b; sleep 1; echo end b
c: ; @echo start c; sleep 1; echo end c
$ make -j 1         # ~3 seconds
start a
end a
start b
end b
start c
end c

$ make -j 3         # ~1 second
start a
start b
start c
end a
end b
end c

In parallel, the three starts happen essentially simultaneously; after the sleep all three end. Now try with -O:

$ make -j 3 -O
start a
end a
start b
end b
start c
end c

Total wall time is still ~1s, but each target's output is grouped.

EX 10.2 medium Spot the race

Find the race condition:

.PHONY: all
all: app/v1 app/v2

app/v1: app/main.o
	mkdir -p app
	cp app/main.o app/v1

app/v2: app/main.o
	mkdir -p app
	cp app/main.o app/v2

app/main.o: main.c
	mkdir -p app
	$(CC) -c main.c -o app/main.o

Why can this fail with -j? How do you fix it?

Show solution

The three rules each invoke mkdir -p app, and the app/main.o rule may run in parallel with the app/v1 / app/v2 rules. In principle mkdir -p is safe for races; in practice, slow NFS / overlayfs filesystems sometimes return errors.

But the bigger problem: both app/v1 and app/v2 list app/main.o as a prereq, so Make knows the order — but in parallel, app/v1 and app/v2 run simultaneously, and both attempt to mkdir -p app. With -p this should be idempotent, but…

Cleanup — use order-only:

.PHONY: all
all: app/v1 app/v2

app/v1: app/main.o | app
	cp $< $@

app/v2: app/main.o | app
	cp $< $@

app/main.o: main.c | app
	$(CC) -c $< -o $@

app: ; mkdir -p $@

mkdir runs at most once, no races.

EX 10.3 medium Measure effective parallelism

Take any C project with at least 10 source files. Run time make -j N for N in 1, 2, 4, 8. Plot (or mentally sketch) wall time vs N. Where does the curve plateau? What's the bottleneck?

Show solution

The curve plateaus when you run out of independent work. Usually the plateau is at around min(cores, number_of_independent_leaves). Beyond the plateau, extra jobs don't help — they're waiting for the critical path.

For a typical C project: wall time drops fast until N ≈ cores, then flattens. The final link step is serial, so ultra-fast parallel compile + a slow link gives a final "tail" you can't shorten with more parallelism — you need a faster linker (mold, lld).

EX 10.4 hard Sequential tests, parallel build

Your build is embarrassingly parallel; your tests must run one at a time (they use a test DB). User types make -j 8 all check. How do you keep compile parallel while forcing tests serial?

Show solution

Either scoped .NOTPARALLEL (4.4+) or a sub-make trick:

# approach 1: GNU Make 4.4+
.NOTPARALLEL: check
check: $(TESTS)
	@for t in $^; do ./$$t || exit 1; done

# approach 2: portable
check:
	$(MAKE) -j 1 check-seq

.PHONY: check-seq
check-seq: $(TESTS)
	@for t in $^; do ./$$t || exit 1; done

The sub-make with -j 1 overrides the inherited jobserver for that branch only.

EX 10.5 hard What does MAKEFLAGS look like?

Write a Makefile that prints $(MAKEFLAGS) and the MAKEFLAGS environment variable inside a recipe. Run with make -j 4 --output-sync=target and inspect what Make tells its children.

Show solution 
all:
	@echo 'Make var: $(MAKEFLAGS)'
	@echo 'env var: '"$$MAKEFLAGS"
$ make -j 4 --output-sync=target
Make var: -j4 --output-sync=target --jobserver-auth=fifo:/tmp/GMfifo12345
env var: -j4 --output-sync=target --jobserver-auth=fifo:/tmp/GMfifo12345

The --jobserver-auth=fifo:… (or older --jobserver-fds=3,4) is the token pipe handle a sub-make uses to participate in the pool. Don't try to read or write to it yourself — Make manages it.

EX 10.6 medium Atomic writes

Rewrite this rule so that a crashed recipe leaves no partial output:

summary.json: raw.csv
	python summarize.py raw.csv > summary.json
Show solution 
.DELETE_ON_ERROR:

summary.json: raw.csv
	python summarize.py raw.csv > $@.tmp
	mv $@.tmp $@

On success: output is atomically renamed.
On crash of python: .DELETE_ON_ERROR removes summary.json.tmp (the target at the moment it fails is summary.json, but the partial file was summary.json.tmp — so actually .DELETE_ON_ERROR may not help here; the key insight is that a crash means mv never ran, so no summary.json exists to be stale).

Double belt-and-braces: 

summary.json: raw.csv
	@rm -f $@.tmp
	python summarize.py raw.csv > $@.tmp
	mv $@.tmp $@

Recap

  • -j N runs up to N recipes in parallel.
  • -O / --output-sync=target groups output per recipe for readability.
  • -l N throttles based on system load.
  • The GNU jobserver protocol lets a tree of recursive Makes cooperate on one token pool, so -j 8 means 8 jobs total, not 8 per level.
  • Recipe lines containing $(MAKE) / ${MAKE} get auto-propagated jobserver info. Use +$(MAKE) … if you need it to run under -n too.
  • Races hide in: missing directory dependencies (use order-only), shared multi-output recipes (use grouped targets), non-atomic writes (write to .tmp + rename).
  • .NOTPARALLEL: (all or scoped) forces sequential execution. Or spawn a sub-make with -j 1.
