Chapter 05 Automatic Vars & Pattern Rules

Remember how in Exercise 2.3 we had to write four near-identical compile rules? This chapter shows you how to replace all of them with one. By the end you'll be writing Makefiles that feel like Lisp macros.

The automatic variables, in one table

Automatic variables are set by Make inside a recipe. They let you refer to the target and prerequisites of the rule currently being executed without hardcoding their names.

VarMeaning
$@The target file name.
$<The first prerequisite.
$^All prerequisites, space-separated, duplicates removed.
$+All prerequisites, with duplicates preserved, in order.
$?Prerequisites newer than the target.
$*The "stem" of a pattern rule match (the part that % matched).
$|All order-only prerequisites (see Chapter 7).

There are also D and F variants that give directory and file parts:

$(@D) $(@F)dir and file of $@
$(<D) $(<F)dir and file of $<
… and so on

You'll use $@, $<, and $^ every day. The others come up in more advanced recipes.

Rewriting the link rule

Here's our Chapter 2 Makefile, rewritten:

makeMakefile — with automatic vars
hello: main.o greet.o farewell.o
	cc $^ -o $@

main.o: main.c
	cc -c $< -o $@

greet.o: greet.c
	cc -c $< -o $@

farewell.o: farewell.c
	cc -c $< -o $@

Small improvement — but now the .o rules are identical except for the file name. That's a job for a pattern rule.

Pattern rules

A pattern rule has a % in its target. % matches any non-empty string (the stem). The same stem is substituted into prerequisites. 

%.o: %.c
	cc -c $< -o $@

This says: "to build anything-dot-o, I need a same-named dot-c, and here's how".

With this single rule, the whole Makefile collapses:

makeMakefile — with pattern rule
hello: main.o greet.o farewell.o
	cc $^ -o $@

%.o: %.c
	cc -c $< -o $@

clean:
	rm -f hello *.o

.PHONY: clean

Add a fifth, sixth, fiftieth source file and you don't touch the pattern rule — only the prerequisite list of hello.

The % is not a regex

% is a single wildcard meaning "any string, including empty". There's no *.*, no character classes, no alternation. Two percents are not allowed in the same target. Prerequisites can contain multiple %s only if the rule target has one — and they all expand to the same stem.

How Make picks a pattern rule

When Make needs to build foo.o, it looks through its pattern rule database for something that matches %.o. It tries them in order and uses the first one whose prerequisites exist or can themselves be built. If nothing fits, it falls back to the built-in rules (more on those in a moment).

Multiple pattern rules can match. Make picks the one whose stem is shortest — the most "specific" match. This is the stem-length tiebreaker, and it's why foo%.o: foo%.c (match anything starting with "foo") wins over %.o: %.c (match anything) for a file like foobar.o.

Static pattern rules

A regular pattern rule applies to any target matching the pattern. Sometimes you want to restrict it to a specific list. That's a static pattern rule: 

OBJ := main.o greet.o farewell.o

$(OBJ): %.o: %.c
	cc -c $< -o $@

Three colons! The form is targets: target-pattern: prereq-pattern. Read: "for each file in OBJ, if it matches %.o, look for the same-stem %.c and run the recipe". This rule applies only to the listed targets, not to every .o in the universe.

When do you want this? Whenever you've got a heterogeneous project and want different rules for different groups:

LIB_OBJ := foo.o bar.o
APP_OBJ := main.o cli.o

$(LIB_OBJ): %.o: %.c
	cc -fPIC -c $< -o $@

$(APP_OBJ): %.o: %.c
	cc -c $< -o $@

Built-in implicit rules

Make ships with a pile of pattern rules baked in — compile C, compile C++, link objects, run yacc, run lex, process tangle, run awk, and so on. You can see them all with make -p.

One important implicit rule is roughly:

%.o: %.c
	$(CC) $(CPPFLAGS) $(CFLAGS) -c $< -o $@

Another is:

%: %.c
	$(CC) $(CPPFLAGS) $(CFLAGS) $(LDFLAGS) $< $(LOADLIBES) $(LDLIBS) -o $@

Which means this Makefile works:

# Yes, really. This is a complete Makefile.
hello: hello.c

Or even less:

$ ls
hello.c
$ make hello
cc     hello.c   -o hello
$ ls
hello  hello.c

Make didn't need a Makefile at all. It saw hello.c, knew the built-in rule %: %.c, and just ran it. This is wonderful for quick hacks and occasionally surprising when you didn't intend it.

The implicit rule variables

The built-in compile rule uses these variables — they are the standard names:

CCC compiler (default: cc)
CXXC++ compiler (default: g++)
CFLAGSC compile flags
CXXFLAGSC++ compile flags
CPPFLAGSpreprocessor flags (-I, -D)
LDFLAGSlinker flags (-L, -Wl,...)
LDLIBSlibraries (-lm, -lpthread)
AR ARFLAGSarchiver (ar cr)
RANLIBranlib symbol indexer

Using these names plays nicely with every other Makefile, with package maintainers, and with tools like make -p. Invent your own MY_COMPILE_FLAGS only when you must.

Disabling built-in rules

Sometimes you want a pristine Makefile with no surprises:

MAKEFLAGS += --no-builtin-rules --no-builtin-variables

Or pass -r -R on the command line. This is common in large projects: built-in rules can cause accidental rebuilds (e.g. Make tries to compile script.py as a yacc file because it matches some weird implicit rule).

A more surgical option: empty-override a pattern rule.

%.o: %.c           # cancel the built-in C rule

A target-less pattern rule with no recipe and no prereqs silently deletes that built-in rule.

Searching for sources elsewhere — vpath

What if your sources are in src/ but your build output should land in build/? One option: use vpath to tell Make where to look. 

vpath %.c src

%.o: %.c
	cc -c $< -o $@

hello: main.o greet.o
	cc $^ -o $@

When Make looks for main.c and doesn't find it in ., it searches directories listed in vpath %.c src. Same for greet.c. The $< in the recipe will be the full path Make found, e.g. src/main.c.

VPATH (uppercase, no pattern) is the older version — it searches these directories for any missing prerequisite: 

VPATH := src:include:generated

Prefer vpath (lowercase, with pattern) when you can — it's more precise. VPATH can cause surprising matches when a file name coincidentally matches something in another directory.

vpath doesn't handle outputs

vpath helps Make find inputs. It doesn't change where outputs go. If src/main.c is the input and the pattern is %.o: %.c, the output will be main.o in the current directory — not src/main.o. That's almost always what you want. For output into a build/ dir, use explicit paths in the pattern (Chapter 9).

Wildcards and $(wildcard …)

Make expands shell globs like *.c only in places the shell would — namely, recipe lines and some function contexts. In variable assignments, *.c is just the literal string: 

SRC := *.c            # literal text "*.c" — rarely what you want

To expand a glob in an assignment, use the wildcard function:

SRC := $(wildcard *.c)
OBJ := $(SRC:.c=.o)

hello: $(OBJ)
	cc $^ -o $@

%.o: %.c
	cc -c $< -o $@

$(SRC:.c=.o) is a substitution reference: "in SRC, replace each word ending with .c with the same word ending in .o". It's shorthand for $(patsubst %.c,%.o,$(SRC)), which we'll see in the next chapter.

Together, these lines give you an automatic Makefile that just picks up every .c file. Add a new file, no Makefile changes needed.

Hands-on: the 3-line Makefile

Hands-on · minimal, automatic

Start fresh in ~/learning-make/ch05 with the three C files from Chapter 2 (you can copy them with cp ~/learning-make/ch02/*.c .). Write:

makeMakefile
SRC := $(wildcard *.c)
OBJ := $(SRC:.c=.o)

hello: $(OBJ)
	$(CC) $(CFLAGS) $^ -o $@

%.o: %.c
	$(CC) $(CFLAGS) -c $< -o $@

clean: ; rm -f hello *.o
.PHONY: clean

Build:

$ make
cc  -c main.c -o main.o
cc  -c greet.c -o greet.o
cc  -c farewell.c -o farewell.o
cc  main.o greet.o farewell.o -o hello
$ ./hello
Hello, world!
Goodbye, world!

Now add a new file wave.c:

#include <stdio.h>
void wave(const char *who) { printf("Hi there, %s.\n", who); }

Call wave("reader") from main. Then:

$ make
cc  -c main.c -o main.o
cc  -c wave.c -o wave.o
cc  main.o greet.o farewell.o wave.o -o hello
$ ./hello
Hello, world!
Goodbye, world!
Hi there, reader.

You didn't touch the Makefile. The wildcard picked up the new file, the substitution produced wave.o, the pattern rule compiled it, and the link rule picked it up because OBJ contains it. This is the kind of Makefile that earns its keep.

The D and F variants

Given a target build/obj/foo.o:

  • $@ = build/obj/foo.o
  • $(@D) = build/obj (directory)
  • $(@F) = foo.o (file, no dir)

Useful for creating output directories on the fly:

build/obj/%.o: src/%.c
	@mkdir -p $(@D)
	$(CC) $(CFLAGS) -c $< -o $@

Exercises

EX 5.1 easy Identify each variable

For this rule, give the values of $@, $<, $^, $?, and $* when the recipe runs:

build/foo.o: src/foo.c include/foo.h

Assume src/foo.c is newer than build/foo.o, but include/foo.h is older.

Show solution
  • $@ = build/foo.o
  • $< = src/foo.c
  • $^ = src/foo.c include/foo.h
  • $? = src/foo.c (only newer prereq)
  • $* = empty, because this isn't a pattern rule — no stem.

If the rule were instead %.o: %.c and the target was build/foo.o, then $* would be build/foo.

EX 5.2 easy One-line Makefile

Create a single file hello.c with a working main. With NO Makefile in the directory, run make hello. Does it work? Why?

Show solution

Yes. Make's built-in rule %: %.c matches, and it runs cc hello.c -o hello. You can verify with make -p | look for "%: %.c". The implicit rules are what make shell demos like make foo (where foo.c is sitting right there) work.

EX 5.3 medium Writing a pattern rule

You have a directory of Markdown files and want each foo.md to be converted to foo.html via pandoc $< -o $@. Write the pattern rule plus an all target that builds every HTML file.

Show solution 
MD   := $(wildcard *.md)
HTML := $(MD:.md=.html)

.PHONY: all clean
all: $(HTML)

%.html: %.md
	pandoc $< -o $@

clean: ; rm -f $(HTML)
EX 5.4 medium Outputs in a subdirectory

Change the C project so that *.o files are written under build/ rather than next to the sources. Sources stay in the current directory. The hello binary should also land in build/.

Show solution 
SRC := $(wildcard *.c)
OBJ := $(patsubst %.c,build/%.o,$(SRC))
BIN := build/hello

.PHONY: all clean
all: $(BIN)

$(BIN): $(OBJ)
	@mkdir -p $(@D)
	$(CC) $(CFLAGS) $^ -o $@

build/%.o: %.c
	@mkdir -p $(@D)
	$(CC) $(CFLAGS) -c $< -o $@

clean: ; rm -rf build

Notice $(@D) giving the directory of the current target, and the @mkdir -p making sure it exists. This is the idiomatic "out-of-tree build" pattern. We'll revisit it in Chapter 9 with order-only prerequisites for a cleaner implementation.

EX 5.5 medium Using $? cleverly

Write a rule that updates a file all.txt by concatenating only the newer of its prerequisites onto itself. (This is a little contrived, but it's a classic use of $?.)

Show solution 
all.txt: a.txt b.txt c.txt
	cat $? >> $@

If only b.txt is newer than all.txt, $? is just b.txt, so we append its contents. $?'s canonical use case is incremental archive updates: 

mylib.a: foo.o bar.o baz.o
	ar cr $@ $?

This adds only the changed .os to the archive, rather than rebuilding it from scratch.

EX 5.6 hard Shadowing a built-in rule

You're getting surprising output: Make seems to be trying to run yacc on your file parser.y, but you actually have no yacc-based tooling. How would you disable the %.c: %.y built-in rule specifically, without killing all built-ins?

Show solution 
%.c: %.y      # empty override — cancel this specific built-in rule

A pattern rule with no recipe and no prerequisites deletes the built-in rule of the same pattern. Now Make will no longer try to yacc your .y file. If you want to see every built-in rule Make knows, run make -p -f /dev/null.

EX 5.7 medium Static vs regular pattern — when?

Your project has .c files that compile with -fPIC (they go into a shared lib) and .c files that don't (they go into the main executable). Show how a static pattern rule lets you handle this without needing separate file extensions or directories.

Show solution 
LIB_SRC := fmt.c log.c util.c
APP_SRC := main.c cli.c

LIB_OBJ := $(LIB_SRC:.c=.o)
APP_OBJ := $(APP_SRC:.c=.o)

$(LIB_OBJ): %.o: %.c
	$(CC) -fPIC $(CFLAGS) -c $< -o $@

$(APP_OBJ): %.o: %.c
	$(CC) $(CFLAGS) -c $< -o $@

libmine.so: $(LIB_OBJ)
	$(CC) -shared -o $@ $^

app: $(APP_OBJ) libmine.so
	$(CC) $(APP_OBJ) -L. -lmine -o $@

A regular pattern rule %.o: %.c would apply to every .o → .c. With the static pattern rule form targets: target-pat: prereq-pat, we restrict each rule to a specific target list.

EX 5.8 hard Explore the built-in database

Run make -p -f /dev/null 2>/dev/null | less. Find the built-in rule for C++ compilation (%.o: %.cc or %.o: %.cpp). What variable is used for "C++ compiler"? What preprocessor flags does it use?

Show solution

Search /^%.o:. You'll find something like:

%.o: %.cc
#  recipe to execute (built-in):
	$(COMPILE.cc) $(OUTPUT_OPTION) $<
# …
COMPILE.cc = $(CXX) $(CXXFLAGS) $(CPPFLAGS) $(TARGET_ARCH) -c
OUTPUT_OPTION = -o $@

CXX is the compiler (default g++). Preprocessor flags come from CPPFLAGS. The conventional names really are:

  • CPPFLAGS — C preprocessor flags (-I, -D). Shared by C and C++.
  • CFLAGS — C compiler flags.
  • CXXFLAGS — C++ compiler flags.
  • LDFLAGS — linker flags (-L, -Wl,...).
  • LDLIBS — libraries (-lm, -lpthread).

Recap

  • $@ $< $^ $? $* $+ $| are the automatic variables. The big three daily are $@, $<, $^.
  • Pattern rules use % as a single wildcard. The matching part is the "stem" ($*).
  • Static pattern rules — targets: target-pat: prereq-pat — restrict a pattern to a specific target list.
  • Make ships with many built-in pattern rules. See them with make -p. Disable with --no-builtin-rules or empty-override a specific one.
  • The conventional variable names (CC, CFLAGS, CXXFLAGS, CPPFLAGS, LDFLAGS, LDLIBS) play well with every other Makefile.
  • vpath PATTERN DIR tells Make where to search for missing prerequisites.
  • $(wildcard *.c) gives you a glob expansion in an assignment context.
  • $(VAR:.c=.o) is the "substitution reference" — a terse pattern substitution.
