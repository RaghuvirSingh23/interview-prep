Chapter 04 Variables — All Six Flavors

Make has six different assignment operators. The difference between = and := alone has caused more confused Slack threads than I can count. Here we'll build a mental model that lets you pick the right one every time.

Why are there six?

Because Make variables aren't really variables — they're macros. The assignment operator decides when the right-hand side is evaluated: at the moment of assignment, or every time the variable is referenced.

Every other language has this choice too, but hides it. In Python, variables are immediate; in Clojure, delay/force give you laziness. Make just makes you pick per assignment.

The six:

OperatorCalledEvaluation
= Recursively expanded Lazy — expanded at each reference
:= Simply expanded Strict — expanded once at assignment
::=Simply expanded (POSIX)Same as :=. Portability flavor.
?= Conditional Assigns only if the variable isn't already set
+= Append Appends to the value, inheriting the flavor of the original
!= Shell Runs shell command, stores stdout

The recursive (=) flavor

FOO = bar stores the text bar. Every time you reference $(FOO), Make re-scans that text and expands any Make variables in it. The value is "rebuilt" at each use. 

X = one
Y = $(X) two
X = three
all:
	@echo $(Y)
$ make
three two

Read this slowly. When we say Y = $(X) two, Make stores the literal text "$(X) two" as the value of Y. Then X gets reassigned to three. When the recipe runs, $(Y) is expanded: Make re-scans its stored text, sees $(X), looks up X's current value (three), and produces three two.

This is powerful. It's also how you write infinite loops:

FOO = $(FOO) bar
all:
	@echo $(FOO)
$ make
Makefile:1: *** Recursive variable 'FOO' references itself (eventually).  Stop.

Make catches the simplest case. It can't always — so be careful with = and variables that reference themselves.

The simple (:=) flavor

FOO := bar expands the right-hand side immediately and stores the result. Subsequent references are just lookups. 

X := one
Y := $(X) two
X := three
all:
	@echo $(Y)
$ make
one two

Y was assigned the value "one two" at the moment Y := was parsed. Later changes to X don't affect Y.

Rule of thumb: use := by default. It behaves the way people expect variables to behave. Reach for = only when you actually want late binding — which is rarer than you'd think.

Why ::= exists

POSIX standardised ::= to mean "simply expanded". GNU Make accepts it as a synonym for :=. You'll occasionally see it in Makefiles that aspire to POSIX portability. Otherwise, stick with :=.

The conditional (?=) flavor

FOO ?= bar sets FOO to bar only if FOO isn't already defined. This is how you write overridable defaults: 

CC ?= gcc
CFLAGS ?= -O2 -Wall

hello: hello.c
	$(CC) $(CFLAGS) hello.c -o hello

Now users can override:

$ make                        # uses CC=gcc, CFLAGS=-O2 -Wall
$ make CC=clang               # uses clang
$ CFLAGS=-O0 make             # override via environment
$ make CFLAGS='-g -O0'        # override on the command line

?= considers "already defined" to include: the environment, the command line, and any earlier assignment in a Makefile. So command-line overrides win.

The environment and implicit CC

CC, CXX, CFLAGS, and friends have built-in default values from Make's implicit rule database (more in Chapter 5). CC ?= gcc on most systems does not override the default because CC is already set to "cc" by Make itself. Use CC := gcc if you want to force it. Or, more commonly, don't set it at all and let the user pass it on the command line.

The append (+=) flavor

FOO += bar appends " bar" (with a leading space) to FOO. If FOO isn't already defined, it becomes "bar" (no leading space). 

CFLAGS := -O2
CFLAGS += -Wall
CFLAGS += -Wextra

After all three lines: CFLAGS = -O2 -Wall -Wextra.

+= preserves the flavor of the original assignment. If FOO was =, appending with += stores the text; if it was :=, the right-hand side is expanded first. 

X := one
Y  = $(X) two
Y += $(X) three   # stores literal "$(X) three" — Y stays recursive
X := four
all: ; @echo $(Y)

Outputs: four two four three.

The shell (!=) flavor

FOO != command runs command in a shell and stores the output (with trailing newlines stripped and embedded newlines replaced by spaces). Great for dynamic info: 

GIT_SHA     != git rev-parse --short HEAD
BUILD_DATE  != date +%Y-%m-%d
SOURCES     != find src -name '*.c'
all:
	@echo "Building $(GIT_SHA) on $(BUILD_DATE)"
	@echo "Sources: $(SOURCES)"

The shell runs once at parse time, not every reference. If you want every reference to re-run the command, use the $(shell …) function instead: 

GIT_SHA = $(shell git rev-parse --short HEAD)

Since this uses =, the $(shell …) is re-evaluated at every reference of GIT_SHA. That's usually wasteful — prefer != or GIT_SHA := $(shell …).

Referencing variables

Reference a variable with $(NAME) or ${NAME}. Both work. Braces and parens are interchangeable — pick a style and stick with it. I use parens; some codebases use braces to distinguish Make vars from shell vars visually.

A one-character variable name can be referenced without braces: $X is the same as $(X). This is how automatic variables like $@ and $< work — they're really $(@) and $(<).

Only the first character!

$NAME expands $N, leaving AME. If N isn't set (and it almost never is), you get AME. That's the bug from Exercise 3.3 (b). Use $(NAME) or ${NAME} for anything longer than one character.

Scopes — where variables live

Make has several layers of variable "scope":

  1. Global. Anything assigned at the top level. Visible everywhere.
  2. Command-line. make FOO=bar. Overrides global assignments unless the global assignment uses override. Wins over the environment.
  3. Environment. Shell vars at invocation time become Make vars, unless a global assignment shadows them. Lowest priority.
  4. Target-specific. target: VAR := value. Visible only while Make is building that target (and its prerequisites).
  5. Automatic. $@, $<, etc. Set by Make during recipe execution.

Target-specific variables

CFLAGS := -O2

debug: CFLAGS := -O0 -g
debug: hello

hello: hello.c
	$(CC) $(CFLAGS) hello.c -o hello

When building hello as a prerequisite of debug, CFLAGS is temporarily -O0 -g. Build it directly (make hello) and you get -O2.

Target-specific vars cascade to prerequisites:

release: CFLAGS := -O3 -DNDEBUG
release: my_program
my_program: my_program.o    # inherits CFLAGS=-O3 ... here too
my_program.o: my_program.c  # and here

The override directive

Normally, command-line FOO=bar wins over any Makefile assignment. override flips that: 

override CFLAGS += -Wall

Now -Wall is always added to CFLAGS, even if the user says make CFLAGS=-O2. Use sparingly — you're ignoring the user's wishes.

Exporting to the child shell

Recipes run in a child process. By default that child inherits the environment Make itself had, plus any command-line overrides Make received, plus a handful of Make-specific variables (MAKEFLAGS, etc.). Make variables you defined in the Makefile are NOT exported by default.

To pass a Make variable to the recipe's environment:

CFLAGS := -O2
export CFLAGS

all:
	@echo "CFLAGS in shell is: $$CFLAGS"

To export everything:

.EXPORT_ALL_VARIABLES:
FOO = hello
BAR = world
all:
	@echo $$FOO $$BAR

To un-export a previously exported variable: unexport FOO.

What the child shell inherits
  • Every environment variable Make had when invoked.
  • Every variable you exported.
  • Every variable you passed on the command line as VAR=value — these are automatically exported, unlike Makefile assignments.
  • MAKE, MAKELEVEL, MAKEFLAGS, and related — always exported.

Where did this value come from? $(origin)

The origin function tells you where a variable was set:

all:
	@echo CC was set by: $(origin CC)
	@echo FOO was set by: $(origin FOO)

Possible return values:

  • undefined
  • default — set by Make's built-in rules (e.g. CC=cc)
  • environment
  • environment override — from env but set with -e flag
  • file — assigned in a Makefile
  • command line
  • override — via override directive
  • automatic — like $@

This is occasionally invaluable when debugging "who the hell set CC?".

Multi-line variables with define

For variables whose value is several lines — scripts, templates — use define:

define HELLO_SCRIPT
echo "line 1"
echo "line 2"
echo "line 3"
endef

all:
	$(HELLO_SCRIPT)

Each line of HELLO_SCRIPT is passed to the recipe intact. You can also choose the flavor: define FOO := makes it simply expanded. Without the operator, define is recursively expanded (=).

This is how you build reusable "functions" in Make — more in Chapter 8.

See every variable Make knows about

$ make -p -f /dev/null 2>/dev/null | head -40

make -p dumps the entire internal database: every variable, every rule, every default. Pointing it at /dev/null as the Makefile gets you just Make's built-ins. It's a lot — and it's worth skimming once.

Hands-on: pick the right flavor

Hands-on · six flavors in one file

Create flavors.mk:

makeflavors.mk
# Recursive vs simple
A  = hello
B  = $(A) world
A  = goodbye
show1:
	@echo "recursive: B = $(B)"

C := hello
D := $(C) world
C := goodbye
show2:
	@echo "simple:    D = $(D)"

# Conditional
E ?= default
show3:
	@echo "conditional: E = $(E)"

# Append preserves flavor
F  = one
F += $(A)         # stores "one $(A)"
show4:
	@echo "append(=): F = $(F)"

G := one
G += $(C)         # stores "one hello" — wait, C is now goodbye!
show5:
	@echo "append(:=): G = $(G)"

# Shell
WHOAMI != whoami
NOW    != date +%H:%M:%S
show6:
	@echo "shell: $(WHOAMI) at $(NOW)"

.PHONY: show1 show2 show3 show4 show5 show6
all: show1 show2 show3 show4 show5 show6
.PHONY: all
.DEFAULT_GOAL := all

Run:

$ make -f flavors.mk
recursive: B = goodbye world
simple:    D = hello world
conditional: E = default
append(=): F = one goodbye
append(:=): G = one hello
shell: raghu at 14:23:07
$ make -f flavors.mk E=custom show3
conditional: E = custom

Study G carefully. At the moment G += $(C) was parsed, C was hello. Since G is simply-expanded, the append evaluated $(C) immediately and stored one hello. Later reassignment of C doesn't change G. Contrast F, which stored the text $(A) and only expands at reference time.

Exercises

EX 4.1 easy Predict the output 
X  = apple
Y  = $(X)
X := banana

all:
	@echo Y is $(Y)
	@echo X is $(X)

What does make print?

Show solution 
Y is banana
X is banana

Y is recursive, so $(X) is re-evaluated whenever Y is referenced. By the time the recipe runs, X has been simply-reassigned to banana — the latest value wins. Both echo banana.

EX 4.2 easy Which flavor for pkg-config?

You want to include the output of pkg-config --cflags libxml-2.0 in your CFLAGS. Write the assignment such that the shell call runs exactly once per make invocation, even if CFLAGS is referenced many times.

Show solution 
CFLAGS := -O2 -Wall $(shell pkg-config --cflags libxml-2.0)

Or equivalently: 

CFLAGS != echo -O2 -Wall $$(pkg-config --cflags libxml-2.0)

The key is := (or !=). Using CFLAGS = -O2 $(shell pkg-config …) would re-run the command every time $(CFLAGS) appears — which, if you have 100 .c files each compiling with $(CFLAGS), is 100 forked processes. Slow.

EX 4.3 medium Override behaviour

Given:

CFLAGS := -O2 -Wall
all:
	@echo CFLAGS = $(CFLAGS)

What does each of the following print? Try each.

  1. make
  2. make CFLAGS=-O0
  3. CFLAGS=-O0 make
  4. make -e CFLAGS=-O0
  5. CFLAGS=-g make -e
Show solution
  1. CFLAGS = -O2 -Wall — the Makefile value.
  2. CFLAGS = -O0 — command-line assignments always win.
  3. CFLAGS = -O2 -Wall — Makefile assignments normally shadow the environment.
  4. CFLAGS = -O0 — command line still wins. -e only affects env-vs-Makefile.
  5. CFLAGS = -g — -e flips the rule: environment wins over Makefile.

-e is the "environment override" flag. It's rarely a good idea because it makes your build's behaviour depend on the user's shell environment.

EX 4.4 medium Target-specific cascading

Write a Makefile with three targets:

  • all depends on hello and uses CFLAGS = -O2.
  • debug depends on hello and uses CFLAGS = -O0 -g.
  • profile depends on hello and uses CFLAGS = -O2 -pg.

Share the hello rule across all three. Verify that the right flags are used each time.

Show solution 
CFLAGS := -O2

.PHONY: all debug profile clean

all: hello

debug:   CFLAGS := -O0 -g
debug:   hello

profile: CFLAGS := -O2 -pg
profile: hello

hello: hello.c
	$(CC) $(CFLAGS) hello.c -o hello

clean:
	rm -f hello

To verify: 

$ make -n all
cc -O2 hello.c -o hello
$ make -n debug
cc -O0 -g hello.c -o hello
$ make -n profile
cc -O2 -pg hello.c -o hello

Notice: you must make clean between runs, otherwise the binary is up to date and the rule doesn't re-fire. Or use -B.

EX 4.5 hard The self-referencing trap

Consider:

PATH := /my/extra/bin:$(PATH)
all:
	@echo PATH = $(PATH)

Is this safe? What would it look like with = instead of :=? Under what conditions could the = version loop forever?

Show solution

With :=, the right-hand side is expanded once: $(PATH) gets the current value of PATH (from the environment, because PATH is always in the environment), we prepend /my/extra/bin:, store the result. Safe.

With =, we'd store the text "/my/extra/bin:$(PATH)". Every reference of $(PATH) would then re-expand — and inside that expansion, there's another $(PATH), which expands to "/my/extra/bin:$(PATH)", etc. Infinite loop. Make detects this and errors out with "recursive variable references itself".

Generalisation: self-referential assignments must use :=.

EX 4.6 medium Reproduce the flavour-preservation of +=

Show, with a tiny Makefile, that FOO += $(BAR) behaves differently when FOO was assigned with = vs :=, even though the append line looks identical.

Show solution 
BAR = one

R  = start
R += $(BAR)

S := start
S += $(BAR)

BAR = two

show:
	@echo "R (recursive): $(R)"
	@echo "S (simple):    $(S)"
$ make show
R (recursive): start two
S (simple):    start one

R kept its recursive flavour; its stored text is start $(BAR), re-expanded at reference time. S is simple; the append evaluated $(BAR) immediately, storing start one.

EX 4.7 medium Export discipline

Given:

NAME := raghu
all:
	@echo "from Make: $(NAME)"
	@echo "from shell: $$NAME"

What's the output? Now add export NAME before the rule. What changes?

Show solution

Without export:

from Make: raghu
from shell:

The Make-level $(NAME) expands to raghu, but the child shell has no environment variable NAME, so $NAME expands to empty.

With export NAME:

from Make: raghu
from shell: raghu

Now the child shell inherits NAME=raghu in its environment.

EX 4.8 hard Build flags sniffing with origin

Write a Makefile that prints a warning if the user set CFLAGS from the environment (not the command line), because that often causes surprising builds. Hint: use $(origin …) and $(warning …).

Show solution 
ifeq ($(origin CFLAGS),environment)
$(warning CFLAGS is being set from your environment ($(CFLAGS)). This can cause unexpected builds. Consider passing it on the command line instead.)
endif

CFLAGS ?= -O2 -Wall

all:
	@echo "CFLAGS = $(CFLAGS)"
$ make
CFLAGS = -O2 -Wall
$ CFLAGS=-g make
Makefile:2: CFLAGS is being set from your environment (-g). This can cause unexpected builds. Consider passing it on the command line instead.
CFLAGS = -g
$ make CFLAGS=-O0
CFLAGS = -O0

The command-line version doesn't trigger the warning because its origin is command line, not environment.

Recap

  • = is lazy — stored text, re-expanded at every reference.
  • := is strict — right-hand side expanded once, value frozen.
  • ?= assigns only if not already set (command-line and env count as set).
  • += appends, preserving the flavor of the original.
  • != runs a shell command and captures stdout.
  • Default to :=; reach for = only for late binding.
  • Reference with $(NAME) or ${NAME}. One-char names can skip braces.
  • Target-specific variables cascade to prerequisites.
  • export, unexport, .EXPORT_ALL_VARIABLES: control what reaches the child shell.
  • $(origin VAR) tells you where a value came from.
