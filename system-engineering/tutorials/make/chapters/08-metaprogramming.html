Chapter 08 Metaprogramming

Conditionals, include, computed variable names, .SECONDEXPANSION, and the art of writing Make that writes Make. This is where Makefiles stop being configuration and start being software.

Conditional directives

Make has four conditional directives: ifeq, ifneq, ifdef, ifndef. They work at parse time — they control which rules and variable assignments exist, not what runs at build time. 

ifeq ($(CC),gcc)
    CFLAGS += -Wall -Wextra -Wpedantic
else
    CFLAGS += -Wall
endif

ifdef DEBUG
    CFLAGS += -g -O0
else
    CFLAGS += -O2
endif

ifneq ($(shell uname -s),Linux)
    LDFLAGS += -framework CoreFoundation
endif

Syntax notes:

  • ifeq and ifneq compare two strings. Two syntaxes: ifeq (A,B) or ifeq "A" "B".
  • ifdef VAR / ifndef VAR tests if a variable is non-empty (not merely "defined" — the name is misleading).
  • Use else, else ifeq, else ifdef for chains. Close with endif.
  • Indentation inside a conditional is optional and uses spaces, not tabs, because we're outside a recipe.
Whitespace in ifeq

ifeq ($(A), $(B)) compares $(A) to " $(B)" (note the leading space). Make's string comparison is literal. Usually you want ifeq ($(A),$(B)) — no space after the comma. Or use strip: ifeq ($(strip $(A)),$(strip $(B))).

Parse time vs build time

This is the most important mental model to get right:

  1. Parse time. Make reads the Makefile, top to bottom. It expands variable references in rule headers (target: prereq), evaluates conditional directives, and builds an in-memory graph of rules and variables. Recipes are not yet expanded — they're stored as text.
  2. Build time. Make walks the graph and runs recipes. When a recipe is about to run, its text is expanded: automatic variables are bound, any $(…) is evaluated.

The distinction matters because:

  • $(info), $(warning), $(error) called at the top level fire at parse time.
  • Conditionals are evaluated once, at parse time. You can't have a rule that "becomes different" based on which target the user asked for.
  • The MAKECMDGOALS variable is set at parse time — you can key conditionals on it, though it's a slippery slope.

The include directive

Split your Makefile into pieces:

include config.mk
include rules/compile.mk
include rules/link.mk

Each included file is processed as if typed in-place. They're cumulative — variables defined in one are visible in all later ones.

Variants:

  • include — error if file not found.
  • -include or sinclude — silently skip missing files.

The -include variant is how auto-dependency generation works (Chapter 9): you include *.d files even before they exist.

Includes expand globs:

-include $(wildcard build/*.d)

Makefiles can be prerequisites

Make can also build the Makefile itself. After reading a Makefile, Make checks if there's a rule to rebuild it. If so, and it's out of date, Make builds it and re-execs itself to re-read the updated Makefile.

This is how autoconf/configure systems make "re-run configure if configure.ac changed":

Makefile: Makefile.in config.status
	./config.status $@

It's also how auto-generated dependency files keep themselves current. It's rarely something you write by hand, but it's worth knowing Make can do it.

Computed variable names

Make lets you compute a variable name at runtime using nested references:

CFLAGS_release := -O2 -DNDEBUG
CFLAGS_debug   := -O0 -g
CFLAGS_profile := -O2 -pg

BUILD ?= release
CFLAGS := $(CFLAGS_$(BUILD))

all:
	@echo Using CFLAGS: $(CFLAGS)
$ make
Using CFLAGS: -O2 -DNDEBUG
$ make BUILD=debug
Using CFLAGS: -O0 -g
$ make BUILD=profile
Using CFLAGS: -O2 -pg

$(CFLAGS_$(BUILD)) expands inner-first: $(BUILD) → release, then $(CFLAGS_release). This pattern replaces chains of ifeqs with a single lookup — much cleaner for "N configurations" problems.

.SECONDEXPANSION — prereq late binding

Normally, Make expands a rule's prerequisites once, at parse time. That means: 

%.o: %.c $(HEADERS)       # HEADERS must be defined BEFORE this rule

If you need a prerequisite that depends on the stem (%) or on automatic variables, regular pattern rules can't help you. Enter .SECONDEXPANSION. 

.SECONDEXPANSION:

DEPS_main  := main.h util.h
DEPS_greet := greet.h

%.o: %.c $$(DEPS_$$*)
	$(CC) $(CFLAGS) -c $< -o $@

Read carefully:

  • .SECONDEXPANSION: enables a second pass for prerequisites.
  • $$ in a prerequisite means "don't expand me now — expand me in the second pass".
  • In the second pass, the automatic variable $* (the stem) is already bound, so $(DEPS_$*) becomes $(DEPS_main), $(DEPS_greet), etc. per target.

So when Make builds main.o, the prerequisites are main.c $(DEPS_main) = main.c main.h util.h.

Why the $$

Without $$, the first pass would try to expand $(DEPS_$*) immediately — but $* isn't defined outside a recipe, so the expansion would be empty, and you'd get a rule with no extra prerequisites. The $$ postpones expansion: in the first pass $$ becomes $; in the second pass $(DEPS_$*) is finally evaluated with $* bound.

You don't reach for .SECONDEXPANSION often. When you do, it's usually because:

  • Per-target header dependencies that vary per stem.
  • Generating rules where the prerequisites are a computed function of the target.
  • Very large Makefiles that replace hand-written dep lists with systematic ones.

Rule generation with eval + call

We saw this briefly in Chapter 6. Here's the full idiom.

# Template: given a list of sources, build a static library.
# Usage: $(eval $(call make-lib, libname, src1.c src2.c src3.c))

define make-lib
$(1)_OBJ := $$(patsubst %.c,%.o,$(2))
lib$(1).a: $$($(1)_OBJ)
	ar crs $$@ $$^
LIBRARIES += lib$(1).a
endef

$(eval $(call make-lib,math,fn.c add.c sub.c))
$(eval $(call make-lib,io,  read.c write.c))

.PHONY: libs
libs: $(LIBRARIES)

Mechanics:

  1. $(call make-lib,math,fn.c add.c sub.c) substitutes $(1)→math, $(2)→fn.c add.c sub.c, and single $s are resolved at call time.
  2. Double $$s survive call as single $s — so $$@ becomes $@ in the generated text.
  3. $(eval ...) feeds the generated text back to Make as if it were typed into the Makefile.

This lets you declare many similar structures compactly. The Linux kernel's build system uses variants of this idiom heavily.

The $ counting rules

Nested expansion contexts change how many $s you need. A rough guide:

ContextEscape single $
Top-level Makefile reference$
Inside a recipe (to reach the shell)$$
Inside a define that will be called$$ (gives $ after call)
Inside a define called then evaled$$$$ (call strips one pair, eval strips another → recipe sees $, shell sees it)

Yes it's painful. The trick is to debug with $(info $(call …)) — print the expanded text before handing it to eval, verify it's the Makefile syntax you meant, then re-enable the eval.

Override directives

The override directive lets a Makefile win against command-line assignments:

override CFLAGS += -Wall

Now make CFLAGS=-O0 still gets CFLAGS = -O0 -Wall. Use this for warnings you refuse to let the user turn off, or for flags that are required for correctness.

The analogous directive for define:

override define commit_msg
release v1.0
endef

Variable scoping directives

DirectiveEffect
export VARExport VAR to recipe environment.
export VAR = valAssign and export in one step.
unexport VARDon't export VAR (even if it came in via environment).
private VAR = valVAR is set only for this target (no cascade to prereqs). Only valid in target-specific context.
undefine VARRemove VAR entirely from Make's namespace (GNU Make 3.82+).
 
debug: private CFLAGS := -O0 -g   # don't cascade to prerequisites
debug: hello

Hands-on: multi-config build

Hands-on · build for debug/release with one Makefile

Create multi.mk:

makemulti.mk
CONFIG ?= release

CFLAGS_release := -O2 -DNDEBUG
CFLAGS_debug   := -O0 -g -DDEBUG
CFLAGS_asan    := -O1 -g -fsanitize=address
LDFLAGS_asan   := -fsanitize=address

CFLAGS  := $(CFLAGS_$(CONFIG))
LDFLAGS := $(LDFLAGS_$(CONFIG))

$(info Building with CONFIG=$(CONFIG))
$(info CFLAGS  = $(CFLAGS))
$(info LDFLAGS = $(LDFLAGS))

all:
	@echo "Done."

Run it with each:

$ make -f multi.mk
Building with CONFIG=release
CFLAGS  = -O2 -DNDEBUG
LDFLAGS =
Done.
$ make -f multi.mk CONFIG=debug
Building with CONFIG=debug
CFLAGS  = -O0 -g -DDEBUG
LDFLAGS =
Done.
$ make -f multi.mk CONFIG=asan
Building with CONFIG=asan
CFLAGS  = -O1 -g -fsanitize=address
LDFLAGS = -fsanitize=address
Done.
$ make -f multi.mk CONFIG=weird
Building with CONFIG=weird
CFLAGS  =
LDFLAGS =
Done.

Notice how the computed-variable trick gave us four configurations with no branching, at the cost of silent failure for unknown configs. We can improve that: 

ifeq ($(origin CFLAGS_$(CONFIG)),undefined)
$(error Unknown CONFIG=$(CONFIG); valid: release debug asan)
endif

Exercises

EX 8.1 easy When does ifeq fire?

Given this Makefile: 

X := a
ifeq ($(X),a)
    Y := yes
else
    Y := no
endif
X := b

all: ; @echo Y is $(Y)

What does it print, and why?

Show solution

Prints Y is yes. The ifeq fires at parse time, when X was still a. The subsequent assignment X := b happens after the ifeq has already been evaluated and the branch chosen.

EX 8.2 easy OS detection

Write a Makefile that sets LIBS := -lrt on Linux, LIBS := -framework CoreFoundation on macOS, and errors out on anything else.

Show solution 
UNAME := $(shell uname -s)

ifeq ($(UNAME),Linux)
    LIBS := -lrt
else ifeq ($(UNAME),Darwin)
    LIBS := -framework CoreFoundation
else
    $(error Unsupported OS: $(UNAME))
endif

all: ; @echo LIBS = $(LIBS)
EX 8.3 medium Computed variables beat ifeq chains

Rewrite the following using computed variable names, no ifeq:

ifeq ($(ARCH),x86_64)
    TRIPLE := x86_64-linux-gnu
else ifeq ($(ARCH),arm64)
    TRIPLE := aarch64-linux-gnu
else ifeq ($(ARCH),riscv)
    TRIPLE := riscv64-linux-gnu
endif
Show solution 
TRIPLE_x86_64 := x86_64-linux-gnu
TRIPLE_arm64  := aarch64-linux-gnu
TRIPLE_riscv  := riscv64-linux-gnu

TRIPLE := $(TRIPLE_$(ARCH))

ifeq ($(TRIPLE),)
$(error Unknown ARCH=$(ARCH))
endif

Scales linearly with new architectures. Adding one doesn't touch the lookup logic.

EX 8.4 medium Per-target header deps with .SECONDEXPANSION

You have main.c (depends on main.h and util.h), greet.c (depends on greet.h), and util.c (depends on util.h). Write a single pattern rule that compiles each to a .o with the right per-file prerequisites.

Show solution 
.SECONDEXPANSION:

DEPS_main  := main.h util.h
DEPS_greet := greet.h
DEPS_util  := util.h

%.o: %.c $$(DEPS_$$*)
	$(CC) $(CFLAGS) -c $< -o $@

Writing and maintaining per-target DEPS lists by hand is tedious and error-prone. Chapter 9 shows auto-dependency generation — which does this automatically from the compiler's output, and is almost always what you want in real projects. But this exercise shows the core mechanic.

EX 8.5 hard Generating many tiny rules

Your project has a list of commands: CMDS := init run deploy rollback. For each, write a phony rule cmd-NAME that simply runs the shell script scripts/NAME.sh. Use foreach + eval to generate the rules from the list.

Show solution 
CMDS := init run deploy rollback

define cmd_rule
.PHONY: cmd-$(1)
cmd-$(1):
	bash scripts/$(1).sh
endef

$(foreach c,$(CMDS),$(eval $(call cmd_rule,$(c))))

Verify:

$ make -n cmd-deploy
bash scripts/deploy.sh
$ make -n cmd-rollback
bash scripts/rollback.sh

This is a pattern you'll see constantly in mature Makefiles.

EX 8.6 hard Debugging a template

A colleague's template produces broken Makefile text. They ask for help. The template:

define build_tool
bin/$(1): tools/$(1).c
	$(CC) $(CFLAGS) $< -o $@
endef

$(foreach t,foo bar,$(eval $(call build_tool,$(t))))

When they run make bin/foo, they get an error like "*** recipe commences before first target". Why, and how do you fix it?

Show solution

The $< and $@ inside the template expand at call time (when we're still in the top-level Make parse). At that point there's no target, and they produce junk that ends up in the rule text. The fix: double them up so they survive call and land in the generated rule as $< and $@: 

define build_tool
bin/$(1): tools/$(1).c
	$$(CC) $$(CFLAGS) $$< -o $$@
endef

Also double $(CC) and $(CFLAGS) — not for correctness (they'd expand to empty at call time if undefined, and to the final value if set), but to be consistent and to defer to build-time expansion.

Debugging trick: replace $(eval $(call …)) with $(info $(call …)) to print the generated text, inspect it, then re-enable eval.

EX 8.7 medium Split a Makefile

Refactor this flat Makefile into three files: Makefile (entry point, targets), config.mk (tool variables), and deps.mk (derived file lists). 

CC      := clang
CFLAGS  := -O2 -Wall
LDFLAGS := -flto

SRC := $(wildcard src/*.c)
OBJ := $(patsubst src/%.c,build/%.o,$(SRC))

all: build/hello

build/hello: $(OBJ)
	$(CC) $(LDFLAGS) $^ -o $@

build/%.o: src/%.c
	@mkdir -p $(@D)
	$(CC) $(CFLAGS) -c $< -o $@

clean: ; rm -rf build
.PHONY: all clean
Show solution
makeconfig.mk
CC      := clang
CFLAGS  := -O2 -Wall
LDFLAGS := -flto
makedeps.mk
SRC := $(wildcard src/*.c)
OBJ := $(patsubst src/%.c,build/%.o,$(SRC))
makeMakefile
include config.mk
include deps.mk

all: build/hello

build/hello: $(OBJ)
	$(CC) $(LDFLAGS) $^ -o $@

build/%.o: src/%.c
	@mkdir -p $(@D)
	$(CC) $(CFLAGS) -c $< -o $@

clean: ; rm -rf build
.PHONY: all clean

The split lets config be tweaked by users (often the only file a packager or OS vendor has to edit) while rules stay untouched. Real projects often ship a sample config.mk.sample and ask users to copy it and edit.

Recap

  • ifeq / ifneq / ifdef / ifndef + else + endif for parse-time branching.
  • Conditionals evaluate once at parse time. Mind the whitespace around commas in ifeq.
  • include FILE, -include FILE (silent-miss), and sinclude. Globs allowed.
  • Computed variable names: $(FOO_$(X)) — lets you replace ifeq chains with a lookup.
  • .SECONDEXPANSION: enables a second pass for prerequisites; use $$ to defer expansion.
  • define … endef + $(call name,a,b) + $(eval …) = rule generation. Mind the $ counts.
  • override forces Makefile-side values to win over command-line. Use sparingly.
  • export, unexport, private, undefine fine-tune variable scope and exportability.
