Chapter 07 Phony & Special Targets

.PHONY, order-only prerequisites, :: double-colon rules, grouped targets, and the full set of .SPECIAL targets Make knows about. This is where your Makefiles go from "works on my machine" to "works correctly and predictably".

Phony, properly

We met .PHONY in Chapter 3: it tells Make that a target isn't a file. Let's do it thoroughly.

A target is phony when its name should not be treated as a file name. Its recipe is always run, timestamps are irrelevant, and Make never tries to find a file with that name. 

.PHONY: all clean test install release docs help

all: hello
clean: ; rm -f hello *.o
test: hello; ./hello
# …

Why does this matter?

$ touch clean           # create a file called "clean"
$ make clean
make: 'clean' is up to date.

If clean weren't phony, Make checks for a file named clean, finds one, has no prerequisites, declares "up to date", and does nothing. Disaster narrowly averted by .PHONY.

There's a less-obvious second benefit: phony targets also opt out of implicit rule matching. If your target is test, Make might otherwise try to run a built-in rule like "compile test.c to test" and surprise you. .PHONY: test shuts that down.

Rule of thumb: every action target goes in .PHONY. No exceptions. Grow the list as you add targets.

The compact .PHONY idiom

Scattering .PHONY: name above each rule is noisy. Consolidate at the top: 

.PHONY: all clean test install

all: hello
clean: ; rm -f hello *.o
test: hello; ./hello
install: hello; cp hello /usr/local/bin/

Or, if you like, per-rule in shorter Makefiles:

.PHONY: all
all: hello

.PHONY: clean
clean: ; rm -f hello *.o

Pick one style. I prefer consolidated at the top because it's a single place to audit.

Order-only prerequisites

Problem: you want a build directory to exist before compiling, but you don't want the build directory's mtime triggering rebuilds. On Unix, a directory's mtime changes whenever files are added to it — so every new output would retrigger every other output.

Solution: order-only prerequisites, separated by a |:

build/%.o: src/%.c | build
	$(CC) $(CFLAGS) -c $< -o $@

build:
	mkdir -p $@

Read: "build/foo.o depends on src/foo.c and the directory build must exist. But build's mtime doesn't count — don't rebuild foo.o just because the directory was touched".

Order-only prerequisites are in $| (their own automatic variable), not $^.

Canonical use: directory creation

Any time you need "make sure this directory exists before producing a file in it", use an order-only prerequisite. It's cleaner than mkdir -p on every line of every recipe, and it composes correctly with parallel builds.

Grouped targets (&:)

Sometimes one recipe produces multiple files simultaneously — think of a yacc generating both parser.c and parser.h. Traditional Makefile tricks to handle this are all wrong (they either rebuild N times in parallel, or miss the dependency entirely).

GNU Make 4.3+ has grouped targets:

parser.c parser.h &: parser.y
	yacc -d parser.y
	mv y.tab.c parser.c
	mv y.tab.h parser.h

Note the &: — one ampersand, one colon. It means "this recipe produces all of these files when run once". If either parser.c or parser.h is missing or stale, the recipe fires exactly once and produces both.

Contrast the classic form:

parser.c parser.h: parser.y        # WRONG in parallel builds
	yacc -d parser.y
	# …

That declares two independent rules sharing a recipe. With -j, Make may try to run the recipe twice simultaneously. The &: form fixes it.

Double-colon rules

A regular (single-colon) rule: you can have one recipe per target. Multiple rules add prerequisites.

A double-colon (::) rule: each :: rule is independent. The target is rebuilt if any of its :: rules has an out-of-date prerequisite. Each rule's recipe runs independently. 

doc.html :: content.md
	pandoc content.md -o doc.html

doc.html :: styles.css
	touch doc.html     # just update its mtime when CSS changes

When do you want this? Rarely. Two legitimate uses:

  • "Update if any of these changes" where each change needs a different handler. Above: content change means full rebuild, CSS change means just re-timestamp so downstream dependents notice.
  • Multi-file generation with distinct recipes per trigger — occasionally shows up in research pipelines.

For 99% of cases, single-colon rules and pattern rules suffice.

The full set of .SPECIAL targets

Make reserves a handful of "target names that aren't really targets" — they configure Make's behaviour. You've met .PHONY already. Here's the full set.

.PHONY: names…

Marks names as phony. Always run recipe. Don't check for files. Don't apply implicit rules.

.DELETE_ON_ERROR:

If a recipe fails, Make deletes the target it was trying to build. Without this, a failed recipe can leave a half-written file that's newer than its prerequisites — and Make will think it's up to date next time. 

.DELETE_ON_ERROR:

report.pdf: report.tex data.csv
	pdflatex report.tex        # if this fails, report.pdf is deleted

Put this in every non-trivial Makefile. It has no downside for correctness.

.INTERMEDIATE, .SECONDARY, .PRECIOUS

These three control how Make treats intermediate files.

TargetEffect
.INTERMEDIATE: names…These files are treated as intermediate — created if needed, deleted when Make finishes.
.SECONDARY: names…Don't delete these when Make finishes — but treat them as intermediate for dependency purposes (don't rebuild if they're missing and something else in the chain is up to date).
.PRECIOUS: names…If a recipe is interrupted (Ctrl-C or signal), don't delete these files. Without this, Make deletes targets on interrupt.
 
.PRECIOUS: %.o                    # keep .o files on interrupt
.SECONDARY:                       # with no args, applies to all intermediates

When Make chains rules (e.g. foo → foo.o → foo.c), any file not explicitly asked for becomes intermediate. By default intermediate files are deleted at the end of the build. .SECONDARY: with no arguments prevents this — very common in Makefiles that chain generators.

.ONESHELL, .SILENT, .IGNORE

.ONESHELL: — run each recipe as a single shell (Chapter 3).

.SILENT: — don't echo recipes. With no arguments: globally; with arguments: only for those targets.

.IGNORE: — ignore exit status. Equivalent to prefixing every recipe line with -.

.NOTPARALLEL:

Force sequential execution even with -j. Use when one of your recipes fundamentally can't be parallelised. 

.NOTPARALLEL:
# Nothing in this Makefile will run in parallel, regardless of -j

You can also scope it to specific targets in GNU Make 4.4+:

.NOTPARALLEL: release     # only release runs non-parallel

.SUFFIXES:

Historic mechanism for "suffix rules" (the ancestor of pattern rules). Mostly obsolete. You'll sometimes see: 

.SUFFIXES:                       # clear the list — disable suffix rules

This disables Make's old .c.o:-style rules. Usually safe and occasionally removes surprising behavior.

.DEFAULT_GOAL

Not a target — a variable. Set it to control which target runs when you type make with no argument: 

.DEFAULT_GOAL := all

clean: ; rm -f *.o
all: hello
# Even though clean is listed first, `make` builds `all`.

.DEFAULT:

A target with no name that provides a recipe for any target that has no rule. Very rarely useful; usually a sign of a Makefile that's trying to be too clever.

.EXPORT_ALL_VARIABLES:

Make's version of set -a: every Make variable becomes an environment variable for child processes.

.RECIPEPREFIX

This one is a peace offering from GNU Make. If the tab character has driven you insane, change it: 

.RECIPEPREFIX := >
hello:
> echo "Now recipe lines start with > instead of tab"
> echo "and tab is just a regular whitespace"

GNU Make 3.82+. Few Makefiles use it (Make users are masochists who have accepted their fate) but it exists. Don't deploy this in a codebase where newcomers might be confused — stick with tabs in shared projects.

.POSIX:

Declares that the Makefile wants POSIX conformance. Changes some behavior subtly (mostly around shell invocation). Honest opinion: rarely needed; if you want POSIX-portable Make, use BSD Make directly.

.SECONDEXPANSION:

Big gun — enables a second pass of variable expansion for rule prerequisites. We give it its own section in Chapter 8.

.LOW_RESOLUTION_TIME

Targets listed here use seconds-granularity time comparisons instead of sub-second. Useful if you're building on a filesystem (FAT32) that doesn't support sub-second mtimes. Rarely needed.

Hands-on: order-only in action

Hands-on · why order-only matters

Create this Makefile:

makeMakefile
.PHONY: all clean

all: build/a.txt build/b.txt

build/a.txt: | build
	echo "a" > $@

build/b.txt: | build
	echo "b" > $@

build:
	mkdir -p $@

clean: ; rm -rf build

Run:

$ make
mkdir -p build
echo "a" > build/a.txt
echo "b" > build/b.txt
$ make
make: Nothing to be done for 'all'.

Now remove the | and make build a regular prerequisite, then touch build:

build/a.txt: build          # regular, not order-only
	echo "a" > $@
$ touch build
$ make
echo "a" > build/a.txt
echo "b" > build/b.txt    # rebuilt — unnecessarily!

With a regular prereq, writing build/a.txt modified build's mtime, which would then trigger build/b.txt's recipe, and so on. Order-only breaks this cycle.

Every Makefile checklist

Here's my short list of "always include these" in real projects:

.DELETE_ON_ERROR:                              # clean up failed targets
.SUFFIXES:                                     # kill suffix-rule surprises
MAKEFLAGS += --warn-undefined-variables        # catch typos
MAKEFLAGS += --no-builtin-rules                # predictability
SHELL       := /bin/bash
.SHELLFLAGS := -eu -o pipefail -c
.ONESHELL:

.DEFAULT_GOAL := all

.PHONY: all clean test install release help

Most of these come up in later chapters — treat the list as a forward reference.

Exercises

EX 7.1 easy Why does this fail?

A user reports: "My make install target stopped working — it just says 'Nothing to do for install'." You look at the Makefile: 

install: hello
	cp hello /usr/local/bin/

You notice there's a file called install in the project root. Explain what happened and give a one-line fix.

Show solution

The file install is newer than hello (or always up-to-date because it has no prereqs with rules), so Make thinks the "target" is already built.

Fix: add .PHONY: install.

EX 7.2 easy Why always DELETE_ON_ERROR?

Give a specific example where .DELETE_ON_ERROR: saves you from a silent wrong-build.

Show solution 
report.pdf: report.tex
	pandoc report.tex -o report.pdf

Suppose pandoc fails halfway through, leaving a partially-written report.pdf. Its mtime is newer than report.tex. Next time you run make, it sees report.pdf is "up to date" and silently succeeds — except the PDF is corrupt. You discover this at 3 AM before a deadline.

With .DELETE_ON_ERROR:, Make removes report.pdf on failure. Next run rebuilds cleanly. You sleep.

EX 7.3 medium Grouped vs shared

You have:

parser.c parser.h: parser.y
	yacc -d $<
	mv y.tab.c parser.c
	mv y.tab.h parser.h

main.o: parser.h
scanner.o: parser.c

Under what circumstances does this produce a wrong build? Fix it.

Show solution

With make -j 2, Make may notice both parser.c and parser.h are needed and start the recipe twice simultaneously. The two instances race for y.tab.c and y.tab.h; you can get duplicated commands, truncated files, and spurious errors.

Fix: grouped target.

parser.c parser.h &: parser.y
	yacc -d $<
	mv y.tab.c parser.c
	mv y.tab.h parser.h

Now the recipe runs exactly once, no matter which of the two files (or both) trigger it.

EX 7.4 medium Implement a help target

Write a phony help target that prints a list of available actions with one-line descriptions. Bonus: auto-generate from annotations in the Makefile so it stays in sync.

Show solution

Simple static version:

.PHONY: help
help:
	@echo "Targets:"
	@echo "  all       — build everything"
	@echo "  test      — run tests"
	@echo "  install   — install to /usr/local"
	@echo "  clean     — remove build artifacts"

Auto-generated from annotations (this is the idiom in many modern Makefiles):

.PHONY: help
help:  ## show this help
	@awk 'BEGIN {FS=":.*##"} /^[a-zA-Z_-]+:.*##/ { \
	    printf "  %-15s %s\n", $$1, $$2 }' $(MAKEFILE_LIST)

.PHONY: all test install clean
all:     ## build everything
	…
test:    ## run tests
	…
install: ## install to /usr/local
	…
clean:   ## remove build artifacts
	…

Running make help:

$ make help
  help            show this help
  all             build everything
  test            run tests
  install         install to /usr/local
  clean           remove build artifacts

The awk one-liner extracts all lines of the form target: ... ## description. A common pattern — worth stealing for every project.

EX 7.5 medium Keeping intermediates

A build chain produces foo.a → foo.b → foo.c. When you ask for foo.c, the foo.a and foo.b are created and then deleted automatically because they're intermediate. You want to keep them for debugging. How?

Show solution

Option 1 — catch-all:

.SECONDARY:       # keep every intermediate

Option 2 — specific:

.SECONDARY: foo.a foo.b

Option 3 — add them as explicit goals so Make doesn't consider them intermediate:

all: foo.c foo.b foo.a

Most codebases go with .SECONDARY: — simple, safe.

EX 7.6 hard Never parallelise tests

Your test suite writes to a shared resource (say, a database) and must run sequentially, but your compilation can happily parallelise. How do you let the user run make -j 8 all test such that compilation is parallel but tests run one at a time?

Show solution

Use .NOTPARALLEL targeted at the test target, or have the test target invoke Make recursively with -j 1:

# GNU Make 4.4+ — scoped .NOTPARALLEL
.NOTPARALLEL: test

.PHONY: all test
all: $(BINARIES)

test: $(TEST_BINS)
	@for t in $^; do ./$$t || exit 1; done

Or portable for older Makes, use a sub-make:

.PHONY: test
test:
	$(MAKE) -j 1 do-test

do-test: $(TEST_BINS)
	@for t in $^; do ./$$t || exit 1; done

Spawning a new make with -j 1 overrides the inherited jobserver and forces sequential execution of do-test's prerequisites.

EX 7.7 hard Investigate a real Makefile

Pick any moderately-sized open-source project (the Linux kernel, Redis, Git, PostgreSQL). Find its top-level Makefile. Identify:

  • Which targets are phony?
  • Which .SPECIAL targets does it use, and why?
  • Does it use order-only prerequisites? For what?
  • Any double-colon rules?
Show solution

No single solution. Some things you're likely to find:

  • Git's Makefile uses .PHONY extensively and .DELETE_ON_ERROR:.
  • Redis uses .PHONY on all action targets and careful .NOTPARALLEL placement.
  • The Linux kernel's Makefile uses order-only prereqs extensively for output directories (it has a "build outside the tree" mode you've probably used: make O=/tmp/kernel-build).

The point of the exercise isn't any one "right" answer — it's to make your eyes more fluent in real Make code.

Recap

  • .PHONY for every action target. Always.
  • Order-only prerequisites (|) for "must exist" dependencies whose mtime shouldn't trigger rebuilds. Canonical: output directories.
  • Grouped targets (&:) when one recipe produces multiple outputs.
  • Double-colon rules when you want multiple independent recipes for the same target — rarely useful.
  • .DELETE_ON_ERROR: belongs in every non-trivial Makefile.
  • .SECONDARY: keeps intermediates around.
  • .PRECIOUS: keeps files on interrupt.
  • .NOTPARALLEL: for recipes that can't share resources.
  • .SUFFIXES: disables legacy suffix rules — turn it on in modern Makefiles.
  • .DEFAULT_GOAL, .RECIPEPREFIX, .EXPORT_ALL_VARIABLES round out your toolkit.
