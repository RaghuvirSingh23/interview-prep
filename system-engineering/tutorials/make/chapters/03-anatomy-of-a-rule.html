Chapter 03 Anatomy of a Rule

A rule has three parts: a target, some prerequisites, and a recipe. That's it. But each part has subtleties that trip people up for years. This chapter dissects them all.

The three parts, drawn out

target : prereq1 prereq2 prereq3
	recipe-line-1
	recipe-line-2
	recipe-line-3

Read top to bottom:

  • target — the file Make is trying to produce, or the name of a phony action.
  • prerequisites — zero or more whitespace-separated file names (or phony names) that must exist / be up-to-date before the recipe runs.
  • recipe — one or more tab-indented lines of shell to execute.

You can have targets with no prerequisites:

greet:
	echo hello

And rules with no recipe (purely for declaring a dependency):

all: hello docs tests

And rules where the target is multiple files:

a.o b.o c.o: shared.h

This declares that three targets each depend on shared.h — useful for shared prerequisites. It is not saying "one recipe produces all three"; that's a grouped target, which uses &: and we cover in Chapter 7.

Recipe semantics — how lines actually run

By default each line of a recipe runs in its own shell. This is the single most important fact about Make's execution model and it burns everyone eventually. 

test:
	cd /tmp
	pwd                 # prints $HOME, not /tmp
$ make test
cd /tmp
pwd
/Users/you

Why? Because Make spawned one shell for cd /tmp, which exited. Then Make spawned a fresh shell for pwd. The first shell's working directory is gone.

Three ways to make lines share state:

1 · Chain with && / ;

test:
	cd /tmp && pwd

Standard shell. The entire line — including the continuation — runs as one shell invocation.

2 · Line continuation with \

test:
	cd /tmp && \
	pwd

Make joins backslash-newline and sends the whole thing to one shell.

3 · .ONESHELL:

.ONESHELL:
test:
	cd /tmp
	pwd                 # now prints /tmp

With .ONESHELL: at the top of the Makefile, every recipe runs as a single shell invocation. Set it once and forget. The catch: error handling changes subtly (more below).

Which shell does Make use?

Make invokes $(SHELL) -c 'the line' for each recipe line. The default for SHELL is /bin/sh on Unix. You can override it: 

SHELL := /bin/bash
.SHELLFLAGS := -eu -o pipefail -c

The two lines above switch to bash with strict mode (-e exit on error, -u error on undefined vars, -o pipefail propagate pipe errors). For any non-trivial Makefile, these are wise defaults. We'll cover SHELL vs .SHELLFLAGS more in Chapter 11.

Error handling per line

If a recipe line exits non-zero, Make prints an error and stops. Under .ONESHELL: there's a subtlety: without set -e, the whole recipe only fails if the last command fails. The safer incantation: 

.ONESHELL:
SHELL := /bin/bash
.SHELLFLAGS := -eu -o pipefail -c

A single - prefix ignores failure for that line:

clean:
	-rm -f *.o *.bak
	-rmdir build

A single @ prefix silences the echo (we saw this in Chapter 2):

hello:
	@echo "  CC   hello.c"
	cc hello.c -o hello

A single + prefix says "run this even in a dry run (-n)":

test:
	+$(MAKE) -C subdir       # always run MAKE, even with -n, for jobserver reasons

You can combine the three prefixes in any order:

clean:
	-@rm -f *.o    # silence echo AND ignore errors

Phony targets

clean and all aren't files. They're names for actions. What happens if you accidentally create a file called clean? 

$ touch clean
$ make clean
make: 'clean' is up to date.

Make sees the file clean, has no prerequisites to check, concludes it's already built, refuses to run the recipe. Disaster.

The fix:

.PHONY: clean
clean:
	rm -f hello main.o greet.o

.PHONY is a special target that says "these targets are phony — don't look for files with these names, always run the recipe". It's a declaration. You can list as many as you like: 

.PHONY: all clean test install release

We'll cover .PHONY in depth in Chapter 7. For now, mark every action-target as phony. Always. No exceptions.

Prerequisite order and parallelism

Prerequisites are unordered. When Make processes a rule, it visits prerequisites in the order listed — but with -j, it will happily run independent prerequisites in parallel. Your Makefile must not depend on prerequisite A finishing before prerequisite B unless B explicitly lists A as its own prerequisite. 

all: a b c   # a, b, c may all run simultaneously with -j

a: ; echo a && sleep 1 && date
b: ; echo b && sleep 1 && date
c: ; echo c && sleep 1 && date

If you need ordering (say, b must run after a), encode it in the graph: 

all: c
c: b
b: a

There's also a halfway house called order-only prerequisites — we'll meet them in Chapter 7. They say "this must be built first if it doesn't exist, but its mtime shouldn't trigger my rebuild".

Multiple rules for the same target

You can define more than one rule for the same target. Make will merge the prerequisites but only one rule can have a recipe: 

# In Makefile:
hello: main.o

# In Makefile.extras (include'd later):
hello: greet.o

Net effect: hello depends on both main.o and greet.o. This is the standard way to add dependencies to a target without rewriting the recipe — common when auto-generated dependency files get pulled in via include.

If you give two recipes for the same target, Make warns and uses the second:

$ make
Makefile:2: warning: overriding recipe for target 'hello'
Makefile:1: warning: ignoring old recipe for target 'hello'

There is a feature called double-colon rules that does allow multiple independent recipes — one for each rule. We cover it in Chapter 7. Short version: you rarely need it.

Shell syntax vs Make syntax — don't confuse them

Make has its own syntax for everything outside recipes (target/prerequisite lines, variable assignments, functions, directives). Recipes, by contrast, are passed verbatim to the shell. This trips people up constantly: 

MSG = hello             # Make assignment, Make's $MSG

greet:
	MSG="world"         # shell assignment — ends when the shell exits
	echo $(MSG)         # Make's $MSG → "hello"  (expanded before shell sees it)
	echo $$MSG          # shell's $MSG → ""       (different shell, empty)

Run this and look at the output:

$ make greet
MSG="world"
echo hello
hello
echo $MSG

Read that carefully. Key facts:

  • $(MSG) is Make's syntax for expanding a variable. It's expanded by Make before the recipe line is handed to the shell.
  • A literal $ in a recipe must be written $$. That produces a single $ in the shell.
  • The shell variable MSG set on line 1 exists only until that shell exits — and it exits at the end of that line, because each line is its own shell.
The $$ rule

If you want the shell to see $foo, write $$foo in the Makefile. Every single $ that you want the shell to see must be doubled. This bites everyone at least once.

Summary of line prefixes

PrefixMeaning
@Don't echo this line before running it.
-Ignore non-zero exit status; don't stop the build.
+Run this line even under -n / -q / -t. Used for recursive $(MAKE).

They combine in any order: @-rm -f foo, -@rm -f foo, etc.

Hands-on: subshells vs .ONESHELL

Hands-on · subshells in action

Create a new directory and this Makefile:

makeMakefile
.PHONY: subshells oneshell

subshells:
	@echo "--- default: one shell per line ---"
	X=1
	echo "X is $$X"

oneshell:
	@echo "--- .ONESHELL not set yet ---"
	Y=1
	echo "Y is $$Y"

Run:

$ make subshells
--- default: one shell per line ---
X=1
echo "X is $X"
X is

$ make oneshell
--- .ONESHELL not set yet ---
Y=1
echo "Y is $Y"
Y is

Now add .ONESHELL: to the top of the Makefile:

.ONESHELL:
.PHONY: subshells oneshell
# … rest unchanged

Re-run:

$ make oneshell
--- .ONESHELL not set yet ---
Y=1
echo "Y is $Y"
Y is 1

With .ONESHELL:, the recipe is handed to one shell, so the Y=1 persists to the next line. Subshells behaviour changed globally — that's the cost.

Exercises

EX 3.1 easy Identify the parts

For each of the following rules, name the target, prerequisites, and recipe: 

(a) all: hello docs
(b) hello.o: hello.c hello.h
	cc -c hello.c -o hello.o
(c) docs:
	pandoc README.md -o docs.pdf
(d) $(OBJ): $(HEADERS)
Show solution
  1. Target: all. Prereqs: hello, docs. Recipe: none (an aggregator rule).
  2. Target: hello.o. Prereqs: hello.c, hello.h. Recipe: the cc command.
  3. Target: docs. Prereqs: none. Recipe: the pandoc command.
  4. Targets: every file listed in the variable OBJ (there can be many). Prereqs: every file listed in HEADERS. Recipe: none. This is the pattern "all object files depend on all headers" — crude but common. A better solution using auto-dep generation comes in Chapter 9.
EX 3.2 medium The subshell trap

A colleague writes this Makefile: 

deploy:
	source env.sh
	scp $$TARGET deploy@host:/var/www

They complain that $TARGET is never set, even though env.sh definitely exports it. What's wrong and how do you fix it?

Show solution

Each recipe line runs in its own shell. source env.sh sets TARGET in a shell that immediately exits. The scp line runs in a new shell with no TARGET defined.

Three fixes, in order of preference:

# (1) one line
deploy:
	source env.sh && scp $$TARGET deploy@host:/var/www

# (2) line continuation
deploy:
	source env.sh && \
	scp $$TARGET deploy@host:/var/www

# (3) .ONESHELL (global)
.ONESHELL:
deploy:
	source env.sh
	scp $$TARGET deploy@host:/var/www

Option 1 or 2 is what I'd use — it's explicit and local. Option 3 changes the behaviour of the whole Makefile and isn't always desirable.

EX 3.3 medium $ vs $$

Predict the output of each recipe. Then run it and check.

NAME = raghu

a:
	echo hello $(NAME)

b:
	echo hello $NAME

c:
	echo hello $$NAME

d:
	NAME=world; echo hello $$NAME
Show solution
RuleEchoedWhy
ahello raghuMake expands $(NAME) before the shell runs.
bhello AMEMake sees $N (a Make variable), expands it to empty, leaves AME. Classic mistake.
chello followed by a newline$$ becomes a single $, so the shell sees $NAME. In a fresh shell, $NAME is empty.
dhello worldThe shell's NAME=world assignment takes effect within the same shell command, so $NAME expands to world.
EX 3.4 easy Quiet and ignore-error

Write a clean target that silently removes *.o, *.bak, and a directory called build/, without failing if any of those don't exist. Don't use rm -f.

Show solution 
.PHONY: clean
clean:
	-@rm *.o 2>/dev/null
	-@rm *.bak 2>/dev/null
	-@rmdir build 2>/dev/null

The - prefix ignores failure, the @ suppresses the echo, and 2>/dev/null hides the "No such file" stderr. That said: in real life, use rm -rf. It's cleaner. This exercise is about understanding the prefixes.

EX 3.5 hard Write it with strict bash

Create a Makefile that uses .ONESHELL: plus bash's strict mode (-eu -o pipefail). Write a single target check whose recipe:

  1. Sets a variable FILES to *.c.
  2. Iterates with for f in $FILES; do ....
  3. Prints each filename and its line count.

The whole recipe should abort if any single step fails.

Show solution 
SHELL := /bin/bash
.SHELLFLAGS := -eu -o pipefail -c
.ONESHELL:

.PHONY: check
check:
	FILES=*.c
	for f in $$FILES; do
	    echo "$$f:"
	    wc -l < "$$f"
	done

Note: even with .ONESHELL:, you still need $$ for shell variables — because Make still parses the recipe and expands $(...) references before handing it to the shell. $$FILES becomes $FILES for bash.

If you have no .c files, the glob won't expand and the for loop sees the literal string *.c. The wc on *.c will fail, and because of set -e, the recipe aborts. Good.

EX 3.6 medium When does it run?

Given:

all: a b

a:
	@echo "running a"

b:
	@echo "running b"

a: c

c:
	@echo "running c"

What does make all print? Note: there are two rules for a.

Show solution

First, Make merges the two rules for a: now a depends on c, and has the recipe from the first rule. The graph is all → {a, b}; a → c. Walking from all: 

$ make all
running c
running a
running b

a is processed first, so c runs, then a, then b. In parallel mode, b might start before c finishes — try it with -j 2 and see.

EX 3.7 hard Override the shell per-target

You want most of your Makefile to use sh (fast, portable), but a specific target report needs bash because it uses arrays. Without changing the global SHELL, make report's recipe run under bash.

Show solution

Target-specific variables:

report: SHELL := /bin/bash
report: .SHELLFLAGS := -eu -o pipefail -c
report:
	arr=(one two three)
	printf '%s\n' "$${arr[@]}"

The first two lines set SHELL and .SHELLFLAGS only when Make is executing the report target's recipe. All other targets see the global defaults. Target-specific variables are covered more in Chapter 4.

Recap

  • A rule is target : prerequisites + tab-indented recipe lines.
  • Each recipe line runs in its own shell unless you chain with &&, continue with \, or set .ONESHELL:.
  • The default shell is /bin/sh. Override globally with SHELL := /bin/bash, adjust flags with .SHELLFLAGS.
  • Line prefixes: @ (silent), - (ignore errors), + (always run).
  • Two rules for the same target merge prerequisites; only one rule can carry the recipe.
  • $ in a recipe must be doubled as $$ to reach the shell.
  • Action-targets (clean, all, test) should be declared .PHONY.
