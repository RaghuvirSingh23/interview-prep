Chapter 13 The 50 Questions

Fifty questions an interviewer might ask about C, C++, Linux, and debugging. They are not trivia. Each one tests whether you understand the model behind the answer. Read the answer fully — the “why” matters more than the verb.

How to use this chapter. Try to answer each question out loud before reading. If your answer matches the first sentence but not the “why” paragraph, you have a gap. Plug it before the interview, not during.

C language & pointers (1–10)

1. What does int *p, q; declare?

One pointer and one int. The * binds to p, not to the type. To declare two pointers write int *p, *q; — or, better, int *p; int *q; on separate lines. This is why systems-programming style guides insist on one declaration per line.

2. What is the difference between an array and a pointer?

An array is an aggregate: it has a fixed size known at compile time and its name evaluates to its first element in most contexts (the “array decay” rule). A pointer is just an address. sizeof(arr) gives the array's byte size; sizeof(p) gives the pointer's size (8 on 64-bit). The exceptions where arrays don't decay are sizeof, &arr, and the initialiser of a character array from a string literal.

3. Read this declaration: char *(*f[3])(int).

An array of 3 pointers to functions taking int and returning char *. Read declarations “spirally”: start at the name f, go right if you can ([3] → array of 3), then left (* → of pointers), then right inside the parens ((int) → to functions taking int), then left (char * → returning char *). When in doubt, run cdecl.

4. Why does if (-1 < sizeof(x)) always evaluate false?

sizeof returns size_t, an unsigned type. The comparison promotes -1 to a huge unsigned value (SIZE_MAX). Always be wary of mixing signed and unsigned in comparisons; turn on -Wsign-compare/-Wconversion.

5. What is undefined behaviour for signed integer overflow, and why does the compiler care?

Signed overflow is UB in C and C++. The compiler is permitted to assume it doesn't happen, which lets it optimise loops like for (int i = 0; i <= n; i++) assuming i can never wrap. If you actually want wrap, use unsigned arithmetic, or build with -fwrapv, or use __builtin_add_overflow for safe checked arithmetic.

6. Why is strncpy dangerous?

It does not guarantee a NUL terminator. If the source is at least as long as n, the destination is left unterminated. It also pads with NULs if the source is shorter — bad for performance on large buffers. Prefer snprintf(dst, n, "%s", src) or strlcpy (BSD/POSIX 2024).

7. What is strict aliasing, and why is the char * exception special?

The compiler assumes pointers of unrelated types don't alias the same memory, allowing it to keep values in registers across stores via foreign types. Casting an int* to float* and dereferencing is UB. The exception: char *, unsigned char *, and std::byte * may alias anything. To reinterpret bytes legally, use memcpy — the compiler optimises it to a register move.

8. When does const on a function parameter matter?

On a pointer-to-const (const char *), it documents and enforces that the function won't modify the pointee. On a top-level const on the parameter itself (void f(int const x)), it's a local promise with no effect on the caller. Top-level const on function parameters is ignored when matching declarations.

9. What is a volatile variable for, and what is it not?

It tells the compiler that the variable can change in ways the compiler can't see — memory-mapped I/O registers, signal handlers writing sig_atomic_t. It is not for thread synchronisation; for that you need atomics or mutexes. volatile doesn't insert memory barriers.

10. What does restrict tell the compiler?

That the pointer is the only access path to the object it points to within its scope. It enables vectorisation and redundant-load elimination. Lying to the compiler with restrict is UB — do not use it on overlapping buffers.

C++ (11–20)

11. Explain RAII in one sentence.

Resource lifetime is bound to object lifetime: acquire in the constructor, release in the destructor. The destructor runs on every exit path — normal return, exception, early break — which is what makes it bulletproof.

12. What's the difference between unique_ptr and shared_ptr?

unique_ptr is a thin wrapper: one owner, no overhead beyond the pointer. shared_ptr owns a control block with a reference count; copies bump the count, destructions decrement it, the resource dies on zero. Prefer unique_ptr by default; reach for shared_ptr only when ownership is genuinely shared (caches, async work).

13. What's a dangling reference and how do you avoid it?

A reference (or pointer) to an object whose lifetime has ended. Common cause: returning a reference to a local; binding a reference to a temporary that immediately dies. Prevent with ownership-aware design (RAII, unique_ptr) and by knowing the lifetime extension rules (const T& to a temporary in a local extends its lifetime; the same in a return value does not).

14. What is the rule of zero, three, five?

Rule of zero: if your class manages no resources directly, let the compiler generate everything. Rule of three: if you define a destructor, copy ctor, or copy assignment, you usually need all three. Rule of five: with C++11, also define move ctor and move assignment (or = delete them) so moves don't fall back to copies.

15. What does std::move actually do?

Nothing at runtime — it's a static cast to an rvalue reference. It's a way of telling the next function that this object is about to die, so it can steal its guts instead of copying. The cast is harmless if no move ctor exists; it just falls back to copy.

16. When should a virtual destructor be declared?

Whenever the class will be deleted polymorphically through a base pointer. Without virtual, only the base destructor runs and derived resources leak. Mark the destructor virtual or make the class non-polymorphic with final.

17. What does noexcept buy you?

It's a contract: this function will not throw. Important on move constructors and move assignment, because containers like std::vector will fall back to copy on reallocation if the move can throw — in the name of strong exception safety. A non-noexcept move silently destroys performance.

18. What is a lambda, and what does the capture clause do?

A lambda is syntactic sugar for an unnamed function-object class with an operator(). The capture clause generates members initialised from local variables: [x] by copy, [&x] by reference. Capturing this stores the pointer; capturing *this stores a copy of the object (C++17).

19. Why does iterator invalidation matter?

Modifying a container often invalidates outstanding iterators and references. vector: any reallocation invalidates all; insertions invalidate from the insertion point. map/set: only the erased iterator is invalidated. Using an invalidated iterator is UB — ASan catches some, not all.

20. What does constexpr mean, and how is it different from const?

const means “I won't modify this”. constexpr means “evaluatable at compile time if the inputs are”. constexpr functions can also run at runtime; they are a superset, not an alternative. C++20 added consteval for “must run at compile time”.

Memory & UB (21–25)

21. Sketch a process's virtual memory layout.

From low to high addresses: the text segment (read-only code), rodata, initialised data (.data), uninitialised data (.bss), the heap growing up, shared libraries somewhere in the middle (ASLR-randomised), the stack growing down from a high address, then the kernel page above. cat /proc/self/maps shows the truth on any Linux box.

22. What is the strict aliasing rule's safe escape?

memcpy. memcpy(&f, &i, sizeof f) is well-defined regardless of types and modern compilers reduce it to a single move instruction at -O2. C++20 added std::bit_cast as a more elegant spelling.

23. What is alignment, and what is an unaligned access?

Each type has an alignment requirement — the address must be a multiple of that value. int typically 4, double 8. An unaligned access on x86 is slow but defined; on ARM and other RISC ISAs it can fault. UBSan's -fsanitize=alignment catches these.

24. What is a use-after-free, and how does ASan catch it?

Reading or writing memory after free. ASan poisons freed regions in shadow memory and quarantines them for a while before recycling, so most UAFs hit the poison and are reported with the original allocation and free stacks.

25. Why is reading an uninitialised local UB, not just “some garbage value”?

Because the compiler may assume it has a single value for the duration of an expression and drop redundant reads, but a later read can still observe a different value — it has “wobbly” values. Optimisers exploit the UB assumption, so the consequence isn't just garbage; it's arbitrary control-flow miscompilation.

Build, link & ABI (26–30)

26. What's the difference between declaration and definition?

A declaration introduces a name and type; a definition allocates storage or provides the function body. You can declare many times, define once. extern int x; is a declaration; int x = 0; is a definition.

27. Static vs. shared library — how do they differ?

Static (.a): archive of object files, copied into the executable at link time. Bigger binary, no runtime resolution, immune to library shuffling. Shared (.so): mapped at runtime by the dynamic loader, code shared across processes, picks up library updates automatically — but breaks on ABI mismatch and adds startup cost.

28. What is name mangling and why does C++ need it?

To support overloading, namespaces, and templates, C++ encodes the full signature into the symbol name. nm -C demangles. To call C++ from C, wrap headers in extern "C" { } so symbols are emitted unmangled.

29. What is RPATH, and how does it differ from LD_LIBRARY_PATH?

RPATH is a path embedded in the ELF binary (DT_RPATH/DT_RUNPATH) telling the loader where to look for shared libraries. LD_LIBRARY_PATH is an environment variable that the loader consults too. Search order: LD_LIBRARY_PATH → DT_RUNPATH → /etc/ld.so.cache → default dirs. Use $ORIGIN in RPATH to make the binary relocatable.

30. How do you debug an ELF binary you didn't build — no source, stripped?

Disassemble with objdump -d; inspect the symbol table with nm (often empty); readelf -a for sections, dynamic libraries, RPATH; strings for embedded literals; strace/ltrace to watch syscalls and library calls live; GDB attached can still set address breakpoints. If you have a build-id, debuginfod can pull symbols from the distributor.

Linux process model & I/O (31–38)

31. What happens during fork?

The kernel duplicates the address space (copy-on-write), the file descriptor table, and most attributes; the child gets PID 0 from fork's return, the parent gets the child's PID. Only the calling thread is duplicated — this is why fork in a multithreaded program is a trap unless you immediately exec.

32. What is a zombie process and how do you reap it?

A child that has exited but whose parent hasn't called wait/waitpid. The kernel keeps the exit status until reaped. Reap by calling wait, setting up a SIGCHLD handler, or using signalfd/signal(SIGCHLD, SIG_IGN) on Linux to auto-reap.

33. Why is printf in a signal handler unsafe?

It's not async-signal-safe: it takes locks (stdio flockfile), allocates, and may have been interrupted mid-state. Use write(2) directly with pre-formatted buffers, or set a volatile sig_atomic_t flag and act on it from main. Best of all, use signalfd: signals become readable events.

34. What's the difference between fsync and fdatasync?

fsync persists file data and metadata (size, mtime) before returning. fdatasync persists only the data and the metadata strictly required to read it back. After atomic-replace + rename, you must also fsync the parent directory — the rename entry isn't durable otherwise.

35. How do you do an atomic file replace?

Write to a sibling tempfile in the same directory, fsync it, rename(2) over the target (atomic on the same filesystem), then fsync the directory. Readers see either the old file or the new file, never a partial one.

36. What is O_DIRECT, and when would you use it?

Bypasses the page cache; reads/writes go to the device. Useful for databases that manage their own cache and want determinism, or for benchmarking. Brings strict alignment requirements (block-aligned buffer, offset, length). Most applications want the page cache.

37. What is epoll, and what's the difference between level- and edge-triggered?

epoll is Linux's scalable readiness notification API. Level-triggered (default): keeps notifying while the fd is ready. Edge-triggered (EPOLLET): notifies only on the transition; you must read until EAGAIN on every event, otherwise you'll miss data. Edge-triggered with non-blocking I/O is what scalable servers use.

38. What does SCM_RIGHTS let you do?

Pass open file descriptors between processes through a Unix domain socket via sendmsg/recvmsg with an ancillary message. The receiving process gets a fresh fd in its table, sharing the underlying open-file description. The pattern behind privileged-helper designs.

Threads & concurrency (39–43)

39. What is a data race?

Two or more threads accessing the same memory, at least one writing, with no happens-before relation between them. In C and C++, a data race is undefined behaviour — not a “maybe wrong value”. The fix: mutex, atomic with proper memory order, or eliminate the sharing.

40. Why must condition-variable waits use a predicate loop?

Spurious wakeups, missed signals, and races between signal and wait. The pattern is while (!ready) cv.wait(lock);, never if. The lock must be held while testing the predicate; wait drops it during sleep and re-acquires it before returning.

41. Acquire/release vs. sequentially consistent — what's the trade-off?

Sequentially consistent (memory_order_seq_cst, the default) gives a single global order across all atomic operations — expensive on weak-memory CPUs (ARM, RISC-V). Acquire/release pairs are cheaper and enough for most producer/consumer patterns: a release on the producer happens-before any acquire on the consumer that observes its value. Use seq_cst until profiling proves you need finer control.

42. What is false sharing?

Two threads writing to different variables that share a cache line. The MESI protocol shuttles the line between cores, destroying performance. Detect with perf c2c; fix by padding/aligning to std::hardware_destructive_interference_size (typically 64 bytes on x86, 128 on ARM big.LITTLE).

43. How does TSan detect races?

It instruments every memory access at compile time and maintains a vector clock per thread. Each location remembers the last access; when a new access has no happens-before to the previous one and at least one is a write, it reports. Costs ~5× CPU and ~10× memory; deterministic enough to find races even when their effect would be invisible.

Perf & debugging (44–50)

44. The program is slow. Where do you start?

In order: (1) time — user vs system vs wall, do they make sense? (2) strace -c — is it stuck in syscalls? (3) perf stat — IPC, branch mispredict, cache misses; (4) perf record -g + flamegraph — where is CPU going? (5) source & data layout. Don't optimise without measuring.

45. What does an IPC of 0.3 tell you?

Most cycles aren't retiring instructions — the CPU is stalled. Look at the breakdown: perf stat -d gives L1/LLC misses, branch mispredicts. Common causes are random-access pointer chasing, giant working sets, or branch-heavy code. IPC above ~2 means the CPU is doing real work.

46. How do you get a useful core dump on a modern systemd box?

ulimit -c unlimited, ensure /proc/sys/kernel/core_pattern routes to systemd-coredump (it does by default), reproduce the crash, then coredumpctl list / coredumpctl debug PID to drop into GDB on the dump. Build with -g and don't strip; the binary must be exactly the one that crashed.

47. What is a watchpoint and when is it gold?

A watchpoint breaks when a memory address is read or written. GDB uses hardware debug registers (DR0–DR3 on x86, four total) when available; software watchpoints are 1000× slower. Gold for “who is corrupting this field?”: set the watchpoint after the value goes wrong, restart, and catch the writer in the act.

48. ASan reported a heap-buffer-overflow with an allocation stack 8 frames deep. How do you read it?

Top of the report: type of error, address, size, access. Then three stacks: where the bad access happened, where the buffer was allocated, and (for UAF) where it was freed. Map the access frame to your source first; usually it's an off-by-one in a loop bound or strncpy-style mistake. Build with -fno-omit-frame-pointer -g for crisp stacks.

49. Your program is being killed but you see no error message. Why?

Usually the OOM killer. Check dmesg | grep -i oom or journalctl -k | grep -i kill. Other suspects: parent sending SIGKILL, exceeded ulimit (ulimit -a), cgroup memory limit, supervisor-imposed timeout. Exit code 137 (128 + 9) is the giveaway for SIGKILL; 139 (128 + 11) is segfault.

50. You've fixed the bug. How do you make sure it never comes back?

(1) Add a regression test that reliably reproduces it pre-fix. (2) Run it in CI under sanitizers (-fsanitize=address,undefined and a separate TSan build for threading code). (3) If it was a build/link issue, pin the toolchain or add the offending flag to the warning set as -Werror. (4) Write a one-paragraph post-mortem in the commit body so the next person to touch the area knows the history. The bug you don't write a test for is the bug you'll ship again.

If you only remember three things from this chapter:
  1. Always pair an answer with the model behind it — “why” over “what”.
  2. UB is not “wrong value” — it's permission for the compiler to miscompile your code arbitrarily.
  3. The shortest path from broken to fixed: reproduce, sanitise, instrument, hypothesise, verify.

Recap

  • C/C++ traps: array vs. pointer, signed/unsigned mixing, strict aliasing, lifetime, alignment.
  • C++ rules: RAII first, ownership second; rule of five; noexcept moves; iterator invalidation.
  • Linux model: fork-exec-wait, signals are async-signal-unsafe, atomic file replace = tmp + fsync + rename + dir fsync.
  • Concurrency: data races are UB, predicate loops on condvars, acquire/release before seq_cst, false sharing kills throughput.
  • Debugging: time → strace → perf stat → perf record → flamegraph; sanitizers in CI; coredumpctl for postmortem; watchpoints for “who corrupted this”.
