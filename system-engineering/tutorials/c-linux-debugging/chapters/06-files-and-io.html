Chapter 06 Files & I/O

open/read/write are the two-screen API that powers everything from cat to a database engine. This chapter covers the syscalls, mmap, atomic file replacement, fsync vs fdatasync, buffered vs direct I/O, the /proc//sys pseudo-filesystems, and the patterns for "I want to write this config without ever leaving a half-written file on disk".

open / read / write / close — the basics

#include <fcntl.h>
#include <unistd.h>
#include <errno.h>
#include <stdio.h>
#include <string.h>

int main(void) {
    int fd = open("/tmp/data", O_RDONLY | O_CLOEXEC);
    if (fd < 0) { perror("open"); return 1; }

    char buf[4096];
    for (;;) {
        ssize_t n = read(fd, buf, sizeof buf);
        if (n > 0) {
            /* process buf[0 .. n) */
        } else if (n == 0) {
            break;             /* EOF */
        } else if (errno == EINTR) {
            continue;          /* signal — retry */
        } else {
            perror("read");
            close(fd);
            return 1;
        }
    }
    close(fd);
    return 0;
}

Things to make second-nature:

  • read may return less than requested. Always loop. The "short read" is normal — pipes, sockets, slow disks all do it.
  • EINTR: a signal interrupted the syscall. Retry. SA_RESTART on the signal handler avoids most of this.
  • Always check the return value; (void) write(fd, ...); is a "you got what you deserved" anti-pattern.
  • Always close. But check the return — close can fail (NFS, network filesystems delay errors).

open() flags worth memorising

FlagEffect
O_RDONLY / O_WRONLY / O_RDWRAccess mode (mandatory; one of these three)
O_CREAT Create if missing; with this, mode arg required (0644, etc.)
O_EXCL With O_CREAT: fail if file exists (atomic create-or-fail)
O_TRUNC Truncate to zero on open
O_APPEND Every write seeks to end first — atomic append on Linux for < PIPE_BUF
O_CLOEXEC Close on exec; default-on by habit, save yourself audit reviews
O_NONBLOCK Non-blocking I/O; reads return -1 with EAGAIN when no data
O_DIRECT Bypass page cache; alignment requirements; databases only
O_SYNC / O_DSYNCEach write flushes to disk before returning — slow, sometimes essential
O_PATH Open without read/write access — only for fstatat, openat, fchdir
O_TMPFILE Create unnamed file; useful for "write then linkat into place"

Position, lseek, pread/pwrite

Each open file description has a position. read/write advance it; lseek moves it.

off_t pos = lseek(fd, 0, SEEK_END);   /* find file size */
lseek(fd, 0, SEEK_SET);                /* back to start */

/* Better — pread/pwrite take an offset, don't change the position */
char buf[8];
pread(fd, buf, sizeof buf, 100);       /* read 8 bytes at offset 100 */
pwrite(fd, "hi", 2, 200);

pread/pwrite are the right primitive for multi-threaded access to one fd — no race on the position. They're also lighter than seek+read.

Atomic file replacement — the safe-write idiom

The naive "open file, truncate, write" approach corrupts the file if the process dies mid-write. The Unix atomic-replace pattern:

  1. Write the new content to file.tmp in the same directory.
  2. Optionally fsync the temp file.
  3. rename(tmp, file) — POSIX guarantees this is atomic.
int write_atomic(const char *path, const void *data, size_t len) {
    char tmp[PATH_MAX];
    snprintf(tmp, sizeof tmp, "%s.tmp.%ld", path, (long)getpid());

    int fd = open(tmp, O_WRONLY | O_CREAT | O_TRUNC | O_CLOEXEC, 0644);
    if (fd < 0) return -1;

    const char *p = data;
    size_t left = len;
    while (left) {
        ssize_t n = write(fd, p, left);
        if (n < 0) {
            if (errno == EINTR) continue;
            close(fd); unlink(tmp); return -1;
        }
        p += n; left -= n;
    }
    if (fsync(fd) < 0) { close(fd); unlink(tmp); return -1; }
    if (close(fd)  < 0) {           unlink(tmp); return -1; }
    if (rename(tmp, path) < 0)    { unlink(tmp); return -1; }

    /* Optionally fsync the directory so the rename hits disk */
    int dfd = open(dirname_of(path), O_RDONLY | O_DIRECTORY | O_CLOEXEC);
    if (dfd >= 0) { fsync(dfd); close(dfd); }
    return 0;
}

The fsync of the parent directory is what makes this survive a power cut: without it, the rename may live only in the directory's page cache.

fsync vs fdatasync vs sync

CallFlushesWhen
fsync(fd) Data + metadata of one file to disk Need full durability
fdatasync(fd) Data + only metadata that affects readers Faster; database log writes
sync() Schedules write of all dirty pages; doesn't waitAlmost never want; very coarse
syncfs(fd) All buffers for the filesystem fd lives on; waits"Flush this disk"

The price of fsync is a millisecond on SSD, several on HDD — non-negligible. Database engines sweat over it. For most applications, fsync the file, fsync the dir, sleep well.

mmap — files as memory

mmap maps a file (or anonymous memory) into the address space. After the call, accessing the address is reading/writing the file — the kernel pages it in on demand.

#include <sys/mman.h>
#include <sys/stat.h>

int fd = open(path, O_RDONLY | O_CLOEXEC);
struct stat st; fstat(fd, &st);
size_t sz = st.st_size;

void *p = mmap(NULL, sz, PROT_READ, MAP_PRIVATE, fd, 0);
if (p == MAP_FAILED) { perror("mmap"); return 1; }
close(fd);                                /* mapping persists after close */

/* p is now sz bytes of the file. Read freely. */
const char *cp = p;
/* ... */

munmap(p, sz);

When to reach for mmap:

  • Big read-only files where you want random access (parsing).
  • Loading huge data sets without copying.
  • Sharing memory between processes (MAP_SHARED).
  • Anonymous mmap for big allocations (MAP_ANONYMOUS) — what malloc often does for large sizes.

When NOT to reach for mmap:

  • Small files: cost more than they save.
  • Files that change while you read: page faults can fault on truncated pages → SIGBUS.
  • Network filesystems (NFS): semantics get murky.
SIGBUS on truncated mmaps

You mmap a file, another process truncates it. Now your mapped region beyond the new size is unmapped — accessing it sends SIGBUS (not SIGSEGV). Plan for it: handle the signal, don't share files with un-coordinated truncators, or use fallocate to keep them sized.

The page cache and "real" disk reads

Linux aggressively caches everything you read or write through the regular filesystem syscalls. Your second cat bigfile is from RAM. vmstat 1 shows free/cached numbers; free -h too.

To bypass the cache (e.g. benchmarking, databases that manage their own cache):

  • O_DIRECT on open — must align reads to filesystem block size, must use aligned buffers (posix_memalign). Skips page cache.
  • posix_fadvise(fd, 0, 0, POSIX_FADV_DONTNEED) after a read — drop those pages from cache.
  • echo 3 > /proc/sys/vm/drop_caches (root) — drop everything. Useful for benchmarks; never in production.

truncate, fallocate, sparse files

ftruncate(fd, 100);                     /* exactly 100 bytes; pads with zeros */
posix_fallocate(fd, 0, 1024 * 1024);     /* allocate disk blocks for 1 MiB */
fallocate(fd, FALLOC_FL_PUNCH_HOLE | FALLOC_FL_KEEP_SIZE, 0, 4096);
                                          /* punch a hole — file stays same size, blocks freed */

A sparse file is one where some byte ranges have no allocated blocks; reads return zeros. Useful for "logically big, physically small" — like virtual disk images. Sparse-aware tools (cp --sparse=auto, tar --sparse) preserve the holes.

/sys, /dev, and tmpfs

/proc Per-process info, kernel state. /proc/sys/* is sysctl.
/sys Device tree, kernel-driver knobs (/sys/class/net/, /sys/block/).
/dev Device files. /dev/null, /dev/zero, /dev/random, /dev/sda, /dev/ttyS0.
tmpfs RAM-backed filesystem. Mounted at /run, /tmp (often), /dev/shm.

Reading /sys files is how you get sensor temperatures, network statistics, MTU values, link speeds, USB device info — all without an API. Writing to them is how you change kernel module params at runtime.

$ cat /sys/class/net/eth0/mtu                        # 1500
$ cat /sys/class/thermal/thermal_zone0/temp          # 45000  (millidegrees)
$ echo 9000 > /sys/class/net/eth0/mtu                # set jumbo frames

Buffered I/O via stdio

#include <stdio.h>

FILE *f = fopen("data.csv", "r");
if (!f) { perror("fopen"); return 1; }

char line[1024];
while (fgets(line, sizeof line, f)) {
    /* line includes trailing \n */
}
fclose(f);

FILE* is libc's wrapper over an fd, with a buffer. Buffering modes:

Line-bufferedDefault for terminals (stdout). Flushes on \n or buffer-full.
Fully bufferedDefault for files / pipes. Flushes on buffer-full or fclose.
UnbufferedDefault for stderr. Each write hits the kernel.

Override with setvbuf(stream, NULL, _IOLBF, 0). The classic gotcha: printf output disappears on a crash because the buffer was never flushed. fflush(stdout) at strategic points, or setvbuf(stdout, NULL, _IONBF, 0) for crash-friendly logs.

Big files and large-file support

On 32-bit systems, off_t was 32-bit and you needed _FILE_OFFSET_BITS=64 to access files > 2 GiB. On 64-bit Linux this is automatic; you don't have to think about it. If you maintain code that targets 32-bit embedded Linux, define _FILE_OFFSET_BITS=64 in your build flags.

Hands-on: a safe config writer

Hands-on · write the safe-write pattern from scratch

Write a function that writes data to path atomically: no half-written file ever exists. Tests:

  1. Run twice; cat path shows the second run's content.
  2. Kill the process mid-write (sleep before fsync); cat path still shows the previous content.
  3. Run on a freshly-formatted ext4 filesystem; everything still consistent after echo b > /proc/sysrq-trigger reboot.

Exercises

EX 6.1 easy Short reads

Why is this wrong?

char buf[1024];
read(fd, buf, sizeof buf);
process(buf);
Show solution
  1. Return value not checked — error or EOF would be silently ignored.
  2. If read returned less than 1024, you process garbage past the actual data.
  3. EINTR not handled.
ssize_t total = 0;
while (total < sizeof buf) {
    ssize_t n = read(fd, buf + total, sizeof buf - total);
    if (n == 0) break;             /* EOF */
    if (n < 0) {
        if (errno == EINTR) continue;
        return -1;
    }
    total += n;
}
process(buf, total);
EX 6.2 medium Why fsync the parent directory?
Show solution

The directory entry is metadata. rename updates the directory: removes the old entry, adds the new one. Until the directory is fsynced, that change may live only in the page cache. Power loss before flush → after reboot, the file could be the old content (or even gone, if both old and new entries weren't both committed).

The fsync ensures the directory metadata is on stable storage. Most filesystems also order things sensibly via journaling, but fsyncing the dir is the only portable guarantee.

EX 6.3 medium mmap or read?

You're parsing 50 GB of structured data, mostly random-access. You can't fit it in RAM. Which API and why?

Show solution

mmap with MAP_PRIVATE + PROT_READ. The kernel pages in only the parts you touch; LRU evicts what you don't. You get pointer arithmetic over the file as if it were memory. read/pread would also work but you'd be re-implementing what the page cache already does.

Add posix_madvise with MADV_RANDOM to hint the kernel about access pattern. For sequential scans, MADV_SEQUENTIAL hints aggressive readahead.

EX 6.4 hard Concurrent writers

Two processes append to the same log file. Some lines come out interleaved (mid-line). Why, and what's the fix?

Show solution

Without coordination, two processes' writes interleave at any byte boundary. The fix is O_APPEND: each write seeks-to-end-and-writes atomically as one syscall, for sizes ≤ PIPE_BUF (4 KiB on Linux). For ≤ 4 KiB lines on the same filesystem, this is enough.

For larger lines, or if you need ordering guarantees: take an advisory lock with flock or fcntl(F_OFD_SETLK), or write through a single multiplexer process (syslog, journald).

EX 6.5 hard Find a leak with /proc/PID/fd

Your daemon's RSS keeps growing. ls /proc/$(pidof mydaemon)/fd | wc -l climbs from 50 to thousands over a week. What's leaking, and how do you find which open are leaking?

Show solution
  1. ls -l /proc/$PID/fd shows where each fd points — files, sockets, pipes, anon-inodes. Group by destination: the fastest-growing is the leak.
  2. Compile the daemon with -finstrument-functions or use eBPF: bpftrace -e 'tracepoint:syscalls:sys_enter_openat { @[ustack] = count(); }' aggregates open call sites; the top contributor is your culprit.
  3. Or attach with gdb and break on open/socket; check stacks at moments when the count surges.
  4. Likeliest fix: missing close on an error path, or storing fds in a structure whose owner doesn't release on drop.

Recap

  • open/read/write are the universal API. Loop on short reads; handle EINTR; check every return.
  • Atomic file replacement: write to tmp in same dir, fsync, rename, fsync the dir.
  • fsync = data + metadata, fdatasync = data + only readable-affecting metadata. Don't reach for sync().
  • mmap for random access into big files; beware SIGBUS on truncate, NFS quirks, and the cost on tiny files.
  • O_DIRECT skips the page cache and has alignment requirements; use only when your code is the cache.
  • /proc and /sys are filesystems-as-API; great for debugging and for talking to drivers.
  • stdio buffering bites: flush before crashes, or unbuffer logs.
