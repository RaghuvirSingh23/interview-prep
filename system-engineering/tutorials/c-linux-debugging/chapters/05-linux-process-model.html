Chapter 05 Linux process model

Process creation, file descriptors, signals, pipes, exit semantics, zombies, and the bits of /proc you'll cat at 3 AM. The Linux kernel exposes a small, opinionated API; once you know the verbs everything else clicks.

Syscalls vs libc

"Linux APIs" really means three layers:

  1. The syscall — the kernel entry point. Numbered (e.g. SYS_open = 2); invoked via syscall instruction with arguments in registers. Documented in man 2.
  2. The libc wrapper — a thin C function (open) that prepares args and traps into the kernel. man 2 open documents both.
  3. Higher-level libc — fopen, printf, etc. Built on top. man 3.
$ man 2 open      # syscall
$ man 3 fopen     # higher-level
$ strace ./my_prog 2>&1 | head -30   # see all syscalls a program makes

fork + exec — how programs spawn programs

Linux has no "spawn this program" syscall. Instead it uses two primitives:

  • fork() — clone the current process. The child is a copy of the parent at this point: same memory (copy-on-write), same fds, same everything. fork returns 0 in the child, the child's PID in the parent, -1 on error.
  • execve() (and the exec* family) — replace the current process image with another program. Same PID, same fds, but new code, new memory.
#include <sys/types.h>
#include <sys/wait.h>
#include <unistd.h>
#include <stdio.h>
#include <stdlib.h>

int main(void) {
    pid_t pid = fork();
    if (pid < 0) { perror("fork"); exit(1); }

    if (pid == 0) {
        /* child */
        char *args[] = { "/bin/echo", "hello, from", "child", NULL };
        execv(args[0], args);
        perror("execv");           /* only reached on failure */
        _exit(127);
    }

    /* parent */
    int status;
    waitpid(pid, &status, 0);
    if (WIFEXITED(status))
        printf("child exited %d\n", WEXITSTATUS(status));
    return 0;
}

The mental model: a shell pipeline like ls | grep foo is the shell calling fork twice, setting up a pipe between the children, then exec'ing ls in one and grep in the other.

posix_spawn — when you don't want fork

For "fork + exec without doing anything in between", posix_spawn is more efficient (especially in low-memory or many-threads cases — fork's copy-on-write is cheap but not free). Most of the time, fork+exec is fine.

Exit semantics

exit(int)libc. Runs atexit handlers, flushes stdio, then calls _exit.
_exit(int) / _ExitSkips atexit handlers; doesn't flush. Use after fork in the child if exec fails.
Returning from mainEquivalent to exit(rc).
abort()Raises SIGABRT — uncatchable by default; usually drops a core.

Exit code conventions: 0 = success, non-zero = failure. 2 is conventional for misuse / config error. >= 128 sometimes means "killed by signal N - 128" — but only by some shells.

Zombies and waitpid

When a child exits, the kernel keeps a tiny record (PID, exit status) until the parent calls wait() or waitpid(). Until then the child is a zombie — visible in ps with state Z, no resources except the entry.

If the parent never reaps, zombies pile up. Eventually you can't fork.

Three idioms:

  1. Reap synchronously with waitpid(pid, &status, 0).
  2. Reap asynchronously in a SIGCHLD handler. Loop: while (waitpid(-1, &status, WNOHANG) > 0) { ... }.
  3. "Don't care": signal(SIGCHLD, SIG_IGN) on Linux makes the kernel auto-reap. POSIX-portable: set SA_NOCLDWAIT.
#include <signal.h>
#include <sys/wait.h>

static void on_sigchld(int sig) {
    (void)sig;
    int saved = errno;
    while (waitpid(-1, NULL, WNOHANG) > 0) { /* reap them all */ }
    errno = saved;
}

void install_reaper(void) {
    struct sigaction sa = { .sa_handler = on_sigchld, .sa_flags = SA_NOCLDSTOP | SA_RESTART };
    sigemptyset(&sa.sa_mask);
    sigaction(SIGCHLD, &sa, NULL);
}

Orphans — children whose parent died — are inherited by PID 1 (init / systemd). It always reaps. So orphan zombies don't accumulate.

Handling a signal — the right way

#include <signal.h>

static volatile sig_atomic_t stop_flag = 0;

static void on_term(int sig) {
    (void)sig;
    stop_flag = 1;          /* set a flag; do NOT do real work in handlers */
}

int main(void) {
    struct sigaction sa = { .sa_handler = on_term, .sa_flags = SA_RESTART };
    sigemptyset(&sa.sa_mask);
    sigaction(SIGTERM, &sa, NULL);
    sigaction(SIGINT,  &sa, NULL);

    while (!stop_flag) {
        /* main loop */
    }
    return 0;
}

The rules of signal handlers:

  1. Only call async-signal-safe functions from the handler. printf, malloc, fprintf are NOT safe. write, _exit, signal, kill are.
  2. Use volatile sig_atomic_t for flags read by main code.
  3. Prefer sigaction over signal — signal's semantics differ between BSD and System V; sigaction is unambiguous.
  4. SA_RESTART auto-resumes interruptible syscalls (most read/write); without it, syscalls return -1 with EINTR and you must retry yourself.
printf in a signal handler

It looks like it works. Sometimes. Then under load, your program hangs because the handler interrupted libc inside its stdio lock and the handler tried to grab the same lock — deadlock. Don't.

Sending signals

kill(pid, SIGTERM);             /* one process */
kill(0,   SIGTERM);             /* whole process group */
kill(-1,  SIGTERM);             /* all processes you can signal — careful! */
raise(SIGUSR1);                 /* send to self */
pthread_kill(thr, SIGUSR1);     /* signal a specific thread */

signalfd — signals as file descriptors

The modern Linux way: deliver signals on a file descriptor you read with poll/epoll. No async surprises, no async-signal-safety to worry about.

#include <sys/signalfd.h>
sigset_t mask;
sigemptyset(&mask);
sigaddset(&mask, SIGTERM);
sigaddset(&mask, SIGINT);
sigprocmask(SIG_BLOCK, &mask, NULL);   /* block normal delivery */

int sfd = signalfd(-1, &mask, SFD_CLOEXEC | SFD_NONBLOCK);
/* read structs from sfd in your event loop; no async handlers needed */

File descriptors

A file descriptor is a small non-negative integer the kernel uses as an index into the process's "fd table". Each entry refers to a file description (an open kernel object).

process A's fd table          system-wide open file table
  0  ──────►  open file: /dev/tty (read), pos=0
  1  ──────►  open file: /dev/tty (write), pos=…
  2  ──────►  open file: /dev/tty (write), pos=…
  3  ──────►  open file: /tmp/log (rw),  pos=24
  4  ─┐
  5  ─┴─────► (same open file: dup'd)

Standard fds:

0 — stdinconventionally readable
1 — stdoutconventionally writable; program output
2 — stderrconventionally writable; diagnostics, never buffered like stdout

Operations:

  • open, close, read, write, lseek
  • dup(fd), dup2(old, new) — duplicate; dup2 is how shells redirect
  • fcntl(fd, F_SETFD, FD_CLOEXEC) — close on exec, important for security
  • fcntl(fd, F_SETFL, O_NONBLOCK) — make I/O non-blocking
/* Redirect stdout to a file in this process: */
int fd = open("/tmp/out.log", O_WRONLY | O_CREAT | O_TRUNC, 0644);
dup2(fd, 1);              /* stdout now points to /tmp/out.log */
close(fd);
puts("hello");            /* goes to the file */

O_CLOEXEC and the security angle

By default, fds are inherited across exec. If your daemon opens /etc/secret, then forks and execs /usr/bin/cat /etc/passwd, the child inherits the secret fd. Always pass O_CLOEXEC to open, socket, pipe2, accept4:

int fd = open("/etc/secret", O_RDONLY | O_CLOEXEC);

Pipes

int p[2];
pipe2(p, O_CLOEXEC);              /* p[0] read end, p[1] write end */
pid_t pid = fork();

if (pid == 0) {                   /* child: write to pipe */
    close(p[0]);
    dup2(p[1], STDOUT_FILENO);    /* stdout is now the pipe */
    close(p[1]);
    execlp("ls", "ls", NULL);
    _exit(127);
}
/* parent: read from pipe */
close(p[1]);
char buf[4096];
ssize_t n;
while ((n = read(p[0], buf, sizeof buf)) > 0)
    write(1, buf, n);
close(p[0]);
waitpid(pid, NULL, 0);

This is exactly what the shell does for ls | grep. Two side notes:

  • If you write to a pipe with no readers, you get SIGPIPE; the default kills you. Servers should ignore it: signal(SIGPIPE, SIG_IGN) or use send(... MSG_NOSIGNAL).
  • The read side returning 0 means EOF — all writers closed.

Environment

The environment is a NUL-terminated array of KEY=value strings inherited across exec.

char *home = getenv("HOME");
setenv("MY_VAR", "value", /*overwrite=*/1);
unsetenv("OLD_VAR");

extern char **environ;
for (char **e = environ; *e; e++) puts(*e);

Note: setenv/getenv are not thread-safe in glibc — use them at startup only or guard with a mutex. execvpe/execve let you set the child's env explicitly, which is cleaner.

Hands-on · strace tells the story
$ strace -f -e trace=clone,execve,exit_group -- bash -c 'echo hi | wc -c'

strace: Process 12345 attached
[pid 12345] execve("/usr/bin/echo", ["echo", "hi"], ...) = 0

Read top-down: bash clones, child execs echo, exits. Bash clones again, child execs wc, exits. The pipeline is set up between them via pipe + dup2 calls before execve (filtered out for clarity).

Exercises

EX 5.1 easy Why _exit after exec?

In the fork-exec example, the child calls _exit(127) if exec fails — not exit. Why?

Show solution

exit runs atexit handlers and flushes stdio. The child's stdio buffers are copies of the parent's; flushing them double-prints output the parent already buffered. _exit bypasses both. Always _exit on the post-fork failure path.

EX 5.2 medium Process is stuck — what now?

A long-running daemon hasn't responded to clients for an hour. You can't restart it (it has live state). What's your diagnostic order using only stock Linux tools?

Show solution
  1. ps -p $PID -o stat,wchan — what state and where in the kernel.
  2. cat /proc/$PID/stack (root) — kernel stack to see what it's blocked on.
  3. ls /proc/$PID/fd | wc -l + ls -l /proc/$PID/fd | tail — fd leak?
  4. cat /proc/$PID/status — threads, memory, signals queued.
  5. strace -p $PID -f -tt -T — live syscall trace; stop after a sample.
  6. gdb -p $PID + thread apply all bt — userspace backtrace per thread.
  7. If safe: kill -USR1 $PID to dump state if your daemon supports it.
EX 5.3 medium SIGPIPE in a server

You wrote a TCP server. Your tests work. In production, the server randomly dies after running fine for 30 minutes. dmesg says nothing. What's likely?

Show solution

A client closed its end of the socket; you called write; the kernel sent SIGPIPE; default action is termination. Fix one of:

  • signal(SIGPIPE, SIG_IGN) at startup. write then returns -1 with errno=EPIPE.
  • Use send(fd, buf, n, MSG_NOSIGNAL) instead of write.
  • Set SO_NOSIGPIPE per-socket on BSD/macOS.

Verify by enabling core dumps (ulimit -c unlimited) and reproducing — you'd see SIGPIPE in the core's signal info.

EX 5.4 hard Child zombie hunt

A daemon spawns 1 helper per minute. After a day, ps shows hundreds of <defunct> processes with the daemon as parent. What's wrong, and what are two fixes?

Show solution

Daemon isn't reaping. Two fixes:

  1. Install a SIGCHLD handler that loops waitpid(-1, NULL, WNOHANG).
  2. If the daemon doesn't care about exit status: signal(SIGCHLD, SIG_IGN); on Linux this makes the kernel auto-reap. POSIX-portable equivalent: sigaction with sa_flags=SA_NOCLDWAIT.

Bonus fix: spawn helpers via fork() + fork() + exit() double-fork pattern, so the helper is reparented to init, which always reaps. Used by nohup and old daemons.

EX 5.5 hard FD leak across exec

Your service opens /etc/db_password at startup, then fork+execs a child to run a customer-supplied script. The customer can read the password from the script. How? Fix?

Show solution

FDs are inherited across exec by default. Inside the script, cat /proc/self/fd/N for each open fd reads the file the parent opened — including the password file.

Fixes (use all three for defence in depth):

  1. Open with O_CLOEXEC: open(path, O_RDONLY | O_CLOEXEC).
  2. Or after open, fcntl(fd, F_SETFD, FD_CLOEXEC).
  3. Or in the child between fork and exec, manually close fds > 2: for (int i = 3; i < sysconf(_SC_OPEN_MAX); i++) close(i);. Better with Linux 5.9's close_range(3, ~0u, 0).

The O_CLOEXEC default-by-construction is the safe one — the audit trail in code review is "this is a hot path; should it be CLOEXEC?" not "did we remember to fcntl?".

Recap

  • fork+exec is the universal "spawn" idiom; the child inherits memory (CoW) and fds.
  • Always reap children — synchronously, via SIGCHLD handler, or by ignoring SIGCHLD on Linux.
  • Signals: use sigaction, set a flag, do work in main loop. Handlers must be async-signal-safe.
  • FDs inherited across exec by default — use O_CLOEXEC on every open/socket/pipe2/accept4.
  • /proc/[pid]/{fd,maps,stack,status} are your "what is this process doing" toolkit.
  • Ignore SIGPIPE in network servers, or use MSG_NOSIGNAL.
