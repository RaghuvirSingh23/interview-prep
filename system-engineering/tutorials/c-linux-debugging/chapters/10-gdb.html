Chapter 10 GDB — deep dive

Most engineers know enough GDB to type bt after a segfault. The other 80% of GDB is what turns a five-hour debug into a fifteen-minute one. Breakpoints with conditions and commands, watchpoints, reverse execution, core dumps, multi-thread, scripting, TUI, remote serial. This chapter covers all of it.

Starting GDB

$ gdb ./prog                                 # interactive
$ gdb --args ./prog --flag arg1 arg2          # with args
$ gdb -p 1234                                 # attach to running PID
$ gdb ./prog core                             # post-mortem on a core dump
$ gdb -ex 'break main' -ex 'run' ./prog       # one-line script

$ gdbserver :1234 ./prog                      # remote server
(on dev machine) $ gdb ./prog
(gdb) target remote 192.168.1.10:1234

Compile with -g (or -g3 for macros). Don't strip the binary — or keep an unstripped copy. -O0 gives the most accurate stepping; -Og is "optimised, but debug-friendly"; -O2 with -g works but variables get optimised away ("<optimized out>") and stepping jumps around.

Breakpoints — and what they really are

(gdb) b main                                  # function name
(gdb) b file.c:42                             # file:line
(gdb) b foo.cpp:100 if x > 0                  # conditional
(gdb) b malloc                                 # libc function
(gdb) b 'MyClass::method'                      # C++ — quote name with ::
(gdb) rb ^my_                                  # regex breakpoint — every fn starting with my_

(gdb) info b                                   # list breakpoints
(gdb) disable 3                                # turn off breakpoint #3
(gdb) enable 3
(gdb) delete 3                                 # remove
(gdb) clear file.c:42                          # remove by location
(gdb) tbreak main                              # one-shot
(gdb) ignore 3 100                             # ignore next 100 hits

Under the hood: GDB writes 0xCC (int3) at the breakpoint address; CPU traps; GDB intercepts. That's why breakpoints don't work on read-only code without set write on or PIE rewrite — and why hardware watchpoints are limited (DR0–DR3, four max on x86).

Conditional and counting breakpoints

(gdb) b parser.c:120 if strcmp(name, "buggy") == 0
(gdb) b alloc.c:50 if size > 1024 * 1024
(gdb) condition 5 retries > 3                  # add condition to existing bp #5

Commands attached to breakpoints — the secret weapon

(gdb) b alloc
(gdb) commands
> silent
> printf "alloc(%d) from %p\n", size, $rip
> bt 5
> continue
> end

Now every alloc call prints its size and a 5-frame stack, then continues. Effective tracing without recompiling. Combine with set logging on to dump to a file.

Watchpoints — when memory changes

(gdb) watch  variable                         # break when written
(gdb) rwatch variable                          # break when read
(gdb) awatch variable                          # break on either
(gdb) watch *(int *)0x7ffdc...                # arbitrary address
(gdb) watch -l obj->field                     # watch the location, not the expression

Hardware watchpoints (the fast kind) are limited to 4 on x86. Above that, GDB falls back to software watchpoints which step every instruction — 100× slower. Use scope: watch x only works while x is in scope; once the function returns, the watchpoint disables.

The classic use: "this struct field gets corrupted somehow; find the writer." A watchpoint catches the moment of corruption with the offender's stack trace.

Multi-threaded debugging

(gdb) info threads                            # list all threads
  Id   Target Id           Frame
* 1    Thread 0x7f...      main () at main.c:32
  2    Thread 0x7f...      sem_wait () from libc
  3    Thread 0x7f...      epoll_wait () from libc

(gdb) thread 2                                # switch to thread 2
(gdb) thread apply all bt                     # backtrace of every thread
(gdb) thread apply all bt full                # ditto + locals
(gdb) thread apply 2 3 bt                     # specific threads

(gdb) set scheduler-locking on                # only the current thread runs while stepping
(gdb) set scheduler-locking step              # default; step current, others run on continue

"thread apply all bt" is what you type when you attach to a hung process. It's three keystrokes shorter than typing it for real and you'll do it constantly. Save it as a defined command in ~/.gdbinit.

Core dumps — debugging the dead

A core dump is a snapshot of process memory at the moment of crash. Enable them, then debug post-mortem:

$ ulimit -c unlimited                          # this shell
$ echo "/tmp/core.%e.%p" | sudo tee /proc/sys/kernel/core_pattern  # location pattern

# After a crash:
$ ls /tmp/core.*
core.prog.12345
$ gdb ./prog /tmp/core.prog.12345
(gdb) bt
(gdb) info threads
(gdb) thread apply all bt

On modern systemd systems, cores are captured by systemd-coredump and accessed via coredumpctl:

$ coredumpctl list
TIME                            PID  UID  SIG     EXE
Mon 2026-04-27 10:00:00 UTC    1234 1000 SIGSEGV /usr/bin/prog
$ coredumpctl debug 1234                       # opens GDB on the core

Tip: include the source file (directory /path/to/src in GDB) and unstripped binary. For very minimal cores, build with -g and keep an unstripped copy alongside the stripped production binary.

Catching signals and faults

(gdb) catch syscall openat                    # break on a specific syscall
(gdb) catch throw                              # C++: break when an exception is thrown
(gdb) catch catch                              # C++: when caught
(gdb) catch signal SIGSEGV                     # break before the default handler runs
(gdb) handle SIGPIPE nostop print              # don't break on SIGPIPE; just print
(gdb) info signals                             # current dispositions

catch throw is the C++ exception detective. Set it before reproducing the bug; GDB stops at every throw, even ones that are caught. bt tells you where, which makes "where does this exception come from" trivial.

Reverse execution — the time machine

(gdb) target record-full                      # start recording
(gdb) c                                       # run; eventually crashes
(gdb) reverse-step                            # step backwards
(gdb) reverse-next
(gdb) reverse-continue                         # run backwards until prev breakpoint

GDB's built-in record-replay works on small programs but is slow. The serious tool: rr. It records execution to a deterministic trace, then GDB replays — every run is bit-identical, you can step backwards across thousands of instructions cheaply.

$ rr record ./prog
$ rr replay
(gdb) c
Program received signal SIGSEGV
(gdb) reverse-stepi
...

For heisenbugs that take a while to reproduce, recording once and replaying many times is genuinely revolutionary.

TUI — text user interface

(gdb) tui enable                              # or start with `gdb -tui`
# Or toggle: Ctrl-X A
# layout: src + reg + asm; switch with `layout regs` etc.

TUI shows source, registers, and current instruction in panes. Useful for stepping through tight code; less great for big projects (use a real editor + gdb-dashboard or VS Code's GDB integration).

GDB Python — when commands aren't enough

GDB embeds Python. You can write commands, pretty-printers, and full inspection scripts.

python~/.gdbinit.d/dump_list.py
import gdb

class DumpList(gdb.Command):
    """Dump a linked list. Usage: dump_list HEAD FIELD"""
    def __init__(self):
        super().__init__("dump_list", gdb.COMMAND_USER)

    def invoke(self, arg, from_tty):
        head_expr, field = arg.split()
        node = gdb.parse_and_eval(head_expr)
        i = 0
        while node and i < 100:
            print(f"  [{i}] {node.dereference()}")
            node = node[field]
            i += 1

DumpList()

Source from .gdbinit: source ~/.gdbinit.d/dump_list.py. Now dump_list head next walks a linked list. Project-specific scripts that print your data structures readably are 10× more useful than p *struct.

Pretty printers

STL containers are unreadable in raw form. GDB ships pretty-printers (libstdc++'s) that show std::vector as {1, 2, 3} not as {_M_start = ..., _M_finish = ...}. They're usually auto-loaded; if not, source libstdc++-v3-printers.py from your GCC install.

~/.gdbinit — make GDB yours

# History

Backtrace with locals
end

Worth setting once. Many engineers dot-file their .gdbinit; check Brendan Gregg's gdb-dashboard for a Python-based replacement of TUI.

Remote debugging

The pattern: gdbserver runs on the target, GDB on the developer machine.

# On target (e.g. embedded board):
$ gdbserver :2345 ./prog arg1 arg2
Listening on port 2345

# On developer:
$ gdb ./prog
(gdb) set sysroot /path/to/target/sysroot     # so libs match
(gdb) target remote target.local:2345
(gdb) b main
(gdb) c

For embedded with no Linux on target — bare-metal, RTOS, kernel debugging — gdb talks the GDB Remote Serial Protocol to JTAG probes (OpenOCD, J-Link, ST-Link). Same GDB, different transport. Cover this in chapter 12.

C++ specific tips

  • Inline functions: stepping into std::vector::push_back takes you somewhere weird. step flashes through templates; use next or finish. set print frame-arguments none to hide noisy template args in stacks.
  • Mangled names: when GDB shows _ZN3foo3barEi, demangle in your head or run c++filt _ZN3foo3barEi. GDB usually demangles automatically with set print demangle on (the default).
  • RTTI: info vtbl variable shows the vtable for a polymorphic object. p typeid(*ptr).name() at the prompt gets the runtime type.
  • Lambdas show up as functor types with auto-generated names. Step through with next until you're back in your code.

Hands-on: the watchpoint trick

Hands-on · catch a corrupting writer
#include <stdio.h>
#include <string.h>

struct {
    int  magic;
    char buffer[16];
    int  count;
} state = { .magic = 0xCAFE };

void hello(const char *msg) {
    strcpy(state.buffer, msg);   // possibly overflows
}

int main(void) {
    hello("hi");                              // ok
    hello("hello world from beyond");          // overflows; corrupts state.count
    if (state.magic != 0xCAFE) puts("magic corrupted!");
    return 0;
}

$ cc -g -O0 corrupt.c -o corrupt
$ gdb ./corrupt
(gdb) start
(gdb) watch state.magic
Hardware watchpoint 2: state.magic
(gdb) c
Hardware watchpoint 2: state.magic
Old value = 51966   (0xcafe)
New value = 1819043176
0x0000... in hello (msg=0x... "hello world from beyond") at corrupt.c:11
11        strcpy(state.buffer, msg);
(gdb) bt

The watchpoint caught the exact instruction that overwrote magic, with the stack pointing at the bad strcpy. Five minutes of GDB beats hours of printf-based hunting.

Exercises

EX 10.1 easy Conditional breakpoint

You loop over 1 million records and exactly one triggers a bug. The records have a id field. Set a breakpoint that fires only when id == 137 at the function process.

Show solution 
(gdb) break process if rec->id == 137

Add commands too if you want it to print and continue without stopping:

(gdb) break process if rec->id == 137
(gdb) commands
> silent
> printf "hit at id=%d state=%d\n", rec->id, rec->state
> bt 3
> continue
> end
EX 10.2 medium Deadlock diagnostic

You attach to a hung process. Show the GDB commands to identify the lock cycle.

Show solution 
$ gdb -p $(pidof prog)
(gdb) info threads
(gdb) thread apply all bt

Look for threads stopped in __lll_lock_wait / pthread_mutex_lock / __cond_wait_common. The argument to the lock call (visible with frame N; info args) tells you which mutex; cross-reference threads to find the cycle (A waiting on M2, holding M1; B waiting on M1, holding M2).

For glibc's mutexes the owner field is at a known offset; p mutex.__data.__owner gives the TID holding it.

EX 10.3 medium Catch exception origin

A C++ program prints terminate called after throwing an instance of 'std::runtime_error' and dies. The catch is somewhere; the throw's location isn't logged. Find the throw.

Show solution 
(gdb) catch throw
(gdb) run
Catchpoint 1 (exception thrown), 0x... in __cxa_throw ()
(gdb) bt
#0  __cxa_throw ()
#1  parse_input(...) at parse.cpp:42
#2  ...

The throw happened on parse.cpp:42. catch throw is universal for "where does this exception come from" — works even if the exception is caught and rethrown.

EX 10.4 hard Core dump from production

A production crash drops a core; the binary is stripped. You have the unstripped binary on the build server. How do you debug?

Show solution 
# Either: copy the unstripped binary to the dev machine alongside the stripped one,
# and tell GDB about the symbols separately.
$ gdb ./prog.stripped /tmp/core
(gdb) symbol-file ./prog.unstripped

# Or use a build-id symlink:
$ readelf -n ./prog.unstripped | grep 'Build ID'
Build ID: deadbeef...
$ mkdir -p ~/.cache/debuginfod/de
$ cp prog.unstripped ~/.cache/debuginfod/de/adbeef....debug

# Or with separate debug info (.gnu_debuglink):
$ objcopy --only-keep-debug prog prog.debug
$ strip --strip-debug prog
$ objcopy --add-gnu-debuglink=prog.debug prog
# GDB now finds prog.debug automatically when loading prog.

Many distros ship debuginfod servers — set debuginfod enabled on in GDB and it fetches debug info on demand from the build's symbol server.

EX 10.5 hard Custom GDB command

Write a GDB Python command tids that prints a table of thread_id, function_name, file:line for every thread. Useful as a one-shot snapshot.

Show solution
python~/.gdbinit.d/tids.py
import gdb

class Tids(gdb.Command):
    """Print one-line summary of every thread."""
    def __init__(self):
        super().__init__("tids", gdb.COMMAND_USER)

    def invoke(self, arg, from_tty):
        inf = gdb.selected_inferior()
        cur = gdb.selected_thread()
        for t in inf.threads():
            t.switch()
            f = gdb.newest_frame()
            sal = f.find_sal()
            print(f"  T{t.num:2d} ptid={t.ptid[1]:<8} {f.name() or '??':<40} "
                  f"{(sal.symtab.filename if sal.symtab else '?')}:{sal.line}")
        cur.switch()

Tids()

(gdb) source ~/.gdbinit.d/tids.py
(gdb) tids
  T 1 ptid=12345    main                                     main.c:32
  T 2 ptid=12346    sem_wait                                  sem_waitcommon.c:45
  T 3 ptid=12347    epoll_wait                                epoll_wait.c:30

Recap

  • Compile with -g (or -Og); core dumps are gold — enable them with ulimit -c unlimited.
  • Conditional breakpoints with commands blocks let you trace without modifying source.
  • Watchpoints catch the writer that corrupts a value.
  • thread apply all bt is your hung-process pocket knife.
  • catch throw for C++ exception origins; catch syscall for kernel-boundary observation.
  • rr for time-travel debugging on hard heisenbugs.
  • GDB Python for project-specific data structure inspection — write the commands once, save lifetime hours.
  • Customise ~/.gdbinit; consider gdb-dashboard for a modern UI.
