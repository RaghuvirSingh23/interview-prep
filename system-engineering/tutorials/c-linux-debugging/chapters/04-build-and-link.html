Chapter 04 Build & link — preprocessor, ELF, symbols, libs

The mysterious "undefined reference to foo" message becomes a five-second fix once you know what's happening between source and binary. This chapter walks the pipeline: preprocessor → translation unit → object file → executable, then the ELF, symbols, and the difference between static and dynamic linkage.

The pipeline, drawn

     foo.c                          libstuff.a / libstuff.so
       │                                       │
   ┌───┴────┐                               (search)
   │ cpp    │  preprocessor                     │
   │ #incl. │                                   │
   └───┬────┘                                   │
       │ foo.i  (preprocessed source)           │
   ┌───┴────┐                                   │
   │ cc1    │  C compiler                       │
   └───┬────┘                                   │
       │ foo.s  (assembly)                      │
   ┌───┴────┐                                   │
   │ as     │  assembler                        │
   └───┬────┘                                   │
       │ foo.o  (object: code + relocations + symbols)
       └───────────────────┐
                           ▼
                       ┌───────┐
                       │  ld   │   linker
                       └───┬───┘
                           ▼
                        a.out  (ELF executable)
                           │
                           ▼ at runtime
                       ld-linux.so   dynamic loader
                           │
                           ▼
                       running process

The driver — cc, gcc, clang — is just a front-end that runs each tool in sequence. You can do each step by hand:

$ cc -E foo.c -o foo.i        # preprocess
$ cc -S foo.i -o foo.s        # compile to assembly
$ cc -c foo.s -o foo.o        # assemble
$ cc foo.o   -o foo           # link

# common shorthand: compile + link in one
$ cc foo.c   -o foo

# split compile/link explicitly:
$ cc -c foo.c bar.c           # makes foo.o, bar.o
$ cc foo.o bar.o -o app

The preprocessor — text in, text out

cpp is a textual replacement engine. Before the compiler ever sees your code, the preprocessor:

  • Inlines #include directives.
  • Expands macros (#define).
  • Evaluates #if / #ifdef.
  • Strips comments.
  • Adds #line directives so error messages point at the original source.
#define MAX(a, b) ((a) > (b) ? (a) : (b))         /* careful! evaluates twice */
#define ARR_LEN(a) (sizeof(a) / sizeof((a)[0]))
#define UNUSED(x) ((void)(x))                       /* silence unused-warning */

#ifdef DEBUG
#  define LOG(fmt, ...) fprintf(stderr, fmt "\n", ##__VA_ARGS__)
#else
#  define LOG(fmt, ...) ((void)0)
#endif

Macro hygiene rules:

  1. Parenthesise every argument and the whole expansion. Otherwise MAX(a, b+1) bites.
  2. Avoid macros with side-effecting arguments — they may evaluate twice or zero times.
  3. Prefer static inline functions, constexpr, or templates over macros where possible.
  4. Use UPPER_SNAKE_CASE for macros so readers can spot them.

#include — quote vs angle brackets

#include "foo.h"Project-relative search first, then system paths.
#include <stdio.h>System paths only (-I dirs and stdlib).

You add search dirs with -I/path; -iquote/path for quote-only; -isystem/path for "system" inclusion (suppresses warnings inside, like stdlib headers).

Header guards / #pragma once

A header may be included many times in one TU (transitively). Without protection, you get redefinition errors.

/* Classic guard — portable */
#ifndef MYAPP_FOO_H
#define MYAPP_FOO_H

void foo(void);

#endif /* MYAPP_FOO_H */


/* Modern alternative — supported by every real compiler */
#pragma once

void foo(void);

#pragma once is technically non-standard but works on GCC, Clang, MSVC, every BSD, every embedded compiler you'll meet. Use it; if your codebase already uses guards, match the style.

Declarations vs definitions

The single most-confused bit of C/C++ linkage:

  • A declaration introduces a name — "this name exists, here's its type". You can have many.
  • A definition provides storage or a body — "this name lives here, here it is". You can have one (per linkage scope).
extern int counter;       /* declaration — counter exists somewhere */
int counter;              /* definition — gives it storage */
int counter = 42;         /* also a definition, with init */

int  add(int a, int b);   /* declaration */
int  add(int a, int b)    /* definition */
{ return a + b; }

Headers should contain declarations; .c/.cpp files contain definitions. The exception: static inline / inline / constexpr / templates may live in headers because the compiler needs the body in every TU that uses them.

Linkage

Every name has a linkage that says how it can be referenced from other translation units:

LinkageMeaningHow to write
ExternalVisible from other TUs by symbol namePlain int x; at file scope; non-static functions
InternalPrivate to this TUstatic int x; at file scope; static on a function
NoneNot a linker concept (locals, function params)Anything inside a function

In C++, anonymous namespaces give internal linkage too:

namespace {                   // anonymous: internal linkage
    int helper_count = 0;
    void helper() { ++helper_count; }
}

The One Definition Rule

The compiler emits a body for every function and gives storage to every variable. The linker then deduplicates. The rule is:

  • An external-linkage symbol must be defined exactly once across the program.
  • An internal-linkage or inline symbol may have multiple definitions, but they must be identical token-for-token (otherwise UB).

Why so strict? Because the linker picks one and discards the others — if they differ, you've changed behaviour silently.

Object files (.o)

An object file is a partial binary: machine code plus tables that say "here are the symbols I define, here are the ones I need, here's where to patch addresses once you've placed me in memory".

$ cc -c foo.c -o foo.o
$ file foo.o
foo.o: ELF 64-bit LSB relocatable, x86-64

$ nm foo.o
0000000000000000 T foo                # defined: T = text section, big endian by convention
                 U printf             # undefined: needed from elsewhere
0000000000000000 R msg                # defined: R = rodata

nm's second column is the symbol type. Common letters:

T / tCode in .text; uppercase = external linkage
D / dInitialised data in .data
B / bUninitialised data in .bss
R / rRead-only data in .rodata
UUndefined — must be supplied by another object
W / wWeak — provided, but overridable

ELF — what's in a binary

$ readelf -h ./hello | head
ELF Header:
  Magic:   7f 45 4c 46 02 01 01 ...    # \x7f E L F
  Class:                             ELF64
  Type:                              DYN (Position-Independent Executable file)
  Machine:                           Advanced Micro Devices X86-64
  Entry point address:               0x...

$ readelf -d ./hello                  # dynamic section
0x0000000000000001 (NEEDED) Shared library: [libc.so.6]
0x000000000000001d (RUNPATH) ...

$ readelf -S ./hello                  # all sections
[ 1] .text          PROGBITS  ...
[ 2] .rodata        PROGBITS  ...
[ 3] .data          PROGBITS  ...
[ 4] .bss           NOBITS    ...
[ 5] .symtab        SYMTAB    ...
[ 6] .strtab        STRTAB    ...

$ objdump -d ./hello | less          # disassemble
$ ldd ./hello                        # what shared libs at runtime

Real binaries you debug, you'll nm, readelf, objdump, strings, strip, file all the time. They're tiny and fast — keep them in muscle memory.

Static libs vs shared libs

Static (.a)Shared (.so)
What is itArchive of .os — like a tar ballReal ELF; loadable; resolved at runtime
Linked whenAt link time; copied into executableTagged at link, resolved at execve
Binary sizeLargerSmaller — code shared in memory across processes
Update behaviourRecompile to upgradeDrop in a new .so; processes pick it up on restart
Symbol visibilityOne copy gets pulled in if any symbol is needed (per object)Whole library mapped; symbols resolved on demand

Build them yourself:

# Static library
$ cc -c add.c sub.c              # → add.o sub.o
$ ar rcs libmath.a add.o sub.o   # archive
$ cc main.c -L. -lmath -o app    # links the .a in

# Shared library — must build with -fPIC
$ cc -fPIC -c add.c sub.c
$ cc -shared -o libmath.so add.o sub.o -Wl,-soname,libmath.so.1
$ cc main.c -L. -lmath -o app
$ LD_LIBRARY_PATH=. ./app        # tell the loader where to find libmath.so

-fPIC = Position-Independent Code: required for shared libraries on most architectures so the same library can be loaded at different addresses in different processes. The price was historically a small slowdown; on x86_64 it's negligible thanks to RIP-relative addressing.

Link order matters

The traditional Unix linker is single-pass left-to-right and only pulls in archive members for symbols that are currently undefined. So:

$ cc -lmylib main.c       # WRONG on classical ld
$ cc main.c -lmylib       # right — lib must come AFTER what needs it

If two libs need each other, you may need to repeat them or use --start-group … --end-group.

$ cc main.c -Wl,--start-group -lA -lB -Wl,--end-group

Modern Linux mostly uses gold or lld; lld is more forgiving but you should still order your inputs correctly for portability.

"Undefined reference to X" — diagnosing it

  1. Spell-check. Especially for C++ overloaded names; mangled names are very specific.
  2. Did the symbol get compiled? nm libfoo.a | grep mysym. If absent, the source defining it wasn't built or has the wrong name.
  3. Is it in the right archive? ar t libfoo.a shows members.
  4. Are you missing a library? -lpthread, -lm, -ldl for dlopen, etc.
  5. Order issue? Move the library after what needs it.
  6. C/C++ name mangling? A C++ caller of a C function needs extern "C" in the header.
  7. Static helper called from another TU? If it's static, it can't be referenced externally — drop the static or move the user.
  8. Templates not instantiated? The body must be visible at the call site (header), or you must explicitly instantiate.

Symbol visibility — keeping shared libs sane

By default on Linux, every external-linkage symbol in a shared library is exported. That's a maintenance nightmare and slows down link/load. Best practice:

$ cc -fvisibility=hidden -fPIC -c foo.c
$ cc -shared -o libfoo.so foo.o

And mark the few you actually want exposed:

#define EXPORT __attribute__((visibility("default")))

EXPORT int  public_api(int x);
       int  internal(int x);            /* hidden — not in dynamic symbol table */

Or use a linker-script / version-script. Hidden internal symbols means safer ABIs (you can change them), faster builds, smaller binaries.

ABI — what's stable, what's not

An ABI (Application Binary Interface) defines how compiled code interoperates: function call conventions, struct layout, name mangling, exception model.

For C ABI: stable across compilers on a platform. extern "C" functions, POD structs, simple types — interoperable.

For C++ ABI: not stable across compilers historically (MSVC vs GCC, even GCC versions until ~5.0). Don't pass std::string or std::vector across a shared-library boundary unless both sides were built with the same compiler version. The Itanium C++ ABI (used by GCC, Clang on Linux) has been stable since GCC 5; pre-5 ABI break around the COW std::string change is the classic war story.

Rule of thumb for shared-library APIs:

  • Expose extern "C" functions only.
  • Use opaque handles (typedef struct Foo Foo; in the public header).
  • Pass POD structs, not C++ classes.
  • Version your .so: libfoo.so.1.2 with symlinks libfoo.so.1 → libfoo.so.1.2, libfoo.so → libfoo.so.1.

RPATH, RUNPATH, LD_LIBRARY_PATH

How the dynamic loader finds .sos:

  1. DT_RPATH in the binary (legacy, takes precedence over LD_LIBRARY_PATH).
  2. LD_LIBRARY_PATH environment variable.
  3. DT_RUNPATH in the binary (modern, after LD_LIBRARY_PATH).
  4. /etc/ld.so.cache from /etc/ld.so.conf.
  5. Default: /lib, /usr/lib.

$ORIGIN in RPATH/RUNPATH is the binary's directory — useful for "ship the libs alongside the binary":

$ cc main.c -Wl,-rpath,'$ORIGIN/lib' -L./lib -lfoo -o app

Don't ship binaries that need LD_LIBRARY_PATH set; it's a footgun for users. Use RPATH/RUNPATH or static-link.

Hands-on: build a tiny library

Hands-on · static and shared, side by side
cmath.h
#pragma once
int add(int a, int b);
int sub(int a, int b);
cadd.c & sub.c
#include "math.h"
int add(int a, int b) { return a + b; }
/* ... */
int sub(int a, int b) { return a - b; }
cmain.c
#include <stdio.h>
#include "math.h"
int main(void) {
    printf("%d %d\n", add(2, 3), sub(10, 4));
    return 0;
}

# Static
$ cc -c add.c sub.c
$ ar rcs libmath.a add.o sub.o
$ cc main.c -L. -lmath -o static_app
$ ./static_app                 # 5 6
$ size static_app              # bigger because the lib is inside

# Shared
$ cc -fPIC -c add.c sub.c
$ cc -shared -o libmath.so add.o sub.o
$ cc main.c -L. -lmath -o shared_app -Wl,-rpath,'$ORIGIN'
$ ./shared_app                 # 5 6
$ size shared_app              # smaller; libmath.so loaded at runtime
$ ldd shared_app               # shows libmath.so resolution

Exercises

EX 4.1 easy Diagnose a link error 
$ cc main.c -o app
/usr/bin/ld: /tmp/cc...o: in function `main':
main.c:(.text+0x12): undefined reference to `pthread_create'
collect2: error: ld returned 1 exit status
Show solution

Missing -lpthread. cc main.c -o app -lpthread. Note the order: library after sources.

Modern glibc (≥ 2.34) merges pthread into libc, so this error appears mostly on older toolchains and embedded.

EX 4.2 medium Why static

You have helper.c with void log_line(const char *s) { ... }. Two unrelated translation units in the same project both want a log_line with different bodies. What's the fix?

Show solution

Make both static in their .c files — internal linkage, no clash. The linker doesn't see them at all from outside the TU.

If both should also be visible inside the TU but you want a unified version externally, give them different names. Sharing one external function across the project is also valid (refactor into a common module).

EX 4.3 medium Use nm to find a missing symbol

The linker complains about an undefined reference to foo_init. You have a static library you think defines it. How do you check, and what does the output tell you?

Show solution 
$ nm libfoo.a | grep foo_init
foo_module.o:
0000000000000000 T foo_init

Capital T = defined in text. Found. So the issue is link order or path. If you got U foo_init instead, the lib references it but doesn't define it — the source compiles a declaration only, not the body.

If you got nothing, the source defining foo_init wasn't compiled into the library (typo, missed in build).

EX 4.4 hard C++ symbols look different

You have C++ code int parse(const std::string&); in parse.cpp. From C, you try to call it. The link fails. Why, and how do you fix it?

Show solution

C++ mangles names to encode argument types so overloads can coexist. The symbol is something like _Z5parseRKNSt7__cxx1112basic_stringIcSt11char_traitsIcESaIcEEE. C looks for plain parse. The fix:

  1. Wrap the function in extern "C", which forces unmangled C-style names. But then it can't accept std::string; pass const char * instead.
  2. Provide a C-friendly wrapper:
// parse.cpp
extern "C" int parse_c(const char *s) {
    return parse(std::string(s));
}

/* parse.h — visible from C and C++ */
#ifdef __cplusplus
extern "C" {
#endif
int parse_c(const char *s);
#ifdef __cplusplus
}
#endif
EX 4.5 hard RPATH detective

A binary works in dev but fails on a customer machine: error while loading shared libraries: libfoo.so: cannot open shared object file. The library is shipped alongside the binary in ./lib/. What's wrong, and how do you fix it without telling the user to set LD_LIBRARY_PATH?

Show solution

The binary doesn't know to look in ./lib/. Bake an RPATH/RUNPATH:

$ cc main.o -L./lib -lfoo -Wl,-rpath,'$ORIGIN/lib' -o app
$ readelf -d app | grep -E 'RPATH|RUNPATH'
0x000000000000001d (RUNPATH) Library runpath: [$ORIGIN/lib]

$ORIGIN is the binary's directory; the loader expands it at runtime. Now no matter where the user runs ./app from, libraries are found relative to the binary.

Quote the dollar to keep the shell from expanding it at build time. Use patchelf --set-rpath to retrofit an existing binary.

Recap

  • Pipeline: preprocessor → compiler → assembler → linker. The driver runs all four; each can be invoked alone.
  • Headers contain declarations (and inline/template/constexpr definitions). .c/.cpp contain the rest.
  • One Definition Rule: one external definition per program; identical inline definitions allowed.
  • nm, readelf, objdump, ldd are your link-error toolkit.
  • Static .a = archive copied in. Shared .so = loaded at runtime; needs -fPIC and visibility discipline.
  • "Undefined reference" diagnostics: spell-check, nm, library order, missing -l, mangled names.
  • RPATH/RUNPATH with $ORIGIN for self-contained deployments; never ship requiring LD_LIBRARY_PATH.
