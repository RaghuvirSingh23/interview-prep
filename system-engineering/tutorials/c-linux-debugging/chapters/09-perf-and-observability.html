Chapter 09 Performance & observability

When your program is slow, "guess and rebuild" is the worst strategy. This chapter is the toolkit for finding out why: time, strace, ltrace, perf, bpftrace, flamegraphs, and the cache effects that explain a 10× slowdown nobody else can see.

First, time it properly

$ time ./prog
real    0m4.523s    # wall-clock
user    0m4.012s    # CPU time in userspace
sys     0m0.498s    # CPU time in kernel

$ /usr/bin/time -v ./prog
        Maximum resident set size (kbytes): 124528
        Major page faults:           7
        Minor page faults:           28391
        Voluntary context switches:  1207
        Involuntary context switches: 412
        Page size (bytes):           4096
        ...

What the numbers mean:

  • real > user + sys: blocked on I/O, waiting on locks, or mostly idle.
  • user >> sys: CPU-bound in userspace. Profile with perf.
  • sys > user: too many syscalls, kernel work. strace / perf top -t kernel.
  • real >> user + sys: waiting. Disk, network, lock contention. perf record -e sched:sched_switch or off-cpu profiling.

Always benchmark with the production-shaped optimisation level (-O2 at minimum). Code under -O0 is a different program.

strace — see every syscall

$ strace ./prog                              # everything
$ strace -c ./prog                           # summary at end (counts, time)
$ strace -p 1234                             # attach to running PID
$ strace -f -p 1234                          # follow forks/threads
$ strace -e trace=openat,read,write ./prog   # filter
$ strace -e trace=network ./prog             # network syscalls only
$ strace -tt -T ./prog                       # timestamps + duration per call
$ strace -y ./prog                           # show file paths next to fd numbers
$ strace -k ./prog                           # userspace stack on each call (slow but informative)

What strace is good for:

  • "What file/socket is this thing actually opening?" — answers most "config not picking up" mysteries.
  • "Why is it slow?" — strace -c shows where time goes by syscall.
  • "What's it waiting on?" — attach to a stuck process; the last call shown is what it's blocked in.
strace slows the program down — a lot

Each syscall trapped through ptrace has overhead. A program doing 100k syscalls/sec runs at 5–10× the time. For just-curious investigations that's fine; for performance work, prefer perf trace or eBPF-based tools.

ltrace — library calls

ltrace traces calls into shared libraries: malloc, printf, your own libfoo.so calls. Useful when the bug is in a library boundary, less common than strace.

$ ltrace -e malloc+free ./prog
malloc(8) = 0x55e3...
free(0x55e3...)
...

perf — the everything tool

perf is the Linux profiler. CPU profiling, hardware counters, tracepoints, USDT — all in one binary.

perf top — what's running right now

$ perf top                                   # interactive, system-wide
$ perf top -p 1234                            # one process
$ perf top -e cycles,cache-misses             # specific events

Refreshes every second; sorted by sample count. The hottest function shows at the top. Press e to drill in.

perf stat — counters and ratios

$ perf stat ./prog
 Performance counter stats for './prog':
          1234.56 msec task-clock                #    0.987 CPUs utilized
              512      context-switches          #    0.415 K/sec
                3      cpu-migrations            #    0.002 K/sec
            8,234      page-faults               #    0.007 M/sec
   12,345,678,901      cycles                    #    9.999 GHz
    8,888,888,888      instructions              #    0.72  insn per cycle
    1,000,000,000      branches                  #  810.000 M/sec
       12,345,678      branch-misses             #    1.23% of all branches

$ perf stat -e cache-misses,cache-references ./prog
$ perf stat -e L1-dcache-load-misses,LLC-load-misses,branch-misses ./prog
$ perf stat -e instructions,cycles -- ls    # IPC for one command

The two numbers most informative when starting:

  • IPC (instructions per cycle): < 0.5 means stalled (memory, branches). > 2 means doing real work.
  • Cache miss rate: high LLC-load-misses → memory bandwidth or working set too large. Re-layout structures, blocking algorithms, prefetch hints.

perf record + perf report — flamegraph-able profiles

$ perf record -F 99 -g ./prog                # 99 Hz sample, with call graph
$ perf record -F 99 -g -p 1234 -- sleep 30   # 30 s sample of running PID
$ perf report                                # interactive TUI
$ perf report --stdio | head -50              # text dump

Build with -fno-omit-frame-pointer -g for accurate call graphs (default frame-pointer omission breaks unwinding). For C++ with broken stacks, try --call-graph=dwarf,16384 (uses DWARF unwinder, slower but accurate).

Flamegraphs

$ git clone https://github.com/brendangregg/FlameGraph
$ perf record -F 99 -g -- ./prog
$ perf script | ./FlameGraph/stackcollapse-perf.pl > out.folded
$ ./FlameGraph/flamegraph.pl out.folded > flame.svg
$ open flame.svg                              # or just open in browser

Flamegraphs are the canonical way to share "what's hot". Wide bars = many samples there. Read top-down; the top is what was running when sampled, the rest is the stack.

bpftrace — eBPF for humans

bpftrace is awk-for-the-kernel. One-liners that would otherwise need a 200-line C eBPF program.

# Count opens system-wide
$ sudo bpftrace -e 'tracepoint:syscalls:sys_enter_openat { @[comm] = count(); }'

# Histogram of read sizes for a PID
$ sudo bpftrace -e 'tracepoint:syscalls:sys_enter_read /pid == 1234/ { @ = hist(args->count); }'

# Trace every malloc > 1 MB in your binary
$ sudo bpftrace -e 'uprobe:/path/to/prog:malloc /arg0 > 1024*1024/ { printf("%d bytes from %s\n", arg0, ustack); }'

# Latency of a function (entry/exit)
$ sudo bpftrace -e '
    uprobe:/path/to/prog:do_request { @start[tid] = nsecs; }
    uretprobe:/path/to/prog:do_request /@start[tid]/ {
        @latency = hist(nsecs - @start[tid]); delete(@start[tid]);
    }'

Power moves:

  • USDT probes — your binary defines static tracepoints (e.g. request_start, request_end) with one macro; production-safe; no overhead when not enabled.
  • Latency histograms — hist() in bpftrace gives log2 buckets; great for tail-latency hunts.
  • System-wide visibility — kernel + userspace, all processes.

Brendan Gregg's "BPF Performance Tools" book is the reference. Most distros ship bcc-tools with ready-made scripts: opensnoop, execsnoop, biolatency, tcpconnect, etc.

Cache effects, the under-appreciated bottleneck

Modern CPUs run at 3–5 GHz. Main memory latency is ~100 ns. That's 300–500 cycles for a missed load — the CPU stalls waiting. Cache hits at L1 are 4 cycles, L2 ~12, L3 ~40.

The math: a tight loop doing x = a[i]; y = b[i*1024] will be dominated by the b accesses if they don't fit in cache. The same loop with y = b[i] (cache-friendly) can be 10–50× faster on the same hardware.

Patterns to know

  • Array-of-Structs vs Struct-of-Arrays. AoS is what you write; SoA is what makes vectorising compilers and caches happy. Worth it for hot loops.
  • Sequential access beats random by 10–100×. Hardware prefetchers love stride-N reads.
  • Working-set size: if your hot data fits in L2 (~256 KB), you're golden. If it spills to LLC (MB), you're memory-bound.
  • False sharing — covered in chapter 7.
  • Branch prediction. A if (likely) in a loop costs ~0 cycles when predicted right; a misprediction costs 15–20.

Measure with perf

$ perf stat -e cycles,instructions,L1-dcache-load-misses,LLC-load-misses,branch-misses ./prog

# What lines are causing cache misses?
$ perf record -e cache-misses -g ./prog
$ perf report

# Top-down analysis (Intel) — shows whether stalls are frontend, backend, retiring, etc.
$ perf stat -M Frontend_Bound,Backend_Bound,Retiring,Bad_Speculation ./prog

Allocator behaviour

malloc is fast for small allocations and slow for large or fragmented ones. To investigate:

# Replace allocator at LD_PRELOAD time
$ LD_PRELOAD=/usr/lib/x86_64-linux-gnu/libtcmalloc.so ./prog
$ LD_PRELOAD=/usr/lib/x86_64-linux-gnu/libjemalloc.so ./prog

# heaptrack — flamegraph of allocations
$ heaptrack ./prog
$ heaptrack_gui heaptrack.prog.12345.gz

# massif (valgrind) — heap usage over time
$ valgrind --tool=massif ./prog
$ ms_print massif.out.12345 | less

For high-throughput servers, jemalloc or tcmalloc usually win 10–30% over glibc's ptmalloc. Always benchmark with your workload.

Latency vs throughput

The two numbers usually trade off:

  • Throughput — work done per unit time. Maximise with batching, parallelism, kernel-bypass (DPDK, io_uring) for extreme cases.
  • Latency — time per individual op. Minimise with smaller queues, less batching, less context switching, locking out noisy neighbours.

Real systems care about percentile latency, not average. p50 is fine and almost meaningless. p99 / p99.9 / p99.99 is what users feel. Coordination omission (sender waits for slow receiver) destroys naive benchmark numbers — use a constant-rate load generator like wrk2, not a "blast as fast as possible" one.

Quick procmon

$ top                                           # the classic
$ htop                                          # better top
$ pidstat -p 1234 -t 1                          # per-thread CPU
$ pidstat -d 1                                  # disk I/O per process

$ vmstat 1                                      # 1-sec system stats
$ iostat -xz 1                                  # per-disk I/O stats
$ mpstat -P ALL 1                               # per-CPU utilisation
$ sar -n DEV 1                                  # network throughput

$ pmap -X 1234                                  # detailed memory map of a process
$ ipcs                                          # SysV IPC objects (semaphores, shm, queues)
$ lsof -p 1234                                  # all open files for a PID

Memorise enough that "is the box overloaded?" is a 30-second answer. top + iostat -xz 1 + vmstat 1 tells you CPU, disk, and memory pressure in three commands.

Trace analysis

For complex multi-component systems, modern observability uses traces:

  • strace -tt -T for one process.
  • perf script for sampled CPU profiles.
  • OpenTelemetry + Jaeger/Tempo/Zipkin for distributed traces.
  • perf-tools + trace-cmd + KernelShark for kernel-level visualisation.

Benchmarking — the pitfalls

  1. CPU frequency scaling. Pin to "performance" governor: sudo cpupower frequency-set -g performance. Otherwise the kernel ramps up/down and your numbers wobble.
  2. Cold caches. The first run is slower. Warm up, then measure.
  3. Process pinning. taskset -c 2 ./bench to pin to a specific core; avoids scheduler noise.
  4. Other workloads. Disable nodaemons, disconnect from network if possible.
  5. One run isn't enough. Run 10+, take median; report variance.
  6. Don't measure debug builds. -O2 minimum; LTO and PGO change real numbers.
  7. Compiler optimisations may eliminate your benchmark. Sink results into a volatile or pass to a function the compiler can't see, or use Google Benchmark's DoNotOptimize.

Hands-on: a flamegraph in 60 seconds

Hands-on · profile, render, read
$ # Compile with frame pointers and debug info
$ cc -O2 -g -fno-omit-frame-pointer prog.c -o prog

$ # Sample 99 Hz with call graphs
$ perf record -F 99 -g ./prog

$ # Render
$ perf script | ./FlameGraph/stackcollapse-perf.pl | ./FlameGraph/flamegraph.pl > flame.svg
$ xdg-open flame.svg

Read the flamegraph: bars wider than ~10% of the chart are worth investigating. Drill into them by clicking. The leaf functions are where time is actually spent; the stacks above show which path got there.

Exercises

EX 9.1 easy Read time output

You see real 10s, user 2s, sys 0.3s. What's the program doing for the missing ~7.7 seconds?

Show solution

Waiting. Possibilities: blocked on I/O (disk, network), sleeping (sleep, select timeouts), waiting on a lock or condition variable, blocked on stdin. Investigate with strace -p while it's running, or perf record -e sched:sched_switch -g for an off-CPU profile.

EX 9.2 medium Low IPC, what's wrong?

perf stat shows IPC = 0.4 (instructions per cycle). What might cause that, and how do you tell which?

Show solution

Low IPC means the CPU is stalling. Likely causes:

  • Cache misses — check L1-dcache-load-misses, LLC-load-misses. If LLC misses are high, you're memory-bound.
  • Branch mispredictions — check branch-misses. > 5% is suspicious.
  • Pipeline frontend stalls — perf top-down (perf stat -M Frontend_Bound); often instruction cache or decode issues.
  • Long-latency instructions (sqrt, divide) in a tight loop.

Top-down analysis (Intel TMA) is the systematic way to attribute stalls.

EX 9.3 medium Why my benchmark lies

Show three reasons a hand-rolled microbenchmark can be 10× off.

Show solution
  1. Compiler optimised it away. Result unused → loop deleted. Sink into volatile or use DoNotOptimize.
  2. CPU frequency scaling. First run cold, others warmed up; or thermals throttle.
  3. Cache state. Tight loop fits in L1; production data doesn't.
  4. Branch prediction. Constant pattern in benchmark; varied input in prod.
  5. Coordinated omission. "as fast as possible" misses queueing-time effects of fixed-rate load.
  6. Unrealistic data. All-zeros vs random; sorted vs unsorted; aligned vs misaligned.
EX 9.4 hard Off-CPU mystery

Your service uses 3% CPU but is missing its latency SLO. perf top shows nothing hot. What kind of profile do you need, and how?

Show solution

An off-CPU profile — what's the program blocked on, weighted by time. perf record -e sched:sched_switch -e sched:sched_wakeup -g captures context switches; combine with userspace stack to flamegraph "wait time". Or use bpftrace's offcputime tool / bcc's offcputime.

Common findings: lock contention, waiting on a slow downstream, blocking I/O on what looked like cached data, scheduler delays from CPU pinning conflicts.

EX 9.5 hard Histograms over time

Write a bpftrace script that prints a histogram of read() return sizes for one process, refreshed every 5 seconds.

Show solution 
$ sudo bpftrace -e '
    tracepoint:syscalls:sys_exit_read /pid == 1234 && args->ret > 0/ {
        @sizes = hist(args->ret);
    }
    interval:s:5 {
        print(@sizes);
        clear(@sizes);
    }'

Useful for spotting "everyone's doing 1-byte reads" patterns or buffer-size mismatches.

Recap

  • time first; real vs user+sys tells you CPU vs wait.
  • strace for "what is it doing"; strace -c for syscall-level summary.
  • perf stat for counters and IPC; perf record/report for sampled profiles; flamegraphs for sharing.
  • bpftrace + bcc tools for kernel and userspace tracing without writing C.
  • Cache effects matter — measure miss rates with perf stat -e ...-misses.
  • Benchmark with optimised builds, fixed CPU governor, pinned cores, and ten runs.
  • Real users care about p99/p99.9 latency, not average. Use rate-controlled load generators.
