Chapter 11 Sanitizers & static analysis

Sanitizers are runtime instrumentation that turns "subtle UB" into "loud and immediate" — at the cost of a slowdown. Static analysers catch issues without running anything. Together they catch most of the bugs that GDB exists to find. Use both, religiously, in CI.

The toolbox at a glance

ToolWhat it catchesCost
AddressSanitizer (ASan)Out-of-bounds, use-after-free, double-free, leaks~2× CPU, ~3× memory
UndefinedBehaviorSanitizer (UBSan)Signed overflow, shift past width, null deref, alignment, type confusion~1.2× CPU
ThreadSanitizer (TSan)Data races, deadlock potential~5–15× CPU, large memory
MemorySanitizer (MSan)Reads of uninitialised memory~3× CPU; clang-only
LeakSanitizer (LSan)Memory leaks at exitCheap (built into ASan)
valgrind / memcheckLike ASan + uninit-reads, but with more false positives~20–50× CPU; emulates everything
helgrind / drd (valgrind)Race detection, alternative to TSan~50× CPU
clang-tidyStatic checks: bugs, modernization, performance, styleNone at runtime; build-time
scan-build / clang static analyzerPath-sensitive analysis: null derefs, leaksBuild-time, slow
cppcheckLighter static analysis; C-friendlyFast
CoverityCommercial; deeper analysis; common in regulated industriesSlow; expensive

Day-to-day discipline:

  • Dev/CI builds: -fsanitize=address,undefined by default.
  • Threading-heavy CI: a separate -fsanitize=thread build.
  • Pre-commit / CI lint: clang-tidy with a chosen check set.
  • Production: none of these. Sanitizers expose your binary's address layout — security risk.

AddressSanitizer — the workhorse

$ cc -O1 -g -fsanitize=address -fno-omit-frame-pointer prog.c -o prog
$ ./prog
=================================================================
==12345==ERROR: AddressSanitizer: heap-use-after-free on address 0x... at pc 0x... bp 0x... sp 0x...
READ of size 4 at 0x... thread T0
    #0 0x... in main prog.c:8
    ...
0x... is located 0 bytes inside of 4-byte region [0x...,0x...)
freed by thread T0 here:
    #0 free
    #1 main prog.c:7
previously allocated by thread T0 here:
    #0 malloc
    #1 main prog.c:5

What ASan catches:

  • Heap buffer overflow / underflow
  • Stack buffer overflow / underflow
  • Global buffer overflow / underflow
  • Use after free
  • Use after return (with -fsanitize-address-use-after-return)
  • Use after scope (with -fsanitize-address-use-after-scope)
  • Double free / wild free
  • Memory leaks (LeakSanitizer, on exit)

Mechanism: ASan replaces malloc/free with versions that pad allocations with red zones and quarantine freed memory. Loads/stores are instrumented to check shadow memory (1 byte per 8 program bytes encoding "valid"/"poisoned"). Out-of-bounds touch a red zone → report.

ASAN_OPTIONS

$ ASAN_OPTIONS=detect_leaks=1:halt_on_error=0:abort_on_error=1:print_stats=1 ./prog

Common options:

halt_on_error=0Continue after each report; useful in test runs that expose multiple issues.
abort_on_error=1Drop a core for GDB post-mortem.
detect_leaks=0/1Toggle LSan.
print_stats=1Memory statistics on exit.
fast_unwind_on_malloc=0More accurate alloc stacks; slower.
strict_string_checks=1Catch strlen etc. reading beyond a string.

UBSan — undefined-behaviour catcher

$ cc -O1 -g -fsanitize=undefined prog.c -o prog
$ ./prog
prog.c:5:9: runtime error: signed integer overflow: 2147483647 + 1 cannot be represented in type 'int'

UBSan groups into many sub-sanitizers; commonly enabled together via -fsanitize=undefined:

  • signed-integer-overflow
  • shift (bad shift amounts)
  • integer-divide-by-zero
  • float-divide-by-zero
  • null (NULL deref)
  • alignment
  • bounds (where compiler can prove an array's size)
  • vptr (calling a virtual function on a freed/wrong-typed object)
  • return (missing return on non-void function)
  • vla-bound

-fno-sanitize-recover turns reports into hard aborts (default is "report and continue"). Useful in CI to fail fast.

UBSan is cheap and catches a huge category of "compiles fine, breaks under -O2 with a different compiler". Always on in dev.

ThreadSanitizer — race detection

$ c++ -O1 -g -fsanitize=thread race.cpp -o race
$ ./race
WARNING: ThreadSanitizer: data race (pid=12345)
  Write of size 4 at 0x... by thread T1:
    #0 worker race.cpp:10
  Previous read of size 4 at 0x... by thread T2:
    #0 reader race.cpp:18
  Location is global 'counter' of size 4

Cost: ~10× slowdown, ~5–10× memory. Enable in dedicated CI builds.

What TSan catches:

  • Concurrent unsynchronised accesses to the same memory.
  • Misuse of synchronisation primitives (e.g., unlock-without-lock).
  • Some atomic-misordering bugs.

What it doesn't catch:

  • Logical races over data that is correctly synchronised but the algorithm is wrong.
  • Races involving custom atomics (inline asm, etc.) not annotated.
  • Some intra-process races involving signals.

Run your tests under TSan often. Every report is real.

MemorySanitizer — uninitialised memory

MSan tracks every byte's "initialisedness" through registers and memory. Reading something never written is a report. Catches the classic "stack variable used before assignment", "malloc + read uninit", "padding read".

$ clang++ -O1 -g -fsanitize=memory -fno-omit-frame-pointer prog.cc -o prog
$ ./prog
==12345==WARNING: MemorySanitizer: use-of-uninitialized-value
    #0 0x... in main prog.cc:5

The catch: MSan needs all dependencies (libstdc++, libc) instrumented too. That's painful — typically requires building a special version of libc++. Less commonly run than ASan; very valuable on the right project. Clang only.

Can I run them together?

ASan + UBSanYes — common combo.
ASan + TSanNo — incompatible.
ASan + MSanNo.
TSan + UBSanYes.
MSan + UBSanYes.

Strategy: maintain three CI builds — (ASan+UBSan), (TSan+UBSan), and a regular optimised build. Run all three. Slow tests should run under at least the optimised build; fast unit tests under all three.

valgrind — when sanitizers don't apply

valgrind runs your program in a CPU emulator (Valgrind's "core") and checks every memory access. Pros: works on unmodified binaries, catches the same things ASan+MSan do, no recompilation. Cons: 20–50× slower, can have false positives on optimised stdlib code, doesn't always understand modern things like AVX-512 immediately.

$ valgrind --leak-check=full --show-leak-kinds=all ./prog
==12345== Memcheck, a memory error detector
==12345== Invalid read of size 4
==12345==    at 0x... main (prog.c:8)
==12345==  Address ... is 0 bytes after a block of size 16 alloc'd
==12345==    at 0x... malloc
==12345==    by 0x... main (prog.c:5)
==12345==
==12345== HEAP SUMMARY:
==12345==     definitely lost: 16 bytes in 1 blocks
==12345==     indirectly lost: 0 bytes
==12345==     possibly lost:   0 bytes

Other valgrind tools:

  • helgrind — race detector. Slower than TSan but works without recompiling.
  • drd — race detector with different heuristics.
  • cachegrind — cache simulation; useful for "would a different layout help?"
  • callgrind — call graph + cost; visualised with KCachegrind.
  • massif — heap profiler (memory usage over time).

Use ASan/TSan when you can recompile. Use valgrind when you can't (vendor binaries, obscure platforms).

Static analysis

clang-tidy

The standard linter for modern C++. Plug-in checks; configurable per project.

$ clang-tidy main.cpp -- -std=c++20 -I./include
main.cpp:8:5: warning: do not use pointer arithmetic
main.cpp:14:9: warning: variable 'count' is uninitialized when used here

# With a config file:
$ cat .clang-tidy
---
Checks: '
  bugprone-*,
  cert-*,
  clang-analyzer-*,
  cppcoreguidelines-*,
  performance-*,
  portability-*,
  readability-*,
  -readability-magic-numbers,
  -cppcoreguidelines-avoid-magic-numbers
'
WarningsAsErrors: 'bugprone-*,cert-*'

# Run across the whole project (with compile_commands.json from CMake):
$ run-clang-tidy -j 8

Powerful checks:

  • bugprone-* — likely-bug patterns: misplaced widening, branch-clone, unchecked optional access.
  • cert-* — CERT-C/C++ secure coding rules.
  • cppcoreguidelines-* — Stroustrup/Sutter Core Guidelines (RAII, init-everywhere, no narrowing).
  • modernize-* — auto-fix to modern C++ idioms (NULL → nullptr, raw loops → ranges).
  • performance-* — unnecessary copies, missed moves, inefficient string usage.

Use --fix for auto-applicable fixes. Wire into CI; treat warnings as errors for a curated subset.

scan-build / clang static analyzer

Path-sensitive analysis: traces actual control flow to find bugs reachable on some path. Slower than clang-tidy but catches different things — null derefs, leaks, uninitialised values across multiple functions.

$ scan-build make
scan-build: 4 bugs found.
scan-build: Run 'scan-view /tmp/scan-build-...' to examine bug reports.
$ scan-view /tmp/scan-build-...           # opens HTML report in browser

cppcheck

Lighter, faster, broader-targeted than clang-tidy. Especially useful for legacy C codebases. Less smart but no compile-database setup needed.

$ cppcheck --enable=all --inconclusive --std=c11 src/
$ cppcheck --enable=all --xml --xml-version=2 src/ 2> cppcheck.xml

iwyu — Include-What-You-Use

Suggests minimal includes — speeds up build, reduces accidental dependency. Imperfect but useful periodically.

CI integration

A typical professional setup:

BuildFlagsTests run
release-O2 -g -DNDEBUGfull suite + benchmarks
asan-ubsan-O1 -g -fsanitize=address,undefinedfull suite
tsan-ubsan-O1 -g -fsanitize=thread,undefinedconcurrency tests
fuzz-O1 -g -fsanitize=address,fuzzerlibFuzzer corpus
tidybuild w/ compile_commands.jsonrun-clang-tidy on diff

Block PRs on sanitizer failures. Surface clang-tidy diff-only warnings in PR comments. Run cppcheck nightly on the whole tree.

Fuzzing — bonus topic

libFuzzer is built into clang and integrates with sanitizers. Write a target that takes (data, size) and runs your code; the fuzzer mutates inputs and finds crashes.

// fuzz_target.cpp
#include <cstdint>
#include <cstddef>

extern "C" int LLVMFuzzerTestOneInput(const uint8_t *data, size_t size) {
    parse_packet(data, size);    // your parser
    return 0;
}

$ clang++ -O1 -g -fsanitize=address,fuzzer fuzz_target.cpp parser.cpp -o fuzz
$ mkdir corpus seeds
$ cp some_real_inputs/* seeds/
$ ./fuzz corpus seeds -max_total_time=300        # 5 minutes

Found inputs are saved as crash-* files; reproduce with ./fuzz crash-deadbeef. OSS-Fuzz runs continuous fuzzing for major projects; Google Project Zero builds careers on fuzzing-discovered CVEs.

Hands-on: build a sanitizer-enabled CI matrix

Hands-on · CMake + sanitizers
option(SANITIZE "Sanitizer to use" "")
if(SANITIZE STREQUAL "asan")
    add_compile_options(-fsanitize=address,undefined -fno-omit-frame-pointer)
    add_link_options(-fsanitize=address,undefined)
elseif(SANITIZE STREQUAL "tsan")
    add_compile_options(-fsanitize=thread,undefined)
    add_link_options(-fsanitize=thread,undefined)
elseif(SANITIZE STREQUAL "msan")
    add_compile_options(-fsanitize=memory -fno-omit-frame-pointer)
    add_link_options(-fsanitize=memory)
endif()

$ cmake -S . -B build/asan -DSANITIZE=asan -DCMAKE_BUILD_TYPE=Debug
$ cmake -S . -B build/tsan -DSANITIZE=tsan -DCMAKE_BUILD_TYPE=Debug
$ cmake --build build/asan
$ ctest --test-dir build/asan

Now your CI matrix has three jobs: regular, ASan+UBSan, TSan+UBSan. Each runs the same tests. Most bugs you'd otherwise debug for hours fail loudly in one of them.

Exercises

EX 11.1 easy Pick the sanitizer

Pick the right tool for each:

  1. Code reads beyond the end of a stack array.
  2. A counter increment loses values when run with 4 threads.
  3. (int)signed_max + 1 evaluates to a small negative.
  4. A struct's padding bytes are read in memcmp.
  5. Memory leaks of 12 bytes per request.
Show solution
  1. ASan — stack-buffer-overflow.
  2. TSan — data race on the counter.
  3. UBSan — signed-integer-overflow.
  4. MSan — use-of-uninitialized-value (or initialise the struct with {}).
  5. LSan (built into ASan) — leak report at exit.
EX 11.2 medium ASan slowdown

Why is ASan only ~2× slower than baseline, while valgrind is 20–50×?

Show solution

ASan is compile-time instrumentation: every load/store gets a few extra instructions to consult shadow memory. The CPU runs natively; just more instructions per access. valgrind runs your code in a CPU emulator and re-checks all of memory through a software MMU — every access is interpreted. Native instrumentation always beats emulation for cost.

EX 11.3 medium Why both ASan and UBSan in CI?
Show solution

They catch different bugs:

  • ASan: out-of-bounds, use-after-free, leaks. Memory-shaped issues.
  • UBSan: signed overflow, shift past width, alignment, null deref via UB inference, divide-by-zero. Compiler-language-rules issues.

An overflow that doesn't access memory won't trip ASan. An out-of-bounds read won't trip UBSan unless the compiler can prove the bounds (rare). Both are cheap to enable; together they catch most C/C++ classics.

EX 11.4 hard Fix flake with TSan

A test fails on CI ~1 time in 50, never reproduces locally. Suspected race. How do you find it?

Show solution
  1. Build with -fsanitize=thread,undefined.
  2. Run the test in a loop locally: for i in $(seq 1 200); do ./test || break; done. Many races reproduce reliably under TSan because each unsynchronised access is checked.
  3. If still elusive, run with TSAN_OPTIONS=halt_on_error=1:second_deadlock_stack=1 for richer reports.
  4. Consider rr (chapter 10) — record one failure, replay deterministically.
EX 11.5 hard Suppress a known false positive

ASan reports a leak in a third-party library you can't fix. How do you keep CI green?

Show solution

Use a suppression file. Create asan.supp:

leak:libthird_party.so
leak:third_party_init

$ LSAN_OPTIONS=suppressions=$(pwd)/asan.supp ./test

Same for TSan (TSAN_OPTIONS=suppressions=...) and UBSan. Document why each suppression exists and review periodically — third parties fix bugs too.

Recap

  • ASan + UBSan: cheap, always-on in dev. They catch the bulk of C/C++ classics.
  • TSan: separate CI build for concurrency. Every report is real.
  • MSan: clang-only, requires instrumented stdlib; valuable when you can pay the setup cost.
  • valgrind: when you can't recompile or for tools beyond memcheck (cachegrind, massif).
  • clang-tidy + scan-build for static analysis; cppcheck for cheap C linting; treat curated checks as errors.
  • Fuzzing with libFuzzer + ASan finds bugs your tests miss.
  • Three CI builds: release, ASan+UBSan, TSan+UBSan. Do this and most "production-only bugs" become "caught at PR".
