Chapter 03 Jenkins — Architecture

Jenkins is the grandfather of CI. It's simultaneously the most powerful tool in this tutorial and the most frustrating. Before we write a Jenkinsfile, understand what Jenkins is: a long-running Java server with a plugin architecture, built around a controller-and-agents model. Get this chapter right and the next three will make sense.

A short, useful history

In 2005 Kohsuke Kawaguchi, at Sun Microsystems, wrote a tool called Hudson to automate build/test cycles for Java projects. Hudson became popular; Oracle acquired Sun in 2010; a governance fight ensued; in 2011 the community forked Hudson and renamed the fork Jenkins. Jenkins flourished, Hudson withered.

Jenkins' defining feature has always been the plugin ecosystem. Anything a CI tool might need — git, docker, kubernetes, every cloud, every language, every notification channel — exists as a plugin. Today there are 1,800+ of them. That's both Jenkins' superpower and its curse.

Why Jenkins is still around

Jenkins solves problems no SaaS CI can: you control the infrastructure. Which means you can plug it into a mainframe, build on classified air-gapped networks, integrate with ancient LDAP and older Kerberos, run on ARM64 cross-compiled for a custom RTOS, orchestrate a 10,000-node simulation farm. The "open-source and self-hosted" design is the point.

The architecture, drawn

   ┌─────────────────────────────────────────┐
   │              Controller                 │
   │  (the "Jenkins server" you browse to)   │
   │                                         │
   │  - schedules jobs                       │
   │  - stores config, credentials, logs     │
   │  - serves the web UI                    │
   │  - runs plugins                         │
   │  - processes Pipeline DSL (Groovy)      │
   └────────┬────────┬────────────┬──────────┘
            │        │            │
      ┌─────┴───┐ ┌──┴────┐ ┌─────┴─────┐
      │ Agent A │ │Agent B│ │  Agent C  │
      │  Linux  │ │ macOS │ │  Windows  │
      │  Docker │ │ Intel │ │ ARM64     │
      └─────────┘ └───────┘ └───────────┘
      (where the actual build work runs)

The Controller is the brain: it holds state, schedules work, and exposes the UI. Agents (historically called "slaves", now "agents" or "nodes") are worker machines that actually run your builds. The Controller can run builds itself, but in any non-trivial setup it shouldn't — agents handle execution, Controller handles scheduling.

Why separate Controller from Agents?

  • Isolation. A build that fork-bombs its machine shouldn't take down your CI system.
  • Parallelism. N agents = N builds running simultaneously.
  • Heterogeneity. One agent is Linux, another macOS, another a Windows box on ARM. Jobs specify which they need.
  • Scaling. Add agents on-demand (cloud plugin) or keep a fleet.

Agent connection methods

  • SSH. Controller SSHes into the agent and starts a Java process. Simple.
  • JNLP / inbound. Agent connects out to the Controller. Required when firewalls forbid inbound connections.
  • Docker cloud. Controller spins up an agent container for each build, tears it down after. Clean, ephemeral, scalable.
  • Kubernetes cloud. Same idea but each build is a K8s pod. The modern-and-scaling answer.

Installing Jenkins

The easiest install is the official LTS (Long-Term Support) docker image. Do this in a throwaway VM or Docker, not your work laptop for real use — Jenkins is a server. 

$ docker run -d \
    --name jenkins \
    -p 8080:8080 -p 50000:50000 \
    -v jenkins_home:/var/jenkins_home \
    -v /var/run/docker.sock:/var/run/docker.sock \
    jenkins/jenkins:lts

$ docker exec jenkins cat /var/jenkins_home/secrets/initialAdminPassword
# use this password on first login at http://localhost:8080

The volume mount of /var/run/docker.sock lets your Jenkins container start other containers on the host — useful for Docker-based agents. Omit it if you don't need that.

Open http://localhost:8080. Paste the password. Step through the setup wizard. When prompted, install "suggested plugins" — roughly 20 plugins that cover basic CI.

A tour of the UI

On the dashboard you'll see these main left-nav items:

  • New Item — create a job (freestyle, pipeline, multibranch, …).
  • People — users who've committed to projects Jenkins knows about.
  • Build History — recent runs across all jobs.
  • Manage Jenkins — settings, plugins, security, credentials, system config, everything admin. This is where you'll spend most of your admin time.
  • My Views — customised dashboards filtered to subsets of jobs.

A job (or "item" or "project") has:

  • A name and description.
  • Source control config (git repo URL, branches).
  • Build triggers (poll SCM, webhook, periodic, upstream).
  • Build steps (what to do — for freestyle jobs) or a Pipeline script.
  • Post-build actions (archive artifacts, publish test results, notify).

Your first (freestyle) job

"Freestyle" is the legacy way. You'll mostly write Pipelines (Chapter 4), but it's worth building one freestyle job to understand the UI.

  1. Dashboard → New Item.
  2. Name: hello-freestyle. Select Freestyle project. OK.
  3. Under Build Steps, Add build step → Execute shell, and enter:
echo "Hello from Jenkins on $(hostname) at $(date -u)"
uname -a

Save. Click Build Now. Watch a run appear in "Build History". Click its number, then "Console Output". You'll see the output of your shell, wrapped in Jenkins preamble like:

Started by user admin
Running as SYSTEM
Building in workspace /var/jenkins_home/workspace/hello-freestyle
[hello-freestyle] $ /bin/sh -xe /tmp/jenkins1234.sh
+ echo Hello from Jenkins on ...
Hello from Jenkins on jenkins-controller at 2026-04-23T...
+ uname -a
Linux jenkins-controller 6.1.0-13-amd64 #1 SMP Debian ...
Finished: SUCCESS

That's it. You just made a CI system run a shell script.

Why Jenkinsfile exists

Freestyle jobs have a fatal flaw: the config lives in Jenkins, not in your repo. Which means:

  • No code review on pipeline changes.
  • No git history of how your CI evolved.
  • No "this build on this commit" atomic pair — if you change the pipeline, every previous commit's build breaks.
  • Disaster recovery is backing up a Jenkins server instead of a git repo.

Around 2015 Jenkins introduced Pipelines — CI logic expressed as code, stored in a Jenkinsfile in your repo. That's how every modern Jenkins installation looks. Freestyle still exists, and you'll find it in the wild, but new work should be Pipeline.

A Jenkinsfile, briefly

groovyJenkinsfile — preview
pipeline {
    agent any
    stages {
        stage('Checkout') { steps { checkout scm } }
        stage('Test')     { steps { sh 'make check' } }
        stage('Build')    { steps { sh 'make' } }
    }
    post {
        always { archiveArtifacts artifacts: 'build/**/*', fingerprint: true }
    }
}

Don't worry about the syntax yet — we dissect it in Chapters 4 and 5. Just notice:

  • It's Groovy, a JVM scripting language.
  • It reads top-to-bottom like a recipe.
  • stages are the visual phases shown in the UI.
  • post runs cleanup/notification.

Plugins — power and pain

Almost every Jenkins capability is a plugin. The "suggested plugins" set includes git, maven, matrix authorisation, timestamper, workflow (which is Pipelines themselves), and maybe 15 others. Want Docker? Install the Docker plugin. Kubernetes? Install the Kubernetes plugin. Slack? Install the Slack Notification plugin.

Go to Manage Jenkins → Plugins → Available and browse. Some plugins you'll almost always want:

  • Blue Ocean — a prettier pipeline UI (though recent Jenkins versions have caught up natively).
  • Pipeline Utility Steps — read/write YAML/JSON, checksums, etc.
  • Credentials Binding — surface credentials as env vars safely.
  • JUnit — parse & display test results.
  • Workspace Cleanup — cleanWs() step.
  • Matrix Authorization Strategy — fine-grained RBAC.
  • Warnings-NG — parse linter/compiler output into findings.
  • HTML Publisher — show generated HTML reports (coverage, etc.).
Plugins are shared state

Plugins are installed system-wide, on the Controller, and affect every job. Upgrading a plugin can break every job in subtle ways. Rule: never upgrade plugins on Friday afternoon. Keep a staging Jenkins; test upgrades there; have a rollback plan.

Adding an agent

Dashboard → Manage Jenkins → Nodes → New Node.

Give it a name (e.g. docker-builder), pick Permanent Agent, and configure:

  • # of executors: how many builds this agent runs simultaneously. Often 2-4 depending on the machine.
  • Remote root directory: where the agent stores its workspace (/home/jenkins).
  • Labels: tags you'll use to pin jobs to certain agents. E.g. linux docker gpu.
  • Launch method: SSH, JNLP, or command.
  • Availability: always online, or on-demand.

For ephemeral agents (preferred in modern setups), use the Kubernetes or Docker plugin to spin up a fresh container per build. We cover this in Chapter 6.

Labels and agent selection

pipeline {
    agent { label 'linux && docker' }     // AND of labels
    // or
    agent none
    stages {
        stage('Linux build')   { agent { label 'linux'   }; steps { sh 'make' } }
        stage('Windows build') { agent { label 'windows' }; steps { bat 'msbuild' } }
    }
}

Expressions like linux && docker, linux || macos, !windows let you pin stages to whichever agent fits.

Credentials, briefly

Never put secrets in a Jenkinsfile. Use Jenkins' credentials store (Manage Jenkins → Credentials). Types include:

  • Username + password (e.g. DB login).
  • Secret text (e.g. API token).
  • Secret file (e.g. a kubeconfig).
  • SSH private key.
  • Certificate.

In a pipeline, reference them with withCredentials:

withCredentials([string(credentialsId: 'npm-token', variable: 'NPM_TOKEN')]) {
    sh 'npm publish'
}

The token is exposed as the NPM_TOKEN env var for the duration of the block, masked in logs.

More on this in Chapter 6 and, cross-tool, Chapter 11.

Hands-on: a local Jenkins, a real job

Hands-on · spin up and build

1. Start Jenkins locally:

$ docker run -d --name jenkins \
    -p 8080:8080 -p 50000:50000 \
    -v jenkins_home:/var/jenkins_home \
    jenkins/jenkins:lts
$ docker exec jenkins cat /var/jenkins_home/secrets/initialAdminPassword

2. Open http://localhost:8080, paste the password, install suggested plugins, create an admin user.

3. Create an item → "Pipeline" (not Freestyle). Name it hello-pipeline.

4. Under "Pipeline" → "Definition", pick Pipeline script. Paste:

pipeline {
    agent any
    stages {
        stage('Hello')       { steps { sh 'echo "Hello from Jenkins"' } }
        stage('System info') { steps { sh 'uname -a; java -version 2>&1' } }
        stage('Fake build')  {
            steps {
                sh 'mkdir -p out && echo "release $(date -u +%F)" > out/version.txt'
            }
        }
    }
    post {
        always { archiveArtifacts artifacts: 'out/**' }
    }
}

5. Save → Build Now. Watch the stages light up green in the stage view. Click the run → "Console Output" for the full log. Note the "Artifacts" section on the build page — click to download version.txt.

Exercises

EX 3.1 easy Two-agent pinning

Sketch a Declarative pipeline that runs make test on Linux and ctest on Windows, in parallel, then a single "report" stage that runs anywhere.

Show solution 
pipeline {
    agent none
    stages {
        stage('Test') {
            parallel {
                stage('Linux')   { agent { label 'linux'   }; steps { sh  'make test' } }
                stage('Windows') { agent { label 'windows' }; steps { bat 'ctest'     } }
            }
        }
        stage('Report') {
            agent any
            steps { sh 'echo both test suites done' }
        }
    }
}
EX 3.2 easy Why is Freestyle inferior?

State three concrete reasons Pipeline-as-code beats Freestyle for anything bigger than a toy.

Show solution
  1. Config lives in git: reviewable, versioned, rollbackable.
  2. Fails atomically with the code: a commit's pipeline is the pipeline that built that commit.
  3. Testable: you can dry-run the Jenkinsfile with the replay feature or a linter.

Other valid reasons: better parallelism primitives, shared libraries for reuse, native stage visualisation, diff-able changes in PRs.

EX 3.3 medium Diagnose a stuck job

A colleague reports a job that shows "pending — (waiting for executor)" and never starts. What are the first three things you check?

Show solution
  1. Label match. Does the job's agent { label '...' } match any online agent? Go to Manage Jenkins → Nodes and verify.
  2. Executor saturation. Are all matching agents' executors busy? Look at node status.
  3. Agent health. Is the agent "offline" or "disconnected"? Often a JVM crash or network issue on the agent itself.

Other causes: quiet period after plugin upgrade; restricted build windows; resource restrictions from the Lockable Resources plugin.

EX 3.4 medium Plugins audit

On your local Jenkins, go to Manage Jenkins → Plugins → Installed. How many are installed? How many have updates available? How many have critical CVEs warnings? Document three of the more surprising ones.

Show solution

Fresh install typically has 60-80 plugins from "suggested" (many are transitive). Updates and CVE advisories are checked continuously against Jenkins' advisories database. Regularly auditing this page (weekly, monthly) is part of running Jenkins responsibly.

EX 3.5 hard Ephemeral agent flow

Sketch what happens (in order) when a pipeline with agent { kubernetes { ... } } triggers: where does the work run, what creates the pod, and what tears it down?

Show solution
  1. Pipeline trigger fires on the Controller (webhook, push, schedule).
  2. The Controller evaluates the Jenkinsfile's agent directive and decides it needs a Kubernetes-backed agent.
  3. The Kubernetes plugin on the Controller calls the K8s API and POST /api/v1/namespaces/jenkins/pods with a pod template.
  4. Kubernetes schedules the pod onto a worker node.
  5. The pod's "jnlp" sidecar starts and connects back to the Controller over port 50000.
  6. Controller assigns the pipeline steps to that pod; the pod runs them.
  7. On completion, the plugin deletes the pod via the K8s API.

Net effect: each build gets a pristine environment, no shared state, autoscales with load. This is the modern default for large Jenkins shops.

Recap

  • Jenkins = long-running Java server + plugin ecosystem + Controller-Agents architecture.
  • Controller schedules & stores state; Agents run the work.
  • Freestyle jobs are legacy — write Pipeline (Jenkinsfile) instead.
  • Plugins give enormous power; they're also the primary source of upgrade pain and security issues.
  • Ephemeral agents via Docker/Kubernetes are the modern default.
  • Credentials live in Jenkins' credentials store; use withCredentials to expose them safely.
