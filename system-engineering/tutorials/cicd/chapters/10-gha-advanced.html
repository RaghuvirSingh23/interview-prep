Chapter 10 GitHub Actions — Advanced

Reusable workflows, composite actions, matrix strategies with include/exclude, environments, concurrency control, and OIDC-based cloud authentication that eliminates long-lived credentials. Plus writing your own actions.

Reusable workflows

Reusable workflows let one workflow call another. Define once, call from many repos or jobs. The called workflow lives at a normal path (.github/workflows/X.yml) and declares on: workflow_call:

yaml.github/workflows/reusable-test.yml
name: Reusable Test

on:
  workflow_call:
    inputs:
      node-version:
        type: string
        default: "20"
      run-e2e:
        type: boolean
        default: false
    secrets:
      NPM_TOKEN:
        required: false
    outputs:
      coverage:
        description: "Coverage %"
        value: ${{ jobs.test.outputs.cov }}

jobs:
  test:
    runs-on: ubuntu-latest
    outputs:
      cov: ${{ steps.cov.outputs.pct }}
    steps:
      - uses: actions/checkout@v4
      - uses: actions/setup-node@v4
        with: { node-version: ${{ inputs.node-version }} }
      - run: npm ci
      - run: npm test
      - id: cov
        run: echo "pct=$(cat coverage/summary.txt)" >> $GITHUB_OUTPUT
      - if: ${{ inputs.run-e2e }}
        run: npm run e2e

Caller:

yaml.github/workflows/ci.yml
jobs:
  test-20:
    uses: ./.github/workflows/reusable-test.yml
    with:
      node-version: "20"
      run-e2e: true
    secrets: inherit

  # Call from another repo
  test-shared:
    uses: myorg/shared-workflows/.github/workflows/test.yml@v1
    with:
      node-version: "18"
    secrets:
      NPM_TOKEN: ${{ secrets.NPM_TOKEN }}

Notes:

  • Callers pass with: for inputs, secrets: (or secrets: inherit).
  • Reference a reusable workflow in another repo with owner/repo/.github/workflows/name.yml@ref.
  • Up to 4 levels of nesting; you can call a workflow that calls another.
  • Reusable workflows run as their own jobs — separate runners, separate logs.

Composite actions

Reusable workflows wrap jobs. Composite actions wrap steps. Define at .github/actions/<name>/action.yml:

yaml.github/actions/setup-pipeline/action.yml
name: "Setup pipeline"
description: "Checkout, install Node, cache, install deps"
inputs:
  node-version:
    description: "Node major"
    default: "20"
runs:
  using: "composite"
  steps:
    - uses: actions/checkout@v4
    - uses: actions/setup-node@v4
      with:
        node-version: ${{ inputs.node-version }}
        cache: npm
    - run: npm ci
      shell: bash

Use inline in a job's steps:

steps:
  - uses: ./.github/actions/setup-pipeline
    with: { node-version: "20" }
  - run: npm test

Shared across a single repo trivially; across repos, publish the action in its own repo. Composite actions are the go-to for "several steps I always do together".

Reusable workflow vs composite action — how to choose
  • Need to define entire jobs (with runs-on, concurrency, matrix)? → Reusable workflow.
  • Need a block of steps inside an existing job? → Composite action.
  • Need conditional logic in input handling? Either — composite is usually lighter.

Matrix — include, exclude, failures

jobs:
  test:
    strategy:
      fail-fast: false
      max-parallel: 4
      matrix:
        os:   [ubuntu-latest, macos-latest]
        node: [18, 20, 22]
        include:
          - os: windows-latest
            node: 20
            special: "add to matrix"
        exclude:
          - os: macos-latest
            node: 18

    runs-on: ${{ matrix.os }}
    steps:
      - uses: actions/setup-node@v4
        with: { node-version: ${{ matrix.node }} }
      - run: npm test

Walking the shape:

  • Base: 2 × 3 = 6 combinations.
  • exclude removes the (macos, 18) pair → 5 combinations.
  • include appends 1 extra: (windows, 20) with an extra special variable → 6 total.
  • fail-fast: false lets every matrix cell run to completion; default true cancels siblings on first failure.
  • max-parallel: 4 caps concurrent matrix cells.

Concurrency — cancelling old runs

concurrency:
  group: ci-${{ github.ref }}
  cancel-in-progress: true

Every run with the same group string competes for a single "slot". If cancel-in-progress is true, a new run cancels the old one. Perfect for PR workflows: push twice quickly, the first run is cancelled in favour of the second.

Common patterns:

  • group: ${{ github.workflow }}-${{ github.ref }} — one run per workflow per branch.
  • group: deploy-prod — serialise all prod deploys globally, never cancel them.
  • cancel-in-progress: ${{ github.ref != 'refs/heads/main' }} — auto-cancel on PRs but queue on main.

Environments

A GitHub environment is a named deploy target with its own secrets and protection rules. Configure in Settings → Environments. Then in a job: 

jobs:
  deploy-prod:
    runs-on: ubuntu-latest
    environment:
      name: production
      url: https://example.com
    needs: [test]
    steps:
      - run: ./deploy.sh

Environment features:

  • Required reviewers — a job targeting this environment waits until a listed user clicks approve.
  • Wait timer — enforce a cooldown period.
  • Deployment branches — limit which branches can deploy (e.g. only main or release/*).
  • Environment-scoped secrets — separate prod vs staging credentials; only jobs targeting that environment can access them.

This is the primary approval mechanism in GHA. Set up production with required reviewers and you've built a gated deploy without writing any code.

OIDC to the cloud — no long-lived credentials

The old way: a long-lived AWS_ACCESS_KEY_ID + AWS_SECRET_ACCESS_KEY stored in GitHub secrets, rotated… sometimes. The token exists in multiple places; losing it is bad.

The new way: GitHub issues a short-lived OIDC token per workflow run. Your cloud trusts GitHub's OIDC issuer. The token is exchanged for cloud credentials that expire in an hour. Nothing long-lived ever touches a secret store.

AWS example

permissions:
  id-token: write      # required to get the OIDC token
  contents: read

jobs:
  deploy:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - uses: aws-actions/configure-aws-credentials@v4
        with:
          role-to-assume: arn:aws:iam::123456789012:role/github-actions-deploy
          aws-region: us-east-1
      - run: aws s3 sync dist/ s3://my-bucket --delete

You also create an IAM OIDC provider and role on AWS that trusts GitHub, scoped to specific repos/branches. Same pattern exists for GCP (Workload Identity Federation), Azure (OIDC login), and Vault.

Rule: new integrations should use OIDC. Don't store long-lived cloud keys in GitHub secrets unless no alternative exists.

Writing your own action

Three flavors — JavaScript, Docker, Composite. JavaScript is the most versatile (runs on Linux/macOS/Windows).

yamlaction.yml (JavaScript action)
name: "Greet"
description: "Prints a greeting"
inputs:
  who:
    description: "Name"
    required: true
outputs:
  greeting:
    description: "The printed greeting"
runs:
  using: "node20"
  main: "dist/index.js"
jssrc/index.js
const core = require('@actions/core');
try {
  const who = core.getInput('who');
  const msg = `Hello, ${who}!`;
  console.log(msg);
  core.setOutput('greeting', msg);
} catch (e) {
  core.setFailed(e.message);
}

You bundle src/ + node_modules/ into dist/index.js with @vercel/ncc; commit the bundle; tag a release. Consumers do uses: myorg/greet-action@v1.

For a one-off team tool, prefer a composite action — no bundling dance.

Dynamic matrix from previous job

Sometimes the matrix isn't known at author time — you want it computed per run:

jobs:
  find-packages:
    runs-on: ubuntu-latest
    outputs:
      matrix: ${{ steps.set.outputs.matrix }}
    steps:
      - uses: actions/checkout@v4
      - id: set
        run: |
          echo 'matrix={"pkg":["alpha","beta","gamma"]}' >> "$GITHUB_OUTPUT"

  build:
    needs: find-packages
    runs-on: ubuntu-latest
    strategy:
      fail-fast: false
      matrix: ${{ fromJSON(needs.find-packages.outputs.matrix) }}
    steps:
      - run: echo "Building ${{ matrix.pkg }}"

The first job computes a JSON matrix. fromJSON parses it in the second job's strategy.matrix. Powerful for monorepos.

Service containers

jobs:
  integration:
    runs-on: ubuntu-latest
    services:
      postgres:
        image: postgres:16
        env:
          POSTGRES_PASSWORD: test
        ports: ['5432:5432']
        options: >-
          --health-cmd "pg_isready"
          --health-interval 10s
          --health-timeout 5s
          --health-retries 5
    steps:
      - uses: actions/checkout@v4
      - run: |
          export DATABASE_URL="postgres://postgres:test@localhost:5432/postgres"
          pip install -r requirements.txt
          pytest tests/integration/

Services run as Docker containers alongside the job. options: lets you pass Docker-run flags; health-check settings let GHA wait for the service to be ready before the job starts.

Artifacts v4 — scoped & immutable

Upload-artifact v4 changed semantics from v3:

  • Artifacts are now immutable — you cannot upload to the same artifact name twice.
  • Each upload becomes a distinct artifact. Merge with actions/upload-artifact/merge@v4 if needed.
  • Up to 10× faster uploads/downloads.

If you had a pattern like "each matrix cell appends to the same artifact", refactor: upload a per-cell artifact, then merge in a final job.

Job summaries

- name: Report
  run: |
    {
      echo "## Test results"
      echo ""
      echo "| Suite | Passed | Failed |"
      echo "|-------|--------|--------|"
      echo "| unit  | 120    | 0      |"
      echo "| integ | 45     | 2      |"
    } >> "$GITHUB_STEP_SUMMARY"

$GITHUB_STEP_SUMMARY is a file that supports Markdown; contents show up as a rich summary on the job page. Underrated feature — ship human-readable reports for free.

Self-hosted runners done right

Quick setup: Repo → Settings → Actions → Runners → "New self-hosted runner". GitHub gives a script. Run it on your machine:

$ mkdir actions-runner && cd actions-runner
$ curl -o actions-runner-linux-x64-2.317.0.tar.gz -L \
     https://github.com/actions/runner/releases/download/v2.317.0/actions-runner-linux-x64-2.317.0.tar.gz
$ tar xzf actions-runner-linux-x64-2.317.0.tar.gz
$ ./config.sh --url https://github.com/owner/repo --token ABCD
$ ./run.sh

For production, you want:

  • Ephemeral runners. One job → one VM → destroyed. Use actions-runner-controller on Kubernetes.
  • Auto-scaling. Spin up on queue depth, down when idle. ARC supports this natively.
  • Fleet isolation. Don't run untrusted PRs on self-hosted runners that touch your infra — fork PRs get limited secrets but a malicious script can still abuse compute.
Never use persistent self-hosted runners for public repos

A PR from a fork can introduce malicious code. If your runner is persistent (not ephemeral), that code can poison subsequent jobs — stealing secrets from other runs, installing backdoors, etc. Use ephemeral runners (ARC, Philips' actions-runner-controller, or GitHub's own) for anything public-facing.

Local testing with act

$ brew install act        # or: curl -fsSL https://raw.githubusercontent.com/nektos/act/master/install.sh | bash
$ act pull_request        # simulate a pull_request event locally
$ act -j test             # run only the "test" job
$ act -l                  # list jobs

act runs your workflows in Docker locally. Not pixel-perfect (services/actions don't all work identically) but saves dozens of "commit-push-wait" cycles when authoring a workflow.

Hands-on: a production-grade pipeline

Hands-on · reusable + environments + OIDC

Composite action:

yaml.github/actions/py-setup/action.yml
name: Python setup
inputs:
  python-version:
    default: "3.11"
runs:
  using: composite
  steps:
    - uses: actions/setup-python@v5
      with:
        python-version: ${{ inputs.python-version }}
        cache: pip
    - run: pip install -r requirements.txt
      shell: bash

Reusable workflow:

yaml.github/workflows/_test.yml
on:
  workflow_call:
    inputs:
      python-version: { type: string, required: true }

jobs:
  run-tests:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - uses: ./.github/actions/py-setup
        with: { python-version: ${{ inputs.python-version }} }
      - run: pytest --junitxml=report.xml
      - if: always()
        uses: actions/upload-artifact@v4
        with:
          name: report-${{ inputs.python-version }}
          path: report.xml

Top-level workflow:

yaml.github/workflows/ci.yml
name: CI
on:
  push: { branches: [main] }
  pull_request:

permissions:
  id-token: write
  contents: read

concurrency:
  group: ci-${{ github.ref }}
  cancel-in-progress: true

jobs:
  test-matrix:
    strategy:
      fail-fast: false
      matrix:
        python-version: ["3.10", "3.11", "3.12"]
    uses: ./.github/workflows/_test.yml
    with:
      python-version: ${{ matrix.python-version }}

  deploy-staging:
    needs: test-matrix
    if: github.ref == 'refs/heads/main'
    runs-on: ubuntu-latest
    environment: staging
    steps:
      - uses: actions/checkout@v4
      - uses: aws-actions/configure-aws-credentials@v4
        with:
          role-to-assume: ${{ vars.AWS_ROLE_ARN }}
          aws-region: us-east-1
      - run: aws s3 sync dist/ s3://staging-bucket/ --delete

Push this to a repo; configure the environments and OIDC trust in AWS. Observe how the reusable workflow shows up as separate job cards per matrix cell.

EX 10.3 medium Dynamic matrix

A job should run tests only for packages changed in the PR. Sketch the workflow: one job computes the list, next runs per-package in a matrix.

Show solution 
jobs:
  changed:
    runs-on: ubuntu-latest
    outputs:
      pkgs: ${{ steps.list.outputs.pkgs }}
    steps:
      - uses: actions/checkout@v4
        with: { fetch-depth: 0 }
      - id: list
        run: |
          changed=$(git diff --name-only origin/${{ github.base_ref }}...HEAD \
                    | grep -oE '^packages/[^/]+' | sort -u \
                    | jq -R -s 'split("\n") | map(select(length>0))')
          echo "pkgs=$changed" >> "$GITHUB_OUTPUT"

  test:
    needs: changed
    if: ${{ fromJSON(needs.changed.outputs.pkgs)[0] != null }}
    runs-on: ubuntu-latest
    strategy:
      fail-fast: false
      matrix:
        pkg: ${{ fromJSON(needs.changed.outputs.pkgs) }}
    steps:
      - uses: actions/checkout@v4
      - run: cd ${{ matrix.pkg }} && npm ci && npm test
EX 10.4 hard OIDC to AWS

Describe, in order, the pieces you need to set up OIDC-based deploy from GHA to AWS. List GitHub side, AWS side.

Show solution

AWS side:

  1. Create an IAM OIDC identity provider with URL https://token.actions.githubusercontent.com and audience sts.amazonaws.com.
  2. Create an IAM role with a trust policy restricting to specific repo:owner/repo:ref:refs/heads/main (use the sub claim).
  3. Grant that role the IAM permissions your deploy needs (S3, ECR, ECS, etc.).

GitHub side:

  1. permissions: { id-token: write, contents: read } in the workflow.
  2. Use aws-actions/configure-aws-credentials@v4 with role-to-assume: arn:….
  3. Run AWS CLI / SDK commands normally — they pick up the short-lived credentials.

Net effect: no AWS_* secrets in GitHub, credentials are per-run and expire in an hour.

EX 10.5 medium Job summaries for coverage

Write a step that reads coverage.txt and renders a Markdown table into the job summary.

Show solution 
- name: Coverage summary
  run: |
    {
      echo "## Coverage"
      echo ""
      echo '```'
      cat coverage.txt
      echo '```'
    } >> "$GITHUB_STEP_SUMMARY"

Everything written to $GITHUB_STEP_SUMMARY is rendered as Markdown on the job page. No plugin needed.

Recap

  • Reusable workflows wrap jobs; composite actions wrap steps; choose based on scope.
  • Matrix includes/excludes and fail-fast control the test grid.
  • concurrency + cancel-in-progress saves runner minutes on rapid pushes.
  • Environments give you approvals, scoped secrets, deploy branches.
  • OIDC to cloud providers eliminates long-lived credentials — use it for all new integrations.
  • Dynamic matrix via fromJSON + outputs is the monorepo escape hatch.
  • $GITHUB_STEP_SUMMARY for rich per-job Markdown reports.
  • Self-hosted runners: ephemeral, isolated, never persistent for public repos.
