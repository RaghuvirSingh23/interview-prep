Rosetta stone

The same operations, in all three. Keep this in your reference folder.

A minimal "hello"

groovyJenkins
pipeline {
    agent any
    stages {
        stage('Hello') { steps { sh 'echo hello' } }
    }
}
yamlGitLab CI
hello:
  script: [echo hello]
yamlGitHub Actions
jobs:
  hello:
    runs-on: ubuntu-latest
    steps: [{ run: echo hello }]

Matrix across Python versions

groovyJenkins
matrix {
    axes {
        axis { name 'PY'; values '3.10', '3.11', '3.12' }
    }
    stages {
        stage('test') {
            agent { docker "python:${PY}" }
            steps { sh 'pytest' }
        }
    }
}
yamlGitLab CI
test:
  image: "python:$PY"
  parallel:
    matrix:
      - PY: ["3.10", "3.11", "3.12"]
  script: [pytest]
yamlGitHub Actions
jobs:
  test:
    strategy:
      matrix:
        python: ["3.10", "3.11", "3.12"]
    runs-on: ubuntu-latest
    container: "python:${{ matrix.python }}"
    steps:
      - uses: actions/checkout@v4
      - run: pytest

Artifact between jobs

groovyJenkins
stage('build') { steps { sh 'make dist'; stash name: 'dist', includes: 'dist/**' } }
stage('deploy') { steps { unstash 'dist'; sh './deploy.sh dist/' } }
yamlGitLab CI
build:  { script: [make dist], artifacts: { paths: [dist/] } }
deploy: { needs: [build], script: ['./deploy.sh dist/'] }
yamlGitHub Actions
jobs:
  build:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - run: make dist
      - uses: actions/upload-artifact@v4
        with: { name: dist, path: dist/ }
  deploy:
    needs: build
    runs-on: ubuntu-latest
    steps:
      - uses: actions/download-artifact@v4
        with: { name: dist, path: dist/ }
      - run: ./deploy.sh dist/

Run only on main

groovyJenkins
stage('deploy') { when { branch 'main' }; steps { sh './deploy.sh' } }
yamlGitLab CI
deploy:
  script: ['./deploy.sh']
  rules:
    - if: $CI_COMMIT_BRANCH == $CI_DEFAULT_BRANCH
yamlGitHub Actions
deploy:
  if: github.ref == 'refs/heads/main'
  steps: [{ run: ./deploy.sh }]

Using a secret

groovyJenkins
withCredentials([string(credentialsId: 'gh', variable: 'GH_TOKEN')]) {
    sh 'curl -H "Authorization: token $GH_TOKEN" https://api.github.com/user'
}
yamlGitLab CI
deploy:
  script:
    - curl -H "Authorization: token $GH_TOKEN" https://api.github.com/user
  # GH_TOKEN comes from Settings → CI/CD → Variables (masked)
yamlGitHub Actions
- env: { GH_TOKEN: "${{ secrets.GH_TOKEN }}" }
  run: curl -H "Authorization: token $GH_TOKEN" https://api.github.com/user

Performance characteristics

Startup time per job

  • Jenkins — fast once controller is warm and agent is available; seconds. Agent startup (if ephemeral) adds 5–30s.
  • GitLab CI — SaaS runners boot fresh per job; ~10–30s overhead. Self-hosted cached runners can be ~5s.
  • GitHub Actions — hosted runners boot in ~15–30s. Self-hosted can be ~1s for warm runners; longer for ephemeral VMs.

Scheduling latency (time from trigger to first job running)

  • Jenkins: seconds if controller not overloaded.
  • GitLab SaaS: 5–30s typically; can spike under load.
  • GHA: 5–60s typically; spikes during peak hours.

Throughput (jobs/hour)

All three scale well with more runners. Bottleneck is usually per-job overhead × concurrency limits. Buy more runner capacity if queueing.

Cost

Rough guidance — always check current pricing, this moves.

  • Jenkins. Only infra cost. For small teams: one EC2 t3.medium controller + on-demand K8s agents ≈ $50–200/month. For large teams: dedicated ops headcount. Indirect cost of ops is usually the dominant cost.
  • GitLab CI SaaS. Free tier: 400 CI/CD minutes/month on shared runners. Premium: 10,000 min. Self-hosted runners bypass the limit entirely — you pay for your own infra.
  • GitHub Actions SaaS. Free tier: 2,000 Linux minutes/month for private repos, unlimited for public. Beyond that: ~$0.008/min Linux, ~$0.08/min macOS, ~$0.016/min Windows. Macs are expensive.

Heuristic: if you're paying for SaaS CI minutes and spending >$500/month, evaluate self-hosted or larger-tier runners. If you're paying >$5000/month, self-hosted on spot instances is almost always cheaper.

Honest trade-offs

Why you'd still pick Jenkins in 2026

  • Your code isn't on GitHub or GitLab.
  • You need air-gapped CI (classified environments, financial networks, OT/ICS).
  • You have custom hardware: mainframes, FPGAs, embedded test rigs.
  • You need to integrate with ancient auth (older LDAP, RADIUS, SAML IdPs).
  • You have genuine scale — 1000+ concurrent builds, tens of thousands of jobs.
  • Your org already runs Jenkins competently and the cost of switching > benefit.

Why you'd still pick GitLab CI

  • Your code is on GitLab (duh).
  • You like monolithic tooling: issues, wikis, code, CI, container registry, pages, all in one pane.
  • You self-host everything and want a single product.
  • You need advanced DAG patterns (dynamic child pipelines are especially nice).
  • DevSecOps: the built-in scanning templates are very competitive.

Why you'd still pick GHA

  • Your code is on GitHub (duh).
  • You want the largest third-party ecosystem.
  • You like the PR-centric UX (inline annotations, required checks).
  • You want near-zero operational overhead.
  • You're happy being coupled to GitHub's Issues/PR model.

A decision tree

Where is your code?
├── GitHub → GitHub Actions (default choice)
│           ├── need private-network access? → add self-hosted runners
│           └── need advanced org policies? → GitHub Enterprise
│
├── GitLab → GitLab CI (default choice)
│           ├── need built-in security scanning out-of-box? → GitLab
│           └── need self-hosted? → easy migration, same config
│
├── Bitbucket → Bitbucket Pipelines (not covered here) OR Jenkins
│
└── Self-hosted Git / SVN / monorepo with weird rules
    ├── resources for ops team? → Jenkins
    └── small team? → consider Woodpecker, Drone, or migrate repos

Do any of the following apply?
- Air-gapped / classified network
- Bizarre compliance (FedRAMP High, HIPAA + specific auditors)
- Must integrate with on-prem tools (JIRA DC, Artifactory, etc.)
→ Jenkins anyway.

Is your team < 10 people with < 20 repos?
→ SaaS CI (GHA or GitLab). Never run your own CI at this size.

Many teams use more than one

Realistic mixed setups:

  • GHA for app CI, Jenkins for platform builds. App teams use GHA because they live on GitHub. Platform team runs Jenkins because they need on-prem integrations.
  • GitLab CI for builds, Argo CD for deploys. GitLab produces artifacts; Argo CD pulls them into K8s.
  • GHA for CI, Buildkite/CircleCI for the heavy stuff. Free GHA runs most jobs; paid specialty CI runs the expensive integration tests on beefier hardware.

Don't be dogmatic — match tools to use cases.

Migration patterns

Switching CI tools is a multi-week project. Rough playbook:

  1. Inventory. List every job, trigger, secret, and deploy target. Document the current pipeline graph.
  2. Translate simple jobs first. Pick five small repos; migrate. Learn idioms.
  3. Run in parallel. Point the new tool at the same repos. Keep the old pipeline green for months.
  4. Feature parity. Ensure approvals, notifications, artifact retention, and dashboards exist in the new tool.
  5. Flip the switch. Make the new tool the required check on PRs; make the old tool optional.
  6. Decommission. After a cooling-off period, turn off the old CI. Archive config for auditors.

EX 12.2 medium Pick a tool, defend it

You work at a 50-person startup using GitHub, shipping a web app to AWS. Pick a CI tool. Defend it in 5 bullet points.

Show solution

Default answer: GitHub Actions.

  • Zero additional infrastructure to run — free tier covers most jobs.
  • Native PR integration and required checks.
  • Marketplace covers almost every AWS integration; aws-actions/configure-aws-credentials + OIDC gets you to production securely without stored secrets.
  • At 50 people, ops time is your constraint; SaaS is cheaper than running Jenkins for us.
  • Migration path later (if we outgrow): self-hosted runners, reusable workflows, then whatever comes next.

Different answers are defensible. If the team already has deep Jenkins expertise, sticking with it is reasonable.

EX 12.3 hard Cost model

Your team runs 200 pipelines/day, average 12 minutes each, 60% Linux, 30% macOS, 10% Windows. Estimate monthly cost on (a) GHA SaaS, (b) GitLab SaaS, (c) self-hosted Jenkins on AWS.

Show solution

Total minutes/month: 200 × 12 × 30 = 72,000 min. Breakdown: 43,200 Linux, 21,600 macOS, 7,200 Windows.

GHA SaaS (approx — verify current pricing):

  • Linux: 43,200 × $0.008 = $346
  • macOS: 21,600 × $0.08 = $1,728
  • Windows: 7,200 × $0.016 = $115
  • Minus 2,000 included = some discount
  • Rough total: ~$2,100/month

GitLab SaaS: similar order of magnitude; macOS via hosted mac runners is pricier.

Self-hosted Jenkins on AWS:

  • Controller: 1 × t3.medium ≈ $30/month
  • Linux workers: 2 × c5.xlarge on-demand running ~30% utilised ≈ $250/month, or spot at ~$100
  • macOS: specialty mac1.metal or build farm; much pricier per host but potentially cheap per minute at high utilisation. Or skip macOS altogether and use GHA just for those jobs.
  • Ops: people cost. Often 0.1–0.5 FTE — the actual dominant cost.
  • Rough infra: ~$1,500/month, plus ops time.

Conclusion: at this volume, self-hosted isn't obviously cheaper once you include ops time. At 10× the volume, it is.

Recap

  • Feature matrix: broadly similar capabilities; huge differences in language, ecosystem, ops burden.
  • Same concepts translate almost line-by-line between the three — the Rosetta stone is a useful lookup.
  • Cost: SaaS CI wins at small-to-medium scale; self-hosted wins at large scale if you have ops capacity.
  • Ops burden: Jenkins is a job; SaaS CI is near-free.
  • Decision tree: follow the repo home; escape hatch to Jenkins only when you need its flexibility.
  • Many orgs use more than one — don't force a single tool to cover every use case.
