Chapter 02 Pipeline Thinking

A tool-agnostic chapter. We'll cover the six concepts that every CI/CD system implements — jobs, stages, artifacts, caches, triggers, environments — and the reasoning behind each. These ideas transfer between tools and between decades.

Jobs: the unit of work

A job is one self-contained unit of work: a sequence of shell-ish commands run in one environment, which succeeds or fails as a whole. Think of it as a tiny shell script with inputs, outputs, and a pass/fail result.

Properties of a well-scoped job:

  • One responsibility. "Run unit tests." Not "run unit tests, then build the docker image, then deploy."
  • Deterministic result. Same inputs, same result, every time.
  • Parallel-safe. Nothing in the job assumes another job ran first, except via explicit dependencies.
  • Reasonable runtime. Under 10 minutes for "fast-feedback" jobs. If it's longer, split it.

Every tool has a name for this:

  • Jenkins: a Stage (loosely) or a Freestyle job (old way).
  • GitLab CI: a job.
  • GitHub Actions: a job (containing steps).

Stages: grouping for order

A stage is a set of jobs that logically belong together and run (conceptually) in parallel. Stages run sequentially: every job in stage N must finish before any job in stage N+1 starts. 

stage: lint  ─────── lint-js, lint-py, lint-shell      (parallel)
stage: test  ─────── test-unit, test-integration       (parallel, after lint)
stage: build ─────── build-image, build-docs           (parallel, after test)
stage: deploy ────── deploy-staging                     (sequential, after build)

This is the classic "stages" model. It's simple, easy to understand, and conservative: jobs in stage N never start early, even if all their real prerequisites finished.

That conservatism is also the problem. If lint-js finishes in 10 seconds and lint-py takes 5 minutes, test-unit waits the full 5 minutes before starting — even if it doesn't actually depend on lint-py.

Hence the modern DAG model: jobs declare their specific prerequisites, and a job can start as soon as its own prereqs are done — not when the whole previous stage is done. GitLab calls this needs:, GHA calls it needs:, Jenkins has parallel blocks and Scripted pipelines.

Artifacts: passing files between jobs

Each job usually runs in a fresh workspace — an empty directory with the repo checked out. If job A builds dist/ and job B needs dist/ to deploy, B needs to download what A produced. That's an artifact.

Two kinds of passing:

  1. In-pipeline: job A uploads, job B downloads, artifact lives as long as the pipeline run.
  2. Cross-pipeline: job A publishes to a persistent store (a container registry, npm, S3, an artifact manager like Nexus/Artifactory). Subsequent runs — including future pipelines — consume from that store.

Artifacts have two rules of hygiene:

  • Small and specific. Uploading node_modules/ as an artifact is almost never right — use a cache.
  • Stored briefly. If you persist every dist/ from every PR forever, you'll fill a TB a month. Every tool has retention policies — configure them.

Artifact syntax snapshot

groovyJenkins — archive and retrieve
// producer
archiveArtifacts artifacts: 'dist/**/*', fingerprint: true

// consumer (within same pipeline, using stash/unstash)
stash name: 'build', includes: 'dist/**'
// … in a later stage:
unstash 'build'
yamlGitLab CI — artifacts
build:
  script: make dist
  artifacts:
    paths: [dist/]
    expire_in: 7 days

deploy:
  needs: [build]      # automatically downloads build's artifacts
  script: ./deploy.sh dist/
yamlGitHub Actions — actions/upload-artifact
jobs:
  build:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - run: make dist
      - uses: actions/upload-artifact@v4
        with:
          name: dist
          path: dist/

  deploy:
    needs: build
    runs-on: ubuntu-latest
    steps:
      - uses: actions/download-artifact@v4
        with: { name: dist, path: dist/ }
      - run: ./deploy.sh dist/

Caches: speeding up repeated work

A cache is also a file store — but with different semantics: it's best-effort, it doesn't need to be present for the job to succeed, and it persists across pipeline runs specifically to avoid redownloading/rebuilding.

Classic cache targets:

  • ~/.npm, ~/.yarn/cache, node_modules/ for Node.
  • ~/.m2 for Maven, ~/.gradle/caches for Gradle.
  • ~/.cache/pip for Python.
  • ~/.cargo/registry, target/ for Rust.
  • Docker layer cache for image builds.

Cache keys typically include a hash of the lockfile:

yamlGitHub Actions — cache
- uses: actions/cache@v4
  with:
    path: ~/.npm
    key:  npm-${{ hashFiles('**/package-lock.json') }}
    restore-keys: |
      npm-

The restore-keys fallback lets a partial match land a slightly-stale cache rather than no cache.

Cache vs artifact — don't confuse them
  • Artifact: required for downstream jobs; persisted with retention; pipeline-run-scoped.
  • Cache: optional speed-up; global; key-scoped.

Symptoms of confusion: "why is my build non-deterministic?" (you cached compiled outputs); "why did my deploy fail?" (you treated an artifact as a cache).

Triggers: what kicks off a run

Most common triggers:

TriggerExample
push Any push to any branch, or a specific branch.
pull_request / MROpen, sync, or close a PR/MR.
schedule Cron: run nightly at 03:00 UTC.
manual Button click in the UI or CLI.
tag Push of a tag matching a pattern (e.g. v*).
upstream Another pipeline finished — trigger downstream.
API A webhook or CLI call.

Well-designed pipelines do different things for different triggers. A push to a feature branch runs lint + test; a push to main also runs build + publish; a tag push also deploys to prod. Combining triggers with if/rules/when conditions is how you express this.

Environments: where deploys go

An environment is a name for a deploy target: staging, prod, preview-PR-123. Each is associated with:

  • A URL, often.
  • A set of secrets (different for staging vs prod).
  • Deploy history and rollback options.
  • Access control: who can deploy here?

All three tools support environments, though the terminology differs. Jenkins represents them loosely (as differentiated credentials, or via plugins). GitLab and GHA have first-class environment: syntax with built-in history views.

Parallelism strategies

Fan-out, fan-in

Most common: one job produces an artifact, then N jobs consume it in parallel, then a final job aggregates results.

Matrix

"Run this job once for every combination of these variables." Used for test-across-versions (Node 16/18/20; Python 3.9/3.10/3.11; Ubuntu/macOS/Windows):

yamlGitHub Actions — matrix
jobs:
  test:
    strategy:
      matrix:
        os:   [ubuntu-latest, macos-latest, windows-latest]
        node: [18, 20, 22]
    runs-on: ${{ matrix.os }}
    steps:
      - uses: actions/setup-node@v4
        with: { node-version: ${{ matrix.node }} }
      - run: npm ci && npm test

That's 9 jobs running in parallel. GitLab has parallel:matrix:; Jenkins has matrix { axes { ... } } in Declarative.

Sharding

Break a huge test suite into N chunks, run N jobs that each take 1/N of the tests. Most test runners have built-in sharding (jest --shard=1/4, pytest-xdist, mocha-parallel-tests).

Pipelines as graphs (again)

The "stages" metaphor is a simplified graph — every job in stage N depends on every job in stage N-1. You get back clarity for this cost:

Stages view (simple):

 ┌─ lint-js     ┐   ┌─ test-unit  ┐
 ├─ lint-py     ┤→→→├─ test-integ ┤→→→ build → deploy
 └─ lint-shell  ┘   └─ test-db    ┘

DAG view (true):

  lint-js ─────┐
  lint-py ─────┼──┬── test-unit ─────────── build ── deploy
  lint-shell ──┘  ├── test-integ ──────────/
                  └── test-db  (only needs lint-py) ┘

In DAG mode, test-unit can start after all the lint jobs it actually depends on (none, really — tests don't care whether the JS linter is happy). Real-world pipelines shave significant wall-clock time by modelling dependencies truthfully.

Pipeline anti-patterns

  • The monolithic job. One 20-minute job that does everything. Fails? You re-run everything. Split into stages.
  • The sleep-based sync. "Wait 60 seconds for the deploy to finish" — use real health checks.
  • The secret in logs. echo $DB_PASSWORD. Happens more than you'd think.
  • The cache that hides breakage. Your cache is warm, builds pass. A fresh clone breaks. Run a weekly "fresh-cache" build.
  • The phantom success. A job "passes" because its failure is silently ignored. || true at the end of a bash line is the usual cause.
  • The manual step disguised as automation. "The pipeline deploys, but first someone has to SSH in and…" — automate it or it doesn't count.
  • The unreviewable YAML. A 2000-line .gitlab-ci.yml. Use include:, reusable workflows, or shared libraries.

Exercises

EX 2.1 easy Draw the graph

A team describes their pipeline: "lint, then unit tests, then build the docker image and also run integration tests (which need the built image). Then push the image. If it's main, also deploy to staging." Draw it as a DAG.

Show solution 
  lint → test-unit → build-image ─┬─→ test-integ ─┐
                                  │                ├→ push-image ─→ deploy-staging (if main)
                                  └────────────────┘

Key subtlety: integration tests need the built image, but the push can happen only after integ passes. A naïve stage-based model would run test-integ in parallel with push-image — wrong, because you'd publish images that later fail integ tests.

EX 2.2 medium Artifact or cache?

Classify each as artifact or cache:

  1. dist/app.tar.gz produced by build, consumed by deploy.
  2. ~/.npm reused between runs to avoid re-downloading.
  3. A test coverage XML report, uploaded so the UI can show it.
  4. A pre-compiled Rust target/ directory reused to speed compiles.
  5. The final SBOM (software bill of materials) published with the release.
Show solution
  • (a) artifact — deploy needs it.
  • (b) cache — optional speed-up.
  • (c) artifact — the UI is a consumer.
  • (d) cache — rebuilding from scratch is correct, just slow.
  • (e) artifact — shipped with the release, persisted long-term.
EX 2.3 medium Pick the triggers

You're designing a pipeline. What triggers should cause: (a) the full build with tests to run? (b) a deploy to staging? (c) a deploy to prod?

Show solution

A sensible default:

  • Full build + tests: every push to any branch, and every PR open/sync. Also nightly via schedule.
  • Deploy to staging: successful build on the main branch.
  • Deploy to prod: push of a tag matching v*, OR a manual button (humans still pick). Never automatic on main.

This is the Continuous Delivery flavor. Continuous Deployment would auto-deploy to prod on successful main push — rare in practice without robust rollback.

EX 2.4 hard Anti-pattern audit

For a real pipeline you have access to, identify at least one of the seven anti-patterns listed above. Propose a fix.

Show solution

No "right" answer — but very common real finds:

  • A sleep 30 before a curl-based health check. Replace with a retry loop that polls until healthy.
  • A 1200-line YAML without any include:. Extract common jobs.
  • A || true at the end of a flaky test. Either fix the flake or quarantine it, don't hide it.
EX 2.5 medium Matrix choice

You maintain a Python library supporting Python 3.9–3.12 on Ubuntu, macOS, and Windows. How many jobs does a full matrix produce? How many do you actually need to ship safely? What heuristics could you use to trim?

Show solution

Full matrix: 4 × 3 = 12 jobs. You probably don't need all 12 on every PR:

  • On PR: minimum + maximum Python × only Ubuntu = 2 jobs (fast feedback).
  • On main branch: full 12.
  • Nightly: full 12 + oldest-supported dependencies pinned.

Every tool supports conditional matrices via rules/if. This is often the single biggest cost lever on CI spend.

Recap

  • Job = unit of work. Stage = group of jobs running in parallel; stages sequence. DAG = truer model.
  • Artifacts carry required files between jobs; caches are best-effort speed-ups. Don't confuse them.
  • Triggers: push, PR, schedule, manual, tag, upstream, API. Different triggers → different pipelines.
  • Environments name deploy targets; they pair with secrets and access control.
  • Parallelism comes in three flavors: fan-out, matrix, sharding.
  • The seven anti-patterns will bite every pipeline eventually. Audit yours quarterly.
