Chapter 09 GitHub Actions — Fundamentals

GitHub Actions (GHA) was the last of the three big tools to arrive (2019) and had the advantage of learning from everyone else's mistakes. Its defining feature is the Marketplace — a huge ecosystem of pre-built "actions" you compose into workflows. This chapter gets you from "empty repo" to "green check mark".

Architecture

  ┌─────────────────────────────────────────┐
  │            GitHub.com                   │
  │  - stores repo & workflows              │
  │  - schedules workflow runs              │
  │  - stores secrets, artifacts, caches    │
  │  - shows results on PRs & commits       │
  └───────────────┬─────────────────────────┘
                  │
          ┌───────┴────────┬───────────────┐
          │                │               │
    [GitHub-hosted     [GitHub-hosted  [Self-hosted
     ubuntu-latest]     macos-latest]   runner]
      ephemeral VM      ephemeral VM   your machine
      ~2 CPU / 7GB      ~3 CPU         whatever you give

GitHub-hosted runners are ephemeral VMs: fresh for every job, torn down after. They come in Linux, Windows, and macOS flavors with pre-installed toolchains. Self-hosted runners are machines you run that poll GitHub for work — use them for private networks, special hardware, or cost control on heavy pipelines.

Files, not config

Your CI lives in .github/workflows/*.yml. Any file in that directory is a separate workflow; you can have many. GitHub reads them, reacts to the on: triggers, and runs them.

yaml.github/workflows/ci.yml
name: CI
on:
  push:
    branches: [main]
  pull_request:

jobs:
  test:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - uses: actions/setup-python@v5
        with:
          python-version: "3.11"
      - run: pip install -r requirements.txt
      - run: pytest

Push this to a repo. Go to the Actions tab. Your workflow runs on every push to main and every PR.

The four concepts

LevelWhat
WorkflowOne YAML file in .github/workflows/. Has triggers and jobs.
JobA set of steps run on a single runner. Jobs can parallelise.
StepA single unit: either run: <shell> or uses: <action>.
ActionReusable step defined elsewhere — in a GitHub repo or on the Marketplace.

The GHA model is fundamentally: a workflow contains jobs, each job has steps, and a step is either inline shell or a reusable action. Actions are the primary reuse mechanism — unlike GitLab where you include YAML, in GHA you uses: an action.

Actions — the key concept

An action is a reusable unit distributed as a git repository. Three kinds:

  • JavaScript actions — a node program run directly on the runner. Fast; required for cross-platform (Linux/Windows/macOS).
  • Docker container actions — a Docker image; the runner pulls and runs it. Linux-only.
  • Composite actions — a bundle of steps defined in an action.yml. Run as if their contents were inlined.

Reference an action with uses::

- uses: actions/checkout@v4                 # official
- uses: actions/setup-node@v4               # official
- uses: docker/build-push-action@v5         # third-party
- uses: ./my-local-action                   # local (in this repo)
- uses: myorg/my-action@v1                  # private action in myorg
- uses: actions/setup-python@a8b72        # pinned to commit SHA (security)
Pin actions by SHA, not tag

Tags are mutable. An attacker who compromises an action's repository can move v4 to a malicious commit. For untrusted or third-party actions, pin to a full commit SHA: uses: tj-actions/changed-files@a1b2c3…. Dependabot can keep these pins updated via PRs you review.

Triggers (on:)

on:
  push:
    branches: [main, 'release/**']
    paths:    ['src/**', 'Dockerfile']
    tags:     ['v*']

  pull_request:
    branches: [main]
    types:    [opened, synchronize, reopened]

  schedule:
    - cron: '0 2 * * *'              # 02:00 UTC daily

  workflow_dispatch:                 # manual "Run workflow" button
    inputs:
      version:
        description: 'Version to deploy'
        required: true
        type: string
      env:
        type: choice
        options: [staging, production]

  repository_dispatch:               # external API trigger
    types: [deploy-request]

  workflow_run:                      # after another workflow finishes
    workflows: ["CI"]
    types: [completed]
    branches: [main]

Some triggers less obvious:

  • workflow_dispatch — manual with inputs, shows a button in the Actions UI.
  • workflow_call — lets other workflows call this one (Chapter 10's reusable workflows).
  • repository_dispatch — trigger via GitHub's REST API; useful for external webhooks.
  • workflow_run — chain workflow A after workflow B.

Runners

Pick with runs-on::

jobs:
  linux:   { runs-on: ubuntu-latest,  ... }
  macos:   { runs-on: macos-latest,   ... }
  win:     { runs-on: windows-latest, ... }
  selfhost: { runs-on: [self-hosted, linux, x64, gpu], ... }
  larger:  { runs-on: ubuntu-latest-8-cores, ... }      # paid larger runners

GitHub-hosted runner images come with heaps of pre-installed tools: git, Docker, Node (multiple versions), Python, Java, Go, .NET, recent Chrome/Firefox, jq, awk, tar, gzip, etc. The actions/runner-images repo documents the full list per image. You can use setup-* actions to pin specific tool versions, but baseline works for most projects out of the box.

Steps and their shapes

A run: step

- name: Install deps
  run: |
    pip install -r requirements.txt
    pip install -e .
  working-directory: ./backend
  env:
    PIP_CACHE_DIR: ~/.cache/pip
  shell: bash                    # 'pwsh' on windows-latest by default
  if: runner.os == 'Linux'
  timeout-minutes: 5
  continue-on-error: false
  id: install-deps

A uses: step

- name: Setup Python
  uses: actions/setup-python@v5
  with:
    python-version: "3.11"
    cache: pip
  id: py

Every step optionally has:

  • name: — shown in logs. Strongly recommended.
  • id: — so later steps can refer to ${{ steps.ID.outputs.* }}.
  • if: — conditional (if: always(), if: failure(), if: success(), if: cancelled(), or any expression).
  • env: — env vars for this step.
  • working-directory:, shell:, timeout-minutes:, continue-on-error:.

Expressions and contexts

GHA has a mini expression language: ${{ … }}.

- run: echo "branch=${{ github.ref_name }}"
- if:  ${{ github.event_name == 'pull_request' }}
  run: echo "It's a PR"

- uses: actions/setup-node@v4
  with:
    node-version: ${{ matrix.node }}

Available contexts (objects the expression can access):

ContextContains
githubEvent payload, actor, repository, refs, SHA, workflow metadata
envEnv vars set at workflow/job/step level
varsRepo/org-level variables set in Settings
secretsSecret names (only usable as ${{ secrets.X }})
jobContainer, services, status
stepsOutputs and conclusions of previous steps
runnerOS, arch, tool cache, temp dir
needsOutputs of jobs this job depends on
inputsInputs to a reusable / dispatch workflow
matrixCurrent matrix values
strategyStrategy context (fail-fast, job-index)

Examples:

run: echo "${{ github.repository }} @ ${{ github.sha }}"
run: echo "Triggered by ${{ github.actor }}"
run: echo "Runner OS is ${{ runner.os }}"
run: echo "Matrix value: ${{ matrix.python-version }}"

Job dependencies & outputs

Default: jobs run in parallel. To sequence, use needs::

jobs:
  lint:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - run: npm run lint

  test:
    needs: lint
    runs-on: ubuntu-latest
    steps: [...]

  build:
    needs: [lint, test]
    runs-on: ubuntu-latest
    steps: [...]

Pass values between jobs via outputs:

jobs:
  version:
    runs-on: ubuntu-latest
    outputs:
      tag: ${{ steps.bump.outputs.tag }}
    steps:
      - uses: actions/checkout@v4
      - id: bump
        run: echo "tag=v$(date +%Y%m%d)" >> $GITHUB_OUTPUT

  build:
    needs: version
    runs-on: ubuntu-latest
    steps:
      - run: echo "Building ${{ needs.version.outputs.tag }}"

Step outputs use $GITHUB_OUTPUT, a special file the runner exposes. Write key=value lines; they become ${{ steps.<id>.outputs.key }}.

Artifacts & caches

Artifacts

- uses: actions/upload-artifact@v4
  with:
    name: build-output
    path: dist/
    retention-days: 14

- uses: actions/download-artifact@v4
  with:
    name: build-output
    path: dist/

Upload stores the files in GitHub's artifact store for the workflow run (up to 90 days default). Download in a later job, or even manually from the Actions UI.

Cache

- uses: actions/cache@v4
  with:
    path: ~/.npm
    key: ${{ runner.os }}-npm-${{ hashFiles('**/package-lock.json') }}
    restore-keys: |
      ${{ runner.os }}-npm-

Most setup-* actions have built-in caching (pass cache: npm to setup-node). Only hand-roll cache for non-obvious paths.

Environment variables

Three scopes, inner wins:

env:
  GLOBAL: "workflow"              # workflow-scope

jobs:
  build:
    env:
      JOB: "job-level"            # job-scope
    runs-on: ubuntu-latest
    steps:
      - env:
          STEP: "step-only"       # step-scope
        run: env | grep -E 'GLOBAL|JOB|STEP'

Setting env vars for later steps in the same job:

- id: sha
  run: echo "FULL_SHA=$(git rev-parse HEAD)" >> $GITHUB_ENV
- run: echo "SHA is $FULL_SHA"

$GITHUB_ENV is a file the runner exports into the environment of every subsequent step.

Secrets

Store at three levels: repo, environment, organisation. Reference only as ${{ secrets.X }} — never echo or log them.

- run: |
    echo "${{ secrets.NPM_TOKEN }}" > ~/.npmrc     # BAD — could leak
    npm publish
- env:
    NPM_TOKEN: ${{ secrets.NPM_TOKEN }}
  run: |
    echo "//registry.npmjs.org/:_authToken=$NPM_TOKEN" > ~/.npmrc
    npm publish

GHA masks secret values in logs if they appear verbatim — but transformations (base64 encoding, JSON-wrapping) can defeat the mask. Pass via env: and never echo directly.

GITHUB_TOKEN and permissions

Every workflow run gets a short-lived token ${{ secrets.GITHUB_TOKEN }} with permissions scoped to the triggering repo. By default it has broad read access. You should lock it down per workflow: 

permissions:
  contents: read
  pull-requests: write     # so this workflow can comment on PRs
  packages: write          # so it can push to GHCR

Set permissions: {} at workflow scope, then grant only what you need at job scope. Principle of least privilege.

Watching a run

On the Actions tab:

  • All workflows on the left.
  • Click a workflow → list of runs.
  • Click a run → per-job tabs with live logs.
  • Logs are collapsible by step; hover a timestamp to get a direct link.
  • Failed jobs show a red X; passed green tick; cancelled grey.
  • "Re-run jobs" button → re-run all, failed only, or just one.

PRs show a consolidated "Checks" tab with every workflow's status and inline annotations from failed tests.

Hands-on: a full workflow

Hands-on · real CI workflow

In any GitHub repo, add:

yaml.github/workflows/ci.yml
name: CI

on:
  push: { branches: [main] }
  pull_request:

permissions:
  contents: read

concurrency:
  group: ci-${{ github.ref }}
  cancel-in-progress: true

jobs:
  lint:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - uses: actions/setup-python@v5
        with:
          python-version: "3.11"
          cache: pip
      - run: pip install ruff
      - run: ruff check src/ tests/

  test:
    needs: lint
    runs-on: ubuntu-latest
    strategy:
      fail-fast: false
      matrix:
        python: ["3.10", "3.11", "3.12"]
    steps:
      - uses: actions/checkout@v4
      - uses: actions/setup-python@v5
        with:
          python-version: ${{ matrix.python }}
          cache: pip
      - run: pip install -r requirements.txt
      - run: pytest --junitxml=report.xml
      - uses: actions/upload-artifact@v4
        if: always()
        with:
          name: test-report-py${{ matrix.python }}
          path: report.xml

  build:
    needs: test
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - uses: actions/setup-python@v5
        with: { python-version: "3.11" }
      - run: pip install build
      - run: python -m build
      - uses: actions/upload-artifact@v4
        with:
          name: dist
          path: dist/
          retention-days: 7

Commit, push, and open the Actions tab. Study the run:

  • concurrency cancels redundant runs on the same branch — push twice quickly, watch the older run cancel.
  • matrix fans out to 3 Python versions in parallel.
  • Test reports are uploaded even on failure thanks to if: always().
  • Build only runs after all test matrix cells succeed.

Exercises

EX 9.1 easy Schedule + manual

Write on: that runs a workflow on every push to main, nightly at 03:00 UTC, and any time someone clicks "Run workflow" with an env choice.

Show solution 
on:
  push:
    branches: [main]
  schedule:
    - cron: '0 3 * * *'
  workflow_dispatch:
    inputs:
      env:
        type: choice
        options: [staging, production]
        default: staging
EX 9.2 easy Step output chain

Step 1 captures the current git short SHA into an output. Step 2 echoes it. Step 3 (in a later job) also echoes it.

Show solution 
jobs:
  a:
    runs-on: ubuntu-latest
    outputs:
      sha: ${{ steps.sha.outputs.value }}
    steps:
      - uses: actions/checkout@v4
      - id: sha
        run: echo "value=$(git rev-parse --short HEAD)" >> $GITHUB_OUTPUT
      - run: echo "from step 2: ${{ steps.sha.outputs.value }}"
  b:
    needs: a
    runs-on: ubuntu-latest
    steps:
      - run: echo "from job b: ${{ needs.a.outputs.sha }}"
EX 9.3 medium Skip on docs-only changes

Don't run the test job on pushes that only touch docs/**.

Show solution

Use paths: on the trigger:

on:
  push:
    paths-ignore: ['docs/**']
  pull_request:
    paths-ignore: ['docs/**']

Caveat: paths-ignore affects whether the workflow runs at all, not individual jobs. If you need per-job gating within a workflow that always runs, use dorny/paths-filter as a first job and key later jobs off its outputs.

EX 9.4 medium Cache a custom path

Cache a Rust target/ directory keyed by Cargo.lock hash, with Cargo.toml-based fallback.

Show solution 
- uses: actions/cache@v4
  with:
    path: |
      ~/.cargo/registry
      ~/.cargo/git
      target
    key: ${{ runner.os }}-cargo-${{ hashFiles('**/Cargo.lock') }}
    restore-keys: |
      ${{ runner.os }}-cargo-${{ hashFiles('**/Cargo.toml') }}
      ${{ runner.os }}-cargo-

In practice, use the purpose-built Swatinem/rust-cache action — same idea, better defaults.

EX 9.5 hard Permissions audit

A workflow writes to the repo (tag pushes) and comments on PRs. Set the minimum permissions: it needs.

Show solution 
permissions:
  contents: write        # for pushing tags
  pull-requests: write   # for commenting
  # everything else implicitly: none

If other workflows don't need these, start at workflow level with permissions: {} and escalate per-job for the ones that do. Minimise blast radius.

Recap

  • GHA = .github/workflows/*.yml + GitHub's scheduler + runners (hosted or self-hosted).
  • Four concepts: workflow → jobs → steps, with actions as the reusable step type.
  • Pin third-party actions to commit SHAs; let Dependabot update them.
  • Triggers cover push/PR/schedule/manual/external and workflow-to-workflow.
  • Jobs default to parallel; use needs: and outputs: for sequencing and data passing.
  • Cache and artifacts are purpose-built actions; setup-* actions include caching automatically.
  • Set permissions: explicitly — the default GITHUB_TOKEN scope is broad.
