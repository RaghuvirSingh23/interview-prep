Chapter 04 Jenkins — Pipelines

Pipelines are Jenkins' flagship feature. They live in your repo as a Jenkinsfile, they're code not config, and they come in two flavors: Scripted and Declarative. This chapter explains both, why Declarative is almost always the right default, and the Groovy essentials you'll need for the rest of the book.

Two flavors

When Jenkins introduced Pipelines in 2016, the first iteration was what we now call Scripted: raw Groovy, do whatever you want:

groovyScripted Pipeline
node('linux') {
    stage('Checkout') {
        checkout scm
    }
    stage('Build') {
        def branch = env.BRANCH_NAME
        if (branch == 'main') {
            sh 'make release'
        } else {
            sh 'make debug'
        }
    }
}

Full Groovy — loops, conditionals, functions, method calls. Wildly flexible. Also wildly easy to foot-gun: the syntax allows things that don't work, and stage visualisation in the UI is poor for dynamically-generated stages.

In 2017 Jenkins added Declarative: a constrained DSL with a fixed structure:

groovyDeclarative Pipeline
pipeline {
    agent { label 'linux' }
    stages {
        stage('Checkout') {
            steps { checkout scm }
        }
        stage('Build') {
            steps {
                script {
                    if (env.BRANCH_NAME == 'main') {
                        sh 'make release'
                    } else {
                        sh 'make debug'
                    }
                }
            }
        }
    }
}

Notice the mandatory pipeline { … } wrapper, the fixed stages → stage → steps hierarchy, and the script { … } escape hatch when you need imperative Groovy. That structure is the whole point: it's easier to read, validate, and visualise.

Which to use

Declarative by default. It covers 95% of real needs, has better errors, better UI support, and is readable by someone who doesn't know Groovy. Use Scripted only when you need dynamic stage generation at runtime — and even then, try to express it with Declarative's matrix or generated stages first.

This tutorial focuses on Declarative from here on. We'll use Scripted only where Declarative can't reach.

A Groovy crash course

Jenkinsfiles are Groovy. You don't need to master Groovy, but you'll need these basics:

// Strings: single or double quotes
def name = 'world'
def msg  = "Hello, ${name}"      // double-quoted => interpolates

// Lists
def langs = ['en', 'fr', 'de']
langs.each { l -> println l }

// Maps
def env = [NODE_VERSION: '20', PYTHON_VERSION: '3.11']

// Functions
def greet(who) {
    return "Hello, ${who}"
}

// Closures (important — used everywhere in Jenkinsfiles)
def loud  = { s -> s.toUpperCase() }
println loud('hi')

// No semicolons needed
def sum = 1 + 2

// Null-safe navigation
def branchName = env?.BRANCH_NAME ?: 'default'

Key facts:

  • Double-quoted strings interpolate ${…}. Single-quoted don't. This matters when mixing Groovy with shell (see below).
  • Closures are the primary unit of callable logic. steps { sh 'make' } is a closure passed to steps.
  • Groovy is dynamically typed. Jenkins' Pipeline Groovy has some additional safety restrictions (CPS transformation — more in Chapter 6).

Groovy vs Shell interpolation — the trap

// GOOD — Groovy interpolates the var before sh runs
def version = '1.2.3'
sh "echo Building ${version}"

// BAD — Groovy interpolates from a secret, exposing it in process listing
withCredentials([string(credentialsId: 'api-token', variable: 'API_TOKEN')]) {
    sh "curl -H 'Authorization: Bearer ${API_TOKEN}' https://api.example.com"
}

// GOOD — single quotes, shell sees $API_TOKEN as env var
withCredentials([string(credentialsId: 'api-token', variable: 'API_TOKEN')]) {
    sh 'curl -H "Authorization: Bearer $API_TOKEN" https://api.example.com'
}

Rule: when a value is secret, use single-quoted shell strings so Groovy doesn't interpolate it. The secret reaches the shell only as an environment variable, and Jenkins will mask ${variable} occurrences in logs.

Double-quoted secrets leak

sh "curl -H 'Authorization: Bearer ${TOKEN}'" lands the token as a literal string in the resulting shell command. On some Linux setups, other users can see the full command line in /proc. Jenkins' log masking catches most prints but not everything. Single-quoted shell + env var is safer.

Declarative structure, one block at a time

Every Declarative Jenkinsfile follows this shape:

pipeline {
    agent { ... }               // mandatory
    environment { ... }         // optional — env vars for the whole pipeline
    options { ... }             // optional — build-wide options
    parameters { ... }          // optional — user inputs
    triggers { ... }            // optional — cron / SCM polling
    tools { ... }               // optional — tool auto-install (JDK, Maven, ...)
    stages {
        stage('Name') {
            agent { ... }       // optional — override per-stage
            when { ... }        // optional — should this stage run?
            environment { ... } // optional — stage-scoped env
            tools { ... }       // optional — stage-scoped tools
            steps { ... }       // mandatory — what to actually do
            post { ... }        // optional — stage-scoped post-actions
        }
        stage('Parallel things') {
            parallel {          // optional — sub-stages run concurrently
                stage('A') { steps { ... } }
                stage('B') { steps { ... } }
            }
        }
    }
    post { ... }                // optional — pipeline-wide post-actions
}

Chapter 5 dives into each block. Here we give the short version:

agent

Where the pipeline (or stage) runs. agent any, agent none (require stage-level overrides), agent { label 'linux' }, agent { docker 'node:20' }, agent { kubernetes { yaml '…' } }.

environment

Set env vars for the block:

environment {
    NODE_VERSION = '20'
    DB_URL       = credentials('staging-db')
}

credentials('id') binds a Jenkins credential to an env var — with username + password-type credentials, it binds three: DB_URL, DB_URL_USR, DB_URL_PSW.

options

Build-wide options:

options {
    timeout(time: 20, unit: 'MINUTES')
    timestamps()
    buildDiscarder(logRotator(numToKeepStr: '20'))
    disableConcurrentBuilds()
    ansiColor('xterm')
}

parameters

User-supplied inputs on manual builds:

parameters {
    string(name: 'VERSION', defaultValue: '1.0.0', description: 'Version to release')
    choice(name: 'ENV', choices: ['staging', 'prod'])
    booleanParam(name: 'SKIP_TESTS', defaultValue: false)
}

Accessed in steps as ${params.VERSION}.

triggers

Automated triggers:

triggers {
    cron('H 2 * * *')          // nightly at 02:xx (H = spread load)
    pollSCM('H/15 * * * *')    // check git every 15 min
}

stages / steps

Where the work happens. We'll do them in depth next chapter.

post

Cleanup or notification. Conditions: always, success, failure, unstable, changed, aborted, cleanup. 

post {
    always   { archiveArtifacts 'build/**' }
    success  { slackSend(channel: '#ci', message: "✅ ${env.JOB_NAME} #${env.BUILD_NUMBER}") }
    failure  { slackSend(channel: '#ci', message: "❌ ${env.JOB_NAME} #${env.BUILD_NUMBER}") }
    cleanup  { cleanWs() }
}

The steps you'll use constantly

StepPurpose
sh 'cmd' / bat 'cmd'Run a shell / Windows batch command.
checkout scmPull the repo (multibranch auto).
git url: '…', branch: 'main'Clone a specific repo.

Every plugin adds steps. A useful reference: Snippet Generator in any pipeline job — build a step interactively and see the Groovy.

sh vs script

Two common escape hatches:

stage('Work') {
    steps {
        // inline shell — one-liner or multiline
        sh '''
            set -euo pipefail
            make
            make test
        '''

        // escape to Groovy when Declarative can't express the logic
        script {
            def branches = sh(returnStdout: true, script: 'git branch -r').trim()
            echo "Branches: ${branches}"
            if (branches.contains('release')) {
                echo 'Release branch exists.'
            }
        }
    }
}

sh(returnStdout: true, script: '…') captures stdout. Without it, sh returns the exit code. returnStatus: true captures the exit code without failing the step — useful for conditionals.

Built-in env vars

Inside any step, these are available:

env.BUILD_NUMBER Monotonic per job
env.BUILD_ID Same as BUILD_NUMBER in modern Jenkins
env.BUILD_URL Link to this build
env.JOB_NAME Job name
env.BRANCH_NAME (multibranch) current branch
env.CHANGE_ID (multibranch) PR number, if applicable
env.CHANGE_BRANCH (multibranch) source branch of PR
env.GIT_COMMIT Full commit SHA
env.GIT_BRANCH Ref name
env.NODE_NAME Agent name
env.WORKSPACE Path to the workspace

Use in strings (${env.BUILD_NUMBER}) or directly (env.BUILD_NUMBER). Setting env.FOO = 'bar' inside a script block sets it for the rest of the pipeline.

Hands-on: a realistic pipeline

Hands-on · lint, test, build, archive

On your local Jenkins, create a Pipeline job and paste this:

groovyJenkinsfile
pipeline {
    agent any
    options {
        timeout(time: 10, unit: 'MINUTES')
        timestamps()
        buildDiscarder(logRotator(numToKeepStr: '10'))
    }
    environment {
        APP = 'hello'
    }
    stages {
        stage('Checkout') {
            steps {
                echo "Building ${env.APP} #${env.BUILD_NUMBER}"
                // In a real job, this would checkout a repo.
                sh '''
                    mkdir -p src
                    cat > src/hello.py <<'EOF'
def greet(name):
    return f"Hello, {name}!"
EOF
                    cat > src/test_hello.py <<'EOF'
from hello import greet
def test_greet():
    assert greet("world") == "Hello, world!"
EOF
                '''
            }
        }

        stage('Lint') {
            steps {
                sh 'python3 -m py_compile src/*.py'
            }
        }

        stage('Test') {
            steps {
                sh '''
                    cd src
                    python3 -m pytest -v --junitxml=../test-results.xml || true
                '''
            }
            post {
                always { junit 'test-results.xml' }
            }
        }

        stage('Package') {
            steps {
                sh '''
                    mkdir -p dist
                    tar czf dist/${APP}-${BUILD_NUMBER}.tar.gz src/
                    ls -la dist/
                '''
            }
        }
    }

    post {
        success { echo "✅ build #${env.BUILD_NUMBER} succeeded" }
        failure { echo "❌ build #${env.BUILD_NUMBER} failed" }
        always  { archiveArtifacts artifacts: 'dist/**', fingerprint: true }
    }
}

Save, Build Now, and watch each stage go green. Check the "Test Result Trend" graph (bottom of the job page) after a couple of builds — junit feeds that.

Now edit a test to fail (assert on a wrong string) and re-run. Notice: because the Test stage uses || true, pytest's failure doesn't stop the pipeline, but junit marks the build UNSTABLE. Remove the || true and you'll get a FAILED build instead.

Multibranch pipelines

The killer feature for most teams: multibranch pipelines. You configure Jenkins once to point at a repo; Jenkins then:

  1. Discovers every branch.
  2. For each branch that has a Jenkinsfile, creates a sub-job.
  3. Runs the pipeline on every push.
  4. For every PR, runs the pipeline using the Jenkinsfile from the PR branch.

To set up: Dashboard → New Item → Multibranch Pipeline. Add a Branch Source (GitHub, GitLab, Bitbucket, git). Save. Scan. Watch Jenkins discover and build every branch.

Inside a multibranch pipeline, env.BRANCH_NAME tells you which branch is being built, and env.CHANGE_ID is set if the build is for a PR. Use in when conditions: 

stage('Deploy to staging') {
    when { branch 'main' }
    steps { sh './deploy.sh staging' }
}
stage('Deploy to prod') {
    when { buildingTag() }       // only on git tag
    steps { sh './deploy.sh prod' }
}

Exercises

EX 4.1 easy Scripted or Declarative?

For each snippet, say if it's Scripted or Declarative and how you can tell:

(a)  node('linux') { stage('X') { sh 'make' } }
(b)  pipeline { agent any; stages { stage('X') { steps { sh 'make' } } } }
(c)  pipeline { agent any; stages { stage('X') { sh 'make' } } }
Show solution
  • (a) Scripted — node { … } as the outermost block is Scripted syntax.
  • (b) Declarative — the pipeline { agent { stages { stage { steps { … } } } } } shape.
  • (c) Declarative but invalid — stage requires a steps block in Declarative. Would fail with a syntax error.
EX 4.2 easy Secret-safe sh

Fix this snippet so the token isn't interpolated by Groovy:

withCredentials([string(credentialsId: 'gh', variable: 'GH_TOKEN')]) {
    sh "curl -H 'Authorization: token ${GH_TOKEN}' https://api.github.com/user"
}
Show solution 
withCredentials([string(credentialsId: 'gh', variable: 'GH_TOKEN')]) {
    sh 'curl -H "Authorization: token $GH_TOKEN" https://api.github.com/user'
}

Single-quoted Groovy string ⇒ no interpolation. Shell sees $GH_TOKEN and expands it from the environment, which Jenkins has populated. Logs mask the value.

EX 4.3 medium Conditional stage

Write a Deploy stage that runs only when the build is for a tag starting with v.

Show solution 
stage('Deploy') {
    when { tag pattern: 'v.*', comparator: 'REGEXP' }
    steps { sh './deploy.sh' }
}

Or with buildingTag() + an env check:

stage('Deploy') {
    when {
        allOf {
            buildingTag()
            expression { env.TAG_NAME?.startsWith('v') }
        }
    }
    steps { sh './deploy.sh' }
}
EX 4.4 medium Capture output

Write a step that captures the current git SHA in a Groovy variable and echoes it.

Show solution 
script {
    def sha = sh(returnStdout: true, script: 'git rev-parse HEAD').trim()
    echo "Building commit ${sha}"
    env.GIT_SHA = sha            // available downstream
}
EX 4.5 hard Input approval

Add a "Deploy to prod" stage that pauses and asks "Really deploy v1.0.0 to prod?" and only proceeds if a user in the release-managers group confirms within 30 minutes.

Show solution 
stage('Deploy to prod') {
    when { branch 'main' }
    steps {
        timeout(time: 30, unit: 'MINUTES') {
            input message: "Really deploy ${env.BUILD_NUMBER} to prod?",
                  ok: 'Deploy',
                  submitter: 'release-managers'
        }
        sh './deploy.sh prod'
    }
}

input holds an executor while waiting. Consider wrapping in a stage('Wait for approval') { agent none; …} so approvals don't tie up a build agent.

EX 4.6 medium Stash/unstash

Two stages where "build" runs on linux and "package" runs on macos. Pass the dist/ directory between them.

Show solution 
stage('Build') {
    agent { label 'linux' }
    steps {
        sh 'make'
        stash name: 'dist', includes: 'dist/**'
    }
}
stage('Package') {
    agent { label 'macos' }
    steps {
        unstash 'dist'
        sh 'hdiutil create dist/app.dmg -srcfolder dist/app'
    }
}

Recap

  • Pipelines come in Scripted (raw Groovy) and Declarative (structured DSL). Prefer Declarative.
  • Jenkinsfile is Groovy. Know enough to read closures, interpolation, and maps.
  • Single-quoted shell strings prevent Groovy from interpolating secrets.
  • Structure: pipeline { agent, options, environment, parameters, triggers, stages, post }.
  • Core steps: sh, checkout, stash/unstash, archiveArtifacts, junit, withCredentials, input.
  • Multibranch pipelines auto-build every branch and every PR — start here for any serious project.
