Chapter 08 GitLab CI — Advanced

rules in depth, needs & DAG, matrix jobs, extends, include, multi-project pipelines, dynamic child pipelines, and the GitLab CI patterns that separate hobby repos from production pipelines.

Rules — full reference

A rules: list is evaluated top-to-bottom; the first matching rule decides if and how the job runs.

unit-tests:
  script: [pytest]
  rules:
    - if: $CI_PIPELINE_SOURCE == "schedule"
      when: always
    - if: $CI_COMMIT_BRANCH == $CI_DEFAULT_BRANCH
      changes: [src/**/*]
      when: on_success
    - if: $CI_PIPELINE_SOURCE == "merge_request_event"
      when: on_success
      allow_failure: true                # don't fail MR if tests fail
    - when: never                         # default: don't run

Rule clauses:

  • if: — expression using predefined or custom CI variables. Operators: ==, !=, =~ (regex match), !~, &&, ||, !.
  • changes: — list of paths; job runs only if any matched file changed.
  • exists: — list of paths; runs only if files exist in the repo.
  • when: — on_success (default), always, never, manual, delayed.
  • allow_failure: — if true, job's failure doesn't fail the pipeline.
  • variables: — rule-scoped variable overrides (powerful).

Common patterns

# Run on MRs and on main, not on feature branches
rules:
  - if: $CI_PIPELINE_SOURCE == "merge_request_event"
  - if: $CI_COMMIT_BRANCH == $CI_DEFAULT_BRANCH

# Skip pipeline if commit message says [skip ci]
rules:
  - if: $CI_COMMIT_MESSAGE =~ /\[skip ci\]/
    when: never
  - when: on_success

# Run only on version tags
rules:
  - if: $CI_COMMIT_TAG =~ /^v[0-9]+\.[0-9]+\.[0-9]+$/

# Nightly job on main
rules:
  - if: $CI_PIPELINE_SOURCE == "schedule" && $CI_COMMIT_BRANCH == "main"
rules: and only:/except: don't mix

A job must use either rules: or the legacy only:/except:. Mixing them is an error. Modern GitLab favours rules — use it exclusively in new code.

needs — the real DAG

needs: on a job means "don't wait for my stage to start — start as soon as these specific jobs finish". It turns waterfall stages into a true directed-acyclic graph. 

stages: [lint, test, build, deploy]

lint-py:   { stage: lint, script: [ruff check] }
lint-yaml: { stage: lint, script: [yamllint .] }

test-unit:
  stage: test
  needs: [lint-py]                # as soon as lint-py finishes
  script: [pytest tests/unit]

test-integ:
  stage: test
  needs: []                       # no deps; start at t=0
  script: [./scripts/integration.sh]

build:
  stage: build
  needs: [test-unit, test-integ]
  script: [make dist]

deploy:
  stage: deploy
  needs: [build]
  script: [./deploy.sh]

Wall-clock: the lint stage no longer blocks slow integration tests. Pipelines that would run for 15 minutes under strict stages finish in 7.

needs can also be cross-pipeline:

deploy-from-upstream:
  stage: deploy
  needs:
    - project: mygroup/upstream
      ref: main
      job: build-artifact
  script: ["./deploy.sh"]

This pulls artifacts from another project's successful pipeline.

Parallel and matrix jobs

One job, many instances:

test:
  parallel: 5
  script: ["pytest --shard=$CI_NODE_INDEX/$CI_NODE_TOTAL"]

GitLab spins up 5 copies; $CI_NODE_INDEX goes 1–5, $CI_NODE_TOTAL is 5. You feed these to your test runner's sharding.

Full matrix:

test:
  parallel:
    matrix:
      - PYTHON: ["3.9", "3.10", "3.11", "3.12"]
        OS:     ["ubuntu-latest", "macos-latest"]
      - PYTHON: ["3.12"]
        OS:     ["windows-latest"]
  image: "python:$PYTHON"
  script: [pytest]

Two matrix entries (OR'd): the first is 4×2=8 combinations, the second is 1×1=1, total 9 jobs. Each gets variables set from the axes.

extends — per-job inheritance

Cleaner than YAML anchors:

.python-base:
  image: python:3.11-slim
  before_script:
    - pip install -r requirements.txt

lint:
  extends: .python-base
  script: [ruff check src/]

test:
  extends: .python-base
  script: [pytest]

You can extend multiple parents and override specifics:

.docker-build:
  image: docker:24
  services: [docker:24-dind]

.registry-login:
  before_script:
    - echo "$CI_REGISTRY_PASSWORD" | docker login $CI_REGISTRY -u $CI_REGISTRY_USER --password-stdin

publish:
  extends: [.docker-build, .registry-login]
  script:
    - docker build -t $CI_REGISTRY_IMAGE:$CI_COMMIT_SHA .
    - docker push $CI_REGISTRY_IMAGE:$CI_COMMIT_SHA

Later parents win on conflicts; the child's own keys win above all.

include — split your config

A big .gitlab-ci.yml is unmaintainable. Split it:

include:
  # From the same repo
  - local: .gitlab/ci/lint.yml
  - local: .gitlab/ci/test.yml
  - local: .gitlab/ci/deploy.yml

  # From a template shipped with GitLab
  - template: Jobs/SAST.gitlab-ci.yml
  - template: Security/Dependency-Scanning.gitlab-ci.yml

  # From another project in the same instance
  - project: mygroup/ci-templates
    ref: v1.2.0
    file: /templates/python.yml

  # From any URL
  - remote: 'https://example.com/shared/build.yml'

  # Component — modern, best practice for sharing reusable bits
  - component: $CI_SERVER_FQDN/mygroup/components/docker-build@1.0

Everything included merges into one final config. A lint job defined in .gitlab/ci/lint.yml is a peer to jobs defined in the main file.

Components (the last entry) are GitLab's modern reuse primitive — versioned, documented, with explicit inputs. Use them over raw include: for shareable logic.

CI/CD components

A component is a small, reusable pipeline fragment stored in its own "CI/CD Catalog" project. Define inputs as spec.inputs:

yamltemplates/docker-build/template.yml
spec:
  inputs:
    image:
      description: "Image to build"
    dockerfile:
      default: Dockerfile
    registry:
      default: $CI_REGISTRY
---
docker-build:
  image: docker:24
  services: [docker:24-dind]
  script:
    - docker build -f $[[ inputs.dockerfile ]] -t $[[ inputs.registry ]]/$[[ inputs.image ]]:$CI_COMMIT_SHA .
    - docker push $[[ inputs.registry ]]/$[[ inputs.image ]]:$CI_COMMIT_SHA

Consumer:

include:
  - component: gitlab.example.com/group/templates/docker-build@1.0
    inputs:
      image: myapp
      dockerfile: ci/Dockerfile

Components have versioning, a catalog UI, and enforced input schemas. Preferable to ad-hoc include: for anything you want to share across projects.

Child & dynamic pipelines

Trigger a separate pipeline from a job — useful for monorepos where only part of the repo should run:

frontend-pipeline:
  stage: build
  trigger:
    include: frontend/.gitlab-ci.yml
    strategy: depend                # parent waits for child

backend-pipeline:
  stage: build
  trigger:
    include: backend/.gitlab-ci.yml

Dynamic child pipelines generate the child YAML on the fly:

generate-config:
  stage: build
  script:
    - python generate-pipeline.py > generated.yml
  artifacts:
    paths: [generated.yml]

trigger-generated:
  stage: build
  needs: [generate-config]
  trigger:
    include:
      - artifact: generated.yml
        job: generate-config

Killer for monorepos: the generate-pipeline.py looks at which files changed, emits only the relevant jobs, and the child pipeline runs just those.

Auto DevOps and SAST templates

GitLab ships built-in pipeline templates for common stages:

  • Auto DevOps — one-setting enable; GitLab auto-detects language, lints, tests, builds, dockerises, and deploys to a K8s cluster.
  • SAST / Dependency Scanning / Container Scanning / Secret Detection / DAST / Fuzz Testing / License Scanning — all available as template: includes. Many are free; some are paid-tier.
include:
  - template: Jobs/SAST.gitlab-ci.yml
  - template: Jobs/Secret-Detection.gitlab-ci.yml
  - template: Jobs/Dependency-Scanning.gitlab-ci.yml
  - template: Jobs/Container-Scanning.gitlab-ci.yml

Results surface on the MR as first-class security reports. More in Chapter 11.

Merge trains

A premium feature: when multiple MRs are ready to merge, GitLab queues them, rebases each onto the prior, runs the pipeline for the combined result, and merges them in order if every combined pipeline passes. Solves the "green-on-its-own, red-when-merged" problem elegantly. Available on Premium/Ultimate tiers.

Merge request pipelines

Three flavors:

  1. Branch pipeline. Runs on every push to a branch. Doesn't know the MR.
  2. Merge request pipeline. Runs in the context of an MR, has access to $CI_MERGE_REQUEST_* variables. Enable via rules.
  3. Merged results pipeline. Runs on a speculative merge-commit (source + target). Catches "my change passes alone but breaks with target" cases.

To enable MR pipelines, gate a job with:

rules:
  - if: $CI_PIPELINE_SOURCE == "merge_request_event"

The integrated container registry

Every GitLab project has its own container registry. Use predefined variables to push:

publish:
  image: docker:24
  services: [docker:24-dind]
  script:
    - echo "$CI_REGISTRY_PASSWORD" | docker login $CI_REGISTRY -u $CI_REGISTRY_USER --password-stdin
    - docker build -t $CI_REGISTRY_IMAGE:$CI_COMMIT_SHA .
    - docker push    $CI_REGISTRY_IMAGE:$CI_COMMIT_SHA
    - docker tag     $CI_REGISTRY_IMAGE:$CI_COMMIT_SHA $CI_REGISTRY_IMAGE:latest
    - docker push    $CI_REGISTRY_IMAGE:latest

No secret management needed — $CI_REGISTRY_PASSWORD is auto-injected and scoped to the job.

Running a self-hosted runner

# Install
$ curl -L --output /tmp/gitlab-runner.deb \
     https://gitlab-runner-downloads.s3.amazonaws.com/latest/deb/gitlab-runner_amd64.deb
$ sudo dpkg -i /tmp/gitlab-runner.deb

# Register
$ sudo gitlab-runner register \
     --url https://gitlab.example.com \
     --token  glrt-XXX \
     --executor docker \
     --docker-image alpine:3.19 \
     --description "linux-docker-1"

# Start
$ sudo gitlab-runner start

Runner config lives in /etc/gitlab-runner/config.toml. Settings worth tuning:

  • concurrent — how many jobs this runner handles at once.
  • [runners.docker] — image pull policy, volume mounts, networks.
  • [runners.cache] — S3 / GCS cache backend so caches survive the runner dying.

Hands-on: a mid-sized pipeline

Hands-on · DAG, rules, extends, include

Start from the Chapter 7 pipeline. Refactor:

yaml.gitlab-ci.yml
include:
  - local: .gitlab/ci/python.yml

stages: [lint, test, build, deploy]

variables:
  PIP_CACHE_DIR: "$CI_PROJECT_DIR/.pip"

lint:
  extends: .python
  stage: lint
  script: [ruff check src/]

test-unit:
  extends: .python
  stage: test
  needs: [lint]
  script: [pytest --junitxml=unit.xml]
  artifacts: { reports: { junit: unit.xml } }

test-integ:
  extends: .python
  stage: test
  needs: [lint]
  services: [postgres:16]
  variables:
    POSTGRES_PASSWORD: test
    DATABASE_URL: "postgres://postgres:test@postgres:5432/postgres"
  script: [pytest tests/integration/]

build:
  extends: .python
  stage: build
  needs: [test-unit, test-integ]
  script: [python -m build]
  artifacts: { paths: [dist/], expire_in: 1 week }

deploy-staging:
  stage: deploy
  needs: [build]
  image: alpine:3.19
  script: ["echo fake-deploy $CI_COMMIT_SHA to staging"]
  environment: { name: staging, url: https://staging.example.com }
  rules:
    - if: $CI_COMMIT_BRANCH == $CI_DEFAULT_BRANCH

deploy-prod:
  stage: deploy
  needs: [build]
  image: alpine:3.19
  script: ["echo fake-deploy $CI_COMMIT_SHA to prod"]
  environment: { name: production }
  rules:
    - if: $CI_COMMIT_TAG =~ /^v/
      when: manual
yaml.gitlab/ci/python.yml
.python:
  image: python:3.11-slim
  cache:
    key: { files: [requirements.txt] }
    paths: [.pip/, .venv/]
  before_script:
    - python -m venv .venv
    - . .venv/bin/activate
    - pip install -r requirements.txt

Push. Observe:

  • The pipeline graph is a DAG — test-unit and test-integ start as soon as lint passes.
  • The deploy-staging job only appears when you're on the default branch.
  • The deploy-prod job only appears on version-tag pipelines, and even then requires a manual click.

Exercises

EX 8.1 easy skip ci

Write rules that make a pipeline skip entirely if the commit message contains [skip ci], without touching any jobs individually.

Show solution

Workflow-level rules apply to the whole pipeline:

workflow:
  rules:
    - if: $CI_COMMIT_MESSAGE =~ /\[skip ci\]/
      when: never
    - when: always

Side note: GitLab already recognises [skip ci] and [ci skip] natively in commit messages — this rule is mostly useful to customise the matching, or add your own patterns like [nopipe].

EX 8.2 medium Sharded tests

Run pytest split across 4 parallel jobs.

Show solution 
test:
  image: python:3.11
  parallel: 4
  script:
    - pip install pytest pytest-split
    - pytest --splits $CI_NODE_TOTAL --group $CI_NODE_INDEX

pytest-split is a plugin that accepts --splits N --group K and divides the test suite deterministically. For Go, go test has native sharding via -shuffle and -run patterns.

EX 8.3 medium Template extraction

You have five projects that each push a Docker image. Extract the Docker-build job into a shared template in a ci-templates project.

Show solution
yamlci-templates/docker.yml
.docker-build:
  image: docker:24
  services: [docker:24-dind]
  before_script:
    - echo "$CI_REGISTRY_PASSWORD" | docker login $CI_REGISTRY -u $CI_REGISTRY_USER --password-stdin
  script:
    - docker build -t $CI_REGISTRY_IMAGE:$CI_COMMIT_SHA .
    - docker push   $CI_REGISTRY_IMAGE:$CI_COMMIT_SHA

Consumer:

include:
  - project: mygroup/ci-templates
    ref: main
    file: /docker.yml

publish:
  extends: .docker-build
  stage: build

Better: wrap as a proper Component (earlier in this chapter). Pin by tag (ref: v1.0.0), not main, so consumers pick when to upgrade.

EX 8.4 hard Dynamic pipeline for monorepo

Sketch a dynamic child pipeline scheme where a generator job inspects changed paths and emits a child YAML that contains only jobs for those paths.

Show solution 
generate:
  image: python:3.11
  script:
    - python ci/generate.py > child.yml
    - cat child.yml
  artifacts: { paths: [child.yml] }

run-child:
  stage: test
  needs: [generate]
  trigger:
    include:
      - artifact: child.yml
        job: generate
    strategy: depend

ci/generate.py looks at the base vs current commit:

changed=$(git diff --name-only "$CI_MERGE_REQUEST_DIFF_BASE_SHA"...HEAD)
echo "$changed"

Then emits Python/Node/etc jobs as appropriate. Very common pattern for monorepos with 20+ microservices.

EX 8.5 hard Merge request pipeline only

Design rules so a pipeline never runs twice for the same commit — either the branch pipeline, or the MR pipeline, never both.

Show solution 
workflow:
  rules:
    # Always run MR pipelines when an MR exists
    - if: $CI_PIPELINE_SOURCE == "merge_request_event"
    # Run branch pipelines only when there is NO open MR
    - if: $CI_COMMIT_BRANCH && $CI_OPEN_MERGE_REQUESTS
      when: never
    - if: $CI_COMMIT_BRANCH == $CI_DEFAULT_BRANCH
    - if: $CI_COMMIT_TAG
    - if: $CI_COMMIT_BRANCH
      when: always

This is GitLab's official recommended workflow rules for "avoid duplicate pipelines". The variable $CI_OPEN_MERGE_REQUESTS is set when the current commit is associated with an open MR.

Recap

  • rules is the modern predicate for "when does this job run"; first match wins; workflow:rules: applies at pipeline scope.
  • needs: turns stages into a DAG — huge wall-time wins for wide pipelines.
  • parallel: N or parallel: matrix for sharding and cross-version testing.
  • extends + include decompose big YAML; Components are the modern reusable primitive.
  • Dynamic child pipelines for monorepos: a generator emits YAML an include:s it from an artifact.
  • Built-in templates cover SAST/DAST/secret scanning/etc. — opt in with one-line includes.
  • Integrated container registry is zero-config: $CI_REGISTRY_* variables hand you auth automatically.
