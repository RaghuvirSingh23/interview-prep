Chapter 07 GitLab CI — Fundamentals

GitLab CI is the "batteries-included" option. Your CI config lives in a single YAML file, runners handle the work, and the whole thing is tightly integrated with GitLab's git hosting, merge requests, environments, and container registry. This chapter covers the fundamentals; the next one goes deep.

Architecture at a glance

  ┌────────────────────────────────┐
  │    GitLab (SaaS or self-hosted)│
  │  - stores repos & MRs          │
  │  - stores .gitlab-ci.yml       │
  │  - schedules pipelines         │
  │  - shows results in UI         │
  └────────────┬───────────────────┘
               │ HTTPS long-poll
               │
       ┌───────┴───────┬───────────┐
       │               │           │
   [Runner A]      [Runner B]  [Runner C]
    shared          group        project
    runner          runner       runner

GitLab itself holds the code, schedules the pipeline, and renders the UI. Runners are the worker processes that run jobs; they poll GitLab for work, receive jobs, execute them, and upload logs and artifacts back.

Three scopes of runner:

  • Shared runners — provisioned by GitLab (on gitlab.com, you get generous free minutes); available to any project on the instance.
  • Group runners — registered to a GitLab group; available to any project in that group.
  • Project (specific) runners — registered to a single project. Useful for projects with unique hardware or secrets.

Runners can execute jobs in multiple executors:

  • Shell — runs commands directly on the runner host. Simple, stateful, dangerous (jobs share state).
  • Docker — each job runs in a fresh container. The default; what you usually want.
  • Kubernetes — each job runs as a K8s pod. For scale.
  • SSH, VirtualBox, Parallels, Custom — niche.

On gitlab.com, the shared runners are Linux containers, with macOS and Windows Docker runners available on paid tiers.

Your first pipeline

Create .gitlab-ci.yml in the root of any GitLab project:

yaml.gitlab-ci.yml
stages:
  - test
  - build

unit-tests:
  stage: test
  image: python:3.11-slim
  script:
    - pip install pytest
    - pytest tests/

build-artifact:
  stage: build
  image: alpine:3.19
  script:
    - mkdir -p dist
    - echo "release $(date -u)" > dist/version.txt
    - tar czf dist/app.tar.gz src/ README.md
  artifacts:
    paths: [dist/]
    expire_in: 1 week

Commit + push. Go to Build → Pipelines in GitLab's UI. A pipeline has started. Click in, you'll see two stages, each with a job, with live log output.

The three first-class concepts

ConceptWhat it is
PipelineOne end-to-end run for a given commit or trigger. Contains stages and jobs.
StageA group of jobs that can run in parallel. Stages run sequentially — every job in stage N finishes before stage N+1 starts (unless you use needs).
JobA unit of work. The top-level keys of .gitlab-ci.yml that aren't reserved are jobs.

The default stages are .pre, build, test, deploy, .post. Override with the top-level stages: list.

A job, block by block

unit-tests:                      # <-- job name
  stage: test                    # which stage it belongs to
  image: python:3.11-slim        # docker image to run in
  services:                      # additional containers
    - postgres:16
  variables:                     # env vars for the job
    POSTGRES_DB: testdb
  before_script:                 # runs before `script`
    - pip install -r requirements.txt
  script:                        # the main commands (required)
    - pytest --junitxml=report.xml
  after_script:                  # runs after `script` (even on failure)
    - echo "cleanup"
  rules:                         # when to run this job
    - if: $CI_PIPELINE_SOURCE == "merge_request_event"
  timeout: 20 minutes            # kill job if it runs longer
  retry: 1                       # retry on failure
  artifacts:
    when: always                 # upload even on failure
    reports:
      junit: report.xml
    paths:
      - coverage/
    expire_in: 7 days
  cache:
    key:
      files: [requirements.txt]
    paths: [.cache/pip/]
  allow_failure: false           # if true, failure doesn't fail the pipeline
  tags:                          # pick runners with these tags
    - docker
    - linux

Memorise the shape; we'll meet each of these repeatedly.

Variables

Variables can be set at three levels (inner wins):

  1. Instance/group/project — via GitLab UI (Settings → CI/CD → Variables). Can be masked, protected, or file-type.
  2. Top-level variables: — pipeline-wide.
  3. Job-level variables: — job-scoped, overrides higher-level.
variables:
  NODE_VERSION: "20"
  CACHE_DIR: ".cache"

unit-tests:
  variables:
    NODE_VERSION: "18"            # override for this job
  script: ["node --version"]

Predefined variables are where GitLab really shines. A huge set of them is exposed:

VariableValue
$CI_COMMIT_SHA Full commit SHA
$CI_COMMIT_SHORT_SHA First 8 chars
$CI_COMMIT_REF_NAME Branch or tag name
$CI_COMMIT_TAG Tag name (empty if not a tag build)
$CI_COMMIT_MESSAGE Full commit message
$CI_PIPELINE_ID Unique pipeline ID
$CI_PIPELINE_URL Link to the pipeline
$CI_PIPELINE_SOURCE push, merge_request_event, schedule, web, api, …
$CI_PROJECT_ID Numeric project ID
$CI_PROJECT_PATH group/project
$CI_PROJECT_NAME Bare project name
$CI_MERGE_REQUEST_IID MR number (in MR pipelines)
$CI_DEFAULT_BRANCH Usually main
$CI_REGISTRY URL of the per-project container registry
$CI_REGISTRY_IMAGE registry.gitlab.com/group/project
$CI_REGISTRY_USER gitlab-ci-token
$CI_JOB_TOKEN Short-lived token for per-job auth (use as a password)

The official list has ~80 more. Ctrl-F-search when you need one.

script / before_script / after_script

Each is a list of commands run by the runner's shell. Default shell: sh in Docker executors; your login shell on shell executors.

test:
  before_script:
    - apt-get update -qq && apt-get install -y libpq-dev
    - pip install -r requirements.txt
  script:
    - pytest --cov
  after_script:
    - rm -rf .tox/

Each line is a separate command but they do share a shell — before_script env vars persist into script, unlike Jenkins. That simplifies things considerably.

Failure semantics: if any line in script fails, the job fails and subsequent lines are skipped. after_script runs no matter what.

Artifacts and caches

Artifacts

build:
  script: [make dist]
  artifacts:
    paths: [dist/]
    expire_in: 7 days
    when: on_success            # always / on_success / on_failure

deploy:
  needs: [build]                # auto-fetches build's artifacts
  script: ["./deploy.sh dist/"]

Key point: jobs in a later stage automatically receive artifacts from all earlier-stage jobs unless you use needs: which makes the dependency explicit.

Caches

default:
  cache:
    key:
      files: [package-lock.json]
    paths:
      - node_modules/
      - .npm/
    policy: pull-push            # pull-push | pull | push

Cache key based on the lockfile means: same lockfile = same cache, different lockfile = new cache. policy: pull lets a job read but not write — useful when many jobs share one warm cache.

Reports (typed artifacts)

test:
  script: [pytest --cov --junitxml=junit.xml --cov-report=cobertura.xml]
  artifacts:
    reports:
      junit: junit.xml
      coverage_report:
        coverage_format: cobertura
        path: cobertura.xml

GitLab understands report types and shows them inline in MRs (test summaries, coverage deltas). Supported types include junit, cobertura, sast, container_scanning, dependency_scanning, dast, license_scanning, terraform, requirements.

rules — when jobs run

Classic approach — only and except keywords. Modern approach — rules:

deploy-staging:
  script: ["./deploy.sh staging"]
  rules:
    - if: $CI_COMMIT_BRANCH == $CI_DEFAULT_BRANCH
      when: on_success
    - if: $CI_PIPELINE_SOURCE == "merge_request_event"
      when: never
    - when: never                       # default: don't run

Rules evaluate top-to-bottom; first match wins. Each rule can set:

  • if: — expression with CI variables and comparison operators.
  • changes: — only if given paths changed.
  • exists: — only if a file exists.
  • when: — on_success, always, never, manual, delayed.
  • allow_failure: — true/false.

Environments & deploys

Mark a job as deploying to a named environment:

deploy-staging:
  stage: deploy
  script: ["./deploy.sh staging"]
  environment:
    name: staging
    url: https://staging.example.com
  rules:
    - if: $CI_COMMIT_BRANCH == $CI_DEFAULT_BRANCH

deploy-prod:
  stage: deploy
  script: ["./deploy.sh prod"]
  environment:
    name: production
    url: https://example.com
  rules:
    - if: $CI_COMMIT_TAG
      when: manual

GitLab tracks every deploy to every environment. Under Operate → Environments you can see who deployed what to where, link to the URL, rollback to a previous release, see a deploy history per environment.

when: manual makes the job a button in the pipeline UI — nobody deploys to prod automatically.

Services (companion containers)

Run supporting containers alongside your job — e.g. a real Postgres for integration tests:

integration-tests:
  image: python:3.11
  services:
    - name: postgres:16
      alias: db
  variables:
    POSTGRES_PASSWORD: secret
    DATABASE_URL: "postgresql://postgres:secret@db:5432/postgres"
  script:
    - pip install -r requirements.txt
    - pytest tests/integration/

The db alias is the hostname your job's container reaches Postgres on. This is a massive quality-of-life feature — no tearing up docker-compose for tests.

needs — the DAG escape

Default: stages enforce strict ordering. Add needs: and a job skips to front-of-line as soon as its named prereqs are done:

stages: [lint, test, build, deploy]

lint:        { stage: lint,  script: [npm run lint] }
test-unit:   { stage: test,  script: [npm test], needs: [] }   # starts immediately
test-integ:  { stage: test,  script: [./integ.sh], needs: [lint] }
build:       { stage: build, script: [npm run build], needs: [test-unit, test-integ] }
deploy:      { stage: deploy, script: [./deploy.sh], needs: [build] }

needs: [] means "no dependencies, go now". Otherwise list specific jobs. This turns a stages waterfall into a DAG — big wall-clock wins for wide pipelines. More in Chapter 8.

Hands-on: a full mini pipeline

Hands-on · real .gitlab-ci.yml

Create a new GitLab project (the free gitlab.com tier is fine). Add this file at the repo root:

yaml.gitlab-ci.yml
stages: [lint, test, build]

default:
  image: python:3.11-slim

variables:
  PIP_CACHE_DIR: "$CI_PROJECT_DIR/.pip"

cache:
  key:
    files: [requirements.txt]
  paths:
    - .pip/
    - .venv/

.setup: &setup
  before_script:
    - python -m venv .venv
    - . .venv/bin/activate
    - pip install -r requirements.txt

lint:
  stage: lint
  <<: *setup
  script:
    - ruff check src/ tests/

test:
  stage: test
  needs: [lint]
  <<: *setup
  script:
    - pytest --junitxml=report.xml --cov=src --cov-report=xml
  artifacts:
    when: always
    reports:
      junit: report.xml
      coverage_report: { coverage_format: cobertura, path: coverage.xml }

build:
  stage: build
  needs: [test]
  <<: *setup
  script:
    - python -m build
  artifacts:
    paths: [dist/]
    expire_in: 7 days

Create a minimal Python project alongside (src/hello.py, tests/test_hello.py, requirements.txt with pytest, ruff, coverage[toml], build). Push. Watch the pipeline run on gitlab.com's shared runners.

Things to click on after the run:

  • The pipeline graph view — drag the stages around.
  • The test report tab (populated by junit).
  • The coverage badge in project Settings → CI/CD → General Pipelines.
  • The artifacts of build — download dist/ directly.

YAML anchors — DRY without include

Notice the .setup: &setup and <<: *setup dance in the example. That's YAML anchors, usable any time you want to reuse a block. GitLab respects them natively: 

.base: &base
  image: node:20
  before_script:
    - npm ci

lint:
  <<: *base
  script: [npm run lint]

test:
  <<: *base
  script: [npm test]

The dot-prefixed .base is a "hidden" job — GitLab ignores dot-prefixed keys as jobs, so they're only useful as anchor sources.

Chapter 8 covers extends and include — more powerful than anchors.

Exercises

EX 7.1 easy Default stages

Without setting stages:, what are the default stages in GitLab CI and in what order?

Show solution

.pre, build, test, deploy, .post. .pre runs before everything; .post runs after everything. Jobs without an explicit stage: go to test.

EX 7.2 easy Manual deploy

Write a deploy-prod job that only appears as a manual button on pipelines built from tags matching v*, and deploys to the production environment.

Show solution 
deploy-prod:
  stage: deploy
  script: ["./deploy.sh prod"]
  environment:
    name: production
    url: https://example.com
  rules:
    - if: $CI_COMMIT_TAG =~ /^v/
      when: manual

Your Ruby project needs Postgres 16 and Redis 7 for integration tests. Write the job config.

integration:

EX 7.4 medium Artifact vs cache

A colleague writes this and wonders why the build job fails saying node_modules not found:

install:
  script: [npm ci]
  cache:
    paths: [node_modules/]

build:
  script: [npm run build]

Fix it.

Show solution

Caches are best-effort — a fresh pipeline might start with an empty cache, and they also depend on cache keys. Artifacts are the contract between jobs in the same pipeline:

install:
  script: [npm ci]
  artifacts:
    paths: [node_modules/]
    expire_in: 1 hour
  cache:
    key: { files: [package-lock.json] }
    paths: [node_modules/]

build:
  needs: [install]
  script: [npm run build]

Now build gets node_modules/ even in a cache-cold run, while the cache still speeds up future install runs.

EX 7.5 hard Run only when changed

A monorepo has frontend/ and backend/. Write jobs so that frontend-tests runs only when frontend files change (and on main/tags), and backend-tests only when backend files change (ditto).

Show solution 
frontend-tests:
  stage: test
  image: node:20
  script: [cd frontend, npm ci, npm test]
  rules:
    - if: $CI_COMMIT_BRANCH == $CI_DEFAULT_BRANCH
    - if: $CI_COMMIT_TAG
    - changes: [frontend/**/*]

backend-tests:
  stage: test
  image: python:3.11
  script: [cd backend, pip install -r req.txt, pytest]
  rules:
    - if: $CI_COMMIT_BRANCH == $CI_DEFAULT_BRANCH
    - if: $CI_COMMIT_TAG
    - changes: [backend/**/*]

On main or tag builds both always run; on feature branches, only whichever directory changed.

Recap

  • GitLab CI = GitLab-hosted pipelines + runners doing the work. Runners come in shared, group, and project scopes.
  • .gitlab-ci.yml at the repo root; stages, jobs, predefined variables, rules, artifacts, caches.
  • Docker executor is the default — image and services define the environment.
  • Artifacts are required contracts between jobs; caches are best-effort.
  • needs turns stages into a DAG; rules decide when jobs run.
  • Environments track deploys; when: manual gates prod behind a button.
  • YAML anchors are OK, but extends + include (next chapter) are cleaner.
