Chapter 15 Jenkins on Kubernetes

Jenkins and Kubernetes fit together when you stop treating Jenkins as a pet VM. The controller runs as a small, persistent service; builds run as disposable Pods; deployment either updates the cluster directly with least-privilege RBAC or hands off desired state to GitOps. This chapter is the bridge between traditional CI and the Kubernetes operating model.

The shape of Jenkins on K8s

A Jenkins-on-Kubernetes setup has two very different kinds of workloads.

PartWhat it doesKubernetes shape
ControllerUI, job metadata, queue, plugin runtime, credentials referencesOne StatefulSet/Pod with a PVC
Agent PodsRun build stages: test, package, scan, publishShort-lived Pods created per build
RegistryStores built images and cache layersExternal service: ECR/GAR/ACR/Harbor/etc.
Deployment targetWhere the image ends up runningSame cluster, another cluster, or GitOps repo

The controller should not compile code, run Docker builds, or hold long-lived workspaces. It should schedule work and keep state. Agents do the heavy lifting and then disappear.

Production default

Set the controller executor count to 0. If a build can run on the controller, someone will eventually put CPU-heavy, secret-heavy, disk-heavy work there. Make the safe path the only path.

Install the controller with Helm

The official Jenkins Helm chart already knows about the controller, PVC, service account, JCasC, and the Kubernetes plugin. A minimal local install looks like this:

$ kubectl create namespace jenkins

$ helm repo add jenkinsci https://charts.jenkins.io
$ helm repo update

$ helm upgrade --install jenkins jenkinsci/jenkins \
    --namespace jenkins \
    --values jenkins-values.yaml

A practical values file

yamljenkins-values.yaml
controller:
  numExecutors: 0
  serviceType: ClusterIP

  # In real environments, pin plugin versions and test upgrades in staging.
  installPlugins:
    - kubernetes
    - workflow-aggregator
    - git
    - configuration-as-code
    - credentials-binding
    - kubernetes-cli

  JCasC:
    defaultConfig: true
    configScripts:
      welcome: |
        jenkins:
          systemMessage: "Jenkins is managed by Helm and JCasC."

  resources:
    requests:
      cpu: "500m"
      memory: "1Gi"
    limits:
      memory: "4Gi"

agent:
  enabled: true
  namespace: jenkins
  podName: default
  workingDir: /home/jenkins/agent
  resources:
    requests:
      cpu: "250m"
      memory: "512Mi"
    limits:
      memory: "2Gi"

persistence:
  enabled: true
  size: 20Gi

rbac:
  create: true

serviceAccount:
  create: true
  name: jenkins

For local exploration, port-forward the controller:

$ kubectl -n jenkins port-forward svc/jenkins 8080:8080

$ kubectl -n jenkins get secret jenkins \
    -o jsonpath='{.data.jenkins-admin-password}' | base64 -d; echo

For a real team, put the controller behind Ingress/Gateway with TLS, SSO, audit logging, backups for the PVC, and a deliberate plugin upgrade process. The Helm chart gets Jenkins running; it does not remove the need to operate Jenkins.

Ephemeral agent Pods

The Kubernetes plugin creates a Pod for a build, runs Jenkins agent code inside it, executes the Pipeline steps, then deletes the Pod. The win is isolation: every build gets a clean filesystem, scoped resources, and its own container toolchain.

groovyJenkinsfile
pipeline {
  agent {
    kubernetes {
      defaultContainer 'python'
      yaml '''
apiVersion: v1
kind: Pod
spec:
  securityContext:
    runAsNonRoot: true
    seccompProfile:
      type: RuntimeDefault
  containers:
    - name: python
      image: python:3.12-slim
      command: ["sleep"]
      args: ["99d"]
      resources:
        requests: { cpu: "250m", memory: "512Mi" }
        limits:   {              memory: "1Gi" }
      securityContext:
        allowPrivilegeEscalation: false
        capabilities: { drop: ["ALL"] }
    - name: kubectl
      image: bitnami/kubectl:latest
      command: ["sleep"]
      args: ["99d"]
'''
    }
  }

  stages {
    stage('Test') {
      steps {
        sh 'python -m pip install -r requirements.txt'
        sh 'python -m pytest -q'
      }
    }

    stage('Inspect cluster') {
      steps {
        container('kubectl') {
          sh 'kubectl get pods -n "$NAMESPACE"'
        }
      }
    }
  }
}

Notice the pattern: one Pod, multiple containers, shared workspace. The python container runs tests. The kubectl container has cluster tooling. You do not need one giant image with every build tool installed.

Do not mount the host Docker socket

/var/run/docker.sock gives the build container control over the node's container runtime. In most clusters, that is effectively root on the node. Use BuildKit, a managed builder, or a registry-native build service instead.

Build images inside the cluster

The old Jenkins VM pattern was: install Docker on the agent, run docker build, push. In Kubernetes, that usually means either privileged Docker-in-Docker or a host socket mount. Both are uncomfortable defaults.

Modern options:

  • BuildKit / Buildx Kubernetes driver — good default for new setups. Build pods run in a dedicated namespace, support cache/export, and can run rootless where the cluster supports it.
  • Managed builders — Cloud Build, CodeBuild, ACR Tasks, Depot, etc. Jenkins triggers the build and records the result.
  • Kaniko or maintained forks — historically common for unprivileged Dockerfile builds. Treat it as a migration topic now, not the only default.

BuildKit from a Jenkins agent

One clean design is to let Jenkins create a normal agent Pod with the Docker CLI, then point buildx at a BuildKit builder running in Kubernetes.

$ kubectl create namespace buildkit

$ docker buildx create \
    --name kube \
    --driver kubernetes \
    --driver-opt namespace=buildkit,rootless=true \
    --bootstrap

$ docker buildx build \
    --builder kube \
    --tag registry.example.com/app:${GIT_COMMIT} \
    --cache-to type=registry,ref=registry.example.com/app:buildcache,mode=max \
    --cache-from type=registry,ref=registry.example.com/app:buildcache \
    --push .

In a locked-down cluster, pre-create the BuildKit builder with platform, node selectors, resource requests, and registry credentials. Jenkins should not need cluster-admin just to build an image.

Kaniko-style build stage

You will still see Kaniko in older Jenkins examples. The shape is useful to understand because the same credential and workspace ideas apply to other builders.

stage('Image') {
  agent {
    kubernetes {
      defaultContainer 'kaniko'
      yaml '''
apiVersion: v1
kind: Pod
spec:
  containers:
    - name: kaniko
      image: gcr.io/kaniko-project/executor:v1.24.0-debug
      command: ["/busybox/cat"]
      tty: true
      volumeMounts:
        - name: docker-config
          mountPath: /kaniko/.docker
  volumes:
    - name: docker-config
      secret:
        secretName: registry-dockerconfig
'''
    }
  }
  steps {
    sh '''
      /kaniko/executor \
        --context "$WORKSPACE" \
        --dockerfile "$WORKSPACE/Dockerfile" \
        --destination "registry.example.com/app:${GIT_COMMIT}" \
        --cache=true
    '''
  }
}

The important parts are independent of the builder: the registry credential is a Kubernetes Secret, the image tag is immutable, and the build Pod has only the permissions it needs.

RBAC for Jenkins

Jenkins has two different Kubernetes identities:

  • The controller identity creates and watches agent Pods in the Jenkins namespace.
  • The deployment identity updates application resources, ideally in only one target namespace.

Do not bind the controller service account to cluster-admin. Give it a narrow Role for agent management, and give deployment jobs separate service accounts or kubeconfigs per environment.

Controller can manage only agent Pods

apiVersion: rbac.authorization.k8s.io/v1
kind: Role
metadata:
  name: jenkins-agent-manager
  namespace: jenkins
rules:
  - apiGroups: [""]
    resources: ["pods", "pods/exec", "pods/log"]
    verbs: ["create", "delete", "get", "list", "watch"]
  - apiGroups: [""]
    resources: ["secrets"]
    verbs: ["get"]
---
apiVersion: rbac.authorization.k8s.io/v1
kind: RoleBinding
metadata:
  name: jenkins-agent-manager
  namespace: jenkins
subjects:
  - kind: ServiceAccount
    name: jenkins
    namespace: jenkins
roleRef:
  apiGroup: rbac.authorization.k8s.io
  kind: Role
  name: jenkins-agent-manager

Deploy job can update only one app namespace

apiVersion: v1
kind: ServiceAccount
metadata:
  name: deployer
  namespace: prod
---
apiVersion: rbac.authorization.k8s.io/v1
kind: Role
metadata:
  name: app-deployer
  namespace: prod
rules:
  - apiGroups: ["apps"]
    resources: ["deployments"]
    verbs: ["get", "list", "watch", "patch", "update"]
  - apiGroups: [""]
    resources: ["services", "configmaps"]
    verbs: ["get", "list", "watch"]
---
apiVersion: rbac.authorization.k8s.io/v1
kind: RoleBinding
metadata:
  name: app-deployer
  namespace: prod
subjects:
  - kind: ServiceAccount
    name: deployer
    namespace: prod
roleRef:
  apiGroup: rbac.authorization.k8s.io
  kind: Role
  name: app-deployer

Then verify the permission before wiring a Pipeline around it:

$ kubectl auth can-i patch deployments \
    --as system:serviceaccount:prod:deployer \
    --namespace prod

Deploy from Jenkins or hand off to GitOps?

There are two respectable models. Pick one deliberately.

ModelPipeline doesBest whenRisk
Jenkins deploys directlyhelm upgrade, kubectl apply, rollout checksSmall teams, simple envs, legacy Jenkins investmentJenkins becomes a privileged deploy box
Jenkins hands off to GitOpsBuilds image, signs/scans, updates a manifest repo or opens PRMultiple clusters/envs, audit-heavy orgs, platform teamsRequires GitOps discipline and repo hygiene

Direct deploy pipeline

stage('Deploy') {
  steps {
    container('kubectl') {
      sh '''
        helm upgrade --install app ./chart \
          --namespace prod \
          --set image.repository=registry.example.com/app \
          --set image.tag="${GIT_COMMIT}" \
          --atomic \
          --timeout 5m

        kubectl -n prod rollout status deploy/app --timeout=5m
      '''
    }
  }
}

This is direct and easy to understand. The tradeoff is that Jenkins credentials now change production. Protect the job with approvals, environment separation, audit logging, and a service account that cannot touch anything except the target app.

GitOps handoff pipeline

stage('Promote manifest') {
  steps {
    sh '''
      git clone git@github.com:example/platform-envs.git envs
      cd envs/apps/app/overlays/prod
      kustomize edit set image registry.example.com/app=registry.example.com/app:${GIT_COMMIT}
      git diff
      git commit -am "promote app ${GIT_COMMIT}"
      git push origin main
    '''
  }
}

Argo CD or Flux sees the git change and reconciles the cluster. Jenkins owns CI and promotion intent; GitOps owns applying desired state. This is the model to prefer once there are several environments or compliance requirements.

Jenkins Configuration as Code

Clicking around the Jenkins UI is fine for learning and bad for operations. JCasC makes controller configuration reviewable, repeatable, and restorable.

yamlvalues.yaml fragment
controller:
  JCasC:
    defaultConfig: true
    overwriteConfiguration: true
    configScripts:
      system: |
        jenkins:
          systemMessage: "Managed by Helm + JCasC"
          numExecutors: 0
          clouds:
            - kubernetes:
                name: "kubernetes"
                namespace: "jenkins"
                serverUrl: "https://kubernetes.default"
                templates:
                  - name: "python"
                    label: "python"
                    containers:
                      - name: "python"
                        image: "python:3.12-slim"
                        command: "sleep"
                        args: "99d"
                        resourceRequestCpu: "250m"
                        resourceRequestMemory: "512Mi"

For day-two operations, keep a repo with:

  • values.yaml for chart-level configuration.
  • JCasC snippets for clouds, security realm, authorization, credentials references, shared libraries, and global tools.
  • A plugin catalog or pinned installPlugins list.
  • Backup/restore runbooks for $JENKINS_HOME.
Plugin upgrades are releases

Jenkins plugins are code running inside your controller. Test plugin updates like application deploys: staging controller, pinned versions, changelog review, rollback plan, and a PVC snapshot before production rollout.

Operating checklist

  • Controller: one replica, persistent volume, backups, requests/limits, probes, zero executors.
  • Agents: short-lived Pods, resource requests, no privileged mode, no host Docker socket, minimal tool images.
  • Credentials: store in Jenkins only when needed; prefer cloud workload identity or external secret managers for cluster access.
  • Build output: immutable image tags, digest capture, SBOM/scanning/signing before promotion.
  • Deployments: either least-privilege direct deploy or GitOps handoff; avoid mixing both for the same app.
  • Audit: job history, git history, chart/JCasC history, Kubernetes audit logs for deploy service accounts.
  • Cost: cap agent concurrency, set resource requests correctly, clean orphan Pods and stale workspaces.

Exercises

EX 15.1 easy Why ephemeral agents?

Why are ephemeral Kubernetes agent Pods usually better than a small pool of long-lived Jenkins agents?

Show solution

They give each build a clean filesystem, fresh process state, scoped resources, and a toolchain matched to that job. Long-lived agents accumulate hidden state: leftover files, cached credentials, mutated tools, and unpredictable resource contention. Ephemeral agents make builds more reproducible and reduce cross-job leakage.

EX 15.2 medium Multi-container pod template

Write the idea, not every line of YAML: why would you put python, kubectl, and helm in separate containers inside one Jenkins agent Pod?

Show solution

They share the workspace but keep toolchains isolated. The Python image stays focused on tests, the kubectl image contains only cluster tooling, and the helm image contains only chart tooling. Updating Helm does not rebuild the Python test image. The Pipeline switches containers with container('helm') { ... } or container('kubectl') { ... }.

EX 15.3 medium Replace docker-build with Kaniko

A legacy Jenkins agent runs docker build -t app:$GIT_COMMIT . && docker push ... by mounting /var/run/docker.sock. What changes when replacing it with a Kaniko-style builder?

Show solution
  • The build runs inside a normal container, not through the node's Docker socket.
  • The Docker context is the Jenkins workspace path.
  • Registry auth is mounted as a Secret, commonly under /kaniko/.docker/config.json.
  • The command writes directly to the registry with --destination; there is no local Docker daemon image store.
  • You should still evaluate maintained builders for new setups, because older Kaniko examples may be stale.
EX 15.4 medium RBAC for the controller

What Kubernetes permissions does the Jenkins controller need to run ephemeral agents in namespace jenkins? What should it not receive?

Show solution

It needs namespaced permissions to create, get, list, watch, and delete agent Pods, plus access to pod logs and exec if Pipelines use those operations. It may need to read specific Secrets used by agent Pods. It should not receive cluster-admin, broad Secret access across namespaces, node permissions, or permission to mutate production Deployments unless the controller service account is intentionally also the deployment identity, which is usually a mistake.

EX 15.5 hard Build vs deploy split

Design a production flow where Jenkins builds the image but Argo CD deploys it. What artifacts cross the boundary?

Show solution
  1. Jenkins tests the commit, builds the image, pushes registry.example.com/app:<sha>, captures the immutable digest, and runs scan/sign steps.
  2. Jenkins opens a PR or pushes a commit to the environment repo changing the image tag/digest in a Helm values file or Kustomize overlay.
  3. Argo CD watches the environment repo, detects the desired-state change, applies it, and reports sync/health.
  4. The artifacts crossing the boundary are the image reference/digest, provenance/SBOM/signature metadata, and the git commit in the environment repo. Jenkins does not need production cluster write access.
EX 15.6 hard JCasC + GitOps for Jenkins itself

You want Jenkins itself to be recoverable from git. What belongs in the repo, and what must stay out?

Show solution

Put chart values, JCasC config, plugin versions, shared library definitions, folder/job seed definitions, RBAC manifests, NetworkPolicies, and backup/restore docs in git. Keep raw secrets, private keys, API tokens, and generated runtime state out. Store secrets in Vault/cloud secret manager/External Secrets and reference them from JCasC or Kubernetes Secret names. Back up the PVC because build history and some runtime state still live in $JENKINS_HOME.

Recap

  • Jenkins on Kubernetes means persistent controller, ephemeral build Pods.
  • Install the controller with Helm, keep executors at 0, and manage configuration with JCasC.
  • Use multi-container agent Pods instead of giant all-tools images.
  • Avoid Docker socket mounts and privileged Docker-in-Docker; prefer BuildKit, managed builders, or carefully evaluated daemonless builders.
  • Separate controller RBAC from deployment RBAC. Least privilege is the difference between CI and a cluster-wide deploy backdoor.
  • Direct Jenkins deploys are simple; Jenkins-plus-GitOps scales better for many environments and audit-heavy teams.
  • Operate Jenkins like a production app: backups, plugin pinning, upgrade tests, resource controls, and clear ownership.
