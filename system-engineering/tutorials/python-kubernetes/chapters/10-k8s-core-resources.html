Chapter 08 Core Resources

Pod, ReplicaSet, Deployment, Service, ConfigMap, Secret, Namespace, ServiceAccount. The atoms most workloads compose from. After this chapter, the manifests in any open-source repo's deploy/ directory will read like English.

Pod

A Pod is one or more containers running together on the same node, sharing a network namespace (same IP, same loopback) and optionally volumes. It's the smallest schedulable unit. Most pods have one container; multi-container pods exist for specific patterns (sidecars).

yamlPod (rare to write directly)
apiVersion: v1
kind: Pod
metadata:
  name: hello
  labels: { app: hello }
spec:
  containers:
    - name: web
      image: nginx:1.27
      ports: [{ containerPort: 80 }]
      resources:
        requests: { cpu: "50m",  memory: "64Mi" }
        limits:   { cpu: "200m", memory: "128Mi" }
  restartPolicy: Always

You will almost never write a bare Pod. You write a Deployment, StatefulSet, or Job, and they create Pods for you. The reason: a bare Pod isn't replaced if its node dies. Workloads above it provide the recovery.

Multi-container pods

spec:
  containers:
    - name: app
      image: my-app:1.0
      volumeMounts: [{ name: shared, mountPath: /data }]
    - name: log-shipper           # sidecar
      image: fluent/fluent-bit:3
      volumeMounts: [{ name: shared, mountPath: /var/log }]
  volumes:
    - name: shared
      emptyDir: {}

Both containers share an emptyDir volume — the app writes logs there, the sidecar reads and ships. Communication is via the filesystem or via localhost.

Init containers

Run before the main containers, to completion, in order. Common uses: wait for a dependency, pre-populate a volume, run schema migrations.

spec:
  initContainers:
    - name: wait-for-db
      image: busybox:1.36
      command: ['sh', '-c', 'until nc -z postgres 5432; do sleep 1; done']
  containers:
    - name: app
      image: my-app:1.0

Labels and selectors — the connective tissue

Resources don't reference each other by ID. They reference each other by label selectors. A Service finds its Pods because the Pods have a label and the Service has a matching selector. Loosely coupled, freely re-shapeable.

metadata:
  labels:
    app: hello
    component: web
    tier: frontend
    version: v1.2.3

Selectors:

$ kubectl get pods -l app=hello
$ kubectl get pods -l 'tier in (frontend, edge)'
$ kubectl get pods -l 'env!=dev'
$ kubectl get pods -l 'app=hello,version=v1.2.3'

Conventions worth following: app.kubernetes.io/name, app.kubernetes.io/instance, app.kubernetes.io/version, app.kubernetes.io/component, app.kubernetes.io/part-of, app.kubernetes.io/managed-by. Used by tools and dashboards to make sense of your cluster.

Annotations

Like labels but not selected on. Free-form; used by tools and humans.

metadata:
  annotations:
    kubernetes.io/change-cause:    "release v1.2.3 — bumps node to 20.10"
    prometheus.io/scrape:          "true"
    prometheus.io/port:            "9100"
    nginx.ingress.kubernetes.io/rewrite-target: /

ReplicaSet

"Run N pods matching this template." You almost never write one directly — Deployment manages a ReplicaSet for you.

apiVersion: apps/v1
kind: ReplicaSet
metadata:
  name: hello-rs
spec:
  replicas: 3
  selector:
    matchLabels: { app: hello }
  template:
    metadata: { labels: { app: hello } }
    spec:
      containers:
        - name: web
          image: nginx:1.27

Controller behaviour: counts existing pods that match the selector. If < replicas, create more. If > replicas, delete the newest. Pods that match the selector but weren't created by the ReplicaSet (orphaned) get adopted — be careful with overlapping selectors.

Deployment — the workhorse

Manages a ReplicaSet. Adds rolling updates, rollback, history, pause/resume, scaling.

yamldeployment.yaml
apiVersion: apps/v1
kind: Deployment
metadata:
  name: hello
  labels: { app: hello }
spec:
  replicas: 3
  revisionHistoryLimit: 10
  strategy:
    type: RollingUpdate
    rollingUpdate:
      maxSurge:       1            # may run 1 above desired during rollout
      maxUnavailable: 0            # never drop below desired
  selector:
    matchLabels: { app: hello }
  template:
    metadata:
      labels: { app: hello }
    spec:
      containers:
        - name: web
          image: hashicorp/http-echo:1.0
          args: ["-text=v1"]
          ports: [{ containerPort: 5678 }]
          readinessProbe:
            httpGet: { path: /, port: 5678 }
            periodSeconds: 5
          resources:
            requests: { cpu: "50m",  memory: "64Mi" }
            limits:   { cpu: "200m", memory: "128Mi" }

Apply, watch a rollout:

$ kubectl apply -f deployment.yaml
$ kubectl rollout status deploy/hello

# Update image
$ kubectl set image deploy/hello web=hashicorp/http-echo:0.2.4
$ kubectl rollout status deploy/hello

# History
$ kubectl rollout history deploy/hello
REVISION  CHANGE-CAUSE
1         <none>
2         <none>

# Rollback
$ kubectl rollout undo deploy/hello
$ kubectl rollout undo deploy/hello --to-revision=1

# Pause & resume (multi-step edits without rolling each time)
$ kubectl rollout pause deploy/hello
$ kubectl set image  deploy/hello web=...:0.2.5
$ kubectl set env    deploy/hello web FOO=bar
$ kubectl rollout resume deploy/hello

How the rollout actually works

  1. You change the Pod template (image, env, anything inside spec.template).
  2. Deployment computes a hash of the new template. If different from the current ReplicaSet's hash, it creates a new ReplicaSet.
  3. It scales the new ReplicaSet up while scaling the old one down, respecting maxSurge and maxUnavailable.
  4. If readiness probes fail on new pods, the rollout stops — old pods keep serving.

That's why probes (Chapter 11) matter — they're what makes "broken new version" stay broken on the rollout, not on production traffic.

Service — stable address for a set of pods

Pods come and go; their IPs change. A Service is a stable virtual IP (ClusterIP) and DNS name that load-balances to whatever pods currently match its selector.

apiVersion: v1
kind: Service
metadata:
  name: hello
spec:
  selector:
    app: hello
  ports:
    - name: http
      port: 80               # the Service's virtual port
      targetPort: 5678       # the pod's port
      protocol: TCP
  type: ClusterIP            # default; in-cluster only

From any pod in the cluster, http://hello.default.svc.cluster.local (or just http://hello within the same namespace) resolves to the Service IP, which round-robins to a backing Pod.

Service types

TypeWhat it gives you
ClusterIP Internal-only virtual IP. Default.
NodePort Plus a port on every node (30000-32767). Crude external access.
LoadBalancer Plus a cloud LB (GCP/AWS/Azure provision one). External access.
ExternalName DNS CNAME — service name maps to an external hostname.
Headless (clusterIP: None)No virtual IP; DNS returns Pod IPs directly. Used by StatefulSets.

For HTTP routing across many services, you don't usually use LoadBalancer per service — you use one Ingress (Chapter 10) backed by one cloud LB.

EndpointSlice — what a Service really points at

Behind every Service, K8s maintains an EndpointSlice resource listing the actual Pod IPs and ports that match the selector. Watch it during a rollout:

$ kubectl get endpointslice -l kubernetes.io/service-name=hello -w
NAME            ADDRESSTYPE   PORTS   ENDPOINTS
hello-abc       IPv4          5678    10.244.0.5,10.244.0.6,10.244.0.7

The Service controller keeps this in sync as Pods are created, deleted, or fail readiness probes. kube-proxy on each node consumes EndpointSlices to set up iptables / IPVS / eBPF rules that load-balance.

ConfigMap

Non-secret config decoupled from images. Mount as files or expose as env vars.

apiVersion: v1
kind: ConfigMap
metadata:
  name: app-config
data:
  log_level: "info"
  feature_x: "true"
  app.yaml: |
    server:
      port: 8080
    db:
      host: postgres.default.svc.cluster.local
      port: 5432

Inject into pods two ways:

# 1. As env vars
spec:
  containers:
    - name: app
      image: my-app:1.0
      env:
        - name: LOG_LEVEL
          valueFrom: { configMapKeyRef: { name: app-config, key: log_level } }
      envFrom:
        - configMapRef: { name: app-config }     # all keys at once

# 2. As files
spec:
  containers:
    - name: app
      image: my-app:1.0
      volumeMounts:
        - name: config
          mountPath: /etc/app
          readOnly: true
  volumes:
    - name: config
      configMap:
        name: app-config
        items:
          - key: app.yaml
            path: app.yaml

Subtle: ConfigMap-as-env is captured at pod start; updates require a restart. ConfigMap-as-volume is updated dynamically (within a sync interval), but your app has to re-read the file. Most apps just don't bother and rely on rollout-on-change.

Roll on change — the trick

To force a Deployment rollout when a ConfigMap changes, put a hash of the ConfigMap into a pod-spec annotation. Helm does this automatically; for plain manifests, your CI can compute and inject:

spec:
  template:
    metadata:
      annotations:
        config-hash: "sha256:abc123..."     # changes when ConfigMap content changes
    spec: ...

The Deployment template hash now includes the config-hash, so applying a new ConfigMap triggers a rolling restart. Without this, your config change sits in the ConfigMap but the running pods still hold the old values.

Secret

Like a ConfigMap, but base64-encoded by default and (with proper cluster setup) encrypted at rest. Base64 is encoding, not encryption — anyone with read access can decode in two seconds.

apiVersion: v1
kind: Secret
metadata:
  name: db-creds
type: Opaque
stringData:                                  # easier than base64-ing yourself
  username: admin
  password: s3cr3t!

Mount or expose:

env:
  - name: DB_USER
    valueFrom: { secretKeyRef: { name: db-creds, key: username } }
  - name: DB_PASS
    valueFrom: { secretKeyRef: { name: db-creds, key: password } }

Secrets best practices

  • Never commit Secret YAML with real values to git. Even base64'd, the value is "plaintext to anyone with the file."
  • Use a secret manager: External Secrets Operator (syncs from Vault/AWS Secrets Manager/GCP/Azure), Sealed Secrets (encrypted in git, decrypted in-cluster), or SOPS.
  • Enable etcd encryption at rest in the cluster.
  • Use RBAC to restrict who can get secrets; default ServiceAccounts often shouldn't.
  • For cloud credentials in pods: use IRSA (AWS), Workload Identity (GCP/Azure) — pod-level cloud auth without a Secret on disk.

Namespace

apiVersion: v1
kind: Namespace
metadata:
  name: promote
  labels:
    pod-security.kubernetes.io/enforce: restricted    # PodSecurityStandards
    pod-security.kubernetes.io/audit:   restricted

Beyond name-scoping, namespaces are units for:

  • RBAC — Roles/RoleBindings are namespaced.
  • ResourceQuota — caps total CPU, memory, pod count, etc. for the namespace.
  • LimitRange — defaults and bounds for individual pod/container resources.
  • NetworkPolicy — usually scoped to a namespace's pods.
  • Pod Security Standards — enforced per-namespace via labels.

ServiceAccount

The identity a Pod uses to talk to the API server. Every Pod has one, defaulting to the namespace's default ServiceAccount.

apiVersion: v1
kind: ServiceAccount
metadata:
  name: promoter
  namespace: promote
---
apiVersion: rbac.authorization.k8s.io/v1
kind: Role
metadata:
  name: promote-role
  namespace: promote
rules:
  - apiGroups: [""]
    resources: ["pods", "configmaps"]
    verbs: ["get", "list", "watch"]
  - apiGroups: ["batch"]
    resources: ["jobs"]
    verbs: ["create", "get", "list", "watch", "delete"]
---
apiVersion: rbac.authorization.k8s.io/v1
kind: RoleBinding
metadata:
  name: promote-binding
  namespace: promote
subjects:
  - kind: ServiceAccount
    name: promoter
    namespace: promote
roleRef:
  apiGroup: rbac.authorization.k8s.io
  kind: Role
  name: promote-role

And in the Pod:

spec:
  serviceAccountName: promoter
  automountServiceAccountToken: true       # the default; mounts a JWT into /var/run/secrets/...

Inside the Pod, the official Kubernetes Python client (or kubectl) reads the mounted token and uses it as a Bearer credential. The Role above means the Pod can list Pods/ConfigMaps and create/delete Jobs in its namespace — and nothing else.

Kustomize — a quick mention

Sooner or later you'll need "this same manifest with image tag X in staging and Y in prod". You can template with sed, or use Kustomize (built into kubectl):

k8s/
├── base/
│   ├── kustomization.yaml
│   ├── deployment.yaml
│   └── service.yaml
└── overlays/
    ├── staging/
    │   ├── kustomization.yaml
    │   └── replica-patch.yaml
    └── prod/
        └── kustomization.yaml
yamloverlays/prod/kustomization.yaml
resources:
  - ../../base
namespace: prod
images:
  - name: my-app
    newTag: v1.2.3
patches:
  - target: { kind: Deployment, name: hello }
    patch: |-
      - op: replace
        path: /spec/replicas
        value: 5

Apply with kubectl apply -k overlays/prod. No new tool to install. We cover Helm — the alternative — in Chapter 12.

Hands-on: full mini-stack

Hands-on · Deployment + Service + ConfigMap + Secret
yamlstack.yaml
apiVersion: v1
kind: Namespace
metadata: { name: demo }
---
apiVersion: v1
kind: ConfigMap
metadata: { name: app-config, namespace: demo }
data:
  greeting: "Hello, demo cluster"
---
apiVersion: v1
kind: Secret
metadata: { name: db-creds, namespace: demo }
type: Opaque
stringData:
  password: notreallyasecret
---
apiVersion: apps/v1
kind: Deployment
metadata: { name: hello, namespace: demo }
spec:
  replicas: 3
  selector: { matchLabels: { app: hello } }
  template:
    metadata: { labels: { app: hello } }
    spec:
      containers:
        - name: web
          image: hashicorp/http-echo:1.0
          args: ["-text=$(GREETING)"]
          env:
            - name: GREETING
              valueFrom: { configMapKeyRef: { name: app-config, key: greeting } }
            - name: DB_PASS
              valueFrom: { secretKeyRef: { name: db-creds, key: password } }
          ports: [{ containerPort: 5678 }]
          readinessProbe:
            httpGet: { path: /, port: 5678 }
            periodSeconds: 5
---
apiVersion: v1
kind: Service
metadata: { name: hello, namespace: demo }
spec:
  selector: { app: hello }
  ports: [{ port: 80, targetPort: 5678 }]
$ kubectl apply -f stack.yaml
$ kubectl -n demo port-forward svc/hello 8080:80 &
$ curl localhost:8080
Hello, demo cluster

# Update the ConfigMap, force a rollout
$ kubectl -n demo set env deploy/hello CONFIG_REV=2     # any change works
$ kubectl -n demo rollout status deploy/hello
$ kubectl -n demo edit configmap app-config             # change greeting
$ kubectl -n demo rollout restart deploy/hello          # explicit rollout
$ curl localhost:8080
Hello, ... (new greeting)

# Clean up
$ kubectl delete -f stack.yaml

Exercises

EX 8.1 easy Pod ↔ Service mapping

How does a Service know which Pods to send traffic to? What happens if you change a Pod's labels at runtime?

Show solution

Selector match. The endpoints controller watches Pods; for each Service, it lists Pods with matching labels in the same namespace and writes them into an EndpointSlice.

Editing a Pod's labels at runtime: if it now matches another Service's selector, traffic for that Service starts arriving. If it no longer matches the original, it's removed from those endpoints. kubectl label pod X foo=bar --overwrite can be used to "evict" a Pod from a Service's pool — useful for debugging.

EX 8.2 easy ConfigMap as files

Mount a ConfigMap with key config.yaml into a pod at /etc/myapp/config.yaml. Show the YAML.

Show solution 
spec:
  containers:
    - name: app
      image: my-app:1.0
      volumeMounts:
        - { name: cfg, mountPath: /etc/myapp, readOnly: true }
  volumes:
    - name: cfg
      configMap:
        name: app-config
        items: [{ key: config.yaml, path: config.yaml }]
EX 8.3 medium Roll on config change

You change the ConfigMap. Pods don't see the new value. How do you make the Deployment rollout when the ConfigMap changes? Two solutions.

Show solution
  1. Annotation hash: compute SHA of the ConfigMap content, write it into spec.template.metadata.annotations.config-hash. New ConfigMap → new hash → new pod template hash → rollout.
  2. Manual: kubectl rollout restart deploy/hello after applying the ConfigMap. Simple, less elegant.

Helm with checksum/config: {{ include … | sha256sum }} automates option 1.

EX 8.4 medium Restrict ServiceAccount permissions

You're writing a Pod that needs to list ConfigMaps in its own namespace, nothing more. Define a ServiceAccount, Role, RoleBinding.

Show solution 
apiVersion: v1
kind: ServiceAccount
metadata: { name: cm-reader, namespace: demo }
---
apiVersion: rbac.authorization.k8s.io/v1
kind: Role
metadata: { name: cm-reader, namespace: demo }
rules:
  - apiGroups: [""]
    resources: ["configmaps"]
    verbs: ["get", "list", "watch"]
---
apiVersion: rbac.authorization.k8s.io/v1
kind: RoleBinding
metadata: { name: cm-reader, namespace: demo }
subjects: [{ kind: ServiceAccount, name: cm-reader, namespace: demo }]
roleRef: { apiGroup: rbac.authorization.k8s.io, kind: Role, name: cm-reader }

In the Pod: spec.serviceAccountName: cm-reader.

EX 8.5 hard Why bare Pods are bad

You write a bare kind: Pod manifest and apply it. The Pod runs. Hours later, the node it's on dies. What happens? Compare to applying a Deployment with replicas=1.

Show solution

Bare Pod: gone. Pods aren't rescheduled by anything. Node dies → Pod gone → no replacement.

Deployment with replicas=1: the ReplicaSet controller notices its desired replica count isn't met and creates a new Pod, which the scheduler places on a surviving node. Self-heals.

This is why you write Deployments, not Pods. Bare Pods are for one-off experiments and debugging.

Recap

  • Pod = group of containers sharing network and (optionally) storage. Smallest unit; rarely written directly.
  • Sidecar containers and init containers compose multi-container patterns.
  • Labels + selectors are the connective tissue between resources. Use the app.kubernetes.io/* conventions.
  • Deployment manages a ReplicaSet, gives rolling updates and rollbacks. Use maxSurge/maxUnavailable to tune.
  • Service = stable VIP/DNS for a label-selected set of pods. Behind it lives an EndpointSlice.
  • ConfigMap for non-secret config (env vars or volume mounts). Force rollout on change with an annotation hash.
  • Secret like ConfigMap but base64'd — encoding, not encryption. Use a secret manager or External Secrets.
  • ServiceAccount + Role + RoleBinding = least-privilege identity for pods talking to the API.
  • Kustomize for env-specific overlays without a templating language.
