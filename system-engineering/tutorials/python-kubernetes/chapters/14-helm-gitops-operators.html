Chapter 12 Helm, GitOps, Operators

Three layers above raw manifests: Helm packages templated YAML, GitOps declares what should be in the cluster from a git repo, operators teach Kubernetes new resource types via custom controllers. After this chapter, the open-source ecosystem stops feeling alien.

Helm — the package manager

Helm packages a set of Kubernetes manifests into a chart: a versioned bundle with templated YAML, a values file for customisation, and a dependency graph. Think of it as apt for Kubernetes.

Anatomy of a chart

my-app/
├── Chart.yaml         # name, version, dependencies
├── values.yaml        # default user-overridable values
├── templates/
│   ├── _helpers.tpl   # reusable Go-template fragments
│   ├── deployment.yaml
│   ├── service.yaml
│   ├── ingress.yaml
│   ├── configmap.yaml
│   └── NOTES.txt      # printed after install
└── charts/            # bundled subcharts

A minimal Chart.yaml

apiVersion: v2
name: my-app
description: My application
type: application
version: 0.1.0          # chart version (SemVer)
appVersion: "1.2.3"     # the app's version (just metadata)
dependencies:
  - name: redis
    version: "20.1.0"
    repository: "https://charts.bitnami.com/bitnami"
    condition: redis.enabled

values.yaml — user-overridable defaults

image:
  repository: registry.example.com/my-app
  tag: ""                       # overridden via --set or values file
  pullPolicy: IfNotPresent

replicas: 3

service:
  type: ClusterIP
  port: 80

resources:
  requests: { cpu: 100m, memory: 128Mi }
  limits:   {              memory: 128Mi }

ingress:
  enabled: false
  host: my-app.example.com

redis:
  enabled: false

A templated manifest

yamltemplates/deployment.yaml
apiVersion: apps/v1
kind: Deployment
metadata:
  name: {{ include "my-app.fullname" . }}
  labels: {{- include "my-app.labels" . | nindent 4 }}
spec:
  replicas: {{ .Values.replicas }}
  selector:
    matchLabels: {{- include "my-app.selectorLabels" . | nindent 6 }}
  template:
    metadata:
      labels: {{- include "my-app.selectorLabels" . | nindent 8 }}
      annotations:
        checksum/config: {{ include (print $.Template.BasePath "/configmap.yaml") . | sha256sum }}
    spec:
      containers:
        - name: {{ .Chart.Name }}
          image: "{{ .Values.image.repository }}:{{ .Values.image.tag | default .Chart.AppVersion }}"
          imagePullPolicy: {{ .Values.image.pullPolicy }}
          ports:
            - { name: http, containerPort: 8080 }
          resources: {{- toYaml .Values.resources | nindent 12 }}

The Go-template syntax ({{ ... }}) lets you parametrise. The checksum/config annotation is the trick we covered in Chapter 8 — a hash of the rendered ConfigMap means changes there force a rolling restart.

The Helm CLI

# Add a repo
$ helm repo add bitnami https://charts.bitnami.com/bitnami
$ helm repo update

# Install
$ helm install my-redis bitnami/redis --namespace data --create-namespace
$ helm install my-app ./my-app --values values-prod.yaml

# What did it install?
$ helm list -A
$ helm status my-app

# See what would be applied (dry run + show)
$ helm install --dry-run --debug my-app ./my-app
$ helm template my-app ./my-app | less       # render to stdout

# Upgrade in place
$ helm upgrade my-app ./my-app --values values-prod.yaml --atomic --timeout 5m

# Rollback to previous revision
$ helm rollback my-app 1

# Uninstall
$ helm uninstall my-app

# Lint the chart
$ helm lint ./my-app

--atomic means: if the upgrade fails, automatically roll back. Combined with --timeout, it's the safest default for production deploys.

Values precedence

Highest to lowest:

  1. --set foo=bar on the command line.
  2. --values file.yaml, in order (later files win).
  3. The chart's values.yaml.

Common pattern: values.yaml is dev defaults, values-staging.yaml and values-prod.yaml override per environment.

Helm gotchas

  • Whitespace is awful. nindent and indent are your friends. Run helm template often to see the rendered output.
  • Released CRDs are not upgraded. Helm v3 has an explicit crds/ directory whose contents are installed once and not touched on upgrade. For evolving CRDs, you usually manage them separately.
  • Hooks fire at install/upgrade time (pre-install, post-install, etc.). Use sparingly — they make releases harder to reason about.
  • The values file is the user's API. Document defaults; don't break compatibility on minor bumps.

Kustomize vs Helm — pick one

KustomizeHelm
IdiomPatches over a baseTemplates with values
Built into kubectlYesSeparate binary
Best for"Same app, slight env differences""Distributable package, lots of knobs"
TemplatingNone — strategic mergeGo templates
DistributionJust YAML in gitChart repos (OCI now), versioned

Rule of thumb: Kustomize for your own apps, Helm for third-party things you install (databases, monitoring stacks, ingress controllers). Mixing both is fine — Kustomize can post-process Helm output.

GitOps — git as the source of truth

The idea: the desired state of your cluster lives in a git repo. A controller in the cluster watches git, sees drift between git and reality, and reconciles. Same desired-state-vs-actual-state model as Kubernetes itself, applied to the cluster's manifests.

Two leading tools:

  • Argo CD — UI-heavy, easier to onboard humans, mature ecosystem.
  • Flux — CLI/CR-heavy, more cloud-native feel, lighter footprint.

Both implement the same idea differently. Capabilities are converging.

Argo CD — basics

# Install
$ kubectl create namespace argocd
$ kubectl apply -n argocd -f https://raw.githubusercontent.com/argoproj/argo-cd/stable/manifests/install.yaml

# Get the initial admin password
$ kubectl -n argocd get secret argocd-initial-admin-secret -o jsonpath="{.data.password}" | base64 -d

# Port-forward and log in
$ kubectl -n argocd port-forward svc/argocd-server 8080:443
# open https://localhost:8080

Then declare an Application that points at git:

apiVersion: argoproj.io/v1alpha1
kind: Application
metadata:
  name: my-app
  namespace: argocd
spec:
  project: default
  source:
    repoURL: https://github.com/myorg/k8s-config.git
    targetRevision: main                 # branch, tag, or commit
    path: apps/my-app/overlays/prod
  destination:
    server: https://kubernetes.default.svc
    namespace: prod
  syncPolicy:
    automated:
      prune: true                        # delete resources removed from git
      selfHeal: true                     # revert manual edits in cluster
    syncOptions:
      - CreateNamespace=true
      - ApplyOutOfSyncOnly=true

Argo CD continuously compares the rendered manifests in git (Helm, Kustomize, plain YAML, all supported) to live cluster state, and applies the diff. If someone kubectl edits a Deployment, Argo notices and reverts (selfHeal) — or alerts (without selfHeal). Drift is visible.

The "App of Apps" pattern

For dozens or hundreds of apps, you don't want to hand-create each Application. The "app of apps" pattern: one root Application points at a folder of other Applications. Add a folder, the root picks it up, the new app appears.

ApplicationSet — even better

apiVersion: argoproj.io/v1alpha1
kind: ApplicationSet
metadata:
  name: cluster-apps
  namespace: argocd
spec:
  generators:
    - git:
        repoURL: https://github.com/myorg/k8s-config.git
        revision: main
        directories:
          - path: apps/*
  template:
    metadata:
      name: '{{path.basename}}'
    spec:
      project: default
      source:
        repoURL: https://github.com/myorg/k8s-config.git
        targetRevision: main
        path: '{{path}}'
      destination:
        server: https://kubernetes.default.svc
        namespace: '{{path.basename}}'
      syncPolicy:
        automated: { prune: true, selfHeal: true }
        syncOptions: [CreateNamespace=true]

One ApplicationSet generates an Application for every directory under apps/. Onboard a new service by creating a folder; nothing else.

GitOps repo layout

The common pattern is two repos:

  • Application repo (my-app/) — source code, Dockerfile, Helm chart or Kustomize base.
  • Config repo (k8s-config/) — environment-specific values, secrets references, the YAML Argo CD watches.

CI builds an image, pushes it to a registry, then opens a PR (or commits directly via a bot) to k8s-config/ updating the image tag for the relevant environment. Argo CD picks up the change. Deploy is a git operation.

k8s-config/
├── apps/
│   ├── my-app/
│   │   ├── base/
│   │   │   ├── kustomization.yaml
│   │   │   └── deployment.yaml
│   │   └── overlays/
│   │       ├── staging/
│   │       │   ├── kustomization.yaml
│   │       │   └── values.yaml
│   │       └── prod/
│   │           ├── kustomization.yaml
│   │           └── values.yaml
│   └── another-app/...
└── argocd/
    └── apps.yaml         # ApplicationSet definition

Auditable, reviewable, rollback-able. Same primitive as code.

Secrets in GitOps — three solutions

You can't put plain Secrets in a public repo, and even private repos shouldn't store rotateable creds. Three good approaches:

External Secrets Operator (recommended for teams)

apiVersion: external-secrets.io/v1beta1
kind: SecretStore
metadata: { name: vault, namespace: prod }
spec:
  provider:
    vault:
      server: https://vault.example.com
      path: secret
      version: v2
      auth: { kubernetes: { mountPath: kubernetes, role: prod } }
---
apiVersion: external-secrets.io/v1beta1
kind: ExternalSecret
metadata: { name: db-creds, namespace: prod }
spec:
  refreshInterval: 1h
  secretStoreRef: { kind: SecretStore, name: vault }
  target: { name: db-creds }
  data:
    - secretKey: password
      remoteRef: { key: prod/db, property: password }

The actual secret lives in Vault/AWS SM/GCP SM. ESO syncs it into a K8s Secret in the cluster. Git only sees the reference, never the value.

Sealed Secrets

Encrypt the Secret with the cluster's public key; commit the encrypted blob to git; an in-cluster controller decrypts. Fine for solo / small teams.

SOPS + age/KMS

Encrypt YAML files with SOPS (using age, GPG, or a cloud KMS). Decrypt at deploy time via Argo CD's plugin or Flux. Git stores ciphertext.

Cloud-native: IRSA / Workload Identity

For cloud credentials specifically, skip the K8s Secret altogether: use AWS IRSA or GCP/Azure Workload Identity to give a Pod's ServiceAccount a cloud IAM identity. The pod uses normal AWS/GCP SDKs; no secrets in K8s.

Operators — extending Kubernetes

An operator is a custom controller for a custom resource. You teach Kubernetes a new kind (e.g. PostgresCluster, KafkaTopic, FirmwareBuild), and you ship a controller that watches that kind and does the work.

The CRD

apiVersion: apiextensions.k8s.io/v1
kind: CustomResourceDefinition
metadata:
  name: firmwarebuilds.factory.acme.com
spec:
  group: factory.acme.com
  scope: Namespaced
  names:
    kind: FirmwareBuild
    plural: firmwarebuilds
    singular: firmwarebuild
    shortNames: [fb]
  versions:
    - name: v1
      served: true
      storage: true
      schema:
        openAPIV3Schema:
          type: object
          properties:
            spec:
              type: object
              required: [machine, sourceRef]
              properties:
                machine:    { type: string, enum: [imx8, rpi4, qemu] }
                sourceRef:  { type: object, properties: { sha: { type: string } } }
                priority:   { type: string, enum: [low, normal, high], default: normal }
            status:
              type: object
              properties:
                phase:      { type: string }
                imageRef:   { type: string }
                durationSeconds: { type: integer }
      additionalPrinterColumns:
        - { name: Machine, type: string, jsonPath: .spec.machine }
        - { name: Phase,   type: string, jsonPath: .status.phase }
        - { name: Image,   type: string, jsonPath: .status.imageRef }
        - { name: Age,     type: date,   jsonPath: .metadata.creationTimestamp }

Once installed, users can:

$ kubectl get firmwarebuilds
NAME           MACHINE   PHASE       IMAGE                 AGE
nightly-imx8   imx8      Succeeded   reg.acme/fw:abc123    2h
$ kubectl describe fb nightly-imx8

Your controller watches FirmwareBuild events, runs the build (probably as a K8s Job under the hood), and updates status. The user wrote ~10 lines of YAML; you handled the rest.

How to write a controller

Two main toolkits:

  • Operator SDK / Kubebuilder in Go — most production operators. Generates scaffolding, types, controller boilerplate.
  • Kopf in Python — decorator-style, fast to prototype, fits Python shops perfectly.

Tiny Kopf example:

import kopf, kubernetes.client as k8s
from kubernetes import config

config.load_incluster_config()
batch = k8s.BatchV1Api()

@kopf.on.create('factory.acme.com', 'v1', 'firmwarebuilds')
def create_fn(spec, name, namespace, patch, **_):
    job = build_job_manifest(name, namespace, spec)
    batch.create_namespaced_job(namespace=namespace, body=job)
    patch.status['phase'] = 'Building'

@kopf.on.event('batch', 'v1', 'jobs', labels={'fb-owner': kopf.PRESENT})
def job_event(body, status, labels, **_):
    fb_name = labels['fb-owner']
    namespace = body['metadata']['namespace']
    api = k8s.CustomObjectsApi()
    if status.get('succeeded'):
        api.patch_namespaced_custom_object_status(
            'factory.acme.com', 'v1', namespace, 'firmwarebuilds', fb_name,
            {'status': {'phase': 'Succeeded'}})
    elif status.get('failed'):
        api.patch_namespaced_custom_object_status(
            'factory.acme.com', 'v1', namespace, 'firmwarebuilds', fb_name,
            {'status': {'phase': 'Failed'}})

def build_job_manifest(name, ns, spec):
    return {
        'apiVersion': 'batch/v1',
        'kind': 'Job',
        'metadata': {'name': f'fb-{name}', 'namespace': ns,
                     'labels': {'fb-owner': name}},
        'spec': {
            'backoffLimit': 1,
            'ttlSecondsAfterFinished': 86400,
            'template': {
                'spec': {
                    'restartPolicy': 'Never',
                    'containers': [{
                        'name': 'build',
                        'image': 'reg.acme/builder:1.0',
                        'args': ['--machine', spec['machine'],
                                 '--sha', spec['sourceRef']['sha']],
                    }],
                },
            },
        },
    }

Package this as a Deployment running in the cluster with the right RBAC (it needs to read FirmwareBuilds and create Jobs in the namespace). Now kubectl apply on a FirmwareBuild manifest triggers a real build.

When to write an operator

Sign you should: the lifecycle of your domain object involves multiple K8s resources, ordering, status reconciliation, and humans keep getting it wrong. Examples: managing a database cluster, provisioning IoT device fleets, modeling per-tenant infrastructure.

Sign you shouldn't: a Helm chart + a couple of CronJobs is enough. Operators are powerful and invasive — they can break upgrades, leak resources, and exhibit subtle bugs. Don't write one for "I have three YAMLs that need to apply in order".

Control plane vs data plane

The Kubernetes-shaped phrase you'll hear from operators authors and platform teams: declare desired state as data, separate from the controller that acts on it. Your YAML is the declarative API, your operator is the imperative implementation. Same shape as core K8s.

This split scales: tens of CRDs sharing the same controller, multiple controllers on different concerns, all coexisting because the API surface is data and the implementation is owned per CRD.

Hands-on: install Argo CD on kind

Hands-on · GitOps in 5 commands
# Install
$ kubectl create ns argocd
$ kubectl apply -n argocd -f https://raw.githubusercontent.com/argoproj/argo-cd/stable/manifests/install.yaml
$ kubectl -n argocd wait --for=condition=available deploy --all --timeout=180s

# Login
$ argocd admin initial-password -n argocd
$ kubectl -n argocd port-forward svc/argocd-server 8080:443 &
$ argocd login localhost:8080 --insecure --username admin
# (paste the password)

# Create an Application from a public sample repo
$ argocd app create guestbook \
    --repo https://github.com/argoproj/argocd-example-apps.git \
    --path guestbook \
    --dest-server https://kubernetes.default.svc \
    --dest-namespace default \
    --sync-policy auto

$ argocd app get guestbook
$ argocd app sync guestbook
$ kubectl get all                      # the resources Argo just synced

Now edit the upstream manifests in your fork, push, watch Argo CD reconcile in seconds. That's GitOps.

Exercises

EX 12.1 easy Helm or Kustomize?

For each, pick: (a) installing Postgres from a community chart, (b) deploying your own app to dev/staging/prod with image tag differences, (c) packaging a tool you'll publish for others to install.

Show solution

(a) Helm — that's how community charts are distributed. (b) Kustomize — small overlays per env, no templating cruft. (c) Helm — the distribution story is much better.

EX 12.2 medium Atomic upgrade

You upgrade a Helm release; one of the new pods crashes on startup. With --atomic --timeout 5m, what happens? Without?

Show solution

With --atomic: Helm waits up to 5 minutes for resources to become healthy. The new ReplicaSet's pods stay in CrashLoopBackOff. After timeout, Helm rolls back to the previous revision. You're back where you started; no traffic served by broken pods.

Without: helm upgrade returns success after applying. The Deployment is broken; Service still routes to old pods (good — readiness gates them) but you've now got a stuck rollout that needs manual intervention.

Use --atomic in CI for production releases. Always.

EX 12.3 medium GitOps drift

An engineer runs kubectl edit deploy/api in prod to bump replicas to 10. Argo CD has selfHeal: true. What happens, and what should the engineer have done?

Show solution

Argo CD detects the drift (live state differs from git), reverts replicas to the value in git, logs the OutOfSync event. The "fix" lasts seconds.

What the engineer should have done: open a PR against the config repo updating the values file, get it reviewed, merge. Argo CD applies the change. Audit log = git log. The constraint is the feature.

For genuine emergencies, GitOps tools have a "break-glass" — temporarily disable auto-sync, make the change, then commit it back to git. Always closed-loop.

EX 12.4 hard Should I write an operator?

For each, decide: write an operator, or skip?

  1. Provisioning a Kafka topic requires creating the topic, an ACL, and a Secret with credentials.
  2. Deploying a Helm chart with different values per env.
  3. Triggering a firmware build pipeline when a CR is created.
  4. Sending a Slack message when a Pod crashes.
Show solution
  1. Operator candidate — three coupled resources whose lifecycle should be atomic. Strimzi (Kafka operator) does exactly this.
  2. Skip. That's what Helm + values files already do. Argo CD + Helm covers it.
  3. Operator candidate — your own domain logic, multi-step, status to report. The capstone in Chapter 14 builds this kind of thing.
  4. Skip. A simple "alerter" Deployment that watches Pod events is enough. No need for a CRD when you don't have an API to model.

Heuristic: the operator's value comes from declarative API for your domain. If you don't have a noun worth naming, you don't need an operator.

EX 12.5 hard Secrets without secrets in git

Design a secrets flow for a GitOps-managed cluster where: production DB password is rotated weekly, no human ever sees it, and nothing sensitive is in git. Sketch the components.

Show solution

Components:

  1. Vault (or AWS Secrets Manager) holds the actual password. Rotation is automated server-side weekly.
  2. External Secrets Operator in the cluster, authenticated to Vault via Vault's Kubernetes auth method (cluster's ServiceAccount JWT proves identity).
  3. SecretStore + ExternalSecret manifests in git, referencing the Vault path — no values, only paths.
  4. Argo CD applies these manifests; ESO syncs the K8s Secret from Vault every hour.
  5. App Deployment mounts the K8s Secret normally.

Net effect: rotation in Vault → ESO picks it up within an hour → K8s Secret updated → app rolling-restarted (via a sidecar like Reloader, or the app re-reads on each request). Git only ever has references and shape; humans see nothing sensitive.

Recap

  • Helm = packaged, templated, distributable Kubernetes manifests; --atomic --timeout for safe upgrades.
  • Kustomize = patches over a base, built into kubectl, no templating language. Mix freely with Helm.
  • GitOps = git is the source of truth, a controller (Argo CD / Flux) reconciles cluster to git.
  • App-of-Apps and ApplicationSets scale GitOps to dozens or hundreds of services.
  • Secrets in GitOps: External Secrets Operator + Vault is the production path; Sealed Secrets / SOPS for smaller teams.
  • Operators teach Kubernetes new resource types via CRDs + custom controllers. Write one only when your domain genuinely warrants a declarative API.
  • Kopf for Python operators; Operator SDK / Kubebuilder for Go.
