Chapter 07 Kubernetes — Mental Model

If you remember one thing from these K8s chapters, remember this: Kubernetes is a database with control loops. You POST your desired state. Controllers watch the desired state and reconcile reality to match it. Once that lands, every other concept is mechanical.

What is Kubernetes, exactly?

Kubernetes is an orchestrator for containerised workloads. It runs on a fleet of machines (nodes), schedules containers across them, keeps them healthy, restarts them if they die, scales them, and exposes them on the network. Its public face is an API server backed by an etcd database, plus a bunch of controllers that act on what the API server says.

The control loop — the One Big Idea

Every controller in Kubernetes runs the same loop:

  1. Read the desired state (what user asked for, in etcd).
  2. Read the actual state (what's running on nodes).
  3. If they differ, take an action to close the gap.
  4. Sleep briefly, repeat forever.

Pseudocode:

while True:
    desired = api_server.get("Deployment/web")
    actual  = api_server.get("ReplicaSet for Deployment/web")
    if desired.replicas != actual.replicas:
        api_server.scale_replicaset(actual, desired.replicas)
    time.sleep(1)

This is exactly the idempotent / desired-state pattern from Chapter 6, applied at industrial scale. Every K8s feature — Deployments, Services, Ingresses, your custom operator — is a controller running this loop.

Why this design wins

Because it's self-healing. If a node crashes, taking 5 Pods with it, the desired state still says "10 Pods of Deployment/web". The controller notices the gap and creates 5 new Pods on surviving nodes. The user never had to issue a "recover" command.

Declarative, not imperative

You don't say "create this pod, then attach this volume, then start it". You say "this is the shape I want; the system: make it so". The "what" is yours; the "how" is K8s's.

# declarative — kubectl apply -f
apiVersion: apps/v1
kind: Deployment
metadata:
  name: web
spec:
  replicas: 3
  selector: { matchLabels: { app: web } }
  template:
    metadata: { labels: { app: web } }
    spec:
      containers:
        - name: nginx
          image: nginx:1.27
          ports: [{ containerPort: 80 }]

This says "I want 3 nginx pods labelled app=web". K8s makes it true and keeps it true.

Everything is a resource

Every concept in Kubernetes is a resource — a JSON document with a fixed shape. Every resource has the same envelope:

apiVersion: <group>/<version>     # e.g. apps/v1, v1, networking.k8s.io/v1
kind: <Type>                       # Pod, Deployment, Service, ConfigMap, ...
metadata:
  name: <string>
  namespace: <string>
  labels:      { ... }
  annotations: { ... }
spec:                              # what the user wants
  ...
status:                            # what the system has done (filled in by controllers)
  ...

Memorise that envelope. Every resource — built-in or custom — follows it. spec is yours to write; status is read-only output from controllers.

kubectl is just a curl wrapper

The API server is a REST/JSON service. kubectl get pods is essentially:

GET /api/v1/namespaces/default/pods
Authorization: Bearer <your token>

kubectl apply -f x.yaml sends an HTTP request to the API server. The API server validates, mutates (admission webhooks), persists to etcd, and notifies watchers. That's it.

Try it: kubectl get pods -v=8 prints the curl-equivalent for any command.

Namespaces — your tenant boundary

A namespace is a name-scope. Resources in different namespaces can have the same name. Common pattern: one namespace per app, one per environment, or both.

$ kubectl get ns
NAME              STATUS   AGE
default           Active   30d
kube-system       Active   30d
ingress-nginx     Active   25d
team-alpha        Active   12d

$ kubectl -n team-alpha get pods
$ kubectl get pods -A         # all namespaces

$ kubectl create namespace promote
$ kubectl config set-context --current --namespace=promote
# now every kubectl runs against this namespace

Namespaces aren't strong isolation — they don't block network traffic by default (NetworkPolicy does that). They're a name-scope plus a unit for RBAC and ResourceQuotas.

kubectl — the verbs you use daily

$ kubectl get pods                           # list
$ kubectl get pods -o wide                   # more columns

$ kubectl logs --previous web-abc123         # last container's logs (after a crash)

$ kubectl exec -it web-abc123 -- /bin/sh     # shell inside the container

$ kubectl apply -k ./overlays/staging        # kustomize build & apply
$ kubectl delete -f manifest.yaml            # remove

$ kubectl port-forward pod/web-abc123 8080:80    # tunnel local 8080 → pod's 80
$ kubectl cp x.txt pod/web:/tmp/                  # copy file

$ kubectl explain pod.spec.containers        # docs from the API server itself
$ kubectl api-resources                      # every kind, with shortnames
$ kubectl api-versions                       # every API group/version

One trick to internalise early: kubectl explain pod.spec.containers describes every field of every resource, sourced from the live API server. You don't need to memorise schemas; you just have to remember explain.

Hands-on: walk the loop

Hands-on · feel the control loop

Apply the hello.yaml above, then:

# In one terminal
$ kubectl get pods -l app=hello -w

# In another, scale up
$ kubectl scale deployment hello --replicas=5

# Watch the first terminal — pods appear, status goes Pending → ContainerCreating → Running

Now scale down:

$ kubectl scale deployment hello --replicas=1
# Watch pods Terminating, then disappear

Now delete the deployment but leave a stranded pod:

$ kubectl get pods -l app=hello -o name | head -1
pod/hello-7f6c5d4b8-q9p2n
$ kubectl delete pod hello-7f6c5d4b8-q9p2n
# A new pod appears almost instantly — replicaset noticed

Final cleanup:

$ kubectl delete -f hello.yaml

You just watched the control loop reconcile, three times. Internalise it.

Exercises

EX 7.1 easy spec vs status

For a Deployment, what goes in spec and what in status? Give two examples each.

Show solution

spec: replicas (desired count), template.spec.containers[].image, strategy.rollingUpdate, selector.matchLabels. Things you set.

status: availableReplicas (how many are actually serving), conditions[], observedGeneration. Things controllers fill in after acting.

EX 7.2 easy Self-healing

Without K8s, what does it take to maintain "exactly 3 web servers running" on three machines? With K8s, what does it take?

Show solution

Without K8s: a process supervisor on each box (systemd, supervisord) restarts on crash; a separate health checker + load-balancer config detects and replaces failed nodes; somebody writes the runbook for "node permanently dies — provision a new one, install software, register".

With K8s: replicas: 3 in a Deployment manifest. The controller does the rest. Process crashes → kubelet restarts container. Container fails repeatedly → pod restarts on a different node. Whole node dies → controller spawns replacement on surviving nodes.

EX 7.3 medium explain the schema

Without consulting docs, find the field that controls a pod's restart policy.

Show solution 
$ kubectl explain pod.spec.restartPolicy
KIND:     Pod
VERSION:  v1
FIELD:    restartPolicy <string>
DESCRIPTION:
    Restart policy for all containers within the pod.
    Values: Always, OnFailure, Never. Default Always.

Whenever you forget a field, kubectl explain is the answer. The schema is documented in the live API.

EX 7.4 medium Watch the API server

Run kubectl get pods -v=8 and copy the curl-equivalent line. What endpoint, what params, what auth?

Show solution

Output includes a line like:

I0423 ... GET https://127.0.0.1:65443/api/v1/namespaces/default/pods?limit=500
I0423 ... Authorization: Bearer ...REDACTED...

Endpoint: standard REST under /api/v1; namespace in the path; limit for pagination. Auth: bearer token (or client cert) from your kubeconfig. K8s isn't magic — it's a JSON API with controllers behind it.

EX 7.5 hard Write a "controller" by hand

In ~30 lines of Python, write a fake controller that ensures exactly N text files exist in a directory: poll, count, create or delete to converge. Why is it idempotent?

Show solution 
import time, uuid
from pathlib import Path

DESIRED = 5
DIR = Path("./files")

def reconcile():
    DIR.mkdir(exist_ok=True)
    actual = list(DIR.iterdir())
    diff = DESIRED - len(actual)
    if diff > 0:
        for _ in range(diff):
            (DIR / f"{uuid.uuid4()}.txt").write_text("hello")
    elif diff < 0:
        for f in actual[:-DESIRED]:
            f.unlink()

while True:
    reconcile()
    time.sleep(1)

Idempotent because each iteration recomputes from current state, not from history. Run twice, miss a tick, recover from a crash mid-write — all fine. This is exactly how every K8s controller works, scaled.

Recap

  • Kubernetes = a database (etcd) + control loops (controllers) reconciling actual to desired state.
  • Every resource has the same envelope: apiVersion, kind, metadata, spec, status.
  • You write spec; controllers fill in status.
  • kubectl is a curl-wrapper. Add -v=8 to see the actual HTTP.
  • kubectl explain documents every field, sourced from the live API.
  • Namespaces are name-scopes, not strong isolation.
  • Self-healing comes free from the loop: state-driven, not event-driven.
