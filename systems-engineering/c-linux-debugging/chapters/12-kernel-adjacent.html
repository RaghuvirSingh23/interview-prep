Chapter 12 Kernel-adjacent debug

Sometimes the bug isn't in your code. The kernel, a driver, an embedded MCU, or a deadlock between userspace and a syscall — these need different tools. dmesg, kprobes, ftrace, kgdb, JTAG, hardware watchpoints, and the embedded debug toolbox.

dmesg — the kernel's voice

The kernel prints to a ring buffer; dmesg reads it. This is where you learn that your USB device disconnected, that an OOM killer fired, that a driver shouted on init.

$ dmesg                                  # whole buffer
$ dmesg --human --ctime                  # human-readable timestamps
$ dmesg -w                               # follow (watch in real time)
$ dmesg --level=err,warn                 # filter by severity
$ dmesg | grep -i memory                 # OOM, page-faults
$ dmesg | grep -i usb                    # device events

# Boot-time messages persist:
$ journalctl -k                          # kernel messages from systemd journal
$ journalctl -k --since "1 hour ago"
$ journalctl -k -f                       # follow
$ journalctl -k -p err                   # error or higher

Things to scan for:

  • Out of memory: Killed process X → OOM killer; investigate memory pressure.
  • SLAB: Unable to allocate → kernel allocation pressure.
  • kernel BUG at ... or oops → driver crash; bug-report-worthy.
  • I/O error, Buffer I/O error, blk_update_request → disk failing.
  • TCP: out of memory -- consider tuning → socket buffer pressure.
  • nf_conntrack: table full → connection-tracking overflow.

Reading an oops

A kernel crash in a driver looks like:

BUG: kernel NULL pointer dereference, address: 0000000000000010
PGD 0 P4D 0
Oops: 0000 [#1] SMP NOPTI
CPU: 3 PID: 1234 Comm: my_app Not tainted 6.6.0
RIP: 0010:my_driver_read+0x42/0x80 [my_driver]
Code: 48 8b 47 10 48 ...
RSP: 0018:ffffabc000123c40 EFLAGS: 00010246
...
Call Trace:
 ? page_fault_handler ...
 my_driver_read+0x42/0x80 [my_driver]
 vfs_read+0xa5/0x180
 ksys_read+0x57/0xb0
 do_syscall_64+0x33/0x80

Read it like a backtrace. my_driver_read+0x42 = byte 0x42 into my_driver_read. Resolve to a line:

$ addr2line -e /lib/modules/$(uname -r)/extra/my_driver.ko -i 0x42
my_driver.c:153

Or use ./scripts/decode_stacktrace.sh from the kernel tree. For tainted kernels, check if a binary blob is loaded — distros often won't accept oops reports from tainted kernels.

ftrace — the in-tree tracer

ftrace lives in /sys/kernel/tracing (or debug/tracing on older). It can trace function entries/exits, syscalls, scheduling events, and more. trace-cmd wraps it ergonomically.

# Quick syscall trace for a process
$ sudo trace-cmd record -e syscalls -P $(pidof my_app) -- sleep 5
$ trace-cmd report | head -30

# Function-graph: tree of every kernel function called
$ sudo trace-cmd record -p function_graph -P $(pidof my_app) -l 'tcp_*' -- sleep 5
$ trace-cmd report

# Top-of-stack visualisation
$ kernelshark trace.dat

The "what's the kernel doing right now" power-tool. Function-graph for "show me the tcp_* call tree under heavy load" is hard to match.

perf for kernel work

Most of chapter 9's perf invocations work for the kernel too. Run with privileges (sudo) and on a kernel built with debug info (CONFIG_DEBUG_INFO; distro packages: linux-image-XXX-dbg):

$ sudo perf top                                          # system-wide hot kernel funcs
$ sudo perf record -ag -- sleep 30                       # 30s system-wide profile
$ sudo perf report --kallsyms=/proc/kallsyms

# Why am I in kernel?
$ sudo perf stat -e 'syscalls:sys_enter_*' -p $PID -- sleep 5

# Block I/O latency:
$ sudo perf record -e 'block:*' -ag -- sleep 5
$ sudo perf script

bpftrace for kernel one-liners

The eBPF-based tools shine in kernel observation. The bcc suite has dozens of pre-built scripts; bpftrace is the awk-equivalent.

# Histogram of disk I/O latencies
$ sudo bpftrace -e '
    kprobe:blk_account_io_start { @start[arg0] = nsecs; }
    kprobe:blk_account_io_done /@start[arg0]/ {
        @us = hist((nsecs - @start[arg0]) / 1000);
        delete(@start[arg0]);
    }'

# Trace TCP retransmissions
$ sudo bpftrace -e 'kprobe:tcp_retransmit_skb { printf("%s -> retransmit\n", comm); }'

# Why am I being killed by OOM killer? Show invoking task and target:
$ sudo bpftrace -e 'kprobe:oom_kill_process { printf("OOM kill: %s\n", str(arg1)); }'

BCC tools you'll reach for: opensnoop, execsnoop, tcpconnect, biolatency, cachetop, profile, offcputime, tcptop, filetop.

kprobes / uprobes

kprobe = breakpoint inside the kernel; uprobe = breakpoint in userspace. Both expose to bpftrace, perf, and ftrace. You can attach to "any address in tcp_v4_connect" without recompiling anything.

# Trace every entry to a kernel function:
$ sudo bpftrace -e 'kprobe:do_sys_openat2 { printf("%s opens\n", comm); }'

# Trace a specific function in a userspace binary at offset:
$ sudo bpftrace -e 'uprobe:/usr/local/bin/myapp:my_function { printf("%d\n", arg0); }'

Note: kprobes need CONFIG_KPROBES=y (default on most distros). Some functions are blacklisted (the kprobe machinery itself). Check cat /sys/kernel/debug/kprobes/blacklist.

kgdb — debugging the kernel itself

kgdb is in-kernel GDB-stub support. With it, you connect a real GDB to a running or panicked kernel.

Setup needs:

  1. Kernel built with CONFIG_KGDB, CONFIG_KGDB_SERIAL_CONSOLE, and debug info.
  2. A serial line between debugger machine and target (or virtio-serial in a VM).
  3. Kernel boot args: kgdboc=ttyS0,115200 nokaslr (KASLR makes addresses move; disable while debugging).
# Trigger entry into kgdb on the target:
$ echo g > /proc/sysrq-trigger        # sysrq-g sends SIGTRAP to kernel

# On debugger machine:
$ gdb vmlinux
(gdb) target remote /dev/ttyS0
(gdb) bt
(gdb) info threads                     # all CPUs, all tasks
(gdb) c

For kernel module debugging, load symbols with:

(gdb) lx-symbols /path/to/module-build-dir

kgdb is the heavy artillery. Day-to-day, kprobes and ftrace cover 99% of kernel curiosity. Reach for kgdb when you have a kernel deadlock, a hard panic that won't reproduce, or are bringing up a new driver.

kdb — kernel debugger console

kdb is an in-kernel mini-debugger that doesn't require a remote GDB. Activated via SysRq+g on the console; you get a prompt right on the screen. Useful on a single-machine system without serial — though most "real" debugging is via kgdb's serial GDB.

SysRq — when nothing else works

Linux's last-resort key combos. Enabled with echo 1 > /proc/sys/kernel/sysrq.

KeyEffect
SysRq + hHelp — list available commands
SysRq + sSync filesystems
SysRq + uRemount read-only
SysRq + bReboot immediately (no sync)
SysRq + cCrash the kernel — drop a kernel core
SysRq + eSIGTERM all processes except init
SysRq + iSIGKILL same
SysRq + tDump task list to dmesg
SysRq + wDump tasks in uninterruptible sleep
SysRq + lStack trace of every CPU
SysRq + gDrop into kgdb/kdb

Trigger from terminal: echo b > /proc/sysrq-trigger (root). The mnemonic for clean reboot from a stuck system is "REISUB": Raw → tErminate → kIll → Sync → Unmount → reBoot.

OOM debugging

The Out-Of-Memory killer fires when memory is critically low. It picks a victim based on a score (RSS, oom_score_adj, etc.). After a kill:

$ dmesg | grep -A 30 'killed process'
[ 4521.123]  oom-kill: ... task=my_app pid=1234 ...
[ 4521.124]  Out of memory: Killed process 1234 (my_app) total-vm:8GiB ...

Tune behaviour with oom_score_adj (write to /proc/PID/oom_score_adj; -1000 = exempt, 1000 = first to die). Or set memory cgroups (systemd's MemoryLimit=) to bound a process group.

Reading the oom-kill log: RSS = resident pages. total-vm = total virtual size (often huge with mmap). shmem = shared mem usage. Mem-Info dump shows the system's memory state — what's free, cached, slab.

Embedded debugging

For an MCU or SoC running bare-metal or an RTOS, you'll typically use:

  • JTAG/SWD probe — Segger J-Link, ST-Link, Black Magic Probe, FT2232-based, or built into evaluation boards. Hardware connection to debug pins.
  • OpenOCD — open-source server that speaks the GDB Remote Serial Protocol on one side and JTAG/SWD on the other.
  • arm-none-eabi-gdb (or aarch64-elf-gdb, riscv64-elf-gdb) — cross-debugger.
# Terminal 1: start OpenOCD against your hardware
$ openocd -f interface/stlink.cfg -f target/stm32f4x.cfg
Open On-Chip Debugger ...
Listening on port 3333 for gdb connections

# Terminal 2: cross-GDB
$ arm-none-eabi-gdb firmware.elf
(gdb) target extended-remote :3333
(gdb) monitor reset halt        # OpenOCD command, prefixed with "monitor"
(gdb) load                      # flash the binary
(gdb) b main
(gdb) c

Hardware niceties:

  • Hardware breakpoints — limited (Cortex-M usually has 6); placed by writing breakpoint registers, not by patching code. Required for code in flash.
  • Watchpoints — usually 4. Same hardware machinery as on x86.
  • Single-step — set the TRAP bit in DEMCR (Cortex-M); the CPU halts after each instruction.
  • SWO/ITM — printf-over-debug-pin, no need for UART. openocd can dump it.

Logic analyzers and protocol decoders

For "is the I2C/SPI/UART actually doing what I think?" — a $30 USB logic analyzer + sigrok/PulseView shows the bus traffic decoded. For "is the timing right?" — an oscilloscope. The kind of bug that's invisible to a debugger: a 5 ns glitch on a clock line, a too-long setup time, a noisy reset. Software won't tell you; the scope will.

Serial console — the embedded developer's printf

Boot a Linux board over serial (USB-to-TTL adapter, 115200 8N1 typical):

$ ls /dev/ttyUSB*       # or /dev/ttyACM*
/dev/ttyUSB0
$ minicom -D /dev/ttyUSB0 -b 115200
$ # or:
$ picocom /dev/ttyUSB0 -b 115200
$ # or just:
$ screen /dev/ttyUSB0 115200

Boot messages, kernel panics, U-Boot prompts — all on serial. Don't go to a customer site without a USB-serial adapter.

Cross-compiling, briefly

# Toolchain naming convention: TARGET-vendor-kernel-libc
$ aarch64-linux-gnu-gcc app.c -o app          # 64-bit ARM, glibc
$ arm-linux-gnueabihf-gcc app.c -o app        # 32-bit ARM hard-float
$ riscv64-linux-gnu-gcc app.c -o app
$ arm-none-eabi-gcc fw.c -o fw                # bare-metal ARM (no OS)

# Sysroot — where the target's libc and headers live
$ aarch64-linux-gnu-gcc --sysroot=/path/to/sysroot ...

# Run target binary on host via QEMU user-mode emulation:
$ qemu-aarch64 -L /path/to/sysroot ./app

Yocto and Buildroot generate sysroots and toolchains for entire embedded distributions. conan, vcpkg, CMake toolchain files are how you wire cross-compilation into the build.

Hands-on: trace why a process is in D-state

Hands-on · uninterruptible sleep — what is it doing?
$ ps -eo pid,state,wchan:30,comm | awk '$2 == "D"'
1234 D    blk_finish_plug                stuck_app

# wchan tells you the kernel function the task is blocked in. Get the full kernel stack:
$ sudo cat /proc/1234/stack
[<0>] blk_finish_plug+0x4a/0x60
[<0>] do_blockdev_direct_IO+0x...
[<0>] ext4_direct_IO+0x...
[<0>] generic_file_read_iter+0x...
[<0>] ksys_read+0x...

# Or with bpftrace:
$ sudo bpftrace -e '
    profile:hz:99 /pid == 1234/ {
        @[kstack] = count();
    }'

The kernel stack tells you the process is doing direct I/O on ext4. If it's there for minutes, the underlying disk is slow or the device is dead. iostat -xz 1 + dmesg will tell you which.

Exercises

EX 12.1 easy Read an oops

From this oops fragment, where in my_driver.c did the crash happen?

RIP: 0010:my_driver_irq+0x36/0x70 [my_driver]
Show solution 
$ addr2line -e /lib/modules/$(uname -r)/extra/my_driver.ko -i 0x36
my_driver.c:148

Or use ./scripts/decode_stacktrace.sh from the kernel source tree, which decodes a whole oops at once.

EX 12.2 medium Why D-state?

A process shows state D in ps for several seconds. kill -9 doesn't work. Why, and how do you find out what it's blocked on?

Show solution

D = uninterruptible sleep. Kernel guarantees this state can't be interrupted by signals — typically because the process is in a critical kernel path (block I/O, NFS, mutex held by another task). kill -9 queues a signal but it can't be delivered until the task returns to user mode.

Find out what it's blocked in: cat /proc/PID/wchan (one function), or cat /proc/PID/stack (full kernel stack, root-only). For NFS, that's usually a stuck server — fix the server or unmount with -l (lazy).

EX 12.3 medium OOM killed without warning

Your service vanishes. systemd restarted it; you don't know why. How do you confirm it was OOM, and how do you keep it from being a victim next time?

Show solution 
$ journalctl -k --since "10 min ago" | grep -i oom
$ dmesg | grep -i 'killed process'

If OOM killer fired, the dmesg shows the victim. Mitigations:

  • echo -1000 > /proc/$PID/oom_score_adj — exempt this process. Use carefully; you might just shift the kill to something else.
  • Lower the score for less important processes (oom_score_adj > 0).
  • Set a cgroup memory limit on the noisy neighbour so it crashes itself rather than the system getting low globally.
  • Add swap; tune vm.swappiness.
  • Fix the actual leak — heaptrack/massif.
EX 12.4 hard Embedded breakpoint limit

You're debugging firmware on a Cortex-M4. You set a 7th breakpoint and GDB silently turns it into a software breakpoint that doesn't fire. Why?

Show solution

Cortex-M4 has 6 hardware breakpoints (FPB unit). Software breakpoints work by patching the instruction with BKPT — but if the code is in flash, you can't patch it without flashing. GDB falls back to "set breakpoint" but the patch never lands; nothing fires.

Fixes:

  • Use fewer hardware breakpoints — clear unused ones.
  • For RAM-resident code, software breakpoints work normally.
  • For flash-resident code, attach a BKPT instruction at the source (insert a __BKPT() intrinsic), or use a JTAG hardware breakpoint resource.
  • Some debug probes support FPB rewriting at runtime.
EX 12.5 hard Latency hidden in the kernel

A real-time process misses its 1 ms deadline a few times per minute. Userspace profile (perf) shows nothing hot. What kernel-side mechanisms could cause this, and how do you confirm?

Show solution

Common culprits:

  • Interrupt storm on the CPU your process runs on. Pin the process to an isolated CPU with taskset + boot with isolcpus=.
  • Long kernel paths with preemption disabled — measure with cyclictest and ftrace's preemptirqsoff tracer.
  • RCU grace periods or workqueue activity on the same CPU.
  • SMI (System Management Interrupts) — invisible to OS profilers; you'll need turbostat or hardware-level tools to detect.
  • Power management — C-states; pin with idle=poll or use cpuidle.off=1 on the kernel cmdline.

Tools: cyclictest -p 99 -t1 -h 100 for latency histogram. tracecmd with function_graph for the offending kernel path. PREEMPT_RT kernel for hard-real-time guarantees.

Recap

  • dmesg / journalctl -k — first stop for kernel-level issues.
  • Kernel oops + addr2line = source location.
  • ftrace / trace-cmd for in-tree tracing of kernel control flow and syscalls.
  • perf and bpftrace work on the kernel as well as userspace.
  • kprobes/uprobes attach to arbitrary functions without recompiling.
  • kgdb + remote GDB to debug kernel itself; sysrq to drop in.
  • Embedded: OpenOCD + JTAG/SWD + cross-GDB, plus serial console.
  • Logic analyzers and oscilloscopes when the bug is below software's view.
