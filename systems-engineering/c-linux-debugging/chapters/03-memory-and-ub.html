Chapter 03 Memory model & undefined behaviour

The thing that separates "writes C/C++" from "writes correct C/C++" is a working model of memory and undefined behaviour. This chapter is the rules and the why-they-exist. Read it once carefully; the rest of your debugging life is easier.

A process's address space

On Linux x86_64, a typical user-space process sees a 48-bit virtual address space (split low/high), laid out roughly:

0x7fff'ffff'ffff  ┌──────────────────────────┐  high
                  │   stack (grows down)     │
                  │ ↓                        │
                  │                          │
                  │   ...                    │
                  │                          │
                  │ ↑                        │
                  │   mmap region            │  <- shared libs, large mallocs
                  │ ↑                        │
                  │                          │
                  │   heap (brk, grows up)   │
                  ├──────────────────────────┤
                  │   .bss   (zero-init)     │
                  │   .data  (init data)     │
                  │   .rodata (read-only)    │
                  │   .text  (code)          │
0x0000'0000'0000  └──────────────────────────┘  low (page 0 unmapped — NULL)

Things to internalise:

  • Every byte of memory you touch goes through the MMU. A wild pointer often hits an unmapped page → SIGSEGV.
  • The first page is never mapped, so any pointer in [0, 4096) — yes including NULL — segfaults on dereference. Useful: NULL derefs are loud.
  • Stack and heap grow toward each other (modern systems use guard pages and ASLR; the picture is approximate).
  • ASLR (Address Space Layout Randomisation) shuffles base addresses every run, so pointers in printouts won't match between runs.

void f(void) {

}

Undefined behaviour — what it really means

UB is not "the program might crash". UB is "the standard says nothing — the compiler can do anything". In practice, modern compilers assume UB doesn't happen and optimise on that assumption. The result of triggering UB can be:

  • The expected behaviour (your luck).
  • A silent miscalculation.
  • A crash now.
  • A crash next Tuesday at 03:00 in production.
  • A change in behaviour across compiler versions, optimisation levels, or unrelated edits.

The compiler is not being mean. It's leveraging UB to optimise — e.g. dead-code elimination relies on "if I prove that path leads to UB, the path can't be taken, so skip it".

The UB hit list

Roughly in order of "how often you'll hit it":

1 · Out-of-bounds access

int a[10];
a[10] = 0;          /* UB — index 10 is one past the end */
a[-1] = 0;          /* UB — too low */

ASan catches this at the moment it happens.

2 · Dereference of NULL or invalid pointer

int *p = NULL;
*p = 0;              /* UB — usually SIGSEGV; but the compiler may have already pruned */

int *q;              /* uninitialised */
*q = 0;              /* UB — q's value is whatever happened to be in that memory */

3 · Use after free

int *p = malloc(sizeof *p);
*p = 7;
free(p);
*p = 8;              /* UB — you don't own that memory anymore */

ASan catches it. p = NULL; after free is a cheap defensive habit.

4 · Signed integer overflow

int x = INT_MAX;
int y = x + 1;       /* UB — signed overflow */

UBSan catches it. Note: unsigned overflow is well-defined (wraps mod 2^N). Use unsigned for hashes and counters where wrap-around is intentional.

5 · Shift by too many bits

int x = 1 << 32;     /* UB on 32-bit int */
int y = -1 << 1;     /* UB before C++14 / C99 — "left shift of negative value" */

6 · Strict aliasing violation

float f = 3.14f;
int   i = *(int *)&f;            /* UB — accessing a float through an int pointer */

Use memcpy instead — guaranteed correct, optimises to nothing on modern compilers:

int i;
memcpy(&i, &f, sizeof i);        /* OK; bit-pattern reinterpretation */

Or in C++20+: std::bit_cast<int>(f).

7 · Misaligned access

char buf[100];
double *p = (double *)(buf + 1); /* alignment violation if buf is not 8-aligned at +1 */
*p = 3.14;                       /* UB — works on x86 (slow), faults on ARMv7 */

8 · Sequencing in expressions

int i = 0;
i = i++ + 1;          /* UB pre-C11/C++17; even now smells. Don't. */

a[i] = i++;           /* UB — same object modified twice between sequence points */
printf("%d %d\n", i, ++i);  /* UB — i and ++i both read; order unspecified */

9 · Reading uninitialised memory

Including padding bytes in structs. MSan catches this exact case (Chapter 11).

10 · Data races (multi-threaded)

Two threads, no synchronisation, at least one writes — UB. TSan catches it.

Strict aliasing — the rules

The compiler may assume that distinct types don't alias (don't refer to the same memory). This lets it cache values across operations on differently-typed pointers.

The legal exceptions:

  • Access via char*, signed char*, or unsigned char* is always allowed (these can alias anything).
  • Access via the same type, including added cv-qualifiers (const T* can read what T* wrote).
  • Access via a "compatible" type as defined by C — same underlying tag, etc.
  • memcpy between objects.
  • In C, a union's active member can be read; in C++ this is conditionally allowed.

The right way to reinterpret bits:

uint32_t bits;
float    f = ...;
memcpy(&bits, &f, sizeof bits);     /* legal everywhere */

C++20 adds std::bit_cast<T> which is a constexpr-friendly version of the same idea.

Alignment

Every type has an alignment requirement: int on a 4-byte boundary, double on 8, etc. malloc returns memory aligned for any standard type. Misaligned access is UB even though x86 is forgiving — ARMv7 happily traps. Get used to alignas when laying out structs for SIMD or hardware MMIO.

#include <stdalign.h>
alignas(64) struct CacheLine { int counter; };

Lifetime

An object's lifetime is the interval from when its storage is allocated and constructed to when it's destroyed. Reading or writing outside this interval is UB.

const std::string& trap() {
    return std::string("temp");      // temporary — destroyed at end of statement
}
const auto& ref = trap();            // ref dangles
puts(ref.c_str());                    // UB

Common lifetime mistakes:

  • Returning a pointer/reference to a local.
  • Storing a string_view or span that outlives its source.
  • Iterator invalidation — push_back into a vector, your old iterators may dangle.
  • Capturing by reference in a lambda that's stored or posted to a thread.

Iterator invalidation cheatsheet

ContainerInvalidates iterators on…

Endianness, sign bit, padding

Integer width and signedness are sized; representation isn't:

  • Endianness: little-endian on x86 and most ARM, big-endian on some embedded and network protocols.
  • Signed representation: two's-complement is the only representation in C++20 / C23 (older standards permitted ones'-complement and sign-magnitude — extinct).
  • Struct padding: the compiler inserts bytes between members to satisfy alignment. memcmping two structs is broken because of padding noise. Either zero-init both, or compare member-wise, or use __attribute__((packed)) for wire formats (with care).
uint32_t htobe32_v(uint32_t v) {        /* host → big-endian (network order) */
    return ((v & 0xff)         << 24)
         | ((v & 0xff00)       << 8)
         | ((v & 0xff'0000)    >> 8)
         | ((v & 0xff00'0000)  >> 24);
}
/* In real code: htonl(v) on POSIX, or __builtin_bswap32(v). */

Stack: layout, growth, overflows

Each thread has a stack — typically 8 MiB on Linux. Each function call pushes a stack frame: saved registers, return address, locals, alignment padding, the next frame's args.

Stack overflow happens when recursion is too deep or you put a giant array on the stack. The kernel's guard page makes the next access fault — usually SIGSEGV. ulimit -s shows the limit.

void infinite(int x) { infinite(x + 1); }     /* stack overflow */

void big_local(void) {
    char huge[16 * 1024 * 1024];               /* 16 MiB on the stack — bang */
}

Use the heap or static storage for large buffers. Recursive algorithms with unbounded depth need iteration.

Heap: allocators, fragmentation

The default allocator on Linux glibc is ptmalloc2 (a thread-local-arena variant). Alternative allocators in real production:

  • jemalloc, tcmalloc, mimalloc — generally faster, better fragmentation.
  • Custom arenas — preallocate, hand out from a region, reset all at once. Game engines, parsers, request handlers.

The cost of malloc is non-trivial: a typical allocation is 100s of cycles. In hot paths, allocate once and reuse. vector::reserve before push-back loops. Pool small objects.

Signed overflow — and why -fwrapv

The compiler exploits "signed overflow doesn't happen" for optimisations. Two relevant flags:

-fwrapvDefine signed overflow as 2's-complement wrap. Pessimises some loops; makes some bugs deterministic.
-ftrapvTrap on signed overflow at runtime. Heavy; useful in test builds.
-fsanitize=signed-integer-overflow (UBSan)Catch and report at runtime. The right choice for dev/test.

Hands-on: see UBSan in action

Hands-on · the compiler is not bluffing
coverflow.c
#include <limits.h>
#include <stdio.h>

int main(void) {
    int x = INT_MAX;
    int y = x + 1;            /* signed overflow */
    printf("%d\n", y);
    return 0;
}

$ cc -O2 overflow.c -o overflow && ./overflow
-2147483648                          # often prints this on x86, but UB

$ cc -O2 -fsanitize=undefined overflow.c -o overflow && ./overflow
overflow.c:6:15: runtime error: signed integer overflow:
2147483647 + 1 cannot be represented in type 'int'
-2147483648

UBSan tells you exactly where, with line and column. In a real bug report, that's three hours saved.

Exercises

EX 3.1 easy UB census

List the UB(s) in this snippet:

void f(int *a, size_t n) {
    int *p;
    for (size_t i = 0; i < n; i++) {
        p = &a[i];
        a[i+1] = *p;          // (1)
    }
    free(p);                  // (2)
}
Show solution
  1. The last iteration writes a[n] — one past the end of a. UB if a is sized exactly n.
  2. You're free()ing a pointer that wasn't returned from malloc — it's a pointer into the middle of a. UB.
EX 3.2 easy memcpy or punning?

Convert this strict-aliasing-violating type-pun to a safe equivalent:

uint32_t bits = *(uint32_t *)&float_value;
Show solution 
uint32_t bits;
memcpy(&bits, &float_value, sizeof bits);

Compilers reliably optimise this to a single load on every modern target. In C++20: auto bits = std::bit_cast<uint32_t>(float_value);.

EX 3.3 medium Optimisation removes my check

This null-check seems to disappear at -O2. Why?

void f(int *p) {
    int x = *p;            /* assume p != NULL */
    if (p == NULL) abort();  /* defensive */
    use(x);
}
Show solution

The compiler sees that the dereference *p would be UB if p == NULL. UB doesn't happen in well-defined programs, so the compiler concludes p can't be NULL at that point. The subsequent check is dead code — eliminated.

Fix: check before dereferencing.

void f(int *p) {
    if (p == NULL) abort();
    use(*p);
}

This is the canonical example of "UB-driven optimisation surprises". -fsanitize=null catches the original at runtime.

EX 3.4 hard Iterator invalidation

Why does this segfault sometimes and not others?

std::vector<int> v = {1, 2, 3};
for (auto it = v.begin(); it != v.end(); ++it) {
    if (*it == 2) v.push_back(99);
}
Show solution

push_back may reallocate — when capacity is exceeded, the vector copies into a new buffer and frees the old. Existing iterators (and pointers, references) into the old buffer dangle. The next ++it or *it is UB.

Whether it segfaults depends on whether reallocation happened, and whether the freed memory has been reused. Hence "sometimes".

Fix one of:

  • v.reserve(big) before the loop, so no reallocation occurs.
  • Collect the new items in a temp, append after.
  • Index-based loop: for (size_t i = 0; i < v.size(); i++).
EX 3.5 hard Why is signed-overflow UB but unsigned isn't?
Show solution

Historically, C had to support multiple representations of signed integers (two's complement, ones' complement, sign-magnitude). Defining overflow behaviour would have pinned the representation. Leaving it undefined preserved the option to compile efficiently on every machine.

The modern reason: leaving signed overflow UB lets the compiler assume i + 1 > i (no wrap), which is essential for many loop optimisations (e.g. proving termination, vectorising). Forcing wrap-around would prevent these.

Unsigned has always had defined wrap-around because it's used as a discrete modular type — for hashing, bit-fiddling, indices.

If you want signed wrap, use -fwrapv or do the arithmetic in unsigned and convert back. But know what you're trading.

Recap

  • UB means the compiler can do anything — it will optimise on the assumption you don't trigger it.
  • The hit list: out-of-bounds, NULL/uninitialised deref, use-after-free, signed overflow, shift-by-too-much, strict aliasing, misalignment, sequence violations, uninitialised reads, data races.
  • Reinterpret bits via memcpy or std::bit_cast, never via differently-typed pointer dereference.
  • Lifetime: the most-foot-gunned bit of C++ — locals, temporaries, iterators, lambda captures.
  • Run dev builds with -fsanitize=address,undefined. Cost is small, payoff is enormous.
