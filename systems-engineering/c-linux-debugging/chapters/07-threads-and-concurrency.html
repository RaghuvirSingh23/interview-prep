Chapter 07 Threads & concurrency

Multi-threading in C/C++ is where the easy bugs become expensive and the expensive ones become career-defining. This chapter: pthreads, std::thread, mutexes, condition variables, atomics with the right memory order, false sharing, the data race, and the patterns that survive code review.

Threads — pthreads, std::thread, std::jthread

#include <thread>
#include <chrono>
#include <iostream>

void worker(int id) {
    std::this_thread::sleep_for(std::chrono::milliseconds(100));
    std::cout << "worker " << id << "\n";
}

int main() {
    std::thread t1(worker, 1);
    std::thread t2(worker, 2);
    t1.join();
    t2.join();   // forget this and the destructor calls std::terminate
    // C++20: std::jthread joins automatically and supports cancellation
}

For C, pthreads:

#include <pthread.h>
#include <stdio.h>

static void *worker(void *arg) {
    int id = *(int *)arg;
    printf("worker %d\n", id);
    return NULL;
}

int main(void) {
    pthread_t t1, t2;
    int a = 1, b = 2;
    pthread_create(&t1, NULL, worker, &a);
    pthread_create(&t2, NULL, worker, &b);
    pthread_join(t1, NULL);
    pthread_join(t2, NULL);
    return 0;
}

Compile with -pthread (defines macros and links the right runtime). Modern glibc folds pthread into libc; older systems need -lpthread at link.

std::jthread (C++20) auto-joins on destruction, supports stop_token for cooperative cancellation. Prefer it.

The data race — what's actually going on

A data race is two threads accessing the same memory location, at least one writing, with no synchronisation between them. It's UB in C and C++ — the standard makes no guarantees. Concrete consequences on real CPUs:

  • Torn reads/writes — a 64-bit write isn't atomic on 32-bit hardware; you can read half-old, half-new.
  • Stale values — the compiler caches the value in a register; doesn't re-read.
  • Reordering — both compiler and CPU may reorder loads and stores around your code.
  • Write tearing in registers — non-atomic stores on x86 are atomic for aligned values up to 64 bits, but the compiler may still split larger stores.
/* Classic broken pattern */
volatile bool stop = false;
/* thread A */
while (!stop) work();

/* thread B */
stop = true;

volatile is not enough. It tells the compiler "don't optimise away accesses" — it does NOT add memory barriers, doesn't synchronise with other threads, doesn't prevent CPU reordering. Use volatile for memory-mapped I/O and signal-handler flags. For thread communication, use atomics or mutexes.

Mutex — the basic synchronisation

#include <mutex>

class Counter {
    mutable std::mutex m_;
    long n_ = 0;
public:
    void inc() {
        std::lock_guard<std::mutex> lk(m_);   // RAII — unlocks on scope exit
        ++n_;
    }
    long get() const {
        std::lock_guard<std::mutex> lk(m_);
        return n_;
    }
};

Three lock guards, all RAII:

TypeUse when
std::lock_guard Simple lock for one scope; can't be moved or unlocked early
std::unique_lock Need to unlock early, transfer ownership, use with condvar, or defer the lock
std::scoped_lock (C++17)Lock multiple mutexes deadlock-free in one go

Rules:

  1. Always RAII — never bare m.lock()/m.unlock(); an exception will leave it locked.
  2. Hold the smallest scope possible — but never call code that may take another lock while holding this one, unless ordering is total.
  3. Lock multiple mutexes in a fixed order across the program, or use std::scoped_lock(m1, m2) which uses deadlock-avoidance.
  4. Don't recurse into a locked region with the same non-recursive mutex. std::recursive_mutex exists; using it is a code smell.
Deadlock — the canonical recipe

Thread A locks M1, then needs M2. Thread B locks M2, then needs M1. Both wait forever. Always lock in the same order, everywhere. std::scoped_lock(m1, m2) uses an algorithm that avoids the cycle.

Condition variables — wait for state changes

Mutexes give "only one at a time"; condition variables let a thread sleep until something becomes true.

#include <mutex>
#include <condition_variable>
#include <queue>

template <class T>
class Channel {
    std::mutex              m_;
    std::condition_variable not_empty_;
    std::queue<T>           q_;
    bool                    closed_ = false;
public:
    void send(T v) {
        {
            std::lock_guard lk(m_);
            q_.push(std::move(v));
        }
        not_empty_.notify_one();
    }
    bool recv(T& out) {
        std::unique_lock lk(m_);
        not_empty_.wait(lk, [this]{ return !q_.empty() || closed_; });
        if (q_.empty()) return false;          // closed, drained
        out = std::move(q_.front()); q_.pop();
        return true;
    }
    void close() {
        { std::lock_guard lk(m_); closed_ = true; }
        not_empty_.notify_all();
    }
};

The crucial idiom: cv.wait(lk, predicate). It atomically releases the lock and sleeps; on wakeup, re-acquires the lock and re-checks the predicate. Never wait without a predicate — spurious wakeups happen and you must re-check anyway.

notify_one wakes one waiter; notify_all wakes all. Notify after releasing the lock if you can — wakees would just block on the lock you still hold.

Atomics — the right primitive for shared flags and counters

#include <atomic>

std::atomic<bool> stop = false;
std::atomic<long> counter = 0;

void worker() {
    while (!stop.load(std::memory_order_acquire)) {
        counter.fetch_add(1, std::memory_order_relaxed);
    }
}

void stopper() {
    stop.store(true, std::memory_order_release);
}

Atomics are lock-free for typical sizes (1, 2, 4, 8 bytes on x86_64). They're fast — no syscall, no kernel involvement — and they prevent the data-race UB. The catch: you must pick a memory order.

Memory orderings, briefly

OrderingWhat it gives youWhen
memory_order_relaxed Atomic only — no ordering with other ops Counters where you only need the final total
memory_order_acquire This load synchronises with a release store; sees prior writes by the storerReading a "ready" flag
memory_order_release This store publishes prior writes; the matching acquire sees themWriting the "ready" flag last
memory_order_acq_rel Both RMW like fetch_add when ordering matters both ways
memory_order_seq_cst (default)Sequentially consistent — total order across all threadsThe safe default; what you want unless profiling says otherwise

The mental model: release is "publish", acquire is "subscribe". The store-release on one thread plus the matching load-acquire on another guarantees that everything written before the release is visible after the acquire.

Default to seq_cst. Use acquire/release when you've measured a hot path and need to relax. Use relaxed only for "just count something; final value is all I care about". Wrong memory orders are subtle bugs that pass tests for years.

Compare-and-swap, lock-free patterns

std::atomic<int> v{0};

/* CAS — atomically: if v == expected, set v = desired; return success/failure
   On failure, expected is updated to current value. Loop is the standard pattern. */
int cur = v.load();
do {
    /* compute new based on cur */
} while (!v.compare_exchange_weak(cur, cur + 1));   // spurious failures allowed

/* compare_exchange_strong: no spurious failures, slightly slower; use outside loops. */

CAS is the heart of lock-free algorithms. compare_exchange_weak in a loop, strong when you're not looping. The implementation is cmpxchg on x86, ldrex/strex (load-linked / store-conditional) on ARM.

Lock-free is hard. ABA problem, memory reclamation, the Treiber stack vs the Michael-Scott queue — these are research-paper-level. Use std::atomic<std::shared_ptr<T>> (C++20), Folly's UnboundedQueue, or just a mutex + std::queue. Profile first, lock-free later.

False sharing

CPU caches operate at cache-line granularity (typically 64 bytes). Two atomic counters on the same cache line cause threads to ping-pong the line between caches — much slower than if they were apart.

// BAD — counters share a cache line
struct Bad {
    std::atomic<long> a;
    std::atomic<long> b;   // probably in the same 64-byte line as a
};

// GOOD — pad to separate lines
struct alignas(64) Counter { std::atomic<long> v; char _pad[64 - sizeof(v)]; };
struct Good { Counter a; Counter b; };

Or use std::hardware_destructive_interference_size (C++17) instead of the literal 64. False sharing is the #1 reason "I added a thread and got slower".

Patterns that survive review

Producer-consumer

BoundedQueue<Job> q(64);

void producer() {
    while (auto job = next_job()) q.push(*job);
    q.close();
}

void consumer() {
    Job j;
    while (q.pop(j)) process(j);
}

Worker pool

std::vector<std::jthread> workers;
for (int i = 0; i < N; i++)
    workers.emplace_back([&](std::stop_token st) {
        Job j;
        while (!st.stop_requested() && q.pop(j)) process(j);
    });
// Destruction joins all jthreads automatically.

Read-mostly state

For data read often, written rarely, std::shared_mutex:

std::shared_mutex sm;
std::unordered_map<K, V> data;

V get(const K& k) {
    std::shared_lock lk(sm);                 // many readers
    return data.at(k);
}
void set(K k, V v) {
    std::unique_lock lk(sm);                 // exclusive writer
    data[std::move(k)] = std::move(v);
}

Don't reach for shared_mutex by default — it's heavier than a regular mutex per op. Only use when the read:write ratio is genuinely high.

Thread-local storage

thread_local int tls_value = 0;
thread_local std::vector<int> per_thread_buffer;

Every thread has its own copy. Useful for per-thread caches and arenas. Costs: first access on a thread initialises (slow), threading models that pool threads carry old TLS state into new uses, fork doesn't reinitialise child's TLS.

A note on RCU and userspace

For really hot read-mostly data structures, RCU (Read-Copy-Update) lets readers proceed without locks. The Linux kernel uses it pervasively. In userspace: liburcu. Complex to use right; reach for it only when profiling shows shared-mutex contention as the bottleneck.

Threads and signals — the rules

  1. A signal sent to a process can be delivered to any thread that doesn't have it blocked.
  2. Mask signals in worker threads, handle them in one designated thread.
  3. pthread_sigmask / signalfd are the modern way.
  4. Async-signal-safe rules apply per signal handler — same as in single-threaded.
// At program start, before spawning threads:
sigset_t set;
sigemptyset(&set);
sigaddset(&set, SIGTERM);
sigaddset(&set, SIGINT);
pthread_sigmask(SIG_BLOCK, &set, nullptr);
// New threads inherit this mask. One designated thread does sigwait().

std::thread signaller([set]{
    int sig;
    sigwait(&set, &sig);
    request_stop();
});

TSan — race detection that works

ThreadSanitizer instruments every memory access with shadow-memory bookkeeping; on a race it prints both stacks. Cost is ~5–15× slowdown — fine for tests.

$ c++ -std=c++20 -O1 -g -fsanitize=thread race.cpp -o race
$ ./race
==================
WARNING: ThreadSanitizer: data race (pid=12345)
  Write of size 4 at 0x... by thread T1:
    #0 worker race.cpp:12

  Previous read of size 4 at 0x... by thread T2:
    #0 reader race.cpp:18

  Location is global 'counter' of size 4 at 0x...
==================

Run your tests under TSan in CI. Every race it finds is real.

Hands-on: a counter that breaks

Hands-on · see TSan in action
#include <thread>
#include <vector>
#include <cstdio>

long counter = 0;

void worker() {
    for (int i = 0; i < 1'000'000; i++) counter++;
}

int main() {
    std::vector<std::thread> ts;
    for (int i = 0; i < 8; i++) ts.emplace_back(worker);
    for (auto& t : ts) t.join();
    std::printf("counter = %ld (expected %d)\n", counter, 8'000'000);
}

$ c++ -O2 -std=c++20 race.cpp -o race && ./race
counter = 1325617 (expected 8000000)            # arbitrary low number — lost increments

$ c++ -O1 -g -fsanitize=thread race.cpp -o race && ./race
WARNING: ThreadSanitizer: data race ...
counter = ... (expected 8000000)

Now make it correct: change long counter to std::atomic<long> counter{0} and counter++ works (atomic RMW). The result is exactly 8,000,000.

Exercises

EX 7.1 easy Why isn't volatile enough?
Show solution

volatile means "the compiler must read/write the variable as written; no caching in registers". It does not:

  • Make accesses atomic. A 64-bit write may still tear on 32-bit hardware.
  • Insert memory barriers — CPU reordering can still happen.
  • Establish a happens-before relationship — other writes around the volatile aren't ordered by it.

Use std::atomic (C++) or _Atomic (C11). Use volatile for memory-mapped I/O registers and sig_atomic_t flags from signal handlers — that's all.

EX 7.2 medium Spurious wakeup

Why does cv.wait(lk) need a predicate?

Show solution

Two reasons:

  1. Spurious wakeups: the implementation is allowed to wake a waiter even when no one notified. Without a predicate, you'd treat noise as signal.
  2. Stolen wakeups: another thread won the race after notify and consumed the resource (e.g. queue went empty between notify and your wakeup). You'd return without data.

The predicate-version cv.wait(lk, [&]{ return ready; }) handles both — re-checks the condition after each wakeup, sleeps again if false.

EX 7.3 medium Memory order for a flag

One thread builds a struct, then sets a "ready" flag. Another thread polls the flag, reads the struct on true. What memory orders make this correct?

Show solution 
std::atomic<bool> ready{false};
Big data;

// Producer
data = build_big();
ready.store(true, std::memory_order_release);

// Consumer
while (!ready.load(std::memory_order_acquire)) std::this_thread::yield();
use(data);

The release-acquire pair guarantees that everything the producer wrote before the store is visible to the consumer after the acquire. Without those orders (or with relaxed), the consumer can read ready=true but stale or partial data — UB-flavoured race even with atomic ready.

EX 7.4 hard Deadlock-free multi-mutex

You have Account a, b. transfer(a, b, 10) needs to lock both. Calls happen in any order. Show two ways to avoid deadlock.

Show solution

(1) Address ordering:

void transfer(Account& a, Account& b, int amount) {
    auto* lo = std::min(&a, &b);
    auto* hi = std::max(&a, &b);
    std::lock_guard l1(lo->m);
    std::lock_guard l2(hi->m);
    a.balance -= amount;
    b.balance += amount;
}

(2) std::scoped_lock (C++17) — uses an algorithm that avoids cycles:

void transfer(Account& a, Account& b, int amount) {
    std::scoped_lock lk(a.m, b.m);
    a.balance -= amount;
    b.balance += amount;
}

scoped_lock is the modern default — readable and correct.

EX 7.5 hard False sharing benchmark

Write a benchmark with two threads each incrementing their own counter 100M times. Compare: counters in same struct (no padding) vs aligned to 64 bytes. Why is the difference what you see?

Show solution

Without padding, both counters land in the same cache line. Each increment makes that line dirty, the other CPU's cache invalidates, and the line ping-pongs between cores at memory-system speed. Throughput collapses by 5–10×.

With alignas(64) or explicit padding, the counters sit on separate lines. Each thread keeps its line in its L1 cache; no coherence traffic; near-linear speedup.

Measure with perf stat -e cache-misses,L1-dcache-load-misses. The difference is dramatic and a real-world cause of "added a thread, got slower".

Recap

  • Data races are UB — even with volatile. Use atomics or mutexes.
  • RAII for every mutex (lock_guard, unique_lock, scoped_lock). Lock multiple in fixed order or via scoped_lock.
  • Condition variables: always loop on a predicate; notify after releasing the mutex.
  • Atomics with seq_cst by default; learn release/acquire when profiling demands it.
  • False sharing causes inexplicable slowdowns; pad shared atomics to cache-line size.
  • Use TSan in CI. Every report is real.
  • Mask signals in workers; handle them via signalfd or one designated thread.
