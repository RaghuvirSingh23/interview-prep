Chapter 02 C++ — the modern subset

The C++ you write in 2026 is a different language from the C++ of 2003. RAII, smart pointers, references, move semantics, lambdas, templates that don't make you cry. This chapter focuses on the modern subset — the parts that earn their complexity.

Pick a dialect, pin it

$ c++ --version
g++ (GCC) 14.2.0
$ c++ -std=c++20 -Wall -Wextra -Wpedantic -O2 -g hello.cpp -o hello

C++20 is the practical default in 2026: concepts, ranges, std::span, std::format, three-way comparison, structured bindings (already in 17), modules (still rough). C++23 adds nice-to-haves but compiler support is uneven. Codebases still on C++17 are common; the gap to 20 is small.

Reach for these warnings: -Wall -Wextra -Wpedantic -Wshadow -Wnon-virtual-dtor -Wnull-dereference -Wuseless-cast. With -fsanitize=address,undefined in dev builds.

RAII — the One Big Idea

Resource Acquisition Is Initialisation. A handle (file, mutex, allocation, lock, socket) is owned by an object whose destructor releases it. When the object goes out of scope — by return, by exception, by anything — the resource is released. Deterministic, automatic.

#include <fstream>
#include <string>

void write_log(const std::string& line) {
    std::ofstream f("/var/log/app.log", std::ios::app);  // ctor opens
    f << line << "\n";
    // dtor closes here, even if an exception is thrown above
}

The mental model: "every resource has an owner; when the owner dies, so does the resource". Apply this and most lifetime bugs vanish.

Smart pointers — owners with semantics

Three you actually use:

TypeOwnsCopy?Move?
std::unique_ptr<T>One ownerNoYes — transfers ownership
std::shared_ptr<T>Reference-countedYes — bumps refcountYes
std::weak_ptr<T>Non-owning observerYesYes
 
#include <memory>
#include <string>

struct Job {
    std::string name;
    Job(std::string n) : name(std::move(n)) {}
};

auto j = std::make_unique<Job>("compile");        // unique owner
// auto k = j;                                     // ERROR — can't copy unique_ptr
auto k = std::move(j);                            // OK — transfer; j is now nullptr

auto s = std::make_shared<Job>("link");           // shared owner
auto t = s;                                       // OK — shared, refcount=2
std::weak_ptr<Job> w = s;                         // observer, no count

Default to unique_ptr. Use shared_ptr only when ownership is genuinely shared. weak_ptr breaks cycles or models "may be alive, may not".

Don't new when make_unique exists

std::make_unique<T>(args...) is exception-safe and concise. Bare new in modern C++ is a code smell — almost always replaceable with a smart pointer or a stack-allocated value.

References — pointers without the rope

void scale(int& x, int factor) { x *= factor; }   // by reference — modifies caller's int
void print(const std::string& s)  { /* ... */ }   // const ref — no copy, no mutate
void take_ownership(std::string&& s) { ... }      // rvalue ref — moves into me

Rules of thumb:

  • Pass by const ref for non-trivial types you're not modifying. Avoids copies.
  • Pass by ref when you intend to modify.
  • Pass by value for small or trivially-copyable types (int, double, struct of two ints, std::string_view).
  • Pass by rvalue ref when you specifically want to take ownership of a temporary.

Move semantics — what they actually mean

A move is a transfer-of-resources operation. After moving from an object, it's left in a valid-but-unspecified state — usually empty.

std::vector<int> make_big() {
    std::vector<int> v(1'000'000);
    return v;                               // NRVO or move; no copy
}

std::vector<int> v = make_big();             // cheap — pointer-sized fields swap

std::string a = "hello";
std::string b = std::move(a);                // b owns the buffer; a is now empty (but valid)
// don't read a's value here — but a.clear(), a.size(), a = "..." are fine

The Rule of Three becomes the Rule of Five: if you write any of (destructor, copy ctor, copy assign), you probably need to write all five (also move ctor, move assign). Better: the Rule of Zero — design types so the compiler-generated specials are correct, and write none of them.

Algorithm idioms — never write a raw loop when an algorithm does it:

#include <algorithm>
#include <numeric>
#include <ranges>       // C++20
#include <vector>

std::vector<int> v = {3, 1, 4, 1, 5, 9, 2, 6};

std::ranges::sort(v);                                       // sorted
auto sum = std::accumulate(v.begin(), v.end(), 0);
auto it  = std::ranges::find(v, 5);
bool any = std::ranges::any_of(v, [](int x){ return x > 8; });

// C++20 ranges
auto evens_squared = v
    | std::views::filter([](int x){ return x % 2 == 0; })
    | std::views::transform([](int x){ return x * x; });

Lambdas

auto add = [](int a, int b) { return a + b; };

int factor = 3;
auto scale = [factor](int x) { return x * factor; };       // capture by value
auto bump  = [&factor]() { factor++; };                    // capture by reference (careful with lifetime)

// generic lambda (C++14)
auto twice = [](auto x) { return x + x; };

// constexpr lambda (C++17), [[nodiscard]] return (C++20)
auto compute = [] [[nodiscard]] (int n) constexpr -> int { return n * n; };

Capture rules: [=] by value (copies), [&] by reference (cheap but careful with lifetime), [this] captures the enclosing object's this, [*this] (C++17) captures by value. Avoid [&] in code that escapes the current scope (returned, posted to a thread, stored).

Templates — the friendly basics

template <typename T>
T max_of(T a, T b) { return (a > b) ? a : b; }

auto m1 = max_of(3, 5);              // T deduced as int
auto m2 = max_of<double>(3, 5.0);    // explicit

Constraints (C++20 concepts) make templates honest about what they need:

#include <concepts>

template <std::integral T>
T sum(std::span<const T> xs) {
    T s = 0;
    for (T x : xs) s += x;
    return s;
}

Compile errors with concepts are 10× more readable than the old SFINAE walls of text. Use them.

Classes — the modern shape

#include <string>
#include <vector>
#include <memory>

class JobQueue {
public:
    JobQueue() = default;                          // explicitly defaulted
    ~JobQueue() = default;

    // Non-copyable, movable — common shape for things-that-own-state.
    JobQueue(const JobQueue&)            = delete;
    JobQueue& operator=(const JobQueue&) = delete;
    JobQueue(JobQueue&&)            noexcept = default;
    JobQueue& operator=(JobQueue&&) noexcept = default;

    void push(std::string name) { jobs_.emplace_back(std::move(name)); }
    [[nodiscard]] std::size_t size() const noexcept { return jobs_.size(); }

private:
    std::vector<std::string> jobs_;
};

Idioms worth committing:

  • Trailing underscore for private members (jobs_) — many style guides; pick one.
  • noexcept on move ops — required for STL containers to use move on resize.
  • [[nodiscard]] on return values that callers shouldn't ignore.
  • = delete for "not allowed" — better than the C++03 trick of declaring private with no body.
  • Initialise members at declaration when sensible: std::size_t count_ = 0;.
  • Single-arg constructors should generally be explicit to avoid surprising implicit conversions.

Errors — exceptions or values?

Three schools, all defensible:

  1. Exceptions — C++ classic. Costly when thrown, free when not. Don't use across module boundaries (ABI). Forbidden in some embedded / kernel work.
  2. Result types — std::expected<T, E> (C++23) or tl::expected, or hand-rolled. Explicit, cheap, clutters call sites.
  3. Error codes + out params — POSIX style. Cumbersome but ABI-safe.

Pick one per codebase. Mixing is the worst of all worlds. Embedded teams typically forbid exceptions and use error codes; modern application code uses exceptions or expected.

Modern formatting and printing

#include <format>             // C++20
#include <print>              // C++23
#include <iostream>

std::string s = std::format("x={:08x} y={:.2f}", 0xc0ffee, 3.14);
std::println("hello, {}!", "world");        // C++23

// fallback: fmt library, identical API

std::format/std::print beat both printf and iostreams on safety and ergonomics. If you're stuck on older compilers, the {fmt} library is the same API and works back to C++11.

A word on iostreams

std::cout << "x=" << x << "\n"; works but it's slow, hard to format, and links a lot of code. Modern C++ leans on std::format/std::print instead. Reach for iostreams only when you have to.

C++ ↔ C interop

// header used from both C and C++
#ifdef __cplusplus
extern "C" {
#endif

int parse_packet(const unsigned char *buf, size_t n);

#ifdef __cplusplus
}
#endif

extern "C" disables C++ name mangling so the symbol is visible to C linkers. Required when:

  • Exposing C++ functions to C code.
  • Using C libraries from C++ — most C headers do this themselves.
  • Writing dynamic-library entry points (dlsym wants un-mangled names).

You can pass C++ classes through an opaque handle: typedef struct Foo Foo; in the C-visible header, full definition in C++.

Hands-on: a tiny RAII guard

Hands-on · finally for C++

Sometimes you have a C-style resource (file descriptor, mutex from pthread.h, OpenGL handle) without a C++ wrapper. Wrap it once:

#include <utility>

template <class F>
class scope_exit {
    F f_;
    bool armed_ = true;
public:
    explicit scope_exit(F f) : f_(std::move(f)) {}
    ~scope_exit() { if (armed_) f_(); }
    void release() noexcept { armed_ = false; }

    scope_exit(const scope_exit&)            = delete;
    scope_exit& operator=(const scope_exit&) = delete;
};

template <class F>
auto on_scope_exit(F f) { return scope_exit<F>(std::move(f)); }

void load_thing(const char *path) {
    int fd = open(path, O_RDONLY);
    if (fd < 0) throw std::system_error(errno, std::generic_category(), "open");

    auto guard = on_scope_exit([fd]{ close(fd); });
    // ... use fd ...
    // close happens automatically on return or throw
}

For one-line cleanup, this beats a class hierarchy. C++23 has std::scope_exit in the experimental TS; until then, write your own.

Things to actively avoid

  • Bare new / delete outside of one-line factories. make_unique/make_shared always.
  • Raw arrays as members. std::array<T, N> instead.
  • printf when std::format works.
  • using namespace std; in headers (or anywhere global). It pollutes every consumer.
  • Macros when a constexpr function or template would do.
  • Inheriting from STL types — they have non-virtual destructors. Compose, don't inherit.
  • Throwing from destructors. Don't.
  • Returning references to locals. They dangle. Compilers warn; ASan catches.

Exercises

EX 2.1 easy Smart-pointer choice

For each, pick unique_ptr, shared_ptr, weak_ptr, or "raw pointer / reference":

  1. A factory returning a newly-allocated Widget.
  2. A cache that holds objects until users drop their last handle.
  3. An observer that wants to act on a target if it's still alive.
  4. A function that reads but doesn't store the argument.
Show solution
  1. unique_ptr<Widget>. Sole owner; caller can move it into a shared_ptr if they want sharing.
  2. shared_ptr with the cache holding weak_ptr, so users hold the last refcount. Or just shared_ptr if the cache is the owner.
  3. weak_ptr; weak.lock() upgrades to a shared_ptr if the target is still alive.
  4. const T& for a non-trivial type, or std::string_view/std::span<const T> when applicable.
EX 2.2 medium Spot the dangling reference 
const std::string& greet(const std::string& name) {
    return "hello, " + name;
}
Show solution

The expression "hello, " + name creates a temporary std::string. Returning a const reference to it returns a reference to a destroyed object — UB. Compiler usually warns: -Wreturn-stack-address / -Wreturn-local-addr.

Fix: return by value. Modern compilers will use NRVO/move, no copy.

std::string greet(const std::string& name) {
    return "hello, " + name;
}
EX 2.3 medium Why move?

Why does v.emplace_back(std::move(s)) matter, given that std::string already supports move construction?

Show solution

Without std::move, s is an lvalue, so the chosen overload copies. The string copy allocates and copies bytes. With std::move, s is treated as an rvalue, the move constructor steals the buffer (pointer swap), and s is left empty. For long strings, the difference is between an O(n) copy and an O(1) pointer swap.

EX 2.4 hard Rule of five from scratch

Write a tiny owning FileHandle RAII type around FILE* that supports moves but not copies, with noexcept moves and a sensible operator bool.

Show solution 
#include <cstdio>
#include <utility>

class FileHandle {
    std::FILE *f_ = nullptr;
public:
    FileHandle() = default;
    explicit FileHandle(std::FILE *f) noexcept : f_(f) {}
    ~FileHandle() { if (f_) std::fclose(f_); }

    FileHandle(const FileHandle&)            = delete;
    FileHandle& operator=(const FileHandle&) = delete;

    FileHandle(FileHandle&& o) noexcept : f_(o.f_) { o.f_ = nullptr; }
    FileHandle& operator=(FileHandle&& o) noexcept {
        if (this != &o) {
            if (f_) std::fclose(f_);
            f_ = o.f_;
            o.f_ = nullptr;
        }
        return *this;
    }

    explicit operator bool() const noexcept { return f_ != nullptr; }
    std::FILE *get()    const noexcept { return f_; }
    std::FILE *release() noexcept       { std::FILE *r = f_; f_ = nullptr; return r; }
};

Better: rely on std::unique_ptr<std::FILE, decltype(&std::fclose)> with fclose as the deleter — same effect, less code.

Recap

  • C++20+ as the default; -std=c++20 -Wall -Wextra -Wpedantic + ASan/UBSan in dev.
  • RAII for every resource. unique_ptr is the workhorse; shared_ptr only for genuinely shared ownership.
  • Pass non-trivial types as const T& or T&&; trivial as value; views (span, string_view) when you don't want to own.
  • Rule of Five if you must, Rule of Zero where you can.
  • std::format/std::print > printf > iostream for new code.
  • C↔C++ via extern "C"; expose opaque handles, never C++ classes, across the boundary.
