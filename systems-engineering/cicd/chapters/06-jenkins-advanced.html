Chapter 06 Jenkins — Advanced

Shared Libraries (how to extract reusable pipeline logic), JCasC (configure-as-code), Kubernetes-backed agents, credentials management, and how to keep Jenkins running without becoming a full-time admin. This is the chapter that turns you from "writes Jenkinsfiles" into "manages Jenkins".

Shared libraries

When every project's Jenkinsfile has the same five stages, you need a way to factor them out. Shared libraries are Jenkins' answer: Groovy code stored in a git repo, loaded into every pipeline that needs it.

Anatomy of a shared library repo

my-shared-lib/
├── vars/               # global variables & steps; one file per entry
│   ├── buildDocker.groovy
│   └── deployK8s.groovy
├── src/                # regular Groovy classes (package-based)
│   └── com/example/
│       └── BuildInfo.groovy
└── resources/          # files you can loadResource()
    └── templates/
        └── prod-values.yaml

vars/buildDocker.groovy:

// Any file in vars/ becomes a global step with the filename (minus .groovy).
// Here we define a step callable as `buildDocker(image: 'x', tag: 'y')`.

def call(Map args) {
    def image = args.image ?: error('buildDocker: image is required')
    def tag   = args.tag   ?: env.BUILD_NUMBER
    sh "docker build -t ${image}:${tag} ${args.context ?: '.'}"
    return "${image}:${tag}"
}

Configure Jenkins: Manage Jenkins → System → Global Pipeline Libraries → Add. Give it a name (my-shared-lib) and point at the git repo.

Then use it in any Jenkinsfile:

@Library('my-shared-lib') _

pipeline {
    agent any
    stages {
        stage('Build') {
            steps {
                script {
                    def ref = buildDocker image: 'registry/myapp', tag: env.BUILD_NUMBER
                    echo "Built ${ref}"
                }
            }
        }
    }
}

The underscore _ imports everything in vars/. Now every project that opts in can call buildDocker(…). When you fix a bug in the library, all consumers benefit instantly — a two-edged sword; test library changes in a staging pipeline first.

Pinning library versions

Live-at-HEAD libraries are risky. Pin to a tag or commit per consumer: 

@Library('my-shared-lib@v1.4.0') _
@Library('my-shared-lib@4f3c9a1') _   // specific commit

Custom steps with Declarative DSL

Shared libraries can also define entire pipelines as reusable DSL:

groovyvars/standardPipeline.groovy
def call(Map args) {
    pipeline {
        agent any
        stages {
            stage('Build') { steps { sh args.buildCmd ?: 'make' } }
            stage('Test')  { steps { sh args.testCmd  ?: 'make test' } }
            stage('Deploy') {
                when { branch 'main' }
                steps { sh args.deployCmd ?: 'make deploy' }
            }
        }
    }
}

Consumer's Jenkinsfile:

@Library('my-shared-lib') _
standardPipeline(testCmd: 'pytest', buildCmd: 'python -m build')

Three-line Jenkinsfile. Scales to 100 projects with consistent behaviour.

The CPS transformation — Groovy's asterisk

Jenkins runs pipeline Groovy under a Continuation-Passing Style transformation. This lets Jenkins pause a running pipeline (across restarts, waiting on input) and resume it later with the same state.

The catch: not all Groovy code survives the CPS rewrite. Problem spots:

  • Closures with side-effectful iteration. list.each { doSomething(it) } can misbehave; prefer for (item in list) doSomething(item).
  • Complex Groovy idioms (method references, some delegation patterns).
  • Calls into non-CPS code are allowed but your code is not resumable through them.

If you must run a chunk of non-CPS Groovy, annotate:

// In shared library code:
@NonCPS
def parseJson(String text) {
    // Safe to use complex Groovy here; but the pipeline can't pause inside it.
    new groovy.json.JsonSlurper().parseText(text)
}

Rule of thumb: keep Pipeline code simple. Push complex Groovy into @NonCPS methods in shared libraries.

Credentials, properly

Credentials have a scope:

  • Global — any job can use them.
  • System — only Jenkins itself (not pipelines) can use them.
  • Folder-scoped — only jobs in a folder can use them.
  • User-scoped — personal credentials for a single user.

Rule: use folder scope to isolate production from development. If a dev job shouldn't access prod credentials, put them in different folders.

Two injection patterns for pipelines:

Via environment { credentials('id') }

environment {
    AWS_CREDS = credentials('aws-prod')      // username/password type
}
// In shell: $AWS_CREDS_USR and $AWS_CREDS_PSW are available
// For secret-text: $AWS_CREDS alone holds the value

Via withCredentials([...])

withCredentials([
    string(credentialsId: 'slack-webhook', variable: 'SLACK_HOOK'),
    usernamePassword(credentialsId: 'registry', usernameVariable: 'U', passwordVariable: 'P'),
    sshUserPrivateKey(credentialsId: 'deploy-key', keyFileVariable: 'SSH_KEY')
]) {
    sh '''
        ssh -i "$SSH_KEY" deploy@server 'cd /app && git pull'
        echo "$P" | docker login registry.example.com -u "$U" --password-stdin
    '''
}

withCredentials scopes exposure to the block only — safer than environment bindings that span the entire pipeline.

Kubernetes agents

The modern default for serious Jenkins: every build gets a fresh Kubernetes pod. Install the Kubernetes plugin; configure Jenkins (Manage Jenkins → Clouds → New Cloud → Kubernetes) with your cluster's credentials and namespace.

Then in a pipeline:

pipeline {
    agent {
        kubernetes {
            yaml '''
                apiVersion: v1
                kind: Pod
                spec:
                  containers:
                    - name: node
                      image: node:20
                      command: [sleep]
                      args: [infinity]
                    - name: python
                      image: python:3.11
                      command: [sleep]
                      args: [infinity]
            '''
        }
    }
    stages {
        stage('JS') {
            steps {
                container('node') { sh 'npm ci && npm test' }
            }
        }
        stage('PY') {
            steps {
                container('python') { sh 'pip install -r req.txt && pytest' }
            }
        }
    }
}

The pod has two containers. The pipeline switches between them for each stage. Each build gets its own pod, torn down on completion. This is the Jenkins answer to "hermetic, reproducible builds".

Configuration as Code (JCasC)

Classic Jenkins stores everything in XML files in $JENKINS_HOME. That's configuration-as-data, stored in a place no one backs up. Awful.

The JCasC (Configuration as Code) plugin lets you write your entire Jenkins config as YAML:

yamljenkins.yaml (JCasC)
jenkins:
  systemMessage: "Production Jenkins — managed by GitOps"
  numExecutors: 0
  mode: EXCLUSIVE
  securityRealm:
    ldap:
      configurations:
        - server: "ldaps://directory.example.com"
          rootDN: "dc=example,dc=com"
  authorizationStrategy:
    roleBased:
      roles:
        global:
          - name: "admin"
            pattern: ".*"
            permissions: [ "Overall/Administer" ]
            assignments: [ "release-managers" ]

  clouds:
    - kubernetes:
        name: "k8s"
        serverUrl: "https://kubernetes.default"
        namespace: "jenkins"
        jenkinsUrl: "http://jenkins:8080"
        templates:
          - name: "default"
            label: "k8s"
            containers:
              - name: "jnlp"
                image: "jenkins/inbound-agent:latest"

unclassified:
  location:
    url: "https://jenkins.example.com"
  slackNotifier:
    teamDomain: "example"
    tokenCredentialId: "slack-hook"

Set CASC_JENKINS_CONFIG=/etc/jenkins/jenkins.yaml in Jenkins' environment. On startup, JCasC applies the config. Now your Jenkins setup lives in git, reviewable, diffable, rollback-able. Huge quality-of-life improvement for admins.

RBAC — who can do what

Jenkins' authorisation strategies:

  • Logged-in users can do anything. Default after initial setup. Fine for a single team.
  • Matrix-based security. A grid of permissions per user/group. Granular but tedious to maintain.
  • Project-based Matrix Authorization Strategy. Per-job matrices override globals. Lets you lock down production jobs to specific groups.
  • Role-Based Authorization Strategy (plugin). Define roles (admin, developer, QA) with permissions, assign to users or LDAP groups. Much more maintainable.

For anything multi-team, install Role-Based Authorization Strategy plugin + LDAP/SSO and manage roles via JCasC.

Backup strategy

Even with JCasC, some state is in $JENKINS_HOME: build history, workspaces (usually on agents), credentials (encrypted). The must-back-up set:

  • config.xml, jobs/*/config.xml, credentials.xml — the state JCasC can't fully reconstruct.
  • secrets/ — the encryption keys. Without these, encrypted credentials are unrecoverable.
  • plugins/ — list of installed plugins with versions (so you can reinstall the same set).

Don't back up full build logs and workspaces — they're replaceable and volume-expensive. Use log rotation instead.

Blue Ocean

Jenkins' modernised pipeline UI. Better visualisation of stages, nicer graph view of parallel execution, friendlier pipeline creation wizard. Recent native Jenkins UI has improved enough that Blue Ocean is less essential than it used to be, but it's still worth installing.

Observability

Key signals to monitor on a Jenkins install:

  • Controller memory & CPU. Big pipelines can OOM a Controller.
  • Executor utilisation. Are builds queued waiting for executors?
  • Build duration trends. Sudden slowdowns often point at plugin regressions.
  • Agent connectivity. Offline agents silently shrink capacity.
  • Plugin warnings. The Update Centre flags security advisories — react within days, not months.

The Prometheus metrics and Metrics plugins expose all of this. Wire them into Grafana.

Exercises

EX 6.1 medium Extract a shared step

You find five Jenkinsfiles all containing the same "docker build + push + tag latest" block. Extract it to a shared library step. What's the signature, and how do consumers call it?

Show solution
groovyvars/dockerPublish.groovy
def call(Map args) {
    def image = args.image ?: error('image required')
    def tag   = args.tag   ?: env.BUILD_NUMBER
    def creds = args.creds ?: 'registry-login'
    def reg   = args.registry ?: env.REGISTRY

    withCredentials([usernamePassword(credentialsId: creds,
                                      usernameVariable: 'U',
                                      passwordVariable: 'P')]) {
        sh """
            echo "\$P" | docker login ${reg} -u "\$U" --password-stdin
            docker build -t ${reg}/${image}:${tag} ${args.context ?: '.'}
            docker push  ${reg}/${image}:${tag}
            docker tag   ${reg}/${image}:${tag} ${reg}/${image}:latest
            docker push  ${reg}/${image}:latest
        """
    }
}

Consumer:

stage('Publish') {
    steps { dockerPublish image: 'myapp', registry: 'registry.example.com' }
}
EX 6.2 easy CPS pitfall

Rewrite this so it's safe under Jenkins' CPS:

def branches = sh(returnStdout: true, script: 'git branch -r').split('\n')
branches.each { b -> echo b.trim() }
Show solution 
def raw = sh(returnStdout: true, script: 'git branch -r')
for (b in raw.split('\n')) {
    echo b.trim()
}

Or push the parsing into a @NonCPS method in a shared library and return a plain list of strings.

Write the JCasC snippet that configures the Slack Notification plugin with workspace my-co, credential ID slack-token, default channel #ci.

Show solution 
unclassified:

    teamDomain: "my-co"

EX 6.4 hard Folder-scoped credentials

You have two folders, dev and prod, each with its own AWS credentials. A pipeline in dev must never access prod's creds. How do you enforce this? What happens when a Jenkinsfile in dev/some-job tries to credentials('aws-prod')?

Show solution

Put aws-prod in the prod folder's credential store (Manage folder → Credentials). It's then visible only to jobs under prod/. A job in dev/ calling credentials('aws-prod') would get a "No such credential" error — the credential is invisible to it.

Combine with RBAC: developers have Configure permission only on dev/, not on prod/. Now they can't even see prod credentials exist.

EX 6.5 hard Multi-container pod

Design a Kubernetes agent pod that has: a build container (golang:1.22), a docker container for image builds, and a kubectl container for deploys. Write the agent { kubernetes { yaml '…' } } block.

Show solution 
agent {
    kubernetes {
        yaml '''
            apiVersion: v1
            kind: Pod
            spec:
              containers:
                - name: build
                  image: golang:1.22
                  command: [sleep]
                  args: [infinity]
                - name: docker
                  image: docker:24
                  command: [sleep]
                  args: [infinity]
                  volumeMounts:
                    - name: sock
                      mountPath: /var/run/docker.sock
                - name: kubectl
                  image: bitnami/kubectl:latest
                  command: [sleep]
                  args: [infinity]
              volumes:
                - name: sock
                  hostPath: { path: /var/run/docker.sock }
        '''
    }
}

Then use container('build') { sh '...' } or container('docker') etc. in stages.

(Caveat: hostPath for docker.sock is the easy mode and a security tradeoff; consider Docker-in-Docker or buildah for stricter environments.)

Recap

  • Shared libraries factor pipeline logic into reusable steps; pin versions for stability.
  • CPS-transformed Groovy has limitations; keep pipelines simple, push complexity to @NonCPS library code.
  • Credentials have scope (global, folder, user). Use folder scope to isolate prod.
  • withCredentials scopes exposure better than environment { credentials(...) }.
  • Kubernetes agents are the modern default: fresh pod per build, multi-container support.
  • JCasC brings Jenkins config into git; combine with RBAC and backup of secrets/ and */config.xml.
  • Monitor executor utilisation, plugin advisories, agent connectivity; invest in this or you'll be paged.
