Chapter 11 Security & Secrets

CI systems are privileged processes that run code on every commit. They're also the path to production. Compromising a CI system means compromising your software supply chain. This chapter covers least-privilege design, OIDC, secret scanning, signing, SBOMs, and the SLSA framework — across all three tools.

The CI/CD threat model

Four attacker goals, in rough order of severity:

  1. Steal secrets. Access cloud credentials, registry tokens, signing keys stored in the CI.
  2. Inject malicious artifacts. Poison the build output so production runs attacker code (the supply-chain attack).
  3. Abuse compute. Mine crypto on your runner minutes, or use your CI as a jump box.
  4. Tamper with approvals / gates. Bypass or forge the "is this safe to deploy" checks.

Vectors include: malicious dependencies, attacker-controlled forks submitting PRs, typo-squatted or hijacked actions, leaked secrets in logs, compromised maintainers, insecure runner isolation, and plain old misconfigured permissions.

Five principles

1 · Least privilege

Each job gets only the permissions it needs. Workflow-level permissions: {} + per-job escalation in GHA. Folder-scoped credentials in Jenkins. Environment-scoped variables in GitLab.

2 · Short-lived credentials

Prefer OIDC-to-cloud over long-lived access keys. Tokens expire in minutes; compromise is time-bounded.

3 · Pin what you depend on

Actions by commit SHA, Docker images by digest (FROM alpine@sha256:…), npm via lockfile, Python via requirements.lock or uv.lock. Tags are mutable; hashes are not.

4 · Defense in depth

Secrets stored in the tool's secret manager, not in repo. Secret scanning on the repo. Secret masking in logs. Branch protection. Required reviews on workflow-file changes.

5 · Assume compromise

Detect, don't just prevent. Monitor for unusual activity — new secrets accessed, unexpected deploy targets, image signatures failing. Have a rotation/incident plan.

OIDC: federate don't store

We touched OIDC in Chapter 10. The concept generalises.

Setup happens twice — once per cloud, once per pipeline tool:

1. On the cloud side

  • Create an OIDC provider trusting the pipeline tool's issuer URL.
  • Create a role with a trust policy that verifies claims: which repo, which branch, which environment, which action is allowed to assume.
  • Scope the role's permissions to just what CI needs: push to this ECR repo, deploy to this ECS service.

2. On the CI side

  • Declare id-token: write (GHA) or id_tokens (GitLab) permission.
  • Exchange the OIDC JWT for a cloud credential.

Trust claim best practices

  • Scope to specific branches (ref:refs/heads/main) — don't allow PRs from forks to assume prod roles.
  • Scope to specific environments (environment:production) — combine with GHA environment approvals.
  • Use different IAM roles per environment; don't reuse the prod role for staging.
  • Review the trust policy during secret rotation — orphaned trusts are attack surface.

Example AWS trust policy (GHA)

{
  "Version": "2012-10-17",
  "Statement": [{
    "Effect": "Allow",
    "Principal": {
      "Federated": "arn:aws:iam::123456789012:oidc-provider/token.actions.githubusercontent.com"
    },
    "Action": "sts:AssumeRoleWithWebIdentity",
    "Condition": {
      "StringEquals": {
        "token.actions.githubusercontent.com:aud": "sts.amazonaws.com"
      },
      "StringLike": {
        "token.actions.githubusercontent.com:sub": [
          "repo:myorg/myrepo:ref:refs/heads/main",
          "repo:myorg/myrepo:environment:production"
        ]
      }
    }
  }]
}

Secret scanning

Committed secrets are forever. Once a secret hits a public commit, assume it's compromised — rotate. Prevention:

  • GitHub secret scanning — built-in, scans public repos for 200+ patterns (AWS keys, Stripe tokens, etc.), automatically revokes tokens for participating providers. Enable "Push protection" in Settings → Security.
  • GitLab secret detection — the Secret-Detection.gitlab-ci.yml template, plus push rules on self-hosted.
  • gitleaks / trufflehog — run in pipelines; block PRs with findings.
  • Pre-commit hooks — catch before push: pre-commit + detect-secrets, gitleaks, or ggshield.
yamlGHA — gitleaks
jobs:
  secrets:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
        with: { fetch-depth: 0 }
      - uses: gitleaks/gitleaks-action@v2
        env:
          GITLEAKS_LICENSE: ${{ secrets.GITLEAKS_LICENSE }}

Log masking & why it sometimes fails

All three tools mask secret values in logs when the raw value appears. But transformations defeat masking:

echo "$SECRET"                              # masked
echo "$SECRET" | base64                     # NOT masked — different bytes
echo "pre-${SECRET}-post"                   # masked (substring match)
curl -H "Auth: $(echo $SECRET | base64)"    # NOT masked

Rules:

  • Never echo or set -x around secrets.
  • Never base64 / hash / rot13 a secret into a log.
  • If a build command accepts a secret via env var, it'll usually do the right thing. Use file-based secrets for tools that only accept path arguments.

SBOMs & provenance

A Software Bill of Materials (SBOM) lists every component in your artifact — direct and transitive dependencies. Regulators and customers increasingly require them. Formats: SPDX, CycloneDX.

Generating one is one command:

# Docker image
$ syft registry/myapp:1.2.3 -o spdx-json > sbom.spdx.json

# npm
$ npm sbom --sbom-format=cyclonedx > sbom.cdx.json

# Python
$ cyclonedx-py env -o sbom.cdx.json

Ship the SBOM alongside your artifacts. Better: publish it as an in-toto attestation signed to your artifact, so consumers can verify.

SLSA — the framework to know

SLSA (Supply-chain Levels for Software Artifacts) defines four levels of build provenance:

  • SLSA 1 — provenance exists: you emit some metadata about the build.
  • SLSA 2 — version-controlled builds, authenticated build service.
  • SLSA 3 — hosted CI system, hardened against tampering, provenance is non-forgeable.
  • SLSA 4 — hermetic, two-person review on every change, deterministic.

GitHub's own attestations feature and the SLSA GitHub Generator make SLSA 3 reachable for most teams: a signed statement saying "this artifact was built from this commit on this workflow at this time". Consumers verify at deploy time.

Signing artifacts

Two ecosystems matter:

Sigstore / cosign

# Keyless signing using OIDC identity — no long-lived keys
$ cosign sign --yes ghcr.io/myorg/myapp@sha256:abc123

# Verify
$ cosign verify \
    --certificate-identity-regexp "^https://github.com/myorg/myapp/\.github/workflows/.*@.*$" \
    --certificate-oidc-issuer https://token.actions.githubusercontent.com \
    ghcr.io/myorg/myapp@sha256:abc123

"Keyless" Sigstore uses your OIDC identity to sign via the public Fulcio CA, logs the certificate to Rekor. No private keys you have to rotate or steal. Pairs beautifully with GHA's OIDC.

GPG / PGP

The old-school approach — import a key in the runner, sign releases, publish the public key. Still common for Debian/RPM packages.

Third-party action / image safety

The supply-chain risk of uses: some-random-action@v1:

  • The tag can be moved to a malicious commit by the action's author.
  • The action's repo can be transferred to a new owner.
  • The action runs inside your runner, with access to your secrets (respecting the workflow's permissions).

Mitigations:

  • Pin by commit SHA: uses: tj-actions/changed-files@ab12cd34.
  • Maintain an allowlist — org-level setting in GHA: "only verified creators + specific list".
  • Vendor critical actions — fork into your org, review code, update deliberately.
  • Run with minimum permissions — so even a malicious action can't do much.
  • Dependabot — keep pinned SHAs updated via reviewable PRs.

Same logic for Docker base images: pin by digest (FROM alpine@sha256:...), rebuild periodically, scan with trivy / grype.

Branch protection & required checks

Most teams require:

  • Pull request review (1–2 reviewers).
  • Required status checks passing (specific CI jobs named explicitly).
  • No direct pushes to main.
  • Required signed commits (in regulated environments).
  • Code owners review on critical paths (CODEOWNERS file).

GitHub's rulesets, GitLab's push rules, and Bitbucket's branch permissions all cover this. Enforce via code when possible — policy as code.

The forked-PR problem

A PR from an external fork can modify the pipeline file itself. If your CI blindly runs that pipeline with full secrets, a malicious PR becomes "run attacker-supplied code with your prod credentials."

All three tools have safeguards:

  • GHA: fork PRs don't get access to secrets by default; pull_request_target does but is riskier; manual approval of first-time contributors.
  • GitLab: by default, forked MR pipelines run in the fork's project, not yours. To run in yours, configure "Pipelines for merge requests results" and scope secrets by protected branches.
  • Jenkins: usually only polls known refs; webhook-triggered PR builds need to be careful.

Rule: secrets and deploy permissions are for protected branches / merged main code. CI for PRs should only verify, never publish.

Hands-on: harden a pipeline

Hands-on · end-to-end hardening

Take any of the Hands-on pipelines from earlier chapters and add:

  1. Minimum permissions. For GHA, permissions: block at workflow scope. For GitLab, protect CI/CD variables. For Jenkins, move secrets into folder-scoped credentials.
  2. Action/image pinning. Replace every @v4 with an explicit commit SHA on third-party actions. For base Docker images, pin by digest.
  3. Secret scanning job. Add gitleaks (or equivalent) that fails the pipeline on findings.
  4. SBOM generation. After building your artifact, run syft to emit an SBOM; upload as an artifact.
  5. OIDC for cloud. Replace any stored cloud credentials with OIDC trust in AWS/GCP/Azure.
  6. Environment approvals. Gate the prod deploy with a required-reviewer environment (GHA) or a manual rule (GitLab) or input step (Jenkins).

Each change alone is modest. Combined, you move from "typical hobbyist CI" to "passes a competent security review".

Exercises

EX 11.1 easy Spot the leak

Find the security issue:

- env:
    TOKEN: ${{ secrets.DEPLOY_TOKEN }}
  run: |
    echo "Deploying with token: $TOKEN"
    curl -H "Auth: $TOKEN" https://api.example.com/deploy
Show solution

The echo "…$TOKEN" line prints the token literally. GHA will mask exact occurrences, but anything that appends text to it can defeat the mask. Fix: remove the debug line; or echo only prefix/suffix (echo "TOKEN is set: ${#TOKEN} chars").

Second subtler issue: curl -H "Auth: $TOKEN" is fine for the API call, but if curl echoes request headers under some verbose flag, that ends up in logs too. Prefer a Netrc or credentials file.

EX 11.2 medium Trust policy review

The AWS trust policy for a GHA OIDC role has "sub": "repo:myorg/myrepo:*". What's wrong? Rewrite it correctly.

Show solution

The * wildcard matches any ref from the repo — PRs from forks, tags, arbitrary branches. A malicious PR could assume the role. Scope tighter:

"StringLike": {
  "token.actions.githubusercontent.com:sub": [
    "repo:myorg/myrepo:ref:refs/heads/main",
    "repo:myorg/myrepo:environment:production",
    "repo:myorg/myrepo:ref:refs/tags/v*"
  ]
}

Principle: every claim should be the tightest match your legitimate workflows need.

EX 11.3 medium Pin by digest

Convert FROM node:20-slim to a digest-pinned form. Write a small command pattern your team could use to refresh pins periodically.

Show solution 
$ docker pull node:20-slim
$ docker inspect --format='{{index .RepoDigests 0}}' node:20-slim
node:20-slim@sha256:ab12cd34...

In Dockerfile:

FROM node:20-slim@sha256:ab12cd34...

Refresh monthly via a renovate or dependabot PR — they understand digest pinning and open automated updates.

EX 11.4 hard Fork PR policy

Design a GHA policy where fork PRs run lint + tests but can never deploy, access prod secrets, or push to registries. What mechanisms enforce this?

Show solution
  • By default, fork PRs don't get secrets. Verify this — don't use pull_request_target for untrusted code.
  • Put deploy steps in a job with if: github.event_name != 'pull_request' and also restrict to the default branch.
  • Move deploys to environments with required reviewers — fork PR jobs can't trigger reviewed environments anyway.
  • For first-time contributors, enable "require approval for all outside collaborators" (org setting).
  • Use OIDC-scoped-to-main for prod: even a fork job that somehow reached the deploy step couldn't assume the role.

Result: fork PRs run CI, but every path to production is blocked by multiple independent controls.

EX 11.5 hard SBOM + signed build

Sketch a GHA workflow that builds a Docker image, generates an SBOM, signs the image and the SBOM with cosign (keyless), then pushes everything to GHCR.

Show solution 
permissions:
  id-token: write          # OIDC for cosign
  packages: write          # push to GHCR
  contents: read

jobs:
  release:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - uses: docker/login-action@v3
        with:
          registry: ghcr.io
          username: ${{ github.actor }}
          password: ${{ secrets.GITHUB_TOKEN }}

      - id: build
        uses: docker/build-push-action@v5
        with:
          push: true
          tags: ghcr.io/${{ github.repository }}:${{ github.sha }}

      - uses: anchore/sbom-action@v0
        with:
          image: ghcr.io/${{ github.repository }}@${{ steps.build.outputs.digest }}
          output-file: sbom.spdx.json

      - uses: sigstore/cosign-installer@v3
      - run: |
          cosign sign --yes ghcr.io/${{ github.repository }}@${{ steps.build.outputs.digest }}
          cosign attest --yes --predicate sbom.spdx.json --type spdxjson \
            ghcr.io/${{ github.repository }}@${{ steps.build.outputs.digest }}

Consumers can verify at pull time: cosign verify-attestation ….

Recap

  • Threat model: secret theft, artifact poisoning, compute abuse, approval bypass.
  • Five principles: least privilege, short-lived credentials, pin dependencies, defense in depth, assume compromise.
  • OIDC eliminates long-lived cloud credentials; scope trust policies to specific repo/branch/environment.
  • Secret scanning in-repo + log-masking awareness + file-type secrets for CLIs that need paths.
  • SBOMs with syft, signing with cosign (keyless), SLSA framework for build provenance.
  • Pin actions by SHA, images by digest, libs by lockfile. Use Dependabot/Renovate for reviewed updates.
  • Fork PRs: run CI yes, access prod no — enforced by multiple mechanisms.
