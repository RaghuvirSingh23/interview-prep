Chapter 01 CI/CD Fundamentals

Before comparing Jenkins, GitLab, and GitHub Actions, we need shared vocabulary. What is CI? What is CD? What problem does either actually solve? If you skip this chapter you'll spend the next 13 copying snippets without understanding why they exist.

The words, precisely

TermMeans
Continuous Integration Every change a developer makes is merged into a shared main branch at least daily, and every merge is validated by an automated build + test run.
Continuous Delivery Every change that passes CI is automatically packaged into a release artifact that could be deployed to production at any time. A human clicks a button to actually deploy.
Continuous Deployment Every change that passes CI is automatically deployed to production with no human step.

CI/CD the umbrella phrase usually means "Continuous Integration plus at least Continuous Delivery". Continuous Deployment is the aggressive end of the spectrum — Etsy, Netflix, and Amazon do it; most businesses stop at Delivery and gate with human approval.

Where these ideas came from

Kent Beck's 1999 book Extreme Programming Explained argued for "continuous integration — integrate and build the system many times a day, every time a task is completed". Paul Duvall's 2007 book Continuous Integration codified the practice. Jez Humble and Dave Farley's 2010 Continuous Delivery extended it past the build to the release.

The tools followed the practices, not the other way around. Understanding the ideas first — "trunk-based, tested, always releasable" — makes every tool feel like a variation on a theme.

Why do it at all?

The short answer: small batches. The long answer:

  • Faster feedback. A test failure five minutes after a commit is easy to fix. A test failure five days after the commit, when fifteen other commits have landed, is a detective novel.
  • Always shippable. If every merge passes tests, you can release any commit at any time. Your "release train" collapses to a one-command deploy.
  • Smaller merges. Frequent small merges beat rare huge merges at nearly every metric that matters — review quality, bug rate, time-to-merge.
  • Automation substitutes for discipline. If humans can skip a step, some human eventually will. Automation doesn't.

The State of DevOps report — DORA, ran annually since 2014 — consistently shows that deployment frequency, lead time for changes, change failure rate, and mean time to recovery predict team performance and business outcomes. Elite teams deploy many times per day with <15% change failure rate. Low teams deploy once per quarter with >60% change failure rate. The practices in this tutorial are what elite teams do.

The graph, again

If you've done the GNU Make tutorial from earlier, you already know the punchline: a pipeline is a dependency graph over jobs. Each job takes inputs (source code, artifacts from previous jobs, secrets) and produces outputs (test results, build artifacts, deploy notifications). 

          [commit]
             │
             ▼
       ┌──── lint ────┐
       │              │
     test-unit    test-integ
       │              │
       └──── build ───┘
             │

        scan / sbom
             │
             ▼

             │
             ▼
       deploy-staging
             │
        (manual gate)
             ▼
        deploy-prod

The specific shape varies. The principle doesn't. Jenkins calls the nodes "stages" (or historically "freestyle projects"), GitLab calls them "jobs" with "stages" for grouping, GitHub Actions calls them "jobs" inside "workflows". Different words. Same concept.

What's actually in a minimum pipeline?

A "minimum viable" CI pipeline for most projects has four stages:

  1. Lint / format. Cheap, fast, catches obvious issues before anything expensive runs.
  2. Test. Unit tests first (fast, no external deps), then integration tests (slower, need services). Fail fast on the first.
  3. Build. Compile, bundle, containerise — produce the artifact you'll deploy.
  4. Publish or deploy. Either push the artifact to a registry/store (Delivery), or actually apply it (Deployment).

Add to taste: security scanning, SBOM generation, signing, notifications, preview environments.

When to use which (a rough first pass)

  • Your code is on GitHub and you don't have strong reasons otherwise → GitHub Actions.
  • Your code is on GitLab → GitLab CI. It's superbly tightly integrated and has no real cost.
  • You need to build on a fleet of weird hardware, integrate with a mainframe, plug into enterprise identity, or run a 5000-job nightly → Jenkins. Nothing else has Jenkins' raw flexibility, and the plugin ecosystem covers almost any edge case.
  • Your code is on Bitbucket or self-hosted git → Jenkins or a SaaS like CircleCI / Buildkite. Teams often mix: Jenkins for the complex cases, GHA or GitLab for the fast path.

We dedicate Chapter 12 to this decision in earnest.

Terminology drift

Each tool uses different words for similar things. Internalise this table — we'll refer to it constantly:

Unit of workStep (within a Stage)Job (within a Stage)Step (within a Job)

Two things deserve special attention because the mapping feels simple but isn't:

  • Jenkins Stages contain Steps; GitLab CI Stages contain Jobs; GitHub Actions Workflows contain Jobs containing Steps. A "Job" in GitLab is roughly a Jenkins Stage.
  • All three can parallelise within a single logical step. The syntax differs wildly.

A minimal pipeline, in all three

To taste the differences, here's "print hello, run a shell command, pass" in each tool. Don't try to understand every line — we'll dissect them in their respective chapters.

Jenkinsfile (Declarative)

groovyJenkinsfile
pipeline {
    agent any
    stages {
        stage('Greet') {
            steps {
                sh 'echo "Hello from Jenkins"'
            }
        }
    }
}

.gitlab-ci.yml

yaml.gitlab-ci.yml
greet:
  stage: build
  script:
    - echo "Hello from GitLab CI"

GitHub Actions workflow

yaml.github/workflows/hello.yml
name: Hello
on: [push]
jobs:
  greet:
    runs-on: ubuntu-latest
    steps:
      - run: echo "Hello from GitHub Actions"

Notice: GitLab and GHA are pure YAML — declarative data. Jenkins is Groovy — a real programming language. That single difference explains half the distinctions we'll draw.

Six principles every good pipeline follows

  1. Fast feedback. The full CI run should ideally finish in under 10 minutes. Past 20 minutes, developers start context-switching and productivity falls off a cliff.
  2. Deterministic. Two runs of the same commit give the same result. No flaky tests. No network dependencies that fail randomly. Pin tool versions.
  3. Hermetic where possible. The build doesn't reach out to the internet for dependencies mid-build. Use a lockfile, cache dependencies, use a proxy/mirror.
  4. Parallelism is built-in. Tests run in parallel; independent jobs run in parallel; only the dependency graph dictates order.
  5. Secrets are never in the repo. Ever. Use the tool's secret store; audit access.
  6. Every step leaves a log. If it didn't log, it didn't happen. Save artifacts, collect test reports, keep history.

We'll reference these by number ("Principle 3 says…") throughout the tutorial.

Exercises

EX 1.1 easy Definitions, unambiguously

In one sentence each, define CI, CD (Delivery), and CD (Deployment). What distinguishes the second from the third?

Show solution
  • CI: every change merged into a shared main branch is validated by automated build + tests.
  • CD (Delivery): every passing change is packaged into a releasable artifact; a human triggers the deploy.
  • CD (Deployment): every passing change is automatically deployed to production.

The difference between the two is the human gate.

EX 1.2 easy Terminology mapping

A colleague on your team writes: "the Jenkins stage failed, but the GitHub Actions step passed, so the GitLab job re-ran." Translate each to the same word.

Show solution

All three are referring to the same concept — "a chunk of work that was scheduled to run". The neutral word is job:

  • Jenkins stage ≈ Jenkins job in a GHA sense — a collection of steps
  • GHA step is smaller — one command inside a job
  • GitLab job is the right-sized unit

The sentence is ambiguous because the words aren't comparable. You'd sharpen it as: "the Jenkins stage and the GitLab job both ran the same logic; the GHA job's individual step passed." Precision matters when you debug across tools.

EX 1.3 medium Argue against your preferred tool

Whatever CI tool you like best, write three legitimate reasons someone might pick another tool instead. Forcing yourself out of defensive mode sharpens future decisions.

Show solution

No single solution. Authentic examples:

  • Against GHA: vendor lock-in to GitHub; limited private-network options; GitHub-hosted runners are slow and memory-starved for big builds.
  • Against GitLab: if your code isn't on GitLab, setting it up is a migration project; some features are paid tiers.
  • Against Jenkins: you are now a Jenkins admin. Plugins break. Groovy is an acquired taste. The LTS upgrade path can be brutal.

Knowing your own blind spots is an engineering skill.

EX 1.4 medium DORA on your team

For a project you know, estimate the four DORA metrics: deployment frequency, lead time for changes (commit → prod), change failure rate, mean time to recovery (MTTR). Which does a better CI/CD pipeline improve most?

Show solution

Deployment frequency and lead time are direct — both go up (or down, for lead time) when CI/CD pipelines are fast, trustworthy, and trigger automatically. Change failure rate goes down because you catch problems earlier. MTTR tends to improve because reverting becomes "push another commit through the same pipeline".

The weakest link for most teams is usually lead time: they have fast CI but slow reviews, slow staging, or a weekly release train. CI alone doesn't fix that — the human process does.

EX 1.5 hard Inventory your pipelines

Pick a repository you have access to. In plain English, describe its pipeline: what triggers runs, what runs in parallel, what artifacts get produced, what deploys. If it doesn't have one, describe the one it should have.

Show solution

No "right" answer. The goal is to force you to articulate the pipeline as a graph before trying to write or improve one. You'll be surprised how often even people familiar with a repo can't answer "what runs on push to main?" precisely.

Recap

  • CI = every merge is validated; CD (Delivery) = every pass is packaged; CD (Deployment) = every pass is released.
  • A pipeline is a dependency graph of jobs. The tools differ; the concept doesn't.
  • Minimum viable pipeline: lint → test → build → publish/deploy.
  • The three tools use different words for similar things. Learn the mapping.
  • Six principles: fast, deterministic, hermetic, parallel, secret-aware, observable.
