Chapter 12 Recursive Make Considered Harmful

In 1997 Peter Miller published a paper that lays out exactly why the recursive-Makefile-per-directory pattern — still the default in most projects — is broken. This chapter summarises that paper, explains the non-recursive alternative, and shows you how to migrate.

"The thesis of this paper is simple: recursive make produces incorrect or inefficient builds, and these problems cannot be fixed by adding more rules." — Peter Miller, 1997

The pattern in question

Nearly every medium-sized project you've seen has a structure like this:

project/
├── Makefile
├── src/
│   └── Makefile
├── lib/
│   └── Makefile
└── tests/
    └── Makefile

Top-level Makefile:

.PHONY: all
all:
	$(MAKE) -C lib
	$(MAKE) -C src
	$(MAKE) -C tests

"Each subdirectory has its own Makefile. The top-level Makefile calls make recursively in each." Feels organised. Feels modular. Is wrong.

What goes wrong

Problem 1: incomplete dependency graph

Each sub-Make only knows about the files in its directory. If src/main.c #includes lib/utils.h, that dependency can't be expressed in src/Makefile in any clean way. Worse: src/Makefile has no way to know when lib/'s outputs change.

The top-level Makefile "solves" this by always building lib before src. But that's order, not a graph. If lib is unchanged, the sub-Make runs anyway, walks its own dir, concludes "nothing to do", and exits. Wasteful. And when dependencies cross directories, Make can't help you: it doesn't see the crossing.

Problem 2: order serialises work that could parallelise

$(MAKE) -C lib then $(MAKE) -C src: these run sequentially. Within each dir, jobs are parallel; across dirs, they're serial. In reality, most src/ files don't depend on anything in lib/ — they're independent — but recursive Make has no way to express that.

Problem 3: redundant work

Every sub-Make invocation is a new process: read Makefile, parse, build graph, walk. For a project with 10 sub-Makefiles, you re-read and re-parse everything 10 times per build.

Problem 4: correctness bugs from repeated targets

If both lib/Makefile and tests/Makefile can produce ../build/libfoo.a, parallel runs of the two sub-Makes can race. No single Make instance sees both and arbitrates.

Problem 5: "phony" shenanigans

Since sub-Makes don't know if anything has changed cross-directory, the top-level Makefile often ends up doing things like:

.PHONY: force
subdirs: force
	for d in lib src tests; do $(MAKE) -C $$d; done

That is, declaring everything phony so sub-Makes always run. Which means the sub-Makes do all their own work of deciding what's up-to-date — exactly what Make is supposed to do globally.

The non-recursive approach

Peter Miller's proposal: one Makefile at the top level that has access to the entire graph. Subdirectories contribute included fragments, not independent Makefiles. 

project/
├── Makefile            # full graph, drives everything
├── src/
│   ├── main.c
│   └── subdir.mk       # contributes src-specific rules
├── lib/
│   ├── utils.c
│   └── subdir.mk
└── tests/
    ├── test_main.c
    └── subdir.mk

Top-level Makefile:

.DELETE_ON_ERROR:
.SUFFIXES:

SUBDIRS := lib src tests

include $(addsuffix /subdir.mk,$(SUBDIRS))

# Aggregate the global lists
$(info all objects: $(OBJ))
$(info all binaries: $(BIN))

.PHONY: all clean
all: $(BIN)

build/%.o: %.c
	@mkdir -p $(@D)
	$(CC) $(CPPFLAGS) $(CFLAGS) -c $< -o $@

clean: ; rm -rf build

lib/subdir.mk:

# Variables contributed by lib
LIB_SRC := $(wildcard lib/*.c)
LIB_OBJ := $(patsubst %.c,build/%.o,$(LIB_SRC))

LIB := build/libmine.a

$(LIB): $(LIB_OBJ)
	ar crs $@ $^

OBJ += $(LIB_OBJ)

src/subdir.mk:

APP_SRC := $(wildcard src/*.c)
APP_OBJ := $(patsubst %.c,build/%.o,$(APP_SRC))

APP := build/hello

$(APP): $(APP_OBJ) build/libmine.a
	$(CC) $(APP_OBJ) build/libmine.a -o $@

OBJ += $(APP_OBJ)
BIN += $(APP)

tests/subdir.mk:

TST_SRC := $(wildcard tests/*.c)
TST_BIN := $(patsubst tests/%.c,build/tests/%,$(TST_SRC))

.PHONY: check
check: $(TST_BIN)
	@for t in $^; do ./$$t || exit 1; done

build/tests/%: tests/%.c build/libmine.a | build/tests
	$(CC) $(CFLAGS) $< build/libmine.a -o $@

build/tests: ; mkdir -p $@

BIN += $(TST_BIN)

Now:

  • One Make process sees the entire graph.
  • Cross-directory dependencies are expressible directly: $(APP): $(LIB) in src/subdir.mk.
  • Parallel execution works across the whole project: an app.o and a utils.o compile in parallel even though they're in different dirs.
  • When you change nothing, make prints one "nothing to be done" instead of ten.

What you give up

The non-recursive approach has real costs. Be honest:

  • Top-level Makefile grows. It's 200-300 lines for a moderately-sized project. Split into many fragments, but the graph is in one process.
  • Namespacing matters. You can't say OBJ = … in each fragment; you must say LIB_OBJ, APP_OBJ, etc. Conventions are enforced by convention, not language.
  • Local builds need a trick. cd src; make doesn't work, because there's no Makefile there. You need make -C .. or a thin stub Makefile in each subdir that forwards to the top.

That last point is a real ergonomic hit. A classic workaround:

makesrc/Makefile (stub)
# Forward everything to the top-level build
MAKEFLAGS += --no-print-directory
.PHONY: all $(MAKECMDGOALS)
all $(MAKECMDGOALS):
	$(MAKE) -C .. $(patsubst %,src-%,$(MAKECMDGOALS))

It's a hack. Most real-world projects eventually decide either:

  • "Run the top-level Make from anywhere" (you train people), or
  • Use stub Makefiles that forward, accepting some ergonomic weirdness.

When recursive is OK

Don't let this chapter make you dogmatic. Recursive Make is fine when:

  • Each subdirectory is genuinely independent: a monorepo of unrelated tools, each with its own build.
  • Sub-projects have different toolchains (one's C, one's Rust, one's Go) and don't share build-graph dependencies.
  • You want to vendor a third-party project whose Makefile you won't touch.
  • Your project is small enough that the waste doesn't matter.

The anti-pattern Miller attacks is recursive Make for a single project whose components really do depend on each other. That's the case where non-recursive wins.

Migrating from recursive to non-recursive

If you inherit a recursive build and want to flatten it, the incremental plan:

  1. Keep the top-level Makefile. Add includes instead of $(MAKE) -C calls.
  2. Each sub-Makefile becomes a subdir.mk fragment. Rewrite references to use absolute-in-tree paths (build/src/foo.o, not build/foo.o).
  3. Gather lists in global variables (OBJ, BIN) with +=.
  4. Wire up cross-directory dependencies where they were implicit before. Use $(info) to verify the aggregated lists.
  5. Run make -j N, measure the speedup. Fix anything that broke.

You'll usually see a speedup of 1.5-3× on "clean build" and a bigger win on incremental (the null-rebuild case).

Alternatives to solving this in Make

Miller's paper was from 1997. Since then, build tools have been designed that sidestep the problem entirely:

ToolApproach
ninjaA minimal build executor. Rules come from a generator (CMake, Meson, or hand-written). No recursion — always one big graph.
bazelHermetic, content-addressable. Every rule has explicit inputs and outputs. No mtimes.
tupTracks filesystem changes via FUSE. Builds are always correct.
redoD.J. Bernstein's minimalist alternative. Per-target shell scripts. Hash-based.

Nonetheless, Make is still the most common build tool. Knowing how to do non-recursive Make correctly means your Makefiles will outlast most trendy alternatives.

Hands-on: convert a small recursive tree

Hands-on · flattening a recursive build

Set up this tree:

ch12/
├── Makefile
├── lib/
│   ├── Makefile
│   └── util.c
└── app/
    ├── Makefile
    └── main.c

With contents:

makeMakefile (recursive)
.PHONY: all clean
all:
	$(MAKE) -C lib
	$(MAKE) -C app
clean:
	$(MAKE) -C lib clean
	$(MAKE) -C app clean
makelib/Makefile
libutil.a: util.o
	ar crs $@ $<
util.o: util.c
	cc -c $< -o $@
clean: ; rm -f *.o *.a
.PHONY: clean
makeapp/Makefile
hello: main.o ../lib/libutil.a
	cc $^ -o $@
main.o: main.c
	cc -c $< -o $@
clean: ; rm -f *.o hello
.PHONY: clean

Notice the problem: app/Makefile depends on ../lib/libutil.a, but can't build it. The top-level ordering saves us by running lib first.

Now flatten:

makeMakefile (non-recursive)
.PHONY: all clean
.DELETE_ON_ERROR:

include lib/subdir.mk
include app/subdir.mk

all: $(BIN)

%.o: %.c
	cc -c $< -o $@

clean: ; rm -f $(OBJ) $(BIN) lib/libutil.a
makelib/subdir.mk
LIB_OBJ := lib/util.o
lib/libutil.a: $(LIB_OBJ)
	ar crs $@ $^

OBJ += $(LIB_OBJ)
makeapp/subdir.mk
APP_OBJ := app/main.o
APP := app/hello

$(APP): $(APP_OBJ) lib/libutil.a
	cc $^ -o $@

OBJ += $(APP_OBJ)
BIN += $(APP)

Build, modify, rebuild, measure. Compare with the recursive version.

$ time make -j 4     # with recursive Makefile
$ time make -j 4     # with non-recursive Makefile

Exercises

EX 12.1 easy Identify Miller's problems

Look at a recursive Makefile in a project you know. Find concrete examples of:

  1. A cross-directory dependency that's not expressed in the build graph.
  2. Work that could run in parallel but doesn't.
  3. A sub-make that always runs, even when its directory hasn't changed.
Show solution

Project-specific. You're looking for patterns like:

  1. app/ links against ../lib/libfoo.a, but the dep isn't declared — top-level ordering saves it.
  2. Top-level runs make -C lib; make -C app sequentially, but app/util.c doesn't actually depend on anything in lib/.
  3. A top-level all: force; $(MAKE) -C subdir using a force phony to re-invoke every time.
EX 12.2 medium The null-build test

For a recursive Makefile, measure how long make takes when nothing has changed. For the equivalent non-recursive version, do the same. Where does the time go?

Show solution

Recursive: each sub-Make reads its Makefile, parses, stats all its targets, concludes "nothing to do", prints, exits. Sum across N sub-Makes.

Non-recursive: one process, one parse, one walk, done. Usually 5-20× faster for null builds.

Null-build speed matters because developers run make constantly while editing. A sub-second null build feels alive. A 5-second null build feels broken.

EX 12.3 medium Stub Makefile for subdirectory entry

Write a stub Makefile that lives in src/ so users can run cd src; make test and have it "do the right thing" against the top-level non-recursive Makefile.

Show solution 
# src/Makefile — forward to top-level
MAKEFLAGS += --no-print-directory

.PHONY: FORCE
% : FORCE
	@$(MAKE) -C .. $@

FORCE:

The catch-all pattern rule %: FORCE sends any target name up a level. FORCE as a phony prerequisite forces the recipe to always run. The result: from src/, you can invoke any top-level target.

Drawback: you lose shell completion of targets unless the top-level Makefile is also referenced somehow. Some projects ship a shell helper to compensate.

EX 12.4 hard Namespace discipline

In a non-recursive project with 10 subdirectories, what naming conventions prevent variable collisions between subdir.mk fragments? Design a small convention and apply it.

Show solution

Common conventions:

  • Prefix-per-subdir. Every variable in lib/subdir.mk starts with LIB_. Simple, robust, verbose.
  • Local-then-append. Use short local names (src, obj), += into globals, then undefine the local names before the next include.
  • Target-specific, not global. Attach flags to specific targets (foo.o: CFLAGS += -DFOO) so they don't leak.

Example of approach 2:

# lib/subdir.mk
d := lib
srcs := $(wildcard $(d)/*.c)
objs := $(srcs:.c=.o)

OBJ += $(objs)

undefine d srcs objs

This is what the Linux kernel's Kbuild system does, with some additional macro magic.

EX 12.5 hard Read Miller's original paper

Read "Recursive Make Considered Harmful" (Peter Miller, 1997). Summarise the three most important points that this chapter didn't cover. Find one argument of Miller's that you disagree with and defend your position.

Show solution

No single solution — the point is to read the original and form your own view. A few things you'll find Miller emphasising:

  • The "Directed Acyclic Graph" view — Make's entire job is to walk a DAG. Recursive Make fragments the DAG and loses information.
  • Miller's cook tool (his own answer to the problem) — he's not just critiquing, he's proposed a solution.
  • Specific failure modes he's seen in real projects with large recursive trees.

A common disagreement: Miller presents non-recursive as unambiguously superior. In practice, vendored sub-projects, polyglot builds, and "monorepo of unrelated tools" scenarios are all cases where recursion is the right call. Your disagreement might be on that ergonomic / real-world note.

Recap

  • Recursive Make fragments the dependency graph. Each sub-Make has only a partial view.
  • Cross-directory dependencies can't be expressed cleanly — they're encoded in top-level ordering, which is a graph only if you squint.
  • Parallelism suffers — independent work in different dirs runs serially because Make doesn't see it as independent.
  • Null builds are N× slower, once per recursive level.
  • Non-recursive alternative: one top-level Makefile includes subdir.mk fragments. Entire graph is known. Parallelism works. Null builds are fast.
  • Costs of non-recursive: namespace discipline, larger top-level file, no native "cd subdir; make" without stubs.
  • Recursive is still fine for truly independent sub-projects, vendored code, polyglot trees.
