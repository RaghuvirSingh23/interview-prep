Chapter 09 Real Projects

Time to put it together. This chapter is four real build patterns: a C project with automatic header dependencies, a data pipeline, a LaTeX document, and a polyglot project that ties them together. By the end you'll recognise these patterns in every mature Makefile you read.

Pattern 1 — C with auto-dependency generation

The biggest weakness of "pure" Make for C is that you have to manually declare which header files each source depends on. For any non-trivial project this is unsustainable — people get it wrong, the build produces wrong output, hours are lost.

The fix is ingenious. Every serious C compiler (gcc, clang) has flags to emit a dependency file — a little Makefile fragment listing exactly which headers the source included. We use those fragments.

makeMakefile — C with auto-deps
CC      := cc
CFLAGS  := -O2 -Wall -Wextra -MMD -MP
LDFLAGS :=
LDLIBS  :=

SRC_DIR := src
BLD_DIR := build

SRC := $(wildcard $(SRC_DIR)/*.c)
OBJ := $(patsubst $(SRC_DIR)/%.c,$(BLD_DIR)/%.o,$(SRC))
DEP := $(OBJ:.o=.d)
BIN := $(BLD_DIR)/hello

.PHONY: all clean
.DELETE_ON_ERROR:

all: $(BIN)

$(BIN): $(OBJ)
	$(CC) $(LDFLAGS) $^ $(LDLIBS) -o $@

$(BLD_DIR)/%.o: $(SRC_DIR)/%.c | $(BLD_DIR)
	$(CC) $(CFLAGS) -c $< -o $@

$(BLD_DIR):
	mkdir -p $@

-include $(DEP)

clean: ; rm -rf $(BLD_DIR)

This is — no exaggeration — the Makefile template I've used for 15 years. It handles dependency tracking for C/C++ projects of any size. Let's dissect the clever parts.

The -MMD -MP incantation

When you compile with -MMD, gcc/clang produces a .d file alongside the .o:

$ cat build/main.d
build/main.o: src/main.c include/greet.h include/util.h

That's Makefile syntax! When we -include it on the next run, Make now knows that build/main.o depends on those headers.

The -MP flag adds an empty rule for each header mentioned. Why? So that when you delete a header, Make doesn't bail with "no rule to make util.h" — it just treats the absent file as a phony target. 

$ cat build/main.d     # with -MMD -MP
build/main.o: src/main.c include/greet.h include/util.h

include/greet.h:

include/util.h:

The -include line

-include $(DEP)

Note the leading -: silent if files are missing. First build, nothing exists — that's fine, we just compile, produce .os and .ds in the same step, and from then on Make knows the header dependencies.

This is the single most valuable Make idiom for C/C++. Memorise it. Every Makefile for a C codebase should have some variant of it.

-MMD vs -MD

-MD records dependencies on all headers, including system headers (stdio.h etc.). -MMD records only user headers. The system headers almost never change between builds; tracking them just bloats the .d files and sometimes causes surprising rebuilds when you upgrade your system. Prefer -MMD.

Try it

Hands-on · auto-deps in the wild

Create this structure:

src/main.c
src/greet.c
include/greet.h

Plus the Makefile above (create the include/ path and add -I include to CFLAGS):

cinclude/greet.h
#ifndef GREET_H
#define GREET_H
void greet(const char *who);
#endif
csrc/main.c
#include "greet.h"
int main(void) { greet("auto-deps"); return 0; }
csrc/greet.c
#include <stdio.h>
#include "greet.h"
void greet(const char *who) { printf("Hi %s\n", who); }

Add -I include to CFLAGS and build:

$ make
mkdir -p build
cc -O2 -Wall -Wextra -MMD -MP -I include -c src/main.c -o build/main.o
cc -O2 -Wall -Wextra -MMD -MP -I include -c src/greet.c -o build/greet.o
cc    build/main.o build/greet.o   -o build/hello
$ cat build/main.d
build/main.o: src/main.c include/greet.h
include/greet.h:
$ touch include/greet.h
$ make
cc -O2 -Wall -Wextra -MMD -MP -I include -c src/main.c -o build/main.o
cc -O2 -Wall -Wextra -MMD -MP -I include -c src/greet.c -o build/greet.o
cc    build/main.o build/greet.o   -o build/hello

The header change triggered both .c files to recompile — correctly — because the .d files from the previous build told Make about the dependency. We never wrote main.o: include/greet.h by hand.

Adding a static library

Evolve the C Makefile to build a library and link against it:

LIB_SRC := $(wildcard src/lib/*.c)
LIB_OBJ := $(patsubst src/lib/%.c,build/lib/%.o,$(LIB_SRC))

APP_SRC := $(wildcard src/app/*.c)
APP_OBJ := $(patsubst src/app/%.c,build/app/%.o,$(APP_SRC))

BIN := build/hello
LIB := build/libmine.a

.PHONY: all clean
all: $(BIN)

$(LIB): $(LIB_OBJ)
	ar crs $@ $^

$(BIN): $(APP_OBJ) $(LIB)
	$(CC) $(LDFLAGS) $(APP_OBJ) $(LIB) $(LDLIBS) -o $@

# Both compile rules use the same pattern but write to different dirs.
build/lib/%.o: src/lib/%.c | build/lib
	$(CC) $(CFLAGS) -I include -c $< -o $@

build/app/%.o: src/app/%.c | build/app
	$(CC) $(CFLAGS) -I include -c $< -o $@

build/lib build/app: ; mkdir -p $@

-include $(LIB_OBJ:.o=.d) $(APP_OBJ:.o=.d)

clean: ; rm -rf build

Notes:

  • We split build/ into build/app/ and build/lib/ to avoid name collisions.
  • The two pattern rules are near-identical; later we'll unify them with canned recipes or .SECONDEXPANSION.
  • The static lib is built with ar crs. c = create, r = replace members, s = write symbol index (replaces the old ranlib step).

Pattern 2 — Data pipeline

Make is not just for C. Its real talent is dependency tracking for anything that reads files and writes files. Data scientists and researchers use it for reproducible pipelines. Example: you have raw CSVs, a cleaning script, a feature-extraction script, and a model.

makeMakefile — data pipeline
.DELETE_ON_ERROR:
.PHONY: all clean

DATA_IN := $(wildcard raw/*.csv)
CLEANED := $(patsubst raw/%.csv,clean/%.csv,$(DATA_IN))
FEATURES := features/all.parquet
MODEL   := models/gbm.pkl
REPORT  := report/report.pdf

all: $(REPORT)

clean/%.csv: raw/%.csv scripts/clean.py | clean
	python scripts/clean.py $< $@

$(FEATURES): $(CLEANED) scripts/featurize.py | features
	python scripts/featurize.py $(CLEANED) $@

$(MODEL): $(FEATURES) scripts/train.py | models
	python scripts/train.py $< $@

$(REPORT): $(MODEL) $(FEATURES) scripts/report.py report/template.tex | report
	python scripts/report.py --model $(MODEL) --features $(FEATURES) --out $@

clean features models report:
	mkdir -p $@

clean-all:
	rm -rf clean features models report

Observations:

  • Scripts are listed as prerequisites. Change clean.py, and everything downstream rebuilds. This is something ad-hoc scripts famously don't do.
  • .DELETE_ON_ERROR: is especially important here. If featurize.py crashes halfway and writes a truncated parquet, deleting it forces a fresh retry next run.
  • Order-only directories create the output hierarchy on demand.
  • make with no argument builds the entire pipeline; change a single CSV and only the affected branches rebuild.

This is worth internalising. Make beats home-grown Python "pipeline frameworks" for small-to-medium data work because it's already installed, it's been debugged since 1976, and it forces you to think in graphs.

Pattern 3 — LaTeX

LaTeX needs two or three runs to resolve cross-references. Captured cleanly:

.DELETE_ON_ERROR:
.PHONY: all clean

SRC    := thesis.tex
FIGS   := $(wildcard figs/*.pdf)
CHAPS  := $(wildcard chapters/*.tex)
OUT    := thesis.pdf

all: $(OUT)

$(OUT): $(SRC) $(CHAPS) $(FIGS) refs.bib
	pdflatex -interaction=nonstopmode $(SRC)
	bibtex   $(basename $(SRC))
	pdflatex -interaction=nonstopmode $(SRC)
	pdflatex -interaction=nonstopmode $(SRC)

clean:
	rm -f $(OUT) *.aux *.log *.toc *.bbl *.blg *.out

The four-command dance is the standard LaTeX idiom; wrapping it in a Make rule gives you "change any source, run make, get a fresh PDF" without memorising the sequence.

More sophisticated: use latexmk which handles the repeat-until-stable for you:

$(OUT): $(SRC) $(CHAPS) $(FIGS) refs.bib
	latexmk -pdf -interaction=nonstopmode $(SRC)

Idiom — directory creation done right

You'll find yourself needing build directories over and over. The cleanest pattern:

build/obj/%.o: src/%.c | build/obj
	$(CC) $(CFLAGS) -c $< -o $@

# Order-only: the directory must exist, but we don't re-run on its mtime.
build/obj:
	@mkdir -p $@

Alternatively, do it in the recipe:

build/obj/%.o: src/%.c
	@mkdir -p $(@D)
	$(CC) $(CFLAGS) -c $< -o $@

Both work. The first is cleaner (one mkdir per directory, not per file). The second is more robust when output directories are computed per-target.

Idiom — install / uninstall

prefix      := /usr/local
bindir      := $(prefix)/bin
mandir      := $(prefix)/share/man/man1
DESTDIR     :=
INSTALL     := install

.PHONY: install uninstall
install: $(BIN)
	$(INSTALL) -d $(DESTDIR)$(bindir)
	$(INSTALL) -m 755 $(BIN) $(DESTDIR)$(bindir)/
	$(INSTALL) -d $(DESTDIR)$(mandir)
	$(INSTALL) -m 644 docs/hello.1 $(DESTDIR)$(mandir)/

uninstall:
	rm -f $(DESTDIR)$(bindir)/hello
	rm -f $(DESTDIR)$(mandir)/hello.1

Notes:

  • prefix, bindir, mandir are GNU conventions — packagers expect these names.
  • DESTDIR is prepended by Linux distribution packagers to stage an install into a fake root (e.g. DESTDIR=/tmp/pkg make install). Always honor it.
  • Use the BSD install(1) tool rather than cp + chmod: it atomically copies and sets permissions.

Idiom — version info from git

VERSION != git describe --tags --dirty --always 2>/dev/null || echo unknown
BUILD_DATE != date -u +%Y-%m-%dT%H:%M:%SZ

CPPFLAGS += -DVERSION='"$(VERSION)"' -DBUILD_DATE='"$(BUILD_DATE)"'

Then in your C code:

printf("hello %s, built %s\n", VERSION, BUILD_DATE);

Every invocation re-queries git — but on a modern machine this is fast. If you hate the cost, guard with a check that rebuilds only on HEAD changes (advanced).

Idiom — pkg-config

For every non-trivial system library, use pkg-config rather than hand-rolling flags:

PKGS := openssl libxml-2.0 sqlite3

CFLAGS  += $(shell pkg-config --cflags $(PKGS))
LDLIBS  += $(shell pkg-config --libs   $(PKGS))

Or, safer, with a fail-fast check:

PKGS := openssl libxml-2.0 sqlite3

ifneq ($(shell pkg-config --exists $(PKGS) && echo ok),ok)
$(error Missing one of: $(PKGS))
endif

CFLAGS  += $(shell pkg-config --cflags $(PKGS))
LDLIBS  += $(shell pkg-config --libs   $(PKGS))

Full reference template

Here's the Makefile I copy-paste into new C projects. Dissect it as you read:

makeMakefile — full reference
.DELETE_ON_ERROR:
.SUFFIXES:
MAKEFLAGS += --no-builtin-rules

SHELL       := /bin/bash
.SHELLFLAGS := -eu -o pipefail -c

# --- project ------------------------------------------------------------
NAME      := hello
VERSION   != git describe --tags --dirty --always 2>/dev/null || echo dev

# --- tooling (overridable) ---------------------------------------------
CC        ?= cc
AR        ?= ar
INSTALL   ?= install

# --- flags --------------------------------------------------------------
CPPFLAGS  += -I include -DVERSION='"$(VERSION)"'
CFLAGS    += -std=c11 -Wall -Wextra -Wpedantic
CFLAGS    += -MMD -MP
LDFLAGS   +=
LDLIBS    +=

ifdef DEBUG
  CFLAGS += -O0 -g
else
  CFLAGS += -O2
endif

# --- layout -------------------------------------------------------------
SRC_DIR   := src
BLD_DIR   := build
BIN       := $(BLD_DIR)/$(NAME)
SRCS      := $(wildcard $(SRC_DIR)/*.c)
OBJS      := $(patsubst $(SRC_DIR)/%.c,$(BLD_DIR)/%.o,$(SRCS))
DEPS      := $(OBJS:.o=.d)

# --- user-facing targets ------------------------------------------------
.PHONY: all clean install uninstall check help
.DEFAULT_GOAL := all

all: $(BIN)

help:
	@printf '%s\n' \
	 'Targets:' \
	 '  all        build $(BIN)' \
	 '  clean      remove $(BLD_DIR)' \
	 '  check      build & run tests' \
	 '  install    install to $$(prefix) (default /usr/local)' \
	 '  uninstall  remove installed files' \
	 '' \
	 'Variables:' \
	 '  DEBUG=1    build -O0 -g' \
	 '  CC=clang   use clang' \
	 '  prefix=... install prefix'

$(BIN): $(OBJS) | $(BLD_DIR)
	$(CC) $(LDFLAGS) $^ $(LDLIBS) -o $@

$(BLD_DIR)/%.o: $(SRC_DIR)/%.c | $(BLD_DIR)
	$(CC) $(CPPFLAGS) $(CFLAGS) -c $< -o $@

$(BLD_DIR):
	@mkdir -p $@

-include $(DEPS)

# --- install ------------------------------------------------------------
prefix ?= /usr/local
bindir := $(prefix)/bin
DESTDIR ?=

install: $(BIN)
	$(INSTALL) -d $(DESTDIR)$(bindir)
	$(INSTALL) -m 755 $(BIN) $(DESTDIR)$(bindir)/

uninstall:
	rm -f $(DESTDIR)$(bindir)/$(NAME)

# --- tests --------------------------------------------------------------
TEST_SRCS := $(wildcard tests/*.c)
TEST_BINS := $(patsubst tests/%.c,$(BLD_DIR)/tests/%,$(TEST_SRCS))

$(BLD_DIR)/tests/%: tests/%.c | $(BLD_DIR)/tests
	$(CC) $(CPPFLAGS) $(CFLAGS) $< -o $@

$(BLD_DIR)/tests:
	@mkdir -p $@

check: $(TEST_BINS)
	@for t in $^; do echo "-- $$t"; "$$t" || exit 1; done
	@echo "All tests passed."

# --- cleanup ------------------------------------------------------------
clean:
	rm -rf $(BLD_DIR)

This template scales from 10 to 1000+ files without structural changes. Swap NAME, add more sources, keep going.

Exercises

EX 9.1 medium Verify auto-deps work

With the auto-deps Makefile, build cleanly. Check build/*.d exists. Now edit a header (add a comment, save). Run make and verify that all .c files using that header recompile, without listing any dependency in the Makefile by hand.

Show solution

The .d files contain lines like:

$ cat build/greet.d
build/greet.o: src/greet.c include/greet.h

After the -include $(DEP) runs, Make knows this. Touching include/greet.h marks greet.c as needing to rebuild:

$ touch include/greet.h
$ make -n
cc -O2 ... -c src/main.c -o build/main.o
cc -O2 ... -c src/greet.c -o build/greet.o
cc build/main.o build/greet.o -o build/hello
EX 9.2 medium Deleting a header gracefully

Without -MP, what happens if you delete a header that's listed in a .d file? What does -MP change?

Show solution

Without -MP, the .d file has:

build/main.o: src/main.c include/gone.h

When you delete include/gone.h, Make reads the .d, sees include/gone.h listed as a prerequisite, can't find it, and aborts with "No rule to make target 'include/gone.h'".

With -MP, the .d also contains:

include/gone.h:

An empty rule for each header. When the file doesn't exist, Make treats this empty rule as a "success" (a file that requires no building), so the missing file is silently tolerated. main.o is rebuilt (because the prereq list has an old header that's gone), and the fresh .d file no longer mentions it. Next run, equilibrium.

EX 9.3 medium Polyglot project

You have a C program that reads data from a CSV that's generated by a Python script. Write a single Makefile where make run:

  1. Generates data.csv from gen.py if needed.
  2. Builds ./processor from processor.c if needed.
  3. Runs ./processor data.csv.
Show solution 
.PHONY: all run clean
.DELETE_ON_ERROR:

all: processor data.csv

processor: processor.c
	$(CC) $(CFLAGS) $< -o $@

data.csv: gen.py
	python $< > $@

run: processor data.csv
	./processor data.csv

clean:
	rm -f processor data.csv
EX 9.4 hard Out-of-tree build

Modify the full reference Makefile so that users can do:

$ make BLD_DIR=/tmp/hello-build

… and have the build artifacts land in /tmp/hello-build while the source tree stays clean. What (if anything) needs to change?

Show solution

Nothing — the reference template already supports this because all outputs are computed as $(BLD_DIR)/.... The only subtle thing: BLD_DIR is set with :=, so a command-line BLD_DIR=... overrides it (command-line wins over Makefile assignments, as per Chapter 4).

Test:

$ make BLD_DIR=/tmp/hb
mkdir -p /tmp/hb
cc ... -c src/main.c -o /tmp/hb/main.o
...
$ ls
src/  include/  Makefile       # no build/
$ ls /tmp/hb
main.o main.d hello

This is exactly the Linux kernel's O=... pattern.

EX 9.5 hard A mini website

You have a directory of Markdown files and a single template.html. Each .md should become an .html by piping through pandoc --template=template.html. The output lands in _site/. Write the Makefile.

Show solution 
.DELETE_ON_ERROR:
.PHONY: all clean

MD    := $(wildcard *.md)
HTML  := $(patsubst %.md,_site/%.html,$(MD))

all: $(HTML)

_site/%.html: %.md template.html | _site
	pandoc --template=template.html $< -o $@

_site:
	mkdir -p $@

clean: ; rm -rf _site

template.html is a prerequisite on every .html — edit the template, everything rebuilds. This scales to blogs of hundreds of pages with sub-second incremental builds.

EX 9.6 hard Handle the compile-flag-change problem

Remember from Chapter 1: if you change CFLAGS in the Makefile, Make won't rebuild anything because the .c files aren't newer. Design a scheme using a "flags file" that tracks current CFLAGS and triggers a rebuild when they change.

Show solution

Idea: write CFLAGS to a file; include that file in every .o's prereq list; regenerate the file only if its contents differ from the current CFLAGS.

CFLAGS_STAMP := build/.cflags

# Regenerate the stamp file only if CFLAGS changed.
$(shell mkdir -p build; \
        new='$(CFLAGS)'; \
        old="$$(cat $(CFLAGS_STAMP) 2>/dev/null)"; \
        [ "$$new" = "$$old" ] || printf '%s' "$$new" > $(CFLAGS_STAMP))

build/%.o: src/%.c $(CFLAGS_STAMP) | build
	$(CC) $(CFLAGS) -c $< -o $@

Change CFLAGS, the $(shell …) at parse time detects the difference, rewrites build/.cflags, which becomes newer than the .os, which triggers a full rebuild. Change nothing, the stamp file isn't touched, mtimes stay stable, no rebuild.

This is a simplified version of what ninja and most serious build systems do with content hashing, without extra machinery.

Recap

  • -MMD -MP + -include $(DEP) is the canonical auto-dependency pattern for C/C++.
  • Set up your build dir as an order-only prerequisite: $(BLD_DIR)/%.o: src/%.c | $(BLD_DIR).
  • Data pipelines are just as much Make's domain as C: list scripts as prerequisites, use .DELETE_ON_ERROR, get reproducible incremental builds for free.
  • LaTeX builds are expressible in Make; latexmk saves you from repeating runs.
  • Follow GNU install conventions: prefix, bindir, DESTDIR, INSTALL.
  • Version strings from git describe via !=.
  • The full reference template is a good starting point for any new C/C++ project.
