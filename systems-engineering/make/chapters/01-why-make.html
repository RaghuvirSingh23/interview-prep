Chapter 01 Why Make Exists

Before we write a single Makefile, it's worth understanding what problem Make solves and what makes it different from a shell script. If you skip this chapter you will keep writing Makefiles that are just shell scripts in a trench coat — and you'll never feel the power of the tool.

The problem: builds are graphs, not lists

Imagine you're writing a C program in 1976. You have three source files: main.c, parse.c, and util.c. Each compiles to a .o file, and those link into an executable called program.

Here is that build as a shell script:

shbuild.sh
cc -c main.c  -o main.o
cc -c parse.c -o parse.o
cc -c util.c  -o util.o
cc main.o parse.o util.o -o program

This works. It also takes 4 compile steps every time you run it, even if you only changed one file. In 1976 on a PDP-11 that could be minutes of recompilation. Today, on a project with 10,000 files, it's still minutes — you've just bumped the scale.

The real build is not a list of commands. It's a graph:

graphdependency graph
    program
   /   |    \
  /    |     \
main.o parse.o util.o
  |      |     |
main.c parse.c util.c

Each node is a file. Each edge says this file depends on this other file. main.o depends on main.c; program depends on all three .o files.

The insight that makes Make special: a file does not need to be rebuilt if it is newer than all the files it depends on. Make reads this graph, compares filesystem timestamps, and rebuilds only the parts that are out of date. That is the whole idea.

How Make was born

Stuart Feldman wrote the first version of Make at Bell Labs in April 1976. The story he tells: a colleague had wasted a whole afternoon debugging an executable that seemed broken, only to realise he'd forgotten to recompile one of its source files. Feldman went home that weekend, came back Monday, and within a few days had a tool that looked at file timestamps and figured out for you what needed to be rebuilt.

The tool stuck. Variants exist — BSD Make, nmake, ninja, bazel — but 50 years later, GNU Make is still the most common build tool on Unix systems. Every Linux kernel, every C project on GitHub, every moderately serious research codebase: all Make.

Why not just a script?

This is the most common question from newcomers: "Why do I need Make? Can't I just write a bash script?" You can. Here's what you lose.

FeatureShell scriptMake
Rebuilds only what's staleNo — runs everythingYes — timestamp-based
Parallel execution of independent stepsManual (&, wait)Built-in with -j
Declarative: describes the graph, not the orderNo — imperativeYes
Stops at first error with full diagnosticsset -e if you rememberYes, by default
Works across machines without tool sprawlMostlyYes — ubiquitous
Scales to 1000+ stepsSlow, error-proneFine

The one Make gets most wrong: "rebuilds only what's stale". Timestamps are a coarse proxy for "did the content change". Modern build systems (bazel, nix) use content hashes instead. But for 99% of projects, timestamps are good enough — and they are fast, because a filesystem stat() is essentially free.

The big idea, stated once

The Make model

A Makefile is a list of rules. Each rule says:

  • This target file
  • depends on these prerequisite files
  • and is built by running this recipe.

When you type make foo, Make looks at foo's prerequisites, checks if any are newer than foo (or if foo doesn't exist), and if so, runs the recipe to (re)build it. It does this recursively: before running foo's recipe, it makes sure all of foo's prerequisites are themselves up to date.

That's it. Everything else in this tutorial is elaboration.

A first Makefile, as a preview

Here is the shell script from above, rewritten as a Makefile:

makeMakefile
program: main.o parse.o util.o
	cc main.o parse.o util.o -o program

main.o: main.c
	cc -c main.c -o main.o

parse.o: parse.c
	cc -c parse.c -o parse.o

util.o: util.c
	cc -c util.c -o util.o

Four rules. Each says "this file depends on these other files and is built this way". If you change only parse.c, running make will:

  1. Notice parse.o is older than parse.c — rebuild it.
  2. Notice program's prerequisites have changed — relink.
  3. Leave main.o and util.o alone.

You've just saved two compile steps. On a large project, this matters enormously.

Under the hood

When Make runs, it:

  1. Parses the Makefile into an in-memory graph.
  2. Determines the goal target (the one you asked for, or the first target in the file).
  3. Walks the graph depth-first, checking stat() timestamps.
  4. For each target whose mtime is older than any prerequisite's mtime (or which doesn't exist), schedules its recipe.
  5. Executes recipes in topological order — or in parallel if you passed -j.

That's the entire algorithm. You can read an early version of Make's source in about an evening.

The most common mistake beginners make

Beginners look at a Makefile and think it's a script. They read the rules top-to-bottom and assume they run in that order. They don't. The order of rules in the file is irrelevant. What matters is the graph they define.

You could write our Makefile in any order:

makeMakefile — same graph, different order
util.o: util.c
	cc -c util.c -o util.o

program: main.o parse.o util.o
	cc main.o parse.o util.o -o program

main.o: main.c
	cc -c main.c -o main.o

parse.o: parse.c
	cc -c parse.c -o parse.o

Same graph, same behaviour. The only thing order affects is which target is the default goal — if you run make with no arguments, it builds the first target in the file. By convention the first target is the "main" one (here, program).

Make vs. modern build tools

Today there are shinier options: ninja, bazel, cmake, meson, buck, nix. Should you learn Make anyway? Yes, and here's why.

  • CMake generates Makefiles. When CMake breaks, you debug a Makefile.
  • Ninja is a faster Make. It uses the same mental model; learning Make teaches you Ninja for free.
  • Bazel is a different beast (content-addressable, hermetic, huge) but it's overkill for most projects. Make is still the right tool for a 20-file C library or a data pipeline.
  • Make is everywhere. Your Linux kernel, your Raspberry Pi cross-compile, your embedded firmware, your Emacs config, your LaTeX thesis — Make is already installed.
  • Make has no dependencies. A Makefile is 15 lines of text. A CMakeLists.txt can evaluate to a 10,000-line generated Makefile. Sometimes you want the small thing.

That said: if you're starting a new C++ project with 500 files and cross-platform needs, use CMake or Meson. Make's weakness is that it has no built-in notion of "find me a compiler" or "is this library installed" — it just runs commands. For large systems that's not enough.

Exercises

EX 1.1 easy Draw the graph

You have a LaTeX document with the following structure:

  • thesis.tex includes intro.tex and results.tex.
  • Running pdflatex thesis.tex produces thesis.pdf.
  • One of the figures, fig1.pdf, is produced by gnuplot fig1.plt reading data.csv.

Draw the dependency graph. Which files are leaves (no prerequisites)? Which are internal nodes? What is the root?

Show solution 
         thesis.pdf  ← root (goal)
              |
    ┌─────────┼──────────┬──────────────┐
    |         |          |              |
thesis.tex intro.tex results.tex    fig1.pdf
                                        |
                                     fig1.plt, data.csv  ← leaves

Leaves: thesis.tex, intro.tex, results.tex, fig1.plt, data.csv (things you edit by hand). Internal nodes: fig1.pdf. Root: thesis.pdf.

Notice: touching data.csv should cause fig1.pdf to regenerate, which should cause thesis.pdf to rebuild. Touching intro.tex should only trigger the latex run, not the gnuplot step. Make's whole job is to enforce this.

EX 1.2 easy Shell script vs Makefile — wasted work

Consider a project with 100 C files, each compiling in 1 second. You change one file. How long does the rebuild take with a build.sh that runs all 100 compilations? How long with a Makefile that tracks dependencies? How much CPU is wasted?

Show solution

Shell: ~100 seconds, with 99 seconds wasted. Make: ~1 second for the changed file plus a second or two for the link step — ~2 seconds total, essentially zero waste.

Multiply by 20 times per day, 200 working days per year, and you begin to see why a senior developer cares so much about build systems. "It only takes 5 minutes to compile" means you wait 5 minutes, 40 times a day, every day. That's 3+ hours of your life, per day, staring at a progress bar.

EX 1.3 medium Find where Make doesn't help

Come up with a scenario where Make's timestamp-based model gives the wrong answer. (Hint: think about what happens if you git checkout an older branch, or touch a file without changing its contents.)

Show solution

Several:

  • Branch switch. You git checkout a branch. The file foo.c now has the contents of that branch's version, but its mtime is set to "now" by git. Its .o file, built earlier, has an older mtime, so Make rebuilds it. That's correct. But if you git checkout back, the old foo.c is restored with a newer mtime than the .o — Make rebuilds, even though the .o is already correct. Wasted work.
  • touch. You run touch foo.c to reset its mtime. Make thinks foo.c changed and rebuilds. No content actually changed. Wasted work.
  • Clock skew. NFS or cross-machine file systems sometimes have clock drift between client and server. Make can be confused into thinking a file is "from the future" and either never-rebuild it or constantly rebuild it.
  • Compiler flag changes. You edit the Makefile to add -O2. foo.c didn't change, so Make doesn't rebuild foo.o — but the flags did change. The .o is now built with the wrong flags and Make has no way to know.

Content-hashing build systems like Bazel or Nix avoid most of these. We'll work around the flag-change one in a later chapter.

Recap

  • A build is a graph of file dependencies, not a list of commands.
  • Make rebuilds a target only if one of its prerequisites is newer than it (or it doesn't exist).
  • Rules can appear in any order; what matters is the graph they define.
  • Timestamp-based dependency tracking is coarse but fast. It's wrong in edge cases (touch, branch switch, flag changes) — we'll patch these holes later.
  • The first target in a Makefile is the default goal.
