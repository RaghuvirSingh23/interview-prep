Chapter 07 Docker — Fundamentals

Containers are the runtime Kubernetes assumes you already understand. This chapter goes from "what is an image, exactly?" through Dockerfile, networking, volumes, and Compose. By the end, every K8s YAML in the rest of the tutorial reads as "schedule one of these containers, with these flags".

Container vs VM, in one paragraph

A virtual machine emulates a whole computer — its own kernel, its own boot sequence, its own filesystem from inode 1. A container shares the host's kernel and only isolates the bits that matter for an app: process tree (PID namespace), filesystem view (mount namespace), network stack (net namespace), users (user namespace), plus resource caps via cgroups. It's "Linux processes wearing a costume". Cheap, fast (start in milliseconds), but only as portable as the kernel ABI they target.

The image model

An image is an immutable, content-addressable bundle of:

  • Layers — tarballs of filesystem changes, identified by SHA256.
  • Config — environment, entrypoint, default command, exposed ports, working directory.
  • Manifest — JSON document tying layers + config together by digest.

A container is an image plus a thin writeable layer on top — when the container runs, writes go to that top layer; the image layers stay shared and read-only. Stop the container, throw the writeable layer away (unless you mount a volume).

┌─────────────────────────────────────────┐
│ writeable layer (per running container) │ ← /tmp/foo, /var/log/whatever
├─────────────────────────────────────────┤
│ layer N: COPY src/ /app                 │
│ layer …: RUN pip install …               │
│ layer 1: FROM python:3.12-slim           │ ← pulled from registry, content-addressed
└─────────────────────────────────────────┘

Layers are deduplicated across images. If two images share a base (python:3.12-slim), it's downloaded and stored once. This is why Docker images "feel small" even when they're notionally hundreds of MB.

OCI — Docker isn't really "Docker" anymore

The image format and the container runtime are both standardised by the Open Container Initiative. Images you build with docker build work in containerd, CRI-O, podman, buildah, and Kubernetes. The "Docker" you use day-to-day is one front-end among many. Useful framing because:

  • Kubernetes nodes don't run Docker — they run containerd or CRI-O.
  • Many CI systems use buildah, kaniko, or buildkit (rootless) instead of Docker Engine.
  • The ecosystem talks about "OCI images" and "container runtimes" generically — same image, many engines.

Install & first container

$ docker --version
Docker version 27.0.3, build ...
$ docker run --rm hello-world
Unable to find image 'hello-world:latest' locally
latest: Pulling from library/hello-world
...
Hello from Docker!
This message shows that your installation appears to be working correctly.

What just happened, in five lines:

  1. CLI asked the daemon to run hello-world:latest.
  2. Daemon didn't have it; pulled from Docker Hub.
  3. Created a container — fresh PID/mount/net namespaces, set up the rootfs from layers.
  4. Ran the image's default command (a tiny C program that prints the banner).
  5. Process exited; --rm deleted the container; layers stay cached.

docker run flags worth memorising

# interactive shell
$ docker run -it --rm ubuntu:24.04 bash

# detached, named, port-publish, env, volume mount
$ docker run -d \
    --name web \
    -p 8080:80 \
    -e GREETING=hi \
    -v $PWD/site:/usr/share/nginx/html:ro \
    nginx:1.27-alpine

# resource caps
$ docker run --rm \
    --cpus 0.5 \
    --memory 256m \
    --pids-limit 100 \
    busybox sleep 5

# user / read-only / no-new-privs (security)
$ docker run --rm \
    --user 10001:10001 \
    --read-only \
    --tmpfs /tmp:rw,size=64m \
    --security-opt no-new-privileges:true \
    --cap-drop=ALL \
    my-app:1.0

Conventions:

  • -d detach — run in background, print the container ID.
  • --rm auto-remove on exit. Use for one-shot commands; without it, stopped containers pile up.
  • --name give a stable name; otherwise Docker invents one (cranky_einstein).
  • -p HOST:CONTAINER publish a port. Without, the container's port is unreachable from the host.
  • -e KEY=VALUE set env var. Use --env-file path for many.
  • -v mount: bind, named volume, or tmpfs (more below).

Dockerfile, every directive

dockerfileDockerfile
# Pinned base; comments start with #.
FROM python:3.12-slim

# Metadata for downstream tools (registries, K8s).
LABEL org.opencontainers.image.source="https://github.com/myorg/promote-bot"
LABEL org.opencontainers.image.licenses="MIT"

# Build-time variable. Override at build with --build-arg APP_VERSION=...
ARG APP_VERSION=dev
ENV APP_VERSION=${APP_VERSION} \
    PYTHONDONTWRITEBYTECODE=1 \
    PYTHONUNBUFFERED=1

WORKDIR /app

# Install OS deps in a single RUN to keep the layer small.
# --no-install-recommends + cleanup avoids ~100MB of cruft.
RUN apt-get update \
 && apt-get install --no-install-recommends -y curl ca-certificates \
 && rm -rf /var/lib/apt/lists/*

# Order matters! Things that change rarely come first for cache reuse.
COPY requirements.txt .
RUN pip install --no-cache-dir -r requirements.txt

# Then the code, which changes every commit.
COPY src/ ./src/

# What user to run as.
RUN useradd -r -u 10001 app
USER 10001

# Expose: pure documentation; doesn't actually publish anything.
EXPOSE 8080

# Where the container's "stop policy" sends signals (PID 1).
STOPSIGNAL SIGTERM

# Optional shallow self-test, run by the runtime.
HEALTHCHECK --interval=30s --timeout=3s --start-period=10s --retries=3 \
  CMD curl -fsS http://localhost:8080/healthz || exit 1

# How to start. Two parts:
ENTRYPOINT ["python", "-m", "promote_bot"]
CMD ["run"]                       # default args; user can override

Directive cheatsheet

DirectiveEffect
FROM Base image. Always pinned (tag and digest in production).
ARG Build-time variable. Pass with --build-arg. Not in final image.
ENV Env var baked into the image, available at build and run.
RUN Run a command at build time, commit the resulting filesystem as a layer.
COPY src dst Copy from build context into the image. Honours .dockerignore.
ADD Like COPY but also auto-extracts tarballs and fetches URLs. Avoid; prefer COPY.
WORKDIR Set CWD for following directives and for the running container.
USER Switch user for following RUN and for the running container.
EXPOSE Documentation. Doesn't open a port. -p at run time does.
VOLUME "Treat this path as external"; if no volume mounted, an anonymous one is created.
ENTRYPOINT The command. Hard to override; --entrypoint can.
CMD Default arguments to ENTRYPOINT, overridable on the run line.
HEALTHCHECK Periodic command; pass/fail flips container's healthy status.
STOPSIGNAL Signal sent on stop (default SIGTERM).
SHELL Override the shell used for shell-form RUN.
ONBUILD Triggers in derived images. Niche; mostly leave alone.

ENTRYPOINT vs CMD — the canonical confusion

The two combine to form the final command, in this rule:

ENTRYPOINT ["python", "-m", "promote_bot"]   # always part of the command
CMD ["run"]                                  # default args, overridable

# docker run my-app                  → python -m promote_bot run
# docker run my-app status           → python -m promote_bot status
# docker run --entrypoint sh my-app  → sh        (CMD becomes "run", but with sh it's just stray)

The pattern: ENTRYPOINT carries the program's identity, CMD carries default arguments. Always use the JSON-array (exec) form, not the shell form — shell-form spawns /bin/sh -c … as PID 1, which doesn't forward signals to your real process. Result: docker stop waits 10 seconds and SIGKILLs you.

Exec form vs shell form
# BAD — shell form. PID 1 is /bin/sh; SIGTERM doesn't reach python.
ENTRYPOINT python -m my_app

# GOOD — exec form. python is PID 1 directly; receives signals.
ENTRYPOINT ["python", "-m", "my_app"]

Always JSON arrays for ENTRYPOINT, CMD, and RUN where signals matter. Shell form is fine for one-shot RUNs at build time.

Build cache & layer ordering

Each Dockerfile directive creates (potentially) a new layer. Docker hashes the inputs (the directive + the files it COPY-ed + the RUN's command line) and reuses the layer from cache if the hash matches. Order directives so frequently-changing things come last.

# BAD — every code change invalidates the pip install layer
FROM python:3.12-slim
WORKDIR /app
COPY . .                            # invalidates whenever any file changes
RUN pip install -r requirements.txt # re-runs every commit


# GOOD — pip install cached unless requirements.txt itself changed
FROM python:3.12-slim
WORKDIR /app
COPY requirements.txt .
RUN pip install -r requirements.txt
COPY src/ ./src/                    # only this layer rebuilds on code change

This single reordering is often a 10× build-time speedup on incremental builds.

.dockerignore — keep the build context small

The "build context" is everything in the directory passed to docker build. The whole context is sent to the daemon (or BuildKit) before the build starts. A 2 GB git repo with build artifacts ⇒ 2 GB transfer per build.

.dockerignore
.git
.venv
__pycache__/
*.pyc
node_modules/
build/
dist/
.pytest_cache/
.mypy_cache/
.ruff_cache/
*.log
.env
**/.DS_Store

Treat .dockerignore like .gitignore — exclude everything that doesn't belong in the image. Side benefit: prevents accidentally COPYing a .env with secrets into the image.

Tags vs digests

An image reference looks like registry/repo:tag or registry/repo@sha256:….

  • Tags are mutable. nginx:1.27 may point at one digest today, another tomorrow. Convenient, surprising in production.
  • Digests are immutable. nginx@sha256:abc… is exactly one image, forever.
$ docker pull nginx:1.27
$ docker inspect --format='{{index .RepoDigests 0}}' nginx:1.27
nginx@sha256:c79f7e7b9a91c75b2c43...

# Pin in a Dockerfile:
FROM nginx:1.27@sha256:c79f7e7b9a91c75b2c43...

Renovate / Dependabot can keep digest pins fresh via reviewable PRs. We dive deeper in Chapter 8.

Networking — bridge, host, none

Each container gets a network namespace. Three drivers cover everyday use:

NetworkBehaviour
bridge (default)Container has its own IP on a private virtual bridge. Reach others on the same bridge by IP. Reach the outside via NAT.
host Container shares the host's network namespace. Same IP as host, same ports. Linux only; not isolated.
none No network. Useful for pure-compute jobs.
user-defined bridgeSame as bridge but with built-in DNS — containers find each other by name. Use this for multi-container apps.
$ docker network create app-net
$ docker run -d --name db --network app-net postgres:16
$ docker run -d --name api --network app-net -e DB_HOST=db my-api:1.0
# from inside `api`, `db` resolves to db's IP automatically

Publishing a port (-p) sets up a userland proxy / iptables rule so packets to the host's port are forwarded to the container. -p 8080:80 means "host 8080 → container 80". -p 127.0.0.1:8080:80 binds only to loopback — non-trivially safer for dev.

Volumes — the three kinds

KindMount withUse for
Bind mount -v /host/path:/container/pathDev — share source code with a running container.
Named volume -v myvol:/var/lib/data Persistence the engine manages. Survives container removal.
tmpfs --tmpfs /tmp:size=64m RAM-backed. Goes away on stop.
 
# Bind: live-reload code into a running container
$ docker run -it --rm \
    -v $PWD:/app \
    -w /app \
    python:3.12-slim \
    python -m my_app

# Named volume: postgres data persists across `docker rm` and `docker run`
$ docker volume create pgdata
$ docker run -d --name db -v pgdata:/var/lib/postgresql/data postgres:16
$ docker stop db && docker rm db
$ docker run -d --name db -v pgdata:/var/lib/postgresql/data postgres:16  # data still there

Read-only mounts: append :ro. Useful for passing in config without letting the container edit it: -v $PWD/config:/etc/app:ro.

Logs & stop semantics

Convention: your app writes to stdout/stderr. The runtime captures and stores. Don't write to a log file inside the container — you'll lose it when the container is removed, and Kubernetes can't ship from random files.

$ docker logs -f --tail 50 web
$ docker logs --since 10m web

Stop: docker stop <c> sends SIGTERM, waits up to 10 s (configurable: -t 30), then SIGKILL. docker kill is immediate SIGKILL — don't reach for it casually; you skip your app's graceful shutdown (Chapter 6's signal-handling pattern).

Registries

An image lives at <registry>/<repo>:<tag>. If you omit the registry, docker defaults to Docker Hub.

# Push to GitHub Container Registry
$ docker login ghcr.io -u USER -p $GHCR_TOKEN
$ docker tag my-app:1.0 ghcr.io/myorg/my-app:1.0
$ docker push ghcr.io/myorg/my-app:1.0

# Pull explicitly from a registry
$ docker pull registry.example.com/team/my-app:1.0

Common registries you'll meet: Docker Hub (docker.io), GitHub Container Registry (ghcr.io), AWS ECR, GCP Artifact Registry, Azure Container Registry, JFrog Artifactory, Harbor (self-hosted). All speak the OCI distribution spec; the auth handshake differs.

Docker Compose — multi-container locally

Compose is a YAML file describing several containers as one logical unit. For local dev, integration tests, and small self-hosted apps, it beats hand-rolled docker run scripts.

yamlcompose.yaml
name: promote-stack

services:
  api:
    build:
      context: .
      args:
        APP_VERSION: dev
    image: promote-bot:dev
    environment:
      LOG_LEVEL: DEBUG
      DB_URL: postgres://postgres:test@db:5432/postgres
    ports:
      - "127.0.0.1:8080:8080"
    depends_on:
      db:
        condition: service_healthy
    develop:
      watch:                              # 2024+, hot-reload friendly
        - { path: src/, action: sync, target: /app/src }
        - { path: requirements.txt, action: rebuild }

  db:
    image: postgres:16
    environment:
      POSTGRES_PASSWORD: test
    volumes:
      - pgdata:/var/lib/postgresql/data
    healthcheck:
      test: ["CMD-SHELL", "pg_isready -U postgres"]
      interval: 5s
      retries: 10

volumes:
  pgdata:
$ docker compose up -d           # build + start everything
$ docker compose logs -f api
$ docker compose exec api sh
$ docker compose down            # stop + remove containers (volumes stay)
$ docker compose down -v         # also remove volumes

Compose is also extremely useful in tests — spin up a real Postgres in CI for integration suites. testcontainers (Chapter 6) does this from Python directly.

Take any small Python project (the Chapter 5 promote CLI works). Add this Dockerfile and .dockerignore:

Build, run, inspect, then push:

$ docker build -t promote:0.1.0 .
$ docker images promote
REPOSITORY   TAG     IMAGE ID       SIZE
promote      0.1.0   8c5d…          ~85MB

$ docker run --rm promote:0.1.0
Usage: promote [OPTIONS] COMMAND [ARGS]...
...

$ docker run --rm promote:0.1.0 hello --name Raghu

$ docker inspect promote:0.1.0 | jq '.[0].Config.{Entrypoint,Cmd,Env,User}'

$ docker tag promote:0.1.0 ghcr.io/myuser/promote:0.1.0
$ docker push ghcr.io/myuser/promote:0.1.0

Now you've got an OCI image you can run locally and that Kubernetes can pull on a node. The K8s chapters that follow assume exactly this shape.

Docker vs containerd vs podman

Daemon?Root?Common use
Docker EngineYes (dockerd)Yes (default)Dev laptops, CI runners, traditional servers.
containerd Yes Yes What Kubernetes uses on nodes; lower-level.
podman No (forks per command)No (rootless first)RHEL/Fedora world; drop-in CLI to Docker.
nerdctl (uses containerd) Yes Docker-flavoured CLI on top of containerd.

For Kubernetes work, the takeaway: your docker build output is consumed by containerd on K8s nodes. Same OCI image format; "Docker" is a frontend.

Exercises

EX 7.1 easy Cache-friendly Dockerfile

Reorder this Dockerfile so changing src/ doesn't invalidate the dependency-install layer.

FROM node:20-slim
WORKDIR /app
COPY . .
RUN npm ci
CMD ["node", "src/server.js"]
Show solution 
FROM node:20-slim
WORKDIR /app
COPY package.json package-lock.json ./
RUN npm ci
COPY src/ ./src/
CMD ["node", "src/server.js"]

Now npm ci only re-runs when package*.json changes. Code edits invalidate just the small final layer.

EX 7.2 easy ENTRYPOINT vs CMD

For ENTRYPOINT ["python", "-m", "tool"] + CMD ["status"], what do these run?

  1. docker run my-img
  2. docker run my-img build
  3. docker run --entrypoint sh my-img
Show solution
  1. python -m tool status
  2. python -m tool build — CMD is replaced by user args.
  3. sh status — ENTRYPOINT replaced; CMD still appended (and sh ignores it). To clear CMD too: --entrypoint sh my-img -c … with explicit args.
EX 7.3 medium Bind mount for hot reload

Run a Python container that re-uses your local src/ directory without rebuilding the image. Show the command.

Show solution 
$ docker run -it --rm \
    -v $PWD/src:/app/src \
    -w /app \
    -p 8080:8080 \
    python:3.12-slim \

EX 7.4 medium Two containers on one network

Without Compose: start a Postgres and a one-off Python container that connects to it by name db. Show the commands.

Show solution 
$ docker network create dev
$ docker run -d --name db --network dev \
    -e POSTGRES_PASSWORD=test postgres:16
$ docker run --rm --network dev \
    -e DB_URL='postgres://postgres:test@db:5432/postgres' \
    python:3.12-slim \

Default bridge doesn't auto-resolve names; user-defined bridges do. db is resolvable from any container on the dev network.

EX 7.5 medium .dockerignore audit

Run docker build . in a project that has none. Note the "Sending build context to daemon" size at the start. Add a .dockerignore; rebuild. By how much did the context shrink?

Show solution

Project-specific. On a typical Python repo with .git, .venv, __pycache__, the context drops from hundreds of MB to a few MB. Faster builds, smaller risk of accidentally COPYing junk into the image.

EX 7.6 hard Pin by digest

Pull nginx:1.27-alpine; find its digest; rewrite a Dockerfile to pin FROM by both tag and digest. Why both?

Show solution 
$ docker pull nginx:1.27-alpine
$ docker inspect --format='{{index .RepoDigests 0}}' nginx:1.27-alpine
nginx@sha256:7a3f3e3d7a...
FROM nginx:1.27-alpine@sha256:7a3f3e3d7a...

Tag = human readable, makes diffs easy to interpret. Digest = immutable, guarantees byte-identical pulls. Renovate updates both atomically.

Recap

  • An image is layers + config + manifest, content-addressed by SHA256. Layers are deduped across images.
  • OCI standardises the format; "Docker" is one of many frontends.
  • Order Dockerfile directives so frequently-changing things come last for cache reuse.
  • Always exec-form (JSON arrays) for ENTRYPOINT/CMD so signals reach PID 1.
  • Three volume kinds: bind (dev), named (persistent), tmpfs (RAM scratch).
  • User-defined bridge networks give DNS-by-name; the default bridge doesn't.
  • Pin by tag and digest in production. Renovate keeps both updated.
  • Docker Compose for local multi-container; testcontainers for Python integration tests.
  • Logs go to stdout/stderr; never to in-container files.
