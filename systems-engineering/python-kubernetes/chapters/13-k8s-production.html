Chapter 11 Production Patterns

The patterns that turn a working manifest into a workload your on-call won't curse you for. Probes, resource requests/limits, affinity, HPA, PDB, RBAC, security context, Pod Security Standards, observability hooks. The chapter that pays for itself the first time prod doesn't burn down on a Friday.

Probes — readiness, liveness, startup

The kubelet checks each container with probes. Three kinds, each answers a different question.

ProbeQuestionIf it fails
readinessProbeAre you ready to serve traffic?Service stops sending traffic to this Pod (removes from EndpointSlice). Pod is not killed.
livenessProbeAre you alive?Container is killed and restarted.
startupProbeAre you done starting?Container is killed and restarted. Disables the other two until it passes.
 
containers:
  - name: app
    image: my-app:1.0
    ports: [{ containerPort: 8080 }]
    readinessProbe:
      httpGet: { path: /ready, port: 8080 }
      periodSeconds: 5
      failureThreshold: 3
    livenessProbe:
      httpGet: { path: /healthz, port: 8080 }
      periodSeconds: 10
      failureThreshold: 3
      initialDelaySeconds: 30
    startupProbe:
      httpGet: { path: /healthz, port: 8080 }
      periodSeconds: 5
      failureThreshold: 60          # allow 5 minutes of startup

Rules of thumb

  • Always have a readiness probe. Without one, traffic hits cold pods that haven't loaded config / opened DB connections / warmed caches.
  • Liveness should detect real deadlocks, not transient errors. Liveness too aggressive = restart loops on intermittent issues = downtime amplified. A common pattern: liveness only fails on "I'm wedged" (no thread responsive); readiness fails on "I depend on a downstream that's flaky".
  • Use startupProbe for slow-starting apps (JVM, large model loads). Otherwise tune initialDelaySeconds on liveness — but startupProbe is the cleaner answer.
  • Endpoints must be cheap. A liveness check that runs a slow query for every probe will kill the pod under load.
  • Different paths per probe: /ready can include downstream checks; /healthz only checks "this process is responsive".

Probe types

# HTTP
readinessProbe:
  httpGet: { path: /ready, port: 8080, httpHeaders: [{ name: Host, value: example.com }] }

# TCP socket — just open a connection
readinessProbe:
  tcpSocket: { port: 5432 }

# Exec — run a command, exit 0 means healthy
livenessProbe:
  exec:
    command: ["sh", "-c", "redis-cli ping | grep -q PONG"]

# gRPC (1.27+)
readinessProbe:
  grpc: { port: 9000 }

Resources — requests & limits

resources:
  requests:
    cpu:    "100m"        # 100 millicores = 0.1 of a core
    memory: "128Mi"
  limits:
    cpu:    "500m"
    memory: "256Mi"
FieldWhat it means
requestsWhat the scheduler reserves on a node before placing the Pod. The Pod gets at least this much.
limitsThe cap. CPU above limits is throttled; memory above is OOM-killed.

The CPU limits debate

For most workloads, set CPU requests but not CPU limits. CPU is compressible — being throttled is fine, being killed is not. CFS-throttling at the cgroup level can cause severe latency spikes at fractional limits. Conventional wisdom in 2026: requests yes, limits only when you have a real reason (multi-tenancy isolation, billing).

For memory: set both, equal to each other. Memory isn't compressible — exceeding limits = OOMKill. Equal means no over-commit; the Pod gets a Guaranteed QoS class.

QoS classes

  • Guaranteed: every container has limits == requests for both CPU and memory. Last to be evicted under node pressure.
  • Burstable: at least one container has requests < limits, or only requests set. Middle-priority on eviction.
  • BestEffort: no requests or limits set anywhere. First evicted under pressure.

Production rule: every container has at least requests. BestEffort pods are a foot-gun — they'll get evicted at the worst moment.

Affinity, anti-affinity, taints, tolerations

Tools to influence scheduling.

nodeSelector — simple

spec:
  nodeSelector:
    disktype: ssd

Only place this Pod on nodes labelled disktype=ssd.

Affinity — flexible

affinity:
  nodeAffinity:                                # I want / prefer these nodes
    requiredDuringSchedulingIgnoredDuringExecution:
      nodeSelectorTerms:
        - matchExpressions:
            - { key: kubernetes.io/arch, operator: In, values: [amd64] }
    preferredDuringSchedulingIgnoredDuringExecution:
      - weight: 100
        preference:
          matchExpressions:
            - { key: topology.kubernetes.io/zone, operator: In, values: [us-east-1a] }
  podAntiAffinity:                             # spread me away from like-pods
    requiredDuringSchedulingIgnoredDuringExecution:
      - labelSelector: { matchLabels: { app: api } }
        topologyKey: kubernetes.io/hostname    # one per node

"required" = scheduling won't happen unless satisfied. "preferred" = soft preference. topologyKey defines what counts as the same domain — hostname (one per node), zone (one per AZ).

Common pattern: spread a Deployment across nodes/zones for HA via pod anti-affinity. Or a cleaner alternative below.

topologySpreadConstraints — modern, cleaner

spec:
  topologySpreadConstraints:
    - maxSkew: 1
      topologyKey: topology.kubernetes.io/zone
      whenUnsatisfiable: DoNotSchedule
      labelSelector: { matchLabels: { app: api } }

"At most 1 imbalance across zones for pods labelled app: api". Cleaner expression of "spread me across zones" than affinity gymnastics.

Taints & tolerations

The inverse: a node says "no pods unless they tolerate me". GPU nodes, Windows nodes, control-plane nodes are typically tainted so only pods that explicitly want them land there.

$ kubectl taint node gpu-1 nvidia.com/gpu=true:NoSchedule
spec:
  tolerations:
    - key: nvidia.com/gpu
      operator: Exists
      effect: NoSchedule

HorizontalPodAutoscaler

"Adjust replicas based on metrics." Most common: scale on CPU.

apiVersion: autoscaling/v2
kind: HorizontalPodAutoscaler
metadata: { name: api }
spec:
  scaleTargetRef:
    apiVersion: apps/v1
    kind: Deployment
    name: api
  minReplicas: 2
  maxReplicas: 20
  metrics:
    - type: Resource
      resource:
        name: cpu
        target:
          type: Utilization
          averageUtilization: 70           # target: avg CPU = 70% of requests
    - type: Resource
      resource:
        name: memory
        target: { type: Utilization, averageUtilization: 80 }
  behavior:                                # 1.23+; control scale-up/down speed
    scaleDown:
      stabilizationWindowSeconds: 300      # avoid flapping
      policies:
        - type: Percent
          value: 10
          periodSeconds: 60
    scaleUp:
      policies:
        - type: Percent
          value: 50
          periodSeconds: 30
        - type: Pods
          value: 4
          periodSeconds: 30
      selectPolicy: Max

Requirements:

  • Containers must have resources.requests.cpu set — utilisation is computed against requests.
  • metrics-server installed in the cluster (it usually is on managed clusters).

For non-CPU metrics (request rate, queue depth, custom Prometheus metric), use the External Metrics path — install kube-prometheus-stack or KEDA, then HPAs can scale on anything.

KEDA — the practical answer for "scale on anything"

KEDA bridges any event source (Kafka lag, SQS depth, Redis list length, Prometheus query result, cron schedule) to HPA. It also enables scale-to-zero, which native HPA doesn't.

VerticalPodAutoscaler — usually not

VPA adjusts requests/limits over time. Sounds great, but in practice it interacts badly with HPA, requires pod restarts to change resources, and most teams use the recommendation mode for sizing guidance rather than auto-update mode. Useful as a tool; not a panacea.

PodDisruptionBudget

"During voluntary disruptions (drain, eviction), don't take more than N pods down at once." Critical for stateful workloads and anything where reduced capacity matters.

apiVersion: policy/v1
kind: PodDisruptionBudget
metadata: { name: api }
spec:
  selector: { matchLabels: { app: api } }
  minAvailable: 2          # OR maxUnavailable: 1
  # unhealthyPodEvictionPolicy: AlwaysAllow   # 1.27+; let unhealthy pods get evicted

Voluntary = node drain by admin, autoscaler scale-down, eviction API. Involuntary (kernel panic, network split) doesn't respect PDBs — they're a soft contract for orchestrated operations.

For a Deployment with 3 replicas: minAvailable: 2 means a node drain pauses if it would leave fewer than 2. Drains progress as pods reschedule and become ready elsewhere.

Security context — least privilege at the pod level

spec:
  securityContext:                         # pod-level
    runAsNonRoot: true
    runAsUser: 10001
    runAsGroup: 10001
    fsGroup: 10001
    seccompProfile: { type: RuntimeDefault }
  containers:
    - name: app
      image: my-app:1.0
      securityContext:                     # container-level (overrides)
        allowPrivilegeEscalation: false
        readOnlyRootFilesystem: true
        capabilities:
          drop: [ALL]
        privileged: false

The minimum set of "production hardening" knobs:

  • runAsNonRoot: true — refuse to start if image runs as UID 0.
  • readOnlyRootFilesystem: true — apps that don't write should not have a writeable rootfs. Mount emptyDir for what does need to write.
  • allowPrivilegeEscalation: false — block setuid binaries.
  • capabilities: drop: [ALL] — drop every Linux capability you didn't ask for.
  • seccompProfile: RuntimeDefault — use the runtime's seccomp profile (containerd ships a sane default).

Pod Security Admission

Replaces the deprecated PodSecurityPolicy. Three levels of profile, applied at the namespace via labels:

apiVersion: v1
kind: Namespace
metadata:
  name: prod
  labels:
    pod-security.kubernetes.io/enforce: restricted    # block non-conforming pods
    pod-security.kubernetes.io/audit:   restricted    # log violations
    pod-security.kubernetes.io/warn:    restricted    # warn at apply time
ProfileAllows
privilegedAnything. For system namespaces.
baselineMost things; blocks the worst (privileged, hostNetwork, hostPath).
restrictedStrict: non-root, cap drop, seccomp default, no privilege escalation, etc.

Set enforce: restricted on app namespaces. The cluster rejects pod manifests that violate the profile — your security context above is essentially the restricted profile written out.

RBAC — properly

RBAC has four building blocks:

  • Role / ClusterRole — what actions are allowed.
  • RoleBinding / ClusterRoleBinding — who gets that Role.
apiVersion: rbac.authorization.k8s.io/v1
kind: ClusterRole
metadata: { name: deploy-watcher }
rules:
  - apiGroups: ["apps"]
    resources: ["deployments"]
    verbs: ["get", "list", "watch"]
  - apiGroups: [""]
    resources: ["events"]
    verbs: ["get", "list", "watch"]
---
apiVersion: rbac.authorization.k8s.io/v1
kind: RoleBinding
metadata: { name: alpha-watcher, namespace: team-alpha }
subjects:
  - kind: User
    name: alice@example.com
    apiGroup: rbac.authorization.k8s.io
  - kind: ServiceAccount
    name: monitor
    namespace: team-alpha
roleRef:
  kind: ClusterRole
  name: deploy-watcher
  apiGroup: rbac.authorization.k8s.io

Role = namespaced; ClusterRole = cluster-wide. RoleBinding = grants in one namespace; ClusterRoleBinding = grants cluster-wide. You can bind a ClusterRole via a RoleBinding to scope cluster-wide-defined permissions to a namespace — handy.

Audit your permissions

$ kubectl auth can-i list pods
yes
$ kubectl auth can-i delete deploy --as=system:serviceaccount:team-alpha:monitor
no
$ kubectl auth can-i --list                          # everything I can do
$ kubectl auth can-i --list --as=user@example.com

can-i is the friendly face of the SubjectAccessReview API. Use it to validate "did I just give the wrong permissions?" before applying.

Observability hooks

Logs

Containers write to stdout/stderr; the runtime captures to log files; a node-level shipper (Fluent Bit, Vector) tails them and forwards to a backend (Loki, Elasticsearch, CloudWatch). Don't write to files inside the container.

Metrics

Pod exposes /metrics in Prometheus format on a port; prometheus.io/scrape: "true" annotation tells Prometheus to scrape (with the right config). For the modern approach, install kube-prometheus-stack via Helm and use ServiceMonitor / PodMonitor CRDs instead of annotations.

Traces

OpenTelemetry SDK in your app, OTel Collector running as a DaemonSet or sidecar, exporting to Jaeger/Tempo/Datadog/etc. Distributed tracing is the only way to debug latency in a microservice mesh.

Events

Kubernetes itself emits Events for everything — pod scheduled, image pulled, probe failed, OOMKilled. kubectl describe pod X shows recent events. kubectl get events -A --sort-by=.lastTimestamp for cluster-wide. They're truncated after an hour by default; ship them to your log backend if you want history.

Graceful shutdown

spec:
  terminationGracePeriodSeconds: 60
  containers:
    - name: app
      image: my-app:1.0
      lifecycle:
        preStop:
          exec:
            command: ["sh", "-c", "sleep 10 && kill -TERM 1"]

Lifecycle when a Pod is deleted:

  1. API server marks the Pod for deletion (deletionTimestamp set).
  2. Endpoints controller removes Pod from EndpointSlice — Service stops sending new traffic. This is async.
  3. Kubelet runs the preStop hook (if any).
  4. Kubelet sends SIGTERM to PID 1.
  5. Wait terminationGracePeriodSeconds for graceful shutdown.
  6. If still running, SIGKILL.

The sleep 10 in preStop is the canonical "give kube-proxy time to update iptables before we stop accepting traffic" trick. Without it, you get a thin window where the Service still routes to a Pod that has already started shutting down.

Your app must handle SIGTERM gracefully (Chapter 6). If it ignores SIGTERM, you get hard kills.

Hands-on: a "production-shaped" Deployment

Hands-on · every production knob in one manifest
apiVersion: apps/v1
kind: Deployment
metadata:
  name: api
  namespace: prod
  labels: { app.kubernetes.io/name: api, app.kubernetes.io/version: "1.2.3" }
spec:
  replicas: 3
  revisionHistoryLimit: 5
  strategy:
    type: RollingUpdate
    rollingUpdate: { maxSurge: 1, maxUnavailable: 0 }
  selector: { matchLabels: { app: api } }
  template:
    metadata:
      labels: { app: api, app.kubernetes.io/version: "1.2.3" }
      annotations:
        prometheus.io/scrape: "true"
        prometheus.io/port:   "9100"
        config-hash:          "sha256:abc123"
    spec:
      serviceAccountName: api
      automountServiceAccountToken: false        # turn off if not calling K8s API
      terminationGracePeriodSeconds: 60
      securityContext:
        runAsNonRoot: true
        runAsUser:    10001
        fsGroup:      10001
        seccompProfile: { type: RuntimeDefault }
      topologySpreadConstraints:
        - maxSkew: 1
          topologyKey: topology.kubernetes.io/zone
          whenUnsatisfiable: ScheduleAnyway
          labelSelector: { matchLabels: { app: api } }
      containers:
        - name: api
          image: registry.example.com/api:1.2.3
          imagePullPolicy: IfNotPresent
          ports:
            - { name: http,    containerPort: 8080 }
            - { name: metrics, containerPort: 9100 }
          env:
            - name: POD_IP
              valueFrom: { fieldRef: { fieldPath: status.podIP } }
            - name: NODE_NAME
              valueFrom: { fieldRef: { fieldPath: spec.nodeName } }
          envFrom:
            - configMapRef: { name: api-config }
          resources:
            requests: { cpu: 100m,  memory: 256Mi }
            limits:   {              memory: 256Mi }   # mem only; no cpu limit
          startupProbe:
            httpGet: { path: /healthz, port: http }
            failureThreshold: 30
            periodSeconds: 5
          readinessProbe:
            httpGet: { path: /ready, port: http }
            periodSeconds: 5
          livenessProbe:
            httpGet: { path: /healthz, port: http }
            periodSeconds: 10
            failureThreshold: 6
          lifecycle:
            preStop:
              exec: { command: ["sh", "-c", "sleep 10"] }
          securityContext:
            allowPrivilegeEscalation: false
            readOnlyRootFilesystem: true
            capabilities: { drop: [ALL] }
          volumeMounts:
            - { name: tmp,   mountPath: /tmp }
            - { name: cache, mountPath: /var/cache/api }
      volumes:
        - { name: tmp,   emptyDir: {} }
        - { name: cache, emptyDir: { sizeLimit: 1Gi } }
---
apiVersion: policy/v1
kind: PodDisruptionBudget
metadata: { name: api, namespace: prod }
spec:
  selector: { matchLabels: { app: api } }
  minAvailable: 2
---
apiVersion: autoscaling/v2
kind: HorizontalPodAutoscaler
metadata: { name: api, namespace: prod }
spec:
  scaleTargetRef: { apiVersion: apps/v1, kind: Deployment, name: api }
  minReplicas: 3
  maxReplicas: 20
  metrics:
    - type: Resource
      resource: { name: cpu, target: { type: Utilization, averageUtilization: 70 } }

Read line by line. Every block solves a real production problem. Use this as a starting template; remove what doesn't apply rather than adding what's missing later.

Exercises

EX 11.1 easy Probe paths

Should /ready and /healthz check the same things? Why or why not?

Show solution

No. /ready can return false if downstream dependencies are unavailable (database, cache) — Service stops sending traffic, but the pod isn't killed and can recover. /healthz should only return false if the process is genuinely wedged and needs a restart. Identical paths conflate "should I serve right now?" with "should I be killed?".

EX 11.2 medium QoS class

What QoS class does this pod end up in?

containers:
  - name: a
    resources: { requests: { cpu: 100m, memory: 100Mi }, limits: { cpu: 100m, memory: 100Mi } }
  - name: b
    resources: { requests: { cpu: 100m, memory: 100Mi } }     # no limits
Show solution

Burstable. For Guaranteed, every container needs limits == requests for both CPU and memory. Container b has only requests, no limits — that downgrades the whole pod.

EX 11.3 medium Spread by zone

Spread a Deployment across 3 AZs evenly, but allow scheduling even if perfect spread isn't possible. Show with topologySpreadConstraints.

Show solution 
spec:
  topologySpreadConstraints:
    - maxSkew: 1
      topologyKey: topology.kubernetes.io/zone
      whenUnsatisfiable: ScheduleAnyway          # soft
      labelSelector: { matchLabels: { app: api } }

ScheduleAnyway = soft. DoNotSchedule = hard (might block scaling if the constraint can't be satisfied).

EX 11.4 hard PDB blocks drain

You have a Deployment with 3 replicas and a PDB minAvailable: 3. You try to drain the only node hosting one of these pods. What happens, and what's your fix?

Show solution

The drain blocks indefinitely — eviction would drop available pods to 2, violating the PDB. Either:

  1. Lower the PDB (minAvailable: 2) — sensible for 3 replicas.
  2. Add capacity (more nodes / more replicas) so eviction can move pods elsewhere first.
  3. Force-drain (kubectl drain --disable-eviction --force) — but you've now bypassed the safety mechanism.

Lesson: a PDB equal to replica count makes the workload undrainable. Use maxUnavailable: 1 or minAvailable: replicas - 1.

EX 11.5 hard Lock down a namespace

Add Pod Security Admission "restricted" enforce to a namespace, then write a Pod manifest that conforms.

Show solution 
apiVersion: v1
kind: Namespace
metadata:
  name: locked
  labels:
    pod-security.kubernetes.io/enforce: restricted
    pod-security.kubernetes.io/enforce-version: latest
---
apiVersion: v1
kind: Pod
metadata: { name: web, namespace: locked }
spec:
  securityContext:
    runAsNonRoot: true
    runAsUser: 10001
    seccompProfile: { type: RuntimeDefault }
  containers:
    - name: web
      image: nginxinc/nginx-unprivileged:1.27        # listens on 8080, runs as non-root
      ports: [{ containerPort: 8080 }]
      securityContext:
        allowPrivilegeEscalation: false
        readOnlyRootFilesystem: true
        capabilities: { drop: [ALL] }
      volumeMounts:
        - { name: tmp,        mountPath: /tmp }
        - { name: var-cache,  mountPath: /var/cache/nginx }
        - { name: var-run,    mountPath: /var/run }
  volumes:
    - { name: tmp,       emptyDir: {} }
    - { name: var-cache, emptyDir: {} }
    - { name: var-run,   emptyDir: {} }

Standard nginx image runs as root and binds 80 — fails restricted. The nginx-unprivileged variant runs as a non-root user on 8080 and is the canonical "restricted-friendly" web server.

Recap

  • Probes: readiness gates traffic; liveness restarts; startup gives slow apps a grace window. Distinct paths matter.
  • Resources: requests for both, memory limits = requests (Guaranteed), often skip CPU limits.
  • Scheduling: topologySpreadConstraints for HA spread; affinity/tolerations for special-purpose nodes.
  • HPA for replica scaling; KEDA when you need to scale on anything other than CPU/memory.
  • PDB protects voluntary disruptions but mustn't be over-tight or it makes drains impossible.
  • SecurityContext: non-root, RO root, drop ALL caps, seccomp default — every prod container.
  • Pod Security Admission at namespace scope to enforce baselines.
  • RBAC: least privilege; kubectl auth can-i to verify.
  • Graceful shutdown: preStop sleep + handle SIGTERM in your app.
