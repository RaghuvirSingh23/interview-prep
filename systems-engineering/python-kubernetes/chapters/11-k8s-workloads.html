Chapter 09 Workloads — StatefulSet, DaemonSet, Job, CronJob

Deployment is for stateless apps. The other workload types handle databases (StatefulSet), per-node agents (DaemonSet), one-off tasks (Job), and scheduled tasks (CronJob). Pick the right one and you inherit the right behaviour for free.

Decision tree

Is it a long-running app?
├── Stateless, identical replicas?         → Deployment
├── Stateful, stable identity per pod?     → StatefulSet
└── One copy per node (e.g., log shipper)? → DaemonSet

Is it a finite task?
├── One-shot?              → Job
└── On a schedule?         → CronJob

StatefulSet

For workloads where each pod needs:

  • A stable name — db-0, db-1, db-2 rather than random hashes.
  • A stable network identity — a DNS name that follows the pod across restarts.
  • A stable persistent volume — when db-0 is rescheduled, it gets the same disk.
  • Ordered rollouts — start db-0 first, wait for ready, then db-1, etc.

Classic uses: databases (PostgreSQL, MongoDB, Cassandra), message brokers (Kafka, RabbitMQ), distributed caches (Redis Cluster).

apiVersion: v1
kind: Service
metadata: { name: db }
spec:
  clusterIP: None                    # headless — DNS gives Pod IPs directly
  selector: { app: db }
  ports: [{ port: 5432 }]
---
apiVersion: apps/v1
kind: StatefulSet
metadata: { name: db }
spec:
  serviceName: db                    # the headless Service above
  replicas: 3
  selector: { matchLabels: { app: db } }
  template:
    metadata: { labels: { app: db } }
    spec:
      containers:
        - name: postgres
          image: postgres:16
          ports: [{ containerPort: 5432 }]
          env:
            - name: POSTGRES_PASSWORD
              valueFrom: { secretKeyRef: { name: db-secret, key: password } }
          volumeMounts:
            - { name: data, mountPath: /var/lib/postgresql/data }
  volumeClaimTemplates:              # one PVC per pod, auto-created
    - metadata: { name: data }
      spec:
        accessModes: [ReadWriteOnce]
        storageClassName: standard
        resources:
          requests: { storage: 20Gi }

What you get:

  • Pod names: db-0, db-1, db-2.
  • Stable DNS: db-0.db.default.svc.cluster.local, etc.
  • Each pod gets its own PVC: data-db-0, data-db-1, data-db-2. Reschedule db-1 to a different node — same PVC, same data.
  • Rollout order: db-2 updated first, then db-1, then db-0. Reverse for scale-down.
StatefulSet doesn't make your app stateful — your app already is

StatefulSet provides the infrastructure for stable identities and storage. The app still has to do the hard parts: replication, leader election, consistency, recovery from a member dying. K8s won't make Postgres into a HA cluster on its own — you need an operator (CloudNativePG, Zalando) or self-managed config.

DaemonSet

"Run one copy of this Pod on every node (or every node matching a selector)." For things tied to the node itself.

Classic uses: log shippers (Fluent Bit, Vector), metrics agents (node-exporter), CSI drivers, kube-proxy itself.

apiVersion: apps/v1
kind: DaemonSet
metadata:
  name: node-exporter
  namespace: monitoring
spec:
  selector: { matchLabels: { app: node-exporter } }
  template:
    metadata: { labels: { app: node-exporter } }
    spec:
      hostNetwork: true            # share node's network namespace
      hostPID: true                # see node's processes
      tolerations:
        - effect: NoSchedule
          operator: Exists         # tolerate any taint, including control-plane
      containers:
        - name: node-exporter
          image: quay.io/prometheus/node-exporter:v1.8.0
          ports: [{ containerPort: 9100, hostPort: 9100 }]
          volumeMounts:
            - { name: proc, mountPath: /host/proc, readOnly: true }
            - { name: sys,  mountPath: /host/sys,  readOnly: true }
          args: ["--path.procfs=/host/proc", "--path.sysfs=/host/sys"]
      volumes:
        - { name: proc, hostPath: { path: /proc } }
        - { name: sys,  hostPath: { path: /sys  } }

Notes:

  • Add new node → DaemonSet controller creates a Pod on it automatically.
  • tolerations let it run on tainted nodes (control plane, GPU, special pools). Without them you'd skip those.
  • hostNetwork, hostPID, hostPath are powerful — and dangerous. DaemonSets are usually privileged; lock them down with PodSecurity standards (Chapter 11).
  • Use nodeSelector or affinity to scope to subset of nodes.

Job

Run a Pod (or several) until completion. Successful exit → done. Non-zero exit → restarted, up to a limit. Use for batch tasks, migrations, image builds, one-shot maintenance.

apiVersion: batch/v1
kind: Job
metadata: { name: db-migrate }
spec:
  backoffLimit: 4                # retry up to 4 times on failure
  activeDeadlineSeconds: 600     # kill if running longer than 10 min total
  ttlSecondsAfterFinished: 86400 # auto-clean after a day
  template:
    spec:
      restartPolicy: Never        # or OnFailure
      containers:
        - name: migrate
          image: my-app:1.2.3
          command: ["python", "-m", "myapp.migrations"]
          env:
            - name: DB_URL
              valueFrom: { secretKeyRef: { name: db-creds, key: url } }

restartPolicy for Job pods is either OnFailure (kubelet restarts the container) or Never (failed pod is replaced by Job). Most use Never + backoffLimit for predictable behaviour.

Parallel Jobs

spec:
  parallelism: 5                 # up to 5 pods concurrently
  completions: 20                # job is done when 20 succeed total
  template: ...

Used for "queue worker" patterns — 20 tasks to do, 5 workers in parallel. Each pod claims a piece of work via shared state (a queue, a database).

For indexed work — pod 0 handles shard 0, pod 1 handles shard 1, etc. — set completionMode: Indexed:

spec:
  completionMode: Indexed
  parallelism: 4
  completions: 4
  template:
    spec:
      containers:
        - name: shard
          image: my-batch:1.0
          env:
            - name: SHARD_INDEX
              valueFrom: { fieldRef: { fieldPath: metadata.annotations['batch.kubernetes.io/job-completion-index'] } }

CronJob

"Create a Job on a schedule." A wrapper around Job with cron-style timing.

apiVersion: batch/v1
kind: CronJob
metadata: { name: nightly-promote }
spec:
  schedule: "0 2 * * *"                  # 02:00 every day
  timeZone: "Etc/UTC"                    # 1.27+, otherwise the controller's TZ
  concurrencyPolicy: Forbid              # don't run a new Job if previous is still running
  successfulJobsHistoryLimit: 3
  failedJobsHistoryLimit:     3
  startingDeadlineSeconds: 600           # if missed by >10 min, skip
  jobTemplate:
    spec:
      backoffLimit: 1
      ttlSecondsAfterFinished: 3600
      template:
        spec:
          restartPolicy: Never
          serviceAccountName: promoter
          containers:
            - name: promote
              image: registry.example.com/promote:1.0.0
              args: ["--from=dev", "--to=staging"]
              resources:
                requests: { cpu: 100m, memory: 128Mi }
                limits:   { cpu: 500m, memory: 512Mi }

concurrencyPolicy

ValueBehaviour
Allow (default)Run the new Job even if the previous is still running.
ForbidSkip the new Job; old run keeps going.
ReplaceKill the old Job, start the new one.

For idempotent jobs that take less than the schedule interval, Allow is fine. For jobs that mutate shared state, use Forbid. Replace is for "always run the latest version" — useful if your old job is stuck.

CronJob is not your friend for second-precision schedules

The controller polls every 10 s. Schedules are evaluated at minute granularity. If you need precise timing or sub-minute frequencies, use a Deployment with an internal scheduler, or a real workflow engine (Argo Workflows, Tekton).

Cleanup with TTL

Without ttlSecondsAfterFinished, completed Jobs (and their pods) stick around forever. They show in kubectl get jobs, eat etcd storage, and clutter dashboards. Always set TTL.

Hands-on: a useful CronJob

Hands-on · pruner that runs every hour
apiVersion: batch/v1
kind: CronJob
metadata: { name: prune-old-builds, namespace: ci }
spec:
  schedule: "17 * * * *"             # every hour at :17 (avoid :00 herd)
  concurrencyPolicy: Forbid
  successfulJobsHistoryLimit: 1
  failedJobsHistoryLimit: 3
  jobTemplate:
    spec:
      backoffLimit: 1
      ttlSecondsAfterFinished: 86400
      template:
        spec:
          restartPolicy: Never
          serviceAccountName: ci-pruner
          containers:
            - name: pruner
              image: alpine:3.19
              command: ["sh", "-c"]
              args:
                - |
                  set -euo pipefail
                  echo "pruning artifacts older than 30 days"
                  find /var/cache/builds -mindepth 1 -maxdepth 1 -type d -mtime +30 -exec rm -rf {} +
                  echo "done"
              volumeMounts:
                - { name: cache, mountPath: /var/cache/builds }
          volumes:
            - name: cache
              persistentVolumeClaim:
                claimName: ci-build-cache
$ kubectl apply -f cronjob.yaml
$ kubectl -n ci get cronjob
NAME              SCHEDULE      SUSPEND   ACTIVE   LAST SCHEDULE   AGE
prune-old-builds  17 * * * *    False     0        4m12s           1h

# Run once on demand
$ kubectl -n ci create job --from=cronjob/prune-old-builds prune-now
$ kubectl -n ci get jobs
$ kubectl -n ci logs job/prune-now

Ephemeral debug containers

Modern K8s (1.25+) has kubectl debug to attach a debug container into a running Pod — without modifying the manifest.

$ kubectl debug -it pod/web-abc123 --image=nicolaka/netshoot --target=web
# now in a shell with curl, dig, tcpdump, ss, etc., sharing the Pod's network namespace

Massive quality-of-life win when production pods don't have curl installed (which they shouldn't, for security).

Pod lifecycle

Phases you'll see in kubectl get pod:

  • Pending — accepted, not scheduled or images downloading.
  • Running — at least one container is running.
  • Succeeded — all containers exited 0; pod won't restart (Jobs).
  • Failed — at least one container exited non-zero.
  • Unknown — kubelet can't be reached.

And container statuses inside: Waiting, Running, Terminated. Each with a reason like ImagePullBackOff, CrashLoopBackOff, OOMKilled.

restartPolicy

AlwaysDefault for Deployment/StatefulSet pods. Kubelet restarts containers that exit, regardless of exit code.
OnFailureFor Jobs. Restart on non-zero exit; success → stop.
NeverFor Jobs. No restart; failed pod is replaced by Job controller.

Exercises

EX 9.1 easy Pick the workload

For each, name the workload type:

  1. 3 stateless API servers fronted by a Service.
  2. A Postgres cluster with stable hostnames and persistent storage.
  3. A log forwarder running on every worker node.
  4. "Apply DB migration" — runs once per release.
  5. Nightly backup at 03:00.
Show solution

(a) Deployment. (b) StatefulSet. (c) DaemonSet. (d) Job. (e) CronJob.

EX 9.2 medium Skip if running

Your CronJob takes ~10 minutes; schedule is every 5. New runs pile up. Fix.

Show solution 
spec:
  schedule: "*/5 * * * *"
  concurrencyPolicy: Forbid    # skip if previous still running

Or change the schedule to be ≥ runtime. Or split the work into smaller chunks. Forbid is the cheap fix.

EX 9.3 medium Sharded batch

You have 100 build artifacts to scan; each scan takes 5 min. Use an indexed Job to scan them in parallel with 10 workers.

Show solution 
spec:
  completionMode: Indexed
  completions: 100
  parallelism: 10
  backoffLimit: 5
  template:
    spec:
      restartPolicy: Never
      containers:
        - name: scanner
          image: my-scanner:1.0
          env:
            - name: SHARD
              valueFrom: { fieldRef: { fieldPath: metadata.annotations['batch.kubernetes.io/job-completion-index'] } }
          command: ["scanner", "--index=$(SHARD)", "--total=100"]

The scanner reads $SHARD as its index (0–99) and grabs the matching artifact. K8s ensures each index runs at most once.

EX 9.4 hard DaemonSet on tainted nodes

You add GPU nodes with a taint nvidia.com/gpu=true:NoSchedule. Your log shipper DaemonSet skips them. Why, and how do you fix it without changing the taint?

Show solution

Pods only land on tainted nodes if they tolerate the taint. The DaemonSet doesn't, so it skips GPU nodes — losing logs from your most expensive workloads.

spec:
  template:
    spec:
      tolerations:
        - key: nvidia.com/gpu
          operator: Exists
          effect: NoSchedule
        # or, blanket:
        - operator: Exists
          effect: NoSchedule

The blanket form covers any future special-purpose taints too. Common pattern for monitoring/logging DaemonSets.

EX 9.5 hard StatefulSet pod identity

You have a 3-pod StatefulSet db. From a Pod inside the cluster, how do you reach db-1 specifically? What happens if it's rescheduled to another node?

Show solution

Address: db-1.db.<namespace>.svc.cluster.local (where db is the headless Service's name and <namespace> is its namespace).

If db-1 is rescheduled (node dies, drain, etc.), the new Pod has the same name and DNS name; the Pod IP changes but DNS resolves to the new IP. Its PVC follows it (provided the storage class supports cross-AZ / cross-node mounting). Clients that addressed db-1 by stable name keep working.

Recap

  • Deployment for stateless replicas; StatefulSet for stable per-pod identity + storage; DaemonSet for one-per-node; Job for run-to-completion; CronJob for scheduled Jobs.
  • StatefulSet provides infrastructure for state, not statefulness itself — your app/operator does the hard parts.
  • DaemonSets often need tolerations to cover tainted nodes.
  • Job's restartPolicy: Never + backoffLimit is the predictable default.
  • parallelism and completions drive parallel batch; completionMode: Indexed for shard-by-index work.
  • CronJob: concurrencyPolicy: Forbid for non-overlapping mutation; always set ttlSecondsAfterFinished.
  • kubectl debug for ephemeral troubleshooting containers.
