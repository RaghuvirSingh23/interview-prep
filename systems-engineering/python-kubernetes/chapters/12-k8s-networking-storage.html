Chapter 10 Networking & Storage

Service deep-dive, Ingress, NetworkPolicy, DNS, plus the storage side: PV, PVC, StorageClass, volume modes, and the patterns that actually work in production.

The Kubernetes network model

The model has three rules:

  1. Every Pod gets its own IP. No NAT inside the cluster.
  2. Every Pod can talk to every other Pod, by IP. Cross-node, cross-namespace, no rewriting.
  3. The network plugin (CNI) makes this true. Calico, Cilium, Flannel, Weave — pick one; the API doesn't care.

This is fundamentally different from Docker's default bridge networking. K8s assumes a flat-ish network. The plumbing is the CNI's problem.

Service types — full coverage

ClusterIP (default)

spec:
  type: ClusterIP
  selector: { app: api }
  ports: [{ port: 80, targetPort: 8080 }]

Internal-only. Allocates a cluster-internal virtual IP. Reachable from any pod. Not reachable from outside the cluster.

NodePort

spec:
  type: NodePort
  selector: { app: api }
  ports: [{ port: 80, targetPort: 8080, nodePort: 30080 }]

ClusterIP plus a port (30000–32767) on every node. Reach the service via <any-node-IP>:30080. Crude; mostly for demos. Don't use in production — use Ingress or a real LoadBalancer.

LoadBalancer

spec:
  type: LoadBalancer
  selector: { app: api }
  ports: [{ port: 80, targetPort: 8080 }]

NodePort plus the cloud provider provisions an external LB pointing at the NodePorts. AWS → ALB/NLB; GCP → Cloud LB; Azure → Standard LB. On bare-metal, you need MetalLB or similar.

Headless

spec:
  clusterIP: None
  selector: { app: db }
  ports: [{ port: 5432 }]

No virtual IP. DNS resolves directly to all matching Pod IPs. Used by StatefulSets so each pod gets a unique DNS name (db-0.db.svc, etc.).

ExternalName

spec:
  type: ExternalName
  externalName: my-db.us-east-1.rds.amazonaws.com

DNS CNAME — service name resolves to an external host. Useful for "make in-cluster apps see db regardless of whether it's running in-cluster or out".

In-cluster DNS

Every Service is auto-resolvable via cluster DNS (CoreDNS). The naming pattern:

<service>.<namespace>.svc.cluster.local

# From the same namespace, just:
http://api/

# From another namespace:
http://api.team-alpha/
http://api.team-alpha.svc.cluster.local/

# Headless service — resolves to all Pod IPs:
$ nslookup db
db.default.svc.cluster.local
Addresses: 10.244.0.5, 10.244.0.6, 10.244.0.7

# Specific stateful pod:
$ nslookup db-0.db
db-0.db.default.svc.cluster.local
Address: 10.244.0.5

Pods get DNS configured to search the cluster's domain by default, so short names work within a namespace.

Ingress — HTTP routing

An Ingress is a set of HTTP routing rules: "foo.example.com/api goes to api Service, foo.example.com/web goes to web Service". You don't run Ingress yourself — you install an Ingress controller (nginx-ingress, Traefik, HAProxy, AWS ALB, GCP GCE, Cilium) which watches Ingress objects and configures itself accordingly.

apiVersion: networking.k8s.io/v1
kind: Ingress
metadata:
  name: app
  annotations:
    nginx.ingress.kubernetes.io/rewrite-target: /
spec:
  ingressClassName: nginx                # which controller handles this
  tls:
    - hosts: ["app.example.com"]
      secretName: app-tls                 # tls.crt, tls.key in this Secret
  rules:
    - host: app.example.com
      http:
        paths:
          - path: /api
            pathType: Prefix
            backend:
              service:
                name: api
                port: { number: 80 }
          - path: /
            pathType: Prefix
            backend:
              service:
                name: web
                port: { number: 80 }

One cloud LB → many services routed by host/path. The cost-saver vs. one LB per Service.

Install an ingress controller (kind)

$ kubectl apply -f https://kind.sigs.k8s.io/examples/ingress/deploy-ingress-nginx.yaml
$ kubectl wait --namespace ingress-nginx \
    --for=condition=ready pod \
    --selector=app.kubernetes.io/component=controller \
    --timeout=90s

For TLS, install cert-manager and use a ClusterIssuer for Let's Encrypt — most people pair it with Ingress for automatic HTTPS.

Gateway API — the modern replacement

Ingress is showing its age — annotations are vendor-specific, multi-tenant routing is awkward. The Gateway API (graduated v1 in 2023) is the successor: distinct resources for GatewayClass, Gateway, HTTPRoute, TLSRoute, with proper role separation between platform admins and app teams.

apiVersion: gateway.networking.k8s.io/v1
kind: Gateway
metadata: { name: external, namespace: gateways }
spec:
  gatewayClassName: nginx
  listeners:
    - name: https
      protocol: HTTPS
      port: 443
      tls:
        mode: Terminate
        certificateRefs:
          - { kind: Secret, name: example-tls }
---
apiVersion: gateway.networking.k8s.io/v1
kind: HTTPRoute
metadata: { name: api, namespace: team-alpha }
spec:
  parentRefs:
    - { name: external, namespace: gateways }
  hostnames: ["api.example.com"]
  rules:
    - matches: [{ path: { type: PathPrefix, value: / } }]
      backendRefs:
        - { name: api, port: 80 }

Adoption is uneven; Ingress still rules in 2026. Worth knowing the direction.

NetworkPolicy — pod-level firewalling

By default, every Pod can talk to every other Pod. NetworkPolicy lets you restrict that. Without one, your namespace boundaries are name-level, not network-level.

apiVersion: networking.k8s.io/v1
kind: NetworkPolicy
metadata:
  name: api-allow-frontend
  namespace: prod
spec:
  podSelector: { matchLabels: { app: api } }
  policyTypes: [Ingress, Egress]
  ingress:
    - from:
        - podSelector: { matchLabels: { app: frontend } }
        - namespaceSelector: { matchLabels: { name: monitoring } }
      ports:
        - { protocol: TCP, port: 8080 }
  egress:
    - to: [{ podSelector: { matchLabels: { app: db } } }]
      ports: [{ protocol: TCP, port: 5432 }]
    - to: [{ namespaceSelector: { matchLabels: { name: kube-system } } }]
      ports: [{ protocol: UDP, port: 53 }]

Read: "pods labelled app: api in prod accept ingress only from app: frontend pods or any pod in the monitoring namespace, on port 8080. They can egress only to app: db on 5432 and to kube-system DNS on 53."

Default-deny is opt-in

Without a NetworkPolicy, all traffic is allowed. The moment you create any NetworkPolicy targeting a pod (via podSelector), all other traffic to/from that pod is denied. So a half-written policy can lock things out fast.

The mature pattern: a baseline "default-deny-all" NetworkPolicy in each namespace, plus per-app allow rules. Test in staging.

Default-deny baseline

apiVersion: networking.k8s.io/v1
kind: NetworkPolicy
metadata: { name: default-deny-all, namespace: prod }
spec:
  podSelector: {}                # all pods in this namespace
  policyTypes: [Ingress, Egress]
  # no ingress / egress blocks => deny everything

Then layer on allow-rules. Same model as a sane corp firewall.

Storage — PV, PVC, StorageClass

Storage in K8s is split across three resources for separation of concerns:

ResourceWho writes itWhat it says
StorageClassCluster admin"This is a class of storage available in the cluster — fast SSD, slow HDD, regional, etc."
PersistentVolumeClaim (PVC)App author"I want some storage of class X, size Y, accessMode Z."
PersistentVolume (PV)Auto-provisioned (or admin)"Here's a piece of actual storage matching that claim."

Static vs dynamic provisioning

Static: admin pre-creates PVs; users claim them via PVCs. Old-school.

Dynamic: user creates a PVC referencing a StorageClass; the cluster's CSI driver provisions a fresh PV matching the request. The default in 2026.

StorageClass

apiVersion: storage.k8s.io/v1
kind: StorageClass
metadata:
  name: fast-ssd
provisioner: ebs.csi.aws.com               # the CSI driver
parameters:
  type: gp3
  encrypted: "true"
  fsType: ext4
reclaimPolicy: Delete                      # delete the underlying disk when PV is removed
volumeBindingMode: WaitForFirstConsumer    # don't pick a zone until a Pod is scheduled
allowVolumeExpansion: true                 # let users grow the PVC later

WaitForFirstConsumer matters in multi-AZ clusters: with Immediate, the PV is provisioned in some AZ and the Pod is then forced into that AZ. Wait-for-first lets the scheduler pick the Pod's AZ first, then provision storage there.

PVC

apiVersion: v1
kind: PersistentVolumeClaim
metadata: { name: data, namespace: prod }
spec:
  storageClassName: fast-ssd
  accessModes: [ReadWriteOnce]              # the only mode most cloud disks support
  resources:
    requests: { storage: 50Gi }

Mounting in a Pod

spec:
  containers:
    - name: app
      image: my-app:1.0
      volumeMounts:
        - { name: data, mountPath: /var/lib/app }
  volumes:
    - name: data
      persistentVolumeClaim:
        claimName: data

For StatefulSets, use volumeClaimTemplates (Chapter 9) — one PVC auto-created per pod with stable identity.

Access modes

ModeMeaningReality
ReadWriteOnce (RWO)Read+write by one nodeEBS, GCP PD, Azure Disk — most block storage
ReadOnlyMany (ROX)Read-only by many nodesObject stores, some NFS
ReadWriteMany (RWX)Read+write by many nodesNFS, EFS, FSx, CephFS, NetApp — file storage
ReadWriteOncePod (RWOP)One Pod, one nodeNewer, stricter than RWO

Most apps use RWO; you typically have one writer pod. Reach for RWX only when you genuinely need shared writers — and brace for the perf and consistency tradeoffs that come with networked file systems.

Ephemeral storage — emptyDir, projected, downwardAPI

emptyDir

volumes:
  - name: cache
    emptyDir: {}
  # or memory-backed
  - name: scratch
    emptyDir:
      medium: Memory
      sizeLimit: 1Gi

Created when the Pod starts on a node, deleted when the Pod is removed. Lives on node-local disk (or RAM if medium: Memory). Use for scratch space and inter-container communication.

projected

volumes:
  - name: combined
    projected:
      sources:
        - configMap: { name: app-config }
        - secret:    { name: db-creds }
        - serviceAccountToken:
            path: token
            expirationSeconds: 3600

Mounts multiple sources at one path. Modern ServiceAccount tokens use this — short-lived, auto-rotated.

downwardAPI

env:
  - name: POD_NAME
    valueFrom: { fieldRef: { fieldPath: metadata.name } }
  - name: POD_IP
    valueFrom: { fieldRef: { fieldPath: status.podIP } }
  - name: NODE_NAME
    valueFrom: { fieldRef: { fieldPath: spec.nodeName } }
  - name: CPU_LIMIT
    valueFrom: { resourceFieldRef: { containerName: app, resource: limits.cpu } }

Expose pod metadata into the container. Critical for self-aware logging (which pod am I?), graceful shutdown messages, and JVM heap-tuning to $CPU_LIMIT.

CSI — the Container Storage Interface

Kubernetes itself doesn't know how to talk to AWS EBS or GCP PD. CSI drivers translate. Each cloud provider ships its own. On-prem options: Rook/Ceph, Longhorn, OpenEBS, Portworx.

Day-to-day, you only care that a CSI driver exists for your storage and is registered as a StorageClass. You'll see CSI drivers as DaemonSets in kube-system.

Resizing PVCs

$ kubectl patch pvc data -p '{"spec":{"resources":{"requests":{"storage":"100Gi"}}}}'

Works if the StorageClass has allowVolumeExpansion: true. The CSI driver expands the underlying disk; for filesystem expansion, the Pod usually needs a restart.

You can grow but generally not shrink. Plan ahead.

VolumeSnapshots

apiVersion: snapshot.storage.k8s.io/v1
kind: VolumeSnapshot
metadata: { name: data-snap-2026-04-23 }
spec:
  volumeSnapshotClassName: csi-snapclass
  source:
    persistentVolumeClaimName: data

Restore by creating a PVC with dataSource referencing the snapshot. Backup automation often uses this.

Hands-on: TLS-terminated Ingress to a Service

Hands-on · expose hello with HTTPS in kind

Set up cluster with port maps, install ingress-nginx, deploy hello, expose via Ingress with self-signed TLS.

yamlkind-config.yaml
kind: Cluster
apiVersion: kind.x-k8s.io/v1alpha4
nodes:
  - role: control-plane
    extraPortMappings:
      - { containerPort: 80,  hostPort: 80,  protocol: TCP }
      - { containerPort: 443, hostPort: 443, protocol: TCP }
    kubeadmConfigPatches:
      - |
        kind: InitConfiguration
        nodeRegistration:
          kubeletExtraArgs:
            node-labels: "ingress-ready=true"
$ kind create cluster --config kind-config.yaml
$ kubectl apply -f https://raw.githubusercontent.com/kubernetes/ingress-nginx/main/deploy/static/provider/kind/deploy.yaml
$ kubectl wait --namespace ingress-nginx \
    --for=condition=ready pod \
    --selector=app.kubernetes.io/component=controller \
    --timeout=120s

# self-signed cert (for testing only)
$ openssl req -x509 -newkey rsa:2048 -nodes -keyout tls.key -out tls.crt \
    -subj "/CN=hello.local" -days 365
$ kubectl create secret tls hello-tls --cert=tls.crt --key=tls.key

# deploy app
$ kubectl create deploy hello --image=hashicorp/http-echo --replicas=2 -- -text=hi
$ kubectl expose deploy hello --port=80 --target-port=5678
$ kubectl apply -f - <<'EOF'
apiVersion: networking.k8s.io/v1
kind: Ingress
metadata: { name: hello }
spec:
  ingressClassName: nginx
  tls: [{ hosts: [hello.local], secretName: hello-tls }]
  rules:
    - host: hello.local
      http:
        paths:
          - path: /
            pathType: Prefix
            backend: { service: { name: hello, port: { number: 80 } } }
EOF

$ echo "127.0.0.1 hello.local" | sudo tee -a /etc/hosts
$ curl -k https://hello.local/
hi

Exercises

EX 10.1 easy Service DNS

From a pod in namespace app, what's the DNS name for a Service db in namespace data? Two valid forms.

Show solution

db.data (short, with namespace) or db.data.svc.cluster.local (FQDN). From within data itself, just db works.

EX 10.2 medium Default-deny + allow

Write two NetworkPolicies for namespace prod: (a) deny all by default; (b) allow only DNS egress and ingress from same-namespace pods on port 8080.

Show solution 
# (a)
apiVersion: networking.k8s.io/v1
kind: NetworkPolicy
metadata: { name: default-deny, namespace: prod }
spec:
  podSelector: {}
  policyTypes: [Ingress, Egress]
---
# (b)
apiVersion: networking.k8s.io/v1
kind: NetworkPolicy
metadata: { name: allow-baseline, namespace: prod }
spec:
  podSelector: {}
  policyTypes: [Ingress, Egress]
  egress:
    - to: [{ namespaceSelector: { matchLabels: { kubernetes.io/metadata.name: kube-system } } }]
      ports: [{ protocol: UDP, port: 53 }, { protocol: TCP, port: 53 }]
  ingress:
    - from: [{ podSelector: {} }]                    # any pod in same namespace
      ports: [{ protocol: TCP, port: 8080 }]
EX 10.3 medium Why Ingress?

Why do you usually want one Ingress + one cloud LB rather than one Service of type: LoadBalancer per app? Give two reasons.

Show solution
  1. Cost. Cloud LBs cost ~$20–30/month each. 50 services × 50 LBs = $1k/month wasted; one shared Ingress ALB serves them all.
  2. Centralised L7 features: TLS termination, rate limiting, auth, redirects, rewrites — all in one place rather than configured per service.

Plus: easier IP allowlisting, single point for cert renewal, one place for WAF rules.

EX 10.4 hard RWO across two nodes

You have an EBS-backed PVC mounted in a Deployment with replicas=2. Both pods need to write. What goes wrong, and how do you fix the design?

Show solution

Goes wrong: EBS is RWO. The first pod attaches; the second pod, scheduled to a different node, fails with "Multi-Attach error". If both happen to land on the same node, EBS will let both attach, but two writers to the same filesystem corrupts it.

Fix the design:

  1. If state-shared writes are essential, use RWX storage (EFS/FSx/NetApp/Ceph) — accept the perf cost.
  2. If pods can be sharded, use a StatefulSet with volumeClaimTemplates — each pod gets its own RWO PVC.
  3. If state belongs in a database, use one writer (a primary Postgres pod) and many readers, plus an external object store for blobs.

Most "two writers want the same disk" cases are an architectural smell, not a storage problem.

EX 10.5 hard Resize a PVC

Your data PVC is at 50Gi and 90% full. Resize to 100Gi. What's the minimum interruption?

Show solution 
$ kubectl patch pvc data -p '{"spec":{"resources":{"requests":{"storage":"100Gi"}}}}'

Provided the StorageClass has allowVolumeExpansion: true:

  1. The CSI driver expands the underlying disk in-place — no data movement, takes seconds.
  2. The PVC's status.conditions shows FileSystemResizePending.
  3. For most modern CSI drivers, the filesystem is also expanded online, no Pod restart needed. Some require a restart — check the driver's docs.

For a StatefulSet pod where you can't avoid a restart: rolling restart pod-by-pod, the new pods come up with the larger filesystem.

Recap

  • K8s networking: every pod gets a real IP, every pod can reach every other pod, the CNI plugin makes it true.
  • Service types: ClusterIP (default), NodePort (crude), LoadBalancer (per-cloud), Headless (StatefulSet), ExternalName (CNAME).
  • In-cluster DNS: service.namespace.svc.cluster.local; short-form within the same namespace.
  • Ingress = HTTP routing; needs an Ingress controller installed; one controller fronting many services saves cost. Gateway API is the modern successor.
  • NetworkPolicy = pod-level firewalls. Default-deny is opt-in; baseline + allow rules.
  • Storage: PVC (claim) + StorageClass (class) + PV (actual disk, usually auto-provisioned via CSI).
  • Access modes: RWO (default for cloud disks), RWX (file storage), RWOP (newer strict mode).
  • Use WaitForFirstConsumer, allowVolumeExpansion: true on production StorageClasses.
  • Snapshots via VolumeSnapshot for backups; resize via PVC patch when expansion is allowed.
