Chapter 08 Docker — Production

Multi-stage builds, BuildKit cache mounts, distroless & scratch base images, security hardening, signing & SBOMs, scanning, CI patterns, rootless and Kaniko alternatives, and the bridge to Kubernetes. The "boring" chapter that pays off forever.

Multi-stage builds — small final images

Build tools (compilers, npm, pip with build deps) are big and have no business in production images. Multi-stage builds let you have a fat "build" stage and copy only the artifacts to a slim "runtime" stage. The final image carries the runtime, nothing else.

dockerfileDockerfile — Python multi-stage
# --- stage 1: builder ---
FROM python:3.12 AS build
WORKDIR /app
RUN pip install --no-cache-dir uv
COPY pyproject.toml requirements.lock ./
COPY src/ ./src/
# Build a wheel; install into a venv we'll later copy out.
RUN uv venv /opt/venv \
 && . /opt/venv/bin/activate \
 && uv pip install --no-cache --requirements requirements.lock \
 && uv pip install --no-cache .

# --- stage 2: runtime ---
FROM python:3.12-slim
ENV PATH="/opt/venv/bin:$PATH" \
    PYTHONUNBUFFERED=1 \
    PYTHONDONTWRITEBYTECODE=1
COPY --from=build /opt/venv /opt/venv
RUN useradd -r -u 10001 app
USER 10001
ENTRYPOINT ["python", "-m", "promote_bot"]
CMD ["run"]

Final image: ~80 MB. The build stage (~600 MB with toolchain, wheels, caches) is discarded entirely. docker images only shows the final tag.

For Go / Rust / C++ apps the win is even bigger — compile in a fat builder, copy a single static binary into scratch or distroless:

FROM golang:1.22 AS build
WORKDIR /src
COPY go.mod go.sum ./
RUN go mod download
COPY . .
RUN CGO_ENABLED=0 go build -ldflags="-s -w" -o /out/app ./cmd/app

FROM gcr.io/distroless/static-debian12:nonroot
COPY --from=build /out/app /app
USER nonroot:nonroot
ENTRYPOINT ["/app"]

Final image: ~10 MB, zero shell, zero package manager, exact same binary. Pulled and started on K8s in milliseconds.

BuildKit — the modern build engine

BuildKit is the build engine the modern Docker uses (and what docker build calls under the hood since 2020+). It gives you parallel build stages, better caching, secret mounts, SSH forwarding, and remote cache exports.

# Confirm BuildKit
$ docker buildx version
github.com/docker/buildx v0.16.0 ...

# Multi-platform build (linux/amd64 + linux/arm64)
$ docker buildx create --name multi --use
$ docker buildx build \
    --platform linux/amd64,linux/arm64 \
    -t ghcr.io/myorg/app:1.0 \
    --push .                              # multi-arch manifest pushed

Cache mounts — build-time cache that doesn't bloat the image

BuildKit can mount a directory during the RUN that persists across builds but isn't baked into the image. Game-changing for package managers.

# syntax=docker/dockerfile:1.7
FROM python:3.12-slim
WORKDIR /app
COPY requirements.txt .
RUN --mount=type=cache,target=/root/.cache/pip \
    pip install --no-cache-dir -r requirements.txt
COPY src/ ./src/
RUN --mount=type=cache,target=/root/.cache/pip \
    pip install --no-cache-dir .

The pip wheel cache lives in BuildKit's cache, not in the layer. Subsequent builds re-use cached wheels even when the layer is invalidated. Same trick for apt (/var/cache/apt), npm (/root/.npm), Go modules (/root/go/pkg/mod), Cargo (/usr/local/cargo).

Secret mounts — credentials at build time without leaking them into the image

# syntax=docker/dockerfile:1.7
FROM python:3.12-slim
WORKDIR /app
COPY pyproject.toml .
RUN --mount=type=secret,id=pypi_creds \
    pip install --no-cache-dir \
        --extra-index-url "$(cat /run/secrets/pypi_creds)" \
        -e .
$ DOCKER_BUILDKIT=1 docker build \
    --secret id=pypi_creds,src=$HOME/.pypi-creds \
    -t my-app:1.0 .

The secret is mounted into /run/secrets/<id> only during that RUN; it's not committed to a layer, doesn't appear in docker history, isn't accessible at runtime. The right way to handle private package indexes, vendor SDK auth, signed-package keys.

Remote cache

$ docker buildx build \
    --cache-from type=registry,ref=ghcr.io/myorg/app:cache \
    --cache-to   type=registry,ref=ghcr.io/myorg/app:cache,mode=max \
    -t ghcr.io/myorg/app:1.0 \
    --push .

CI runners are usually ephemeral; remote cache lets a fresh runner reuse the previous build's layers from a registry. Order-of-magnitude speedup for cold-cache CI.

Alpine in Python — be careful

Alpine uses musl libc instead of glibc. Most Python wheels on PyPI are built against glibc; Alpine forces source compilation, which means installing GCC, headers, etc. — often making the build slower and the final image bigger than a Debian-slim base. Use Debian-slim for Python by default; Alpine only if you've benchmarked it.

Security hardening — the checklist

Every production container should pass this checklist. None of it is exotic; all of it gets skipped by accident if you don't have the list in front of you.

1 · Don't run as root

RUN useradd -r -u 10001 app
USER 10001

Default many base images run as root. Add a non-root user and switch. K8s' "restricted" Pod Security profile rejects images that don't.

2 · Read-only root filesystem

$ docker run --read-only --tmpfs /tmp:rw,size=64m my-app:1.0

Apps that don't write should not have a writeable rootfs. Mount /tmp as tmpfs if needed. K8s achieves the same with readOnlyRootFilesystem: true (Chapter 13).

3 · Drop all capabilities, add only what's needed

$ docker run --cap-drop=ALL --cap-add=NET_BIND_SERVICE my-web:1.0

Linux capabilities are a granular alternative to "root vs not root". Drop everything, add the specific cap (e.g. binding port < 1024). Most apps need none.

4 · No new privileges

$ docker run --security-opt=no-new-privileges:true my-app:1.0

Stops setuid binaries from gaining privileges mid-execution. Should be the default for any non-system-tooling container.

5 · Pin everything by digest

FROM python:3.12-slim@sha256:9f03a...

Tags can be moved silently. Digests can't.

6 · Don't bake secrets into the image

Even if you delete a file in a later layer, the file is in the previous layer's tarball. Anyone with the image can extract it. Use BuildKit secret mounts at build, env / Secret mounts at runtime.

7 · Minimise the attack surface

Distroless or scratch where possible. No shell, no curl, no wget, nothing for an attacker to use.

8 · The Dockerfile as a security artefact

It's reviewed in PRs. Linters exist: hadolint, dockle. Wire them into CI.

$ hadolint Dockerfile
Dockerfile:5 DL3015 info: Avoid additional packages by specifying `--no-install-recommends`
Dockerfile:9 DL3008 warning: Pin versions in apt-get install

Vulnerability scanning

Trivy, Grype, and cloud-native scanners (Snyk, Wiz, Prisma) walk an image's layers, identify packages by SBOM, cross-reference against CVE databases. Run on every build.

$ trivy image --severity HIGH,CRITICAL --exit-code 1 my-app:1.0
my-app:1.0 (debian 12.5)
========================================================
Total: 4 (HIGH: 3, CRITICAL: 1)

┌─────────────────┬──────────────────┬──────────┬─────────┬───────────────────┬────────────────────────────────────────────────────────┐
│     Library     │  Vulnerability   │ Severity │ Status  │ Installed Version │                         Title                          │
├─────────────────┼──────────────────┼──────────┼─────────┼───────────────────┼────────────────────────────────────────────────────────┤
│ libssl3         │ CVE-2024-12345   │ HIGH     │ fixed   │ 3.0.11-1          │ openssl: ...                                           │
...

Wire --exit-code 1 into CI to fail the build on findings above your bar (HIGH / CRITICAL is the usual gate). Allow-list known false positives via .trivyignore with a documented expiry date.

SBOM

A Software Bill of Materials lists every component in the image. Customers, regulators, and your future self need them. Syft generates one in seconds:

$ syft my-app:1.0 -o spdx-json > sbom.spdx.json
$ syft my-app:1.0 -o cyclonedx-json > sbom.cdx.json
$ syft my-app:1.0 -o table | head -20
NAME              VERSION         TYPE
ca-certificates   20230311        deb
libc6             2.36-9+deb12u9  deb
python3           3.12.3          python
requests          2.32.3          python
...

Ship the SBOM alongside the image as an OCI artefact, ideally signed. Modern registries (GHCR, ECR, Harbor) accept attestations linked to the image digest.

Signing — Sigstore / cosign

"This image was built by us, on this commit, by this CI run." Cosign + Sigstore makes signing keyless: the CI's OIDC identity signs via Sigstore's public Fulcio CA; the certificate is logged in Rekor for transparency. No long-lived keys to rotate.

# Sign (run in CI with id-token: write permission on GHA)
$ cosign sign --yes ghcr.io/myorg/my-app@sha256:abc123

# Sign an SBOM as an attestation linked to the image
$ cosign attest --yes \
    --predicate sbom.spdx.json \
    --type spdxjson \
    ghcr.io/myorg/my-app@sha256:abc123

# Verify (consumer, e.g. K8s admission)
$ cosign verify \
    --certificate-identity-regexp '^https://github.com/myorg/.*$' \
    --certificate-oidc-issuer https://token.actions.githubusercontent.com \
    ghcr.io/myorg/my-app@sha256:abc123

Pair with a K8s admission webhook (cosign's policy-controller, Kyverno, OPA Gatekeeper) that refuses to start unsigned images. Production-grade supply-chain security in two lines of CI plus a policy.

CI patterns — Docker in pipelines

Three problems Docker-in-CI tends to hit, and the modern answers:

1 · Cold cache on every run

Use BuildKit's registry cache (--cache-from/--cache-to) or GHA's type=gha cache. The first build is full; subsequent ones are fast.

- uses: docker/setup-buildx-action@v3
- uses: docker/build-push-action@v5
  with:
    context: .
    push: true
    tags: ghcr.io/myorg/app:${{ github.sha }}
    cache-from: type=gha
    cache-to:   type=gha,mode=max

2 · Need root, hate Docker-in-Docker

Three modern alternatives:

  • Rootless BuildKit — buildkitd as a non-root daemon. Native; secure; first-class.
  • Kaniko — Google's image builder that runs as an unprivileged container, building images by parsing Dockerfile in userspace. Common in K8s-based CI.
  • Buildah — Red Hat's tool. Daemonless; rootless. Builds OCI images from Dockerfiles or scriptable from shell.

3 · Multi-arch builds

Use buildx with --platform linux/amd64,linux/arm64. QEMU emulation under the hood for cross-builds; native nodes preferred when you have them. ARM64 in CI is common in 2026 thanks to GitHub's free arm64 runners.

Debugging distroless images

Distroless has no shell. kubectl exec -it pod/X -- sh fails. The modern fix: ephemeral debug containers (K8s 1.25+):

$ kubectl debug -it pod/web-abc123 \
    --image=nicolaka/netshoot \
    --target=web \
    --share-processes

Ephemeral container shares the Pod's network and process namespaces with the target. You get a shell with curl, dig, tcpdump, ss, even strace — without baking any of that into the production image. The "I can't debug distroless" objection is solved.

The bridge to Kubernetes

How does Kubernetes use your image?

  1. You push ghcr.io/myorg/my-app@sha256:abc to a registry.
  2. A Pod's container spec references that image (spec.containers[].image).
  3. The kubelet on whichever node is scheduled tells the runtime (containerd / CRI-O) to pull and run.
  4. The runtime invokes runc (or another OCI runtime) to instantiate the container — same OCI image format, same config.json, same Linux primitives.

The container command/args in K8s YAML override the image's ENTRYPOINT/CMD respectively (different field names, same semantics):

spec:
  containers:
    - name: app
      image: ghcr.io/myorg/my-app@sha256:abc...
      command: ["python", "-m", "my_app"]    # overrides ENTRYPOINT
      args:    ["run", "--config", "/etc/app/config.yaml"]  # overrides CMD

Almost everything else (ports, env, volumes, healthchecks, resource limits) is set in the K8s manifest, not the image. Bake the right shape in the image; let manifests choose how to operate it.

imagePullPolicy and pull secrets

Two K8s knobs you'll meet immediately:

PolicyBehaviour
Always Pull every time the Pod starts. Default for images tagged :latest.
IfNotPresentPull only if image isn't already on the node. Default for non-:latest tags.
Never Never pull. Image must be pre-loaded on the node.

For private registries: store credentials as a kubernetes.io/dockerconfigjson Secret and reference via imagePullSecrets on the Pod spec or the ServiceAccount. Or use IRSA (AWS) / Workload Identity (GCP) for keyless ECR/Artifact Registry access.

Hands-on: a fully-hardened image

Hands-on · multi-stage, distroless-friendly, signed
dockerfileDockerfile
# syntax=docker/dockerfile:1.7
ARG PY_VERSION=3.12-slim

# --- builder ---
FROM python:${PY_VERSION} AS build
WORKDIR /app
RUN pip install --no-cache-dir uv
COPY pyproject.toml requirements.lock ./
COPY src/ ./src/
RUN --mount=type=cache,target=/root/.cache/uv \
    uv venv /opt/venv \
 && . /opt/venv/bin/activate \
 && uv pip install --no-cache --requirements requirements.lock \
 && uv pip install --no-cache .

# --- runtime ---
FROM python:${PY_VERSION}@sha256:DIGEST_HERE
ENV PATH="/opt/venv/bin:$PATH" \
    PYTHONUNBUFFERED=1 \
    PYTHONDONTWRITEBYTECODE=1
RUN useradd -r -u 10001 app
COPY --from=build /opt/venv /opt/venv
USER 10001

ENTRYPOINT ["python", "-m", "promote_bot"]
CMD ["run"]
HEALTHCHECK --interval=30s --timeout=3s --start-period=10s \
    CMD ["python", "-c", "import urllib.request, sys; sys.exit(0 if urllib.request.urlopen('http://localhost:8080/healthz', timeout=2).status == 200 else 1)"]
yaml.github/workflows/release.yml
name: Release
on: { push: { tags: ['v*'] } }
permissions:
  contents: read
  id-token: write
  packages: write

jobs:
  build:
    runs-on: ubuntu-latest
    outputs:
      digest: ${{ steps.build.outputs.digest }}
    steps:
      - uses: actions/checkout@v4
      - uses: docker/login-action@v3
        with:
          registry: ghcr.io
          username: ${{ github.actor }}
          password: ${{ secrets.GITHUB_TOKEN }}
      - uses: docker/setup-buildx-action@v3
      - id: build
        uses: docker/build-push-action@v5
        with:
          context: .
          platforms: linux/amd64,linux/arm64
          push: true
          tags: |
            ghcr.io/${{ github.repository }}:${{ github.ref_name }}
            ghcr.io/${{ github.repository }}:latest
          cache-from: type=gha
          cache-to:   type=gha,mode=max
      - uses: aquasecurity/trivy-action@master
        with:
          image-ref: ghcr.io/${{ github.repository }}@${{ steps.build.outputs.digest }}
          severity: HIGH,CRITICAL
          exit-code: "1"
      - uses: anchore/sbom-action@v0
        with:
          image: ghcr.io/${{ github.repository }}@${{ steps.build.outputs.digest }}
          output-file: sbom.spdx.json
      - uses: sigstore/cosign-installer@v3
      - run: |
          cosign sign --yes ghcr.io/${{ github.repository }}@${{ steps.build.outputs.digest }}
          cosign attest --yes --type spdxjson \
            --predicate sbom.spdx.json \
            ghcr.io/${{ github.repository }}@${{ steps.build.outputs.digest }}

This pipeline produces a multi-arch image, scanned for CVEs, accompanied by a signed SBOM, with no long-lived registry credentials. The K8s capstone (Chapter 16) consumes exactly this kind of image.

EX 8.1 easy Convert to multi-stage

Rewrite this single-stage Dockerfile as multi-stage so the final image doesn't carry build tools.

FROM golang:1.22
WORKDIR /src
COPY . .

Show solution 
FROM golang:1.22 AS build
WORKDIR /src
COPY go.mod go.sum ./
RUN go mod download
COPY . .
RUN CGO_ENABLED=0 go build -ldflags="-s -w" -o /out/app ./cmd/app

EX 8.2 medium BuildKit cache mount

Add a BuildKit cache mount so npm ci reuses the cache across builds even when package-lock.json changes.

Show solution 
# syntax=docker/dockerfile:1.7
FROM node:20-slim
WORKDIR /app
COPY package.json package-lock.json ./
RUN --mount=type=cache,target=/root/.npm \
    npm ci --prefer-offline
COPY . .
CMD ["node", "src/server.js"]

The cache survives across builds and is shared between layers; even when the layer rebuilds, individual package downloads are reused. Half-or-more reduction in CI build time on incremental builds.

EX 8.3 medium Why not just RUN apt-get install?

What's wrong with this RUN, and how do you fix it?

RUN apt-get update
RUN apt-get install -y curl gnupg
RUN curl -fsSL https://example.com/install.sh | bash
Show solution
  1. Three layers where one would do — wastes cache headroom.
  2. apt-get update in a separate layer than install means you can hit install with stale package lists from cache.
  3. No cleanup; the /var/lib/apt/lists/* remains in the image (~30 MB of nothing useful).
  4. Piping curl into bash is uncached; if the URL changes content, Docker has no idea.
RUN apt-get update \
 && apt-get install --no-install-recommends -y curl gnupg \
 && curl -fsSL https://example.com/install.sh | bash \
 && rm -rf /var/lib/apt/lists/*

For better integrity, fetch the install script with a known SHA, verify, then run.

EX 8.4 medium Trim the attack surface

Adapt this Python image to: non-root user, read-only rootfs (use a tmpfs for /tmp at runtime), all caps dropped, no-new-privileges. Show the Dockerfile changes and the docker run flags.

Show solution 
FROM python:3.12-slim
RUN useradd -r -u 10001 app
WORKDIR /app
COPY src/ ./src/
USER 10001
ENTRYPOINT ["python", "-m", "src"]
$ docker run --rm \
    --read-only \
    --tmpfs /tmp:rw,size=64m \
    --cap-drop=ALL \
    --security-opt=no-new-privileges:true \
    my-app:1.0

K8s achieves the same with securityContext in the Pod spec; this docker run form is exactly what the K8s "restricted" PSA profile generates.

EX 8.5 hard Sign & verify

Sign an image with cosign keyless, then write the verify command a downstream consumer would use to enforce "this came from our org's GHA workflow".

Show solution 
# Sign (in GHA, with permissions: id-token: write)
$ cosign sign --yes ghcr.io/myorg/app@sha256:abc

# Verify (consumer)
$ cosign verify \
    --certificate-identity-regexp '^https://github.com/myorg/[^/]+/\.github/workflows/.*$' \
    --certificate-oidc-issuer 'https://token.actions.githubusercontent.com' \
    ghcr.io/myorg/app@sha256:abc

The verify checks Sigstore's transparency log (Rekor) for a signature where the signer's OIDC identity matches the regex (a GHA workflow inside myorg). No long-lived keys involved on either side.

EX 8.6 hard Multi-arch in one command

Build the same Dockerfile for amd64 and arm64, push as a single multi-arch tag. Show the buildx commands.

Show solution 
$ docker buildx create --use --name multi   # create a multi-arch builder
$ docker buildx inspect --bootstrap          # ensure QEMU emulators are loaded
$ docker buildx build \
    --platform linux/amd64,linux/arm64 \
    --tag ghcr.io/myorg/app:1.0 \
    --push .

The push results in a manifest list at the tag; pulling on amd64 fetches the amd64 image, on arm64 the arm64 one. Same digest URL for both. Run on a native arm64 runner if you have one — QEMU emulation works but is slow.

Recap

  • Multi-stage builds keep build tools out of final images. Distroless or scratch for static binaries; Debian-slim for Python.
  • BuildKit cache mounts speed up package-manager steps without bloating layers.
  • Secret mounts keep build-time credentials out of the image and out of docker history.
  • Security checklist: non-root, read-only rootfs, drop caps, no-new-privs, pin by digest, lint with hadolint.
  • Scan with trivy, generate SBOMs with syft, sign with cosign keyless.
  • CI patterns: registry cache, multi-arch via buildx, rootless / Kaniko / Buildah for K8s-based runners.
  • Debug distroless via kubectl debug ephemeral containers.
  • K8s consumes OCI images; command/args in YAML override ENTRYPOINT/CMD.
